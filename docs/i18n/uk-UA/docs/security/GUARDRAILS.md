> **Джерело істини:** `src/lib/guardrails/`
> **Останнє оновлення:** 2026-08-29 — v3.8.51 (Походження стенограми Video Bridge оголошується абонентом,
> ще не перевірено сервером — уточнено згідно з #11661)

Захисні механізми забезпечують безпеку, політику та трансформації вмісту на межі між OmniRoute та вищестоящими провайдерами. Кожен захисний механізм може перевіряти (та за бажанням відхиляти, трансформувати або анотувати) корисні навантаження запитів (`preCall`) та відповіді вищестоящих систем (`postCall`).

Система є **відкритою при збої**: якщо захисний механізм видає помилку під час виконання, реєстр записує помилку та продовжує роботу з наступним захисним механізмом, замість того, щоб відхиляти запит. Блокування є явним рішенням (`block: true`), а не випадковістю.

### Міст для зображень (`visionBridge.ts`) — Міст модальностей PR-1

Перехоплює запити із зображеннями, спрямовані до **моделей без підтримки зображень**, і або
перенаправляє весь запит до моделі з підтримкою зображень, або замінює частини із
зображеннями текстовими описами, створеними налаштовуваною моделлю для роботи із
зображеннями, перш ніж виконати зовнішній виклик. Це дає змогу постачальникам, що
підтримують лише текст, прозоро обробляти мультимодальні корисні навантаження.

Потік виконання:

1. Пропустити, якщо цільова модель уже підтримує зображення (якщо тільки вона не входить
   до списку моделей із примусовим використанням моста `isVisionBridgeForcedModel`).
2. Видобути частини із зображеннями за допомогою `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), що делегує обробку **уніфікованому детектору
   медіаданих** `detectMediaParts()` у `open-sse/utils/mediaParts.ts` — єдиному
   джерелу істини, спільному з фільтром сумісності комбінацій.
   Видобування за білим списком обмежене частинами верхнього рівня тих форм,
   які `replaceImageParts` може вставити назад (контракт видобування↔заміни): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` і Responses API `input_image`. Вкладені збіги та
   форми, що містять лише індикатори, призначені для фільтра комбінацій і ніколи
   не видобуваються. Пропустити, якщо нічого не знайдено.
3. Визначити конфігурацію середовища виконання за допомогою `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): нові ключі налаштувань
   `modalityBridge*` мають перевагу; застарілі ключі `visionBridge*` залишаються
   **резервним варіантом на один цикл** (вікно відкату). Якщо міст вимкнено,
   пропустити обробку ще до будь-якого обходу медіаданих.
4. Селектор режиму (`modalityBridgeVisionMode`, див. таблицю нижче) визначає,
   чи слід виконати перенаправлення або створення опису. Перенаправлення повертає
   `modifiedPayload`, у якому замінено лише `model`, а також метадані
   `{ rerouted, fromModel, toModel, imagesKept }`.
5. Шлях створення опису: обмежити кількість зображень значенням `maxImages`,
   сформувати підказку з урахуванням завдання, перевірити кеш описів, викликати
   модель для роботи із зображеннями **паралельно** (`Promise.allSettled`) і
   вставити замість зображень текстові частини `[Image N]: <description>`.
   Якщо створити опис не вдалося, повертається `null`, а вихідна частина із
   зображенням **зберігається** (#4012) — за винятком шляху створення описів
   для комбінації, коли не вдалося створити жодного опису: у такому разі для
   підтвердженої зовнішньої системи без підтримки зображень натомість використовується
   заглушка `(unavailable — no vision-capable provider connected)` (#8430).
6. Повернути `modifiedPayload` і метадані (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### Селектор режиму (`modalityBridgeVisionMode`)

| Режим      | Типовий | Поведінка                                                                                                                                                                                                                                                                                                                                                                                |
| ---------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔       | Застаріла евристика без змін (#6640/#7204): моделі, що не належать до комбінацій, і моделі `auto/` перенаправляються до найкращої моделі з підтримкою зображень, якщо тільки вихідна модель уже не має придатних облікових даних (тоді створюється опис); для цільових комбінацій опис створюється завжди.                                                                               |
| `describe` |         | Завжди створювати опис — блок перенаправлення повністю пропускається; відповідь завжди надає вибрана користувачем модель.                                                                                                                                                                                                                                                                |
| `reroute`  |         | Примусове перенаправлення: перевірка збереження моделі з обліковими даними оминається. Перевірка облікових даних **цільової моделі** перенаправлення все одно застосовується — якщо придатної цільової моделі з підтримкою зображень немає, запит переходить до створення опису, щоб необроблені зображення ніколи не потрапляли до серверної системи, яка підтримує лише текст (#8430). |

Примусові режими виконують ранній вихід **до** запуску автоматичної евристики; поведінка
`auto` побайтово ідентична поведінці захисного механізму до PR-1.

#### Область дії API-ключа (`visionBridgeKeyScope.ts`)

Коли API-ключ виклику обмежує `allowedConnections`, пули квот
(`allowedQuotas`) або моделі (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), міст вибирає
для перенаправлення та створення описів лише ті моделі й підключення, які
дозволено використовувати цьому ключу. Після цього виклик для створення опису
завжди проходить через самозамкнений цикл OmniRoute із заголовком
`x-omniroute-self-loop-key-id`, тому чат-запит, який його отримує, повторно
застосовує політику підключень і моделей цього ключа. `enforceApiKeyPolicy()`
враховує цей заголовок лише разом із токеном-носієм самозамкненого циклу, тому
він може лише звужувати доступ, а ідентифікатор, який не вдається розпізнати,
відхиляється.

Якщо для ключа не дозволено жодної моделі з підтримкою зображень, шлях створення
опису не втручається, а запит передається без змін — це така сама поведінка
«дозволити в разі помилки», як і для вимкненого захисного механізму (метадані
`{ skipped: true, reason: "no_permitted_vision_model" }`).
Запити без ключа та ключі без цих обмежень поводяться так само, як і раніше.

#### Підказка для створення опису з урахуванням завдання (`modalityBridgeVisionTaskAware`)

За замовчуванням **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) додає
текст **останнього повідомлення користувача** (обрізаний до 500 символів) до базового
запиту на опис, спрямовуючи опис на те, про що фактично запитав користувач
(патерн codex-vision-proxy), і просить модель комп’ютерного зору транскрибувати видимий
текст. Якщо прапорець вимкнено — або текст користувача відсутній — базовий запит
використовується без змін.

Власний OpenAI-сумісний запит циклу опису до самого себе (`callVisionModelSingle()`
у `visionBridgeHelpers.ts`) завжди запитує `image_url.detail: "high"` —
безумовно, для кожного виклику/провайдера, без прив’язки до будь-якого сигналу клієнта.
Вибірка з низькою деталізацією погіршує точність OCR саме для завдання транскрибування
тексту, яке задає цей запит, тому сам виклик опису завжди запитує високу
деталізацію незалежно від того, який рівень деталізації використовував початковий вхідний запит. Це
впливає лише на тіло внутрішнього запиту опису; це не змінює того, як
OmniRoute пересилає власне значення `image_url.detail` виклику в основному запиті —
це значення за замовчуванням застосовується окремо й лише для виявлених клієнтів OpenCode у
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). Гілка
дротового формату Anthropic у циклі опису до самого себе не має поля `detail`
і не залежить від жодного з цих значень за замовчуванням.

#### Обмеження результату опису (`modalityBridgeVisionMaxChars`)

| Ключ                           | За замовчуванням | Діапазон          |
| ------------------------------ | ---------------- | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`              | `0` або 100–50000 |

`0` (за замовчуванням) означає **без обмеження** — опис, повернений
`callVisionModel()`, передається без змін, зберігаючи наявну
поведінку. Будь-яке значення в діапазоні 100–50000 обрізає опис із
суфіксом `…` перед його вставленням у вигляді `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` у `src/lib/guardrails/visionBridge.ts`).
Збільшуйте це значення для насичених деталями завдань OCR, де наступній моделі потрібна
повна транскрипція; зменшуйте його, щоб обмежити використання токенів надто багатослівними моделями комп’ютерного зору.
Поле на панелі керування розташоване в розділі Advanced вкладки Vision
(`modality-bridge-max-chars` у `ModalityBridgeVisionTab.tsx`) і підвищує будь-яке
значення від 1 до 99 до мінімуму 100, водночас залишаючи явно вказане `0`
без змін — `0` є самостійним допустимим значенням Zod
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не просто
значенням за замовчуванням «не задано».

#### Кеш описів (`modalityBridge/bridgeCache.ts`)

Внутрішньопроцесний кеш LRU + TTL для результатів опису, спільний для всього процесу.
Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` із
фреймінгом за префіксом довжини (без колізій на межах полів). Компонент моделі —
це **налаштована** модель мосту, а не модель, яка фактично відповіла:
`callVisionModel` може внутрішньо переходити до резервної моделі, а створення ключа для кожної
спроби фрагментувало б кеш. Невдалі описи ніколи не кешуються. Налаштування:

| Ключ                            | За замовчуванням | Діапазон |
| ------------------------------- | ---------------- | -------- |
| `modalityBridgeCacheEnabled`    | `true`           | —        |
| `modalityBridgeCacheTtlMinutes` | `60`             | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`            | 10–5000  |

#### Нормалізація віддалених зображень (опис у циклі до самого себе/отримання base64)

Коли міст самостійно отримує **віддалене** зображення — для внутрішнього виклику опису
Anthropic і перетворення на base64 для claude-wire-format
(`ensureBase64ImagesForClaudeWire`), в обох випадках через
`fetchRemoteImageAsDataUri()` у `visionBridgeHelpers.ts` — отриманий URI даних
перед вбудовуванням у запит до моделі комп’ютерного зору пропускається через `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`). Завеликі зображення зменшуються до
**2048px за довшою стороною** (відповідно до обмеження зміни розміру, яке OpenAI/Anthropic уже
застосовують на сервері), що скорочує кількість передаваних байтів і затримку,
не змінюючи того, що бачить модель комп’ютерного зору. Для зміни розміру
використовується `sharp`, завантажений через динамічний імпорт: на платформі, де його нативний
бінарний файл не вдається завантажити, `normalizeDataUri()` **ніколи не генерує виняток** —
натомість він без змін передає оригінальні байти, тож шлях опису/перетворення на base64
завжди продовжує працювати. Байти, що не є зображенням (результат отримання, який
не містить декодованого зображення), також передаються без змін. Ця нормалізація
застосовується лише до зображень, які міст отримує для власного внутрішнього виклику, —
вона ніколи не застосовується до необробленого наскрізного корисного навантаження виклику,
відповідно до принципу внесення змін лише за явною згодою (Жорстке правило №20).

#### Схема налаштувань + міграція

Нові ключі `modalityBridge*` перевіряються за допомогою Zod у `updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, трійка `modalityBridgeCache*` і група
`modalityBridgeAudio*`, яку використовує Audio Bridge. Міграція
`141_modality_bridge_settings.sql` копіює наявні застарілі значення
`visionBridge*` до відповідних нових ключів (ідемпотентно, ніколи не перезаписуючи
встановлене оператором значення `modalityBridge*`); застарілі ключі й надалі приймаються як
резервний варіант читання протягом одного циклу випуску.

#### Заголовок прозорості + статистика

Перетворені через опис відповіді містять
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(створюється `buildModalityBridgeHeader()` у `modalityBridge/bridgeStats.ts`,
додається `withModalityBridgeHeader()` у `src/sse/handlers/chatHelpers.ts`).
Перенаправлені запити **не** отримують заголовка — корисне навантаження не змінювалося, а заміну моделі
вже видно в полі `model` тіла відповіді.

`GET /api/modality-bridge/stats` (автентифікація керування, той самий рівень, що й
`GET /api/settings`) повертає збережені в пам’яті лічильники для кожної модальності
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` та
`video`. `averageLatencyMs` використовує `latencySamples`, а не всі спроби, як
знаменник; операція без вимірювання часу не створює штучний зразок із нульовою
кількістю мілісекунд. `bridged` залишається зворотно сумісним псевдонімом для успішних
перетворень; невдалі спроби не збільшують його значення.
Лічильники навмисно скидаються після перезапуску процесу
(телеметрія, а не облік).

#### Конфігурація панелі керування

Окрема сторінка панелі керування розташована за адресою
`/dashboard/settings/modality-bridge`. Її вкладки `Vision`, `Audio`
та `Video`, доступні через URL, зберігають параметри запиту під час перемикання значення `tab`.
Вкладка Vision надає налаштування ввімкнення, режиму, вибору моделі (включно з автоматичним
значенням за замовчуванням), формування підказок з урахуванням завдання, розширених обмежень
часу очікування, зображення, довжини опису та кешу, лічильники
середовища виконання й захищений тестовий запит. Вкладка Audio також активна: вона надає
налаштування ввімкнення, засіб вибору лише STT-моделей із параметром Auto, обмеження часу
очікування й максимальної тривалості кліпу, лічильники аудіо та тестовий запит `input_audio`.
Вкладка Video функціональна: вона повідомляє про стан середовища виконання FFmpeg/ffprobe —
один із чотирьох явних станів інтерфейсу (`unknown`, поки перевірка виконується або не
змогла завершитися, `restricted` для хосту панелі керування, що не є loopback-адресою,
де перевірка пропускається на боці клієнта, `unavailable` після завершення перевірки
та підтвердження відсутності, або `available` із версіями FFmpeg/ffprobe), — зберігає
налаштування ввімкнення, моделі й обмежень кадрів, відео та часу очікування, фільтрує
засіб вибору моделей, залишаючи моделі з підтримкою зору, і надає лічильники відео.

Колишня картка Vision Bridge у налаштуваннях ШІ тепер є посиланням сумісності на
нову сторінку; вона більше не містить другої копії форми. Media Providers також
пов’язує робочі процеси Image-to-Text і Speech-to-Text із відповідними вкладками Modality
Bridge, не видаляючи наявний тестовий майданчик Speech-to-Text.

**Обхід контролю допуску для власного циклу:** коли виклик опису маршрутизується через
власний цикл `/v1` OmniRoute (нестандартна модель постачальника), підзапит надсилає
`x-omniroute-admission-bypass: internal` та автентифікується за допомогою визначених
облікових даних власного циклу — локального маркера `sk_omniroute` у локальному режимі
або налаштованого оператором ключа середовища `OMNIROUTE_API_KEY` / `ROUTER_API_KEY`
(#1350), щоб розгортання з `REQUIRE_API_KEY=true` усе ще могли виконувати виклик опису.
Обхід дозволено лише для цих точних облікових даних, тому зовнішні клієнти не можуть
використовувати цей заголовок для пропуску контролю допуску.

Застарілі значення за замовчуванням містяться в `src/shared/constants/visionBridgeDefaults.ts`;
нові значення за замовчуванням для режиму, урахування завдання й кешу, а також засіб
визначення налаштувань містяться в
`src/shared/constants/modalityBridgeDefaults.ts`. Захисний механізм надає параметр
конструктора `deps`, щоб тести могли підставляти фіктивні реалізації `getSettings` і
`callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Перехоплює запити чату, що містять аудіо, перш ніж вони досягнуть цільового сервісу,
для якого не відома підтримка вхідних аудіоданих. Він ніколи не перемаршрутовує запит
чату: аудіочастини транскрибуються через наявну OpenAI-сумісну multipart-кінцеву точку,
а вибрана модель чату продовжує роботу з текстовими транскрипціями.

Потік виконання:

1. Визначити `supportsAudio` через `getResolvedModelCapabilities()`. Явні метадані
   реєстру постачальників мають пріоритет, за ними йдуть статичні метадані моделі, а потім
   синхронізовані `modalities_input`. Оголошений список вхідних даних без `audio` має
   значення `false`; за відсутності будь-яких даних про можливості залишається `null`.
   І `false`, і `null` активують консервативний міст, тоді як `true` обходить його.
2. Визначити налаштування `modalityBridgeAudio*` і витягти придатні для вирізання
   аудіочастини верхнього рівня з кожного повідомлення за допомогою спільного детектора
   `detectMediaParts()`. Підтримувані формати передавання — OpenAI `input_audio`,
   `audio_url` і `source.media_type: "audio/*"`. Вкладене аудіо виявляється для
   маршрутизації, але не видаляється шляхом вирізання. Обсяг роботи обмежується
   `modalityBridgeAudioMaxClips`; наступні частини залишаються незмінними.
3. Використати налаштоване значення `provider/model` або дозволити
   `selectAudioBridgeModel()` послідовно обійти `AUDIO_TRANSCRIPTION_PROVIDERS`
   у стабільному порядку каталогу й вибрати першу модель із придатними активними
   обліковими даними постачальника.
4. `callAudioTranscription()` перетворює аудіо у форматі base64/data-URI на multipart-
   `file` або завантажує віддалений `audio_url` через захист вихідних з’єднань лише
   з публічними адресами, із закріпленням DNS і обмеженням у 25 МБ. Потім він надсилає
   файл і вибрану модель методом POST у локальний власний цикл
   `/v1/audio/transcriptions`, автентифікований за допомогою
   `resolveSelfLoopBearer()`. Наявний маршрут транскрибування виконує звичайний пошук
   облікових даних, обробку періодів очікування та обмежень швидкості, а також
   перенаправлення до постачальника.
5. Успішні виклики замінюють відповідні частини на `[Audio N]: <transcript>`. Виклики
   виконуються через `Promise.allSettled`: помилка окремого виклику зберігає початкову
   аудіочастину (контракт #4012). Якщо всі виклики завершилися невдало, а для цільового
   сервісу доведено `supportsAudio === false`, частини стають
   `[Audio N]: (unavailable — no STT provider connected)` (контракт #8430). Для
   невідомого цільового сервісу (`null`) у разі помилки всіх викликів частини залишаються
   незмінними. Цільовий сервіс, для якого доведено підтримку лише тексту й для якого
   немає придатних облікових даних STT, отримує ту саму явну заглушку без виконання
   мережевого виклику.

Успішні транскрипції використовують спільний для всього процесу LRU/TTL-кеш Modality Bridge.
Ключ поєднує посилання на аудіо, стабільну мітку операції `audio-transcription`
і вибрану STT-модель; помилки ніколи не кешуються. Спроби обробки аудіо оновлюють
спільні лічильники `bridged`, `cacheHits`, `failures` і `lastUsedAt`.
Перетворені відповіді містять
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; незмінені
запити не отримують сегмент Audio Bridge.

Налаштування середовища виконання зберігаються в БД і перевіряються за допомогою Zod:

| Ключ                          | Типове значення | Діапазон        |
| ----------------------------- | --------------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`          | —               |
| `modalityBridgeAudioModel`    | `""`            | Auto або STT ID |
| `modalityBridgeAudioTimeout`  | `60000`         | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`             | 1–10            |

Спільний кеш і надалі керується параметрами `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` і `modalityBridgeCacheMaxEntries`.

### Відеоміст (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехоплює відеочастини верхнього рівня в `messages` Chat Completions та `input`
Responses API, перш ніж буде викликано цільову модель без відомої вбудованої
підтримки відео. Підтримувані формати: `input_video`, `video_url`, `video_source`,
HTTPS URL-адреси та URI даних `data:video/*;base64,...`. Звичайні імена файлів
у тексті не вважаються відео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) відповідає за обхід запиту,
перевірку можливостей і політик, агрегацію в межах запиту та корисне навантаження
відповіді. Обробка кожного відео — отримання даних, кешування повного результату,
опис послідовності кадрів (з поєднанням будь-якої заявленої викликачем аудіотранскрипції),
а також метрики, переривання й очищення для кожної спроби — прихована за
`processVideoPart` у `videoBridgePipeline.ts`, що викликається один раз для кожної
відеочастини всередині циклу `preCall`. Цей модуль також визначає явні межі портів
`VideoMediaBrokerPort` (отримання байтів і вилучення вибіркових кадрів),
`VideoAudioTranscriptionPort` (поєднання заявленої викликачем аудіотранскрипції
з вибірковими підписами) і `VideoDrilldownPort` (межа збереження деталізації
кадрів; ще не підключена до `processVideoPart` — наразі записи деталізації
створює лише окремий маршрут `/api/modality-bridge/video/drilldown`).

Публічний шлях запиту `/v1` ніколи не імпортує та не викликає підпроцес.
Віддалені відео завантажуються з обмеженням у 50 МіБ; вбудовані відео у форматі
base64 мають консервативне обмеження декодованого розміру в 36 МіБ на одне відео,
щоб конверт моделі, повідомлень і фреймінгу міг залишатися в межах публічного
ліміту приймання JSON-запитів у 50 МіБ. Довжина вбудованих даних і оцінка
декодованого розміру перевіряються до виділення пам’яті. HTTPS обов’язковий
для початкової віддаленої URL-адреси й кожного переспрямування; для цього
використовується наявний захист вихідних з’єднань лише з публічними адресами
та закріпленням DNS. Потім байти перетинають точну внутрішню межу брокера
`POST /api/modality-bridge/video/extract`. Цей маршрут має одночасно позначки
`LOCAL_ONLY` і `SPAWN_CAPABLE`, приймає лише автентифікований у межах процесу
запит із довіреної loopback-адреси та ніколи не приймає URL-адресу, шлях
файлової системи, виконуваний файл або список аргументів. Конвеєр обмеження
розміру тіла API та інкрементний зчитувач тіла обробника незалежно один від
одного забезпечують обмеження вхідних даних брокера до 50 МіБ. Його обмежена
черга одночасно виконує одне вилучення, допускає чотири завдання в очікуванні
та обмежує обсяг вхідних даних в очікуванні до 100 МіБ.

Усередині брокера `ffprobe` читає приватний локальний файл; фіксований список
дозволених форматів виключає формати списків відтворення та маніфестів. Для
дозволених контейнерів сімейства MOV зовнішні посилання на дані MOV залишаються
вимкненими за замовчуванням, і фіксована команда не вмикає їх. І `ffprobe`,
і `ffmpeg` використовують список дозволених протоколів, що містить лише `file`,
один потік, фіксовані масиви аргументів, не використовують оболонку, а виконувані
файли визначаються через `PATH`. Потоки обкладинок, вбудованих як прикріплені
зображення, не вважаються кандидатами для відтворення. Усі відтворювані потоки
мають відповідати обмеженням, причому явний потік за замовчуванням має перевагу
перед детермінованим резервним вибором із найменшим індексом. Тривалість відео
обмежена 600 секундами, розмір — 8 192 пікселями на вимір, а кількість пікселів
джерела — 33 554 432. FFmpeg вибирає 1–16 JPEG-кадрів у середніх точках, зменшує
довгу сторону щонайбільше до 1 024 пікселів без збільшення менших вхідних даних
та ніколи не отримує URL-адресу. Типово вибірка має значення `uniform`.
Необов’язкова політика `scene_aware` та експериментальна політика `segment_aware`
виконують один додатковий фіксований прохід FFmpeg уже перевіреним локальним
потоком, вибирають обмежений набір часових позначок сцен `showinfo` і
детерміновано повертаються до тих самих рівномірних середніх точок у разі
помилки детектора, завершення за тайм-аутом, некоректного виводу або порожнього
набору кандидатів. Режим з урахуванням сегментів розподіляє вибірки середніх
точок пропорційно до перевірених інтервалів сцен; свідчення для режиму з
урахуванням сегментів і поведінку резервного варіанта докладно описано нижче.
Жорстке обмеження в 16 кадрів застосовується після вибору для кожної політики.
Якщо запит з урахуванням сцен має бюджет лише в один кадр, використовується
рівномірна середня точка активного повного відео або вікна фокусування, а у
звіті зазначається `policyEffective: uniform`: один вибраний кадр сцени не може
охопити обидва часові кінці. Викликач може за потреби надати скінченне вікно
фокусування (`start`/`end` у секундах); межі обмежуються тривалістю медіафайлу,
вікна зі зворотним порядком або нескінченними значеннями відхиляються, а всі
політики вибірки застосовуються лише в нормалізованому інтервалі. Отримане вікно
включається до метаданих вибірки та до префікса ненадійного опису, щоб наступні
моделі могли відрізнити сфокусований фрагмент від повної часової шкали.

Семантичне фокусування підписів є окремим явним налаштуванням. Типовий режим
аналізу `full` зберігає наявний запит для кадрів і ніколи не передає текст
запиту моделі підписів. У режимі `focused` міст зчитує лише найновіший непорожній
авторський текст користувача `text`/`input_text` із того самого контейнера Chat
або Responses, нормалізує його до NFC, згортає керівні символи та пробільні
символи й обмежує довжину до 500 кодових точок Unicode. Порожній результат
спричиняє повернення до точного запиту `full`. Придатна підказка серіалізується
як JSON у спеціальному блоці ненадійного користувацького контексту й може лише
визначати пріоритет спостережуваних деталей; вона не може скасувати окреме
попередження про заборону виконання інструкцій, видимих або чутних у медіа.
Текстове фокусування ніколи не визначає `start`/`end` і не змінює часовий
семплер.

#### FU-07 структурні свідчення сегментів

`segment_aware` використовує один обмежений прохід попереднього аналізу вже перевіреного
локального відеопотоку. Фіксований ланцюжок фільтрів спочатку масштабує відео до ширини
не більше 320 пікселів, виявляє зміни сцен і завмерлі інтервали, а потім виконує вибірку
з частотою 1 кадр на секунду для оцінювання розмиття, середньої яскравості та
просторової/часової інформації. Прохід обмежено 600 структурними зразками, одним
потоком FFmpeg/фільтра, тими самими списками дозволених лише для протоколу
`file` та контейнерів, обмеженням виводу процесу в 1 MiB і щонайбільше 30 секундами
в межах спільного механізму переривання/кінцевого строку брокера. Він ніколи
не приймає команду, фільтр, шлях або URL із запиту.

Структурні значення є детермінованими даними вибірки, а не семантичним розумінням
відео. Вони не визначають об’єкти, дії, субтитри, мовлення чи наміри користувача.
Межі сцен і завмирань формують сегменти; покриття завмирань, розмиття,
експозиція, просторова деталізація та часові зміни впливають лише на розподіл
наявного бюджету в 1–16 кадрів. Повністю завмерлий сегмент обмежується одним кадром,
тоді як незавмерлі сегменти конкурують за решту бюджету. Коли кількість меж
перевищує кількість кадрів, зберігається рівномірне покриття часової шкали, щоб
швидкі переходи на початку не могли приховати довгий завершальний сегмент. Межі
сцен, розташовані в межах 1-секундної роздільності аналізу від межі завмирання,
об’єднуються.

Відсутні фільтри, некоректні/порожні дані, помилка детектора або перевищення часу
обмеженого попереднього аналізу призводять до відкритої відмови з переходом до
точної політики рівномірного вибору середніх точок. Переривання з боку виклику
або досягнення кінцевого строку брокера не призводить до відкритої відмови:
це завершує активний підпроцес, запобігає подальшому вилученню кадрів, а приватне
тимчасове дерево видаляється в `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` створює детерміновані реальні тестові
дані FFmpeg для оцінювання економії викликів створення підписів після усунення
дублікатів, розподілу бюджету за щільного руху, даних про розмиття/експозицію/SI-TI,
швидких переходів із довгим завершальним фрагментом і хибнопозитивних результатів
під час поступового згасання. Скрипт записує фактичний час попереднього аналізу,
а там, де доступний `/usr/bin/time`, — процесорний час дочірнього процесу та
піковий RSS. Його перевірки якості є лише структурними оракулами. Якість реальної
моделі створення підписів залишається `HOLD`, оскільки цей стенд не має
авторизованої кінцевої точки або зафіксованого оцінювача. Грошова економія також
залишається `HOLD`, якщо `--caption-cost-per-call-usd` не задає явну додатну
оцінку вартості одного виклику; скрипт ніколи не фабрикує жоден із цих результатів.

Розмір кожного кадру обмежено 4 MiB, сумарний розмір усіх необроблених кадрів —
23 MiB, а серіалізованої відповіді брокера — 32 MiB. Приватний тимчасовий каталог
видаляється в `finally`. OmniRoute не постачається з FFmpeg і не приймає власний
шлях до виконуваного файлу. Перед створенням підписів міст застосовує консервативний
прохід візуального усунення дублікатів: кожне зображення JPEG зменшується до
16×16-буфера у відтінках сірого та порівнюється лише з останнім збереженим кадром.
Для запитаного бюджету підписів, що перевищує один кадр, вилучення надає
обмежений пул кандидатів, розміром щонайбільше вдвічі більшим за цей бюджет,
але не більше 16 кадрів. Запитане обмеження застосовується лише після усунення
дублікатів, а перший і останній вибрані кандидати зберігаються під час остаточного
проріджування, якщо бюджет становить щонайменше два кадри. Версіонована політика
`grayscale-16x16-mean-cells-v2` використовує більше зі значень: середньої різниці
яскравості та частки комірок мініатюри, нормалізована різниця яких становить
щонайменше 0.05. Порогом дублювання є константа 0.04, вибрана заради
передбачуваності, а не надана як параметр часу виконання. Цей вторинний
висококонтрастний сигнал зберігає незначний рух і зміни видимого тексту, які
може приховати порівняння лише за середнім значенням. Помилки компаратора або
декодера призводять до відкритої відмови та збереження покриття. Метадані виводу
окремо відображають вилучених кандидатів, успішно використані кадри та відкинуті
візуальні дублікати.

Явно позначена відеочастина може запитувати контактний аркуш із часовими позначками.
Міст створює JPEG-сітку щонайбільше з 4 стовпців і 16 кадрів. У кожну 512-піксельну
комірку часова позначка вихідного кадру вбудовується у висококонтрастну нижню
смугу, а ті самі часові позначки зберігаються в текстових метаданих для подальшого
зіставлення та аудиту. Розмір повного JPEG залишається обмеженим 32 MiB. Якщо
`sharp` не може декодувати або скомпонувати сітку, міст повертається до окремих
JPEG-кадрів; переривання з боку клієнта все одно поширюється на операцію з аркушем.

Докази для просування навмисно відокремлено від синтетичного мікротесту
компонування. `scripts/perf/video-bridge-contact-sheet-eval.ts` визначає
версіонований за схемою A/B-стенд для реальних моделей комп’ютерного зору,
сумісних з OpenAI. Він вимірює повідомлену постачальником кількість токенів,
наскрізну фактичну затримку (включно з компонуванням аркуша), кількість викликів
моделі та збереження фактів, визначених маніфестом. Необроблені відповіді моделі
не записуються у звіт; зберігаються лише дайджести SHA-256 та ідентифікатори
зіставлених фактів. Стенд не здійснює мережевих або платних викликів моделі, якщо
не передано `--execute-real` і не налаштовано `--model`, `OMNIROUTE_BASE_URL` та
`OMNIROUTE_API_KEY`. Без такого явно заданого реального запуску його машинозчитуваний
вердикт залишається `HOLD`; самі лише синтетичні вимірювання корисного навантаження
та кількості викликів не є доказами для просування.

Виклики можуть додавати необов’язковий масив `transcript.cues` до підтримуваної
відеочастини, якщо вони вже мають синхронізований текст. Кожна репліка повинна
містити `text`, скінченний інтервал `start`/`end` у межах визначеної тривалості
та `source` із білого списку (`client`, `embedded` або `audio-bridge`);
`confidence` за замовчуванням дорівнює `1` і має залишатися в межах від `0` до
`1`. Точні дублікати реплік згортаються. OmniRoute ніколи не запускає
транскрибування на основі цих метаданих: перевірені репліки копіюються до
описаного результату разом із джерелом, рівнем довіри та інтервалом і
відображаються як ненадійні спостереження поряд із підписами кадрів. Некоректний
текст, текст поза допустимим діапазоном або текст без даних про походження
відхиляється, а не додається до потоку підписів. Обидва канали транскрипту в тілі
запиту нормалізують надане походження до `client`, включно із самостійно заявленими
позначками `embedded` або `audio-bridge`. Лише адаптер під керуванням сервера може
призначати ці довірені позначки через доступний лише в коді аргумент
`trustedSource`; поле JSON запиту не може передати значення цьому аргументу.
Текст транскрипту залишається ненадійним вмістом, отриманим із медіаданих,
незалежно від його походження, і ніколи не повинен визначати авторизацію.

Досвідчений викликач може надати доріжку `audioTranscript` для того самого відео;
вона розглядається як текст, наданий клієнтом, а не як доказ серверної транскрипції.
Точка об’єднання виконує візуальні й аудіоспостереження в межах
одного кінцевого терміну та сигналу переривання, упорядковує їх на спільній часовій шкалі, згортає
точні дублікати й повертає частковий результат, коли успішно завершується лише одна сторона.
Недійсний `audioTranscript` призводить до такого часткового результату — візуальний
опис зберігається, а аудіогілка записує санітизований код помилки —
замість завершення обробки всього відео з помилкою. Доступність кожної гілки, ознака часткового результату
та санітизовані коди помилок зберігаються в описаному результаті, у
метаданих захисних обмежень (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), у метаданих кешу результатів і в лічильниках
об’єднання мосту. Стандартний шлях Video Bridge не викликає перетворення мовлення на текст
і не завантажує другу копію медіафайлу; без такої явно наданої доріжки він залишається
суто відеошляхом.

**Зберігання транскриптів (#12150 P1).** Це застосовується автоматично щоразу, коли
Video Bridge (який сам вимагає явного ввімкнення) відтворює репліку транскрипту — окремої
ознаки зберігання немає. Коли запит відтворює будь-яку репліку транскрипту (оголошений викликачем
`transcript` або об’єднаний `audioTranscript`), захисне обмеження позначає його як
`videoBridgeObserved` і створює редаговану тінь опису відео —
ідентичне відтворення, у якому довільний текстовий вміст кожної репліки замінено на
`[redacted-video-transcript]`; вона створюється шляхом підстановки структурованого поля репліки
до збирання рядка (а не шляхом розбору зведеного тексту, тому жоден вміст репліки —
шкідливий чи звичайний, зокрема вміст із символом `]`, як-от
`[inaudible]`/`[music]`, — не може зберегтися). У збереженому тілі запиту журналу викликів
кожна похідна від відео текстова частина замінюється цією редагованою тінню шляхом
зіставлення за рівністю вмісту; якір `fullText` повторно зчитується із завершеного корисного
навантаження захисних обмежень перед викликом, тому зіставлення й надалі успішне після того, як
подальші захисні обмеження ланцюжка (маскувальники PII та облікових даних із пріоритетами 10/95)
переписують текст опису на місці, а також після того, як впровадження системного запиту,
передавання контексту й пам’яті змінює форму масиву повідомлень. Тіло,
надіслане моделі, залишається незмінним. Спостережуваний запит також не наповнює
довготривалу Memory (вилучення даних як із запиту, так і з відповіді пропускається),
тож власна відповідь моделі не може продублювати текст транскрипту в Memory.

**Необроблені поля відео (#12430).** Коли міст увімкнено, а нативна підтримка відео невідома або відсутня, визначені поля `transcript`/`audioTranscript` також активують `videoBridgeObserved`, навіть після помилки опису або досягнення обмеження `maxVideos`. Значення `null` і порожні рядки враховуються; відсутні поля та метадані, не пов’язані з відео, — ні. У збережених копіях ці поля редагуються або запит вилучається, а кеші/Memory обходяться.

На цих резервних шляхах дійсні репліки викликача перетворюються на підтримувані частини `text`/`input_text`,
а не на нестандартні поля провайдера. Обидві надані із запитом доріжки
залишаються недовіреними спостереженнями `client` з явним попередженням про те, що відео
не було описано, а часові позначки не перевірялися за медіаданими. Наявні
обмеження у 256 реплік/64 КіБ загалом і на одну репліку застосовуються до обох доріжок разом;
часові позначки мають вкладатися в 600-секундну межу брокера та будь-яке надане
вікно фокусування. Недійсні доріжки відкидаються, а не пересилаються як довільний текст; дійсну
сусідню доріжку все ще можна використати, якщо не перевищено їхній спільний ліміт. Поля зі значенням `null`/порожні
поля не додають тексту. Цей резервний механізм не додає отримання медіаданих або транскрипції.
Поля розширення транскрипту видаляються з резервного контейнера відео та його
об’єктів `video_url`/`source`. Дозвільний список формату передачі OpenAI залишається суворим; відеоконтейнери
з невідомою нативною підтримкою залишаються доступними, а відомі суто текстові цілі зберігають безпечні маркери.
Структуровані редаговані тіні захищають доданий текст транскрипту, тоді як
оригінальний запит, що належить викликачу, залишається незмінним. Цілі з нативною підтримкою та
вимкнені мости зберігають наявну поведінку обходу.

Додаткові збережені копії використовують той самий сигнал спостережуваного запиту. Необроблений
знімок клієнтського запиту до застосування захисних обмежень, незавершений запит у пам’яті та журнал
рано відхиленого запиту структурно замінюють поля транскрипту у відеочастинах;
рядкові запити, синтезовані етапами конвеєра та передаванням контексту, редагуються
в точці збереження тіла запиту. Збережений маркер `video_content_removed`
змушує продовження через `previous_response_id` завершуватися безпечною помилкою замість відновлення
тексту, який було навмисно відкинуто. Якщо спостережуваний запит втрачає свою
окрему для кожної частини редаговану тінь перед журналюванням або навіть одна з кількох тіней відео
не збігається після подальших змін запиту, збережене тіло запиту
повністю вилучається замість зберігання частково редагованого транскрипту.

Для спостережуваного запиту відповідь моделі може цитувати будь-яку частину
транскрипту без структурованої межі репліки. Тому збережене в журналі викликів
`responseBody` замінюється маркером вилучення; докладний
артефакт конвеєра (який може містити тіла даних постачальника/клієнта та фрагменти потоку)
не зберігається. Семантичний кеш, кеш ідемпотентності та кеш повторного відтворення міркувань
обходять операції читання й запису для цього запиту. Запит до провайдера та видима
клієнту відповідь залишаються незмінними. Ранні байти підтримання з’єднання видаляються з тимчасового
буфера, коли докладний артефакт вилучається. Попередження Kiro про некоректний EventStream
повідомляє лише кількість байтів корисного навантаження, але ніколи не його вміст чи необроблену помилку
парсера JSON.
Це не є твердженням, що кожну непов’язану діагностику провайдера/плагіна було
перевірено; ширший аудит точок збереження відстежується в #11658.

Внутрішній життєвий цикл `/api/modality-bridge/video/drilldown` є окремою,
автентифікованою за допомогою loopback/token підсистемою кешу. Кожна операція також потребує
канонічного непрозорого ID принципала. Перш ніж активувати виклик із виробничого середовища, він має
вивести цей ID з автентифікованого орендаря й ніколи не пересилати
значення, вибране клієнтом. Ключі кешу пов’язують цього принципала з канонічними ID сеансу та
відеопосилання, зберігають лише похідні від них ключі SHA-256 і обмежують як читання,
так і видалення тим самим принципалом. Кеш зберігає не більше 16 похідних кадрів JPEG
на запис, вилучає їх через десять хвилин і підтримує обмежене читання
`start`/`end` або явне видалення сеансу.

Для кожного принципала встановлено обмеження у 16 записів і 64 МіБ канонічних даних JPEG. Ці
обмеження не залежать від глобальної межі у 64 записи/256 МіБ: тиск на квоту
принципала спочатку витісняє лише записи цього принципала, які використовувалися найдавніше, і лише потім
розглядається глобальне витіснення LRU. Прострочені записи видаляються як з обліку принципала,
так і з глобального обліку під час активності кешу, тоді як скасування та помилка валідації
не призводять до фіксації часткової заміни.

Кеш відхиляє неканонічний Base64, надлишкове доповнення, дані не у форматі JPEG, пошкоджені або
усічені JPEG, а також JPEG, які спричиняють попередження під час обмеженого повного декодування зображення за допомогою `sharp`.
Кожне прийняте зображення повторно кодується як канонічний JPEG, ширина й висота
визначаються з декодованих байтів без довіри до полів виклику, а всі кінцеві
поліглотні байти відкидаються, а не зберігаються. До обох квот зараховується лише
обмежений канонічний стиснений буфер. Обмеження передавання JSON враховує накладні витрати Base64 для межі
декодованих вхідних даних у 32 МіБ. Кожна
збережена похідна сутність записує валідований формат/роздільну здатність JPEG, політику вибірки,
версію формування похідної сутності, час створення, обчислений сервером хеш вмісту та хешоване батьківське
посилання разом із хешем батьківського вмісту від довіреного виклику.
Скасування перевіряється між асинхронними фазами декодування/хешування до атомарної фіксації в кеші.

Цей етап ще не підключає виробничого постачальника до маршруту й не
забезпечує вибір варіантів із різною роздільною здатністю. Тому прозорий шлях запиту Video Bridge
не виконує додаткової роботи, а виведення прив’язаного до орендаря принципала та
повний життєвий цикл FU-08 із різною роздільною здатністю залишаються явно визначеною подальшою роботою,
а не задокументованою як завершена поведінка.

Для кадрів послідовно створюються підписи за допомогою налаштованої моделі Video. Порожнє
перевизначення Video успадковує налаштування Vision; якщо обидва значення порожні, автоматичний маршрутизатор
Vision вибирає ефективну модель із підтримкою зору. Успішні підписи
замінюють початкову частину стабільним префіксом `[Video description:`, який також
позначає текст як ненадійне спостереження, отримане з медіаданих, і вказує наступним
моделям не виконувати інструкції, знайдені в медіаданих. Ключі кешу підписів кадрів
включають байти JPEG, запит, часову позначку й ефективну модель; кешуються лише успішні
підписи. Записи кешу зберігають фактичну успішну модель-виробника,
зокрема резервну модель; міст повідомляє `mixed`, коли різні кадри
були створені різними моделями. Влучання в кеш повторно використовує ідентичність цього виробника
замість перепозначення відповідно до запитаного плану маршрутизації. Кеш результатів для всього відео
має ключ на основі кожного вхідного параметра, що змінює результат: запиту, ефективної
моделі, політики вибірки, кількості кадрів, режиму семантичного аналізу, відбитка SHA-256
нормалізованої підказки фокуса, вікна фокуса, `transcript`,
`audioTranscript` і прапорця контактного аркуша — тому зміна будь-якого з цих
вимірів призводить до промаху кешу, а не повторного використання застарілих даних. Версія
політики візуальної дедуплікації, порогове значення та обмежена кількість кадрів-кандидатів також явно
включені до ключа й метаданих кешу результатів; отже, зміна політики не може повторно використати застарілий
опис усього відео. Метадані кешу результатів v4 зберігають режим і
відбиток, але ніколи не зберігають необроблене завдання користувача. Метадані захисного механізму повідомляють як
запитаний, так і ефективний режими аналізу; запитаний режим `focused` без
придатного тексту користувача вказується як фактично `full`.

Захисний механізм вилучає всі підтримувані частини відео, але описує не більше ніж
`modalityBridgeVideoMaxVideos`. Для цільового об’єкта, для якого доведено
`supportsVideo === false`, відео з помилками та відео понад ліміт перетворюються на явні безпечні
текстові маркери, щоб необроблене відео не зберігалося. Коли можливості невідомі, ці частини
зберігають свій відеоконтейнер; будь-який резервний транскрипт проходить описане вище обмежене
перетворення тексту. Цільові об’єкти з `supportsVideo === true` обходять міст.
Сигнал переривання клієнтського запиту поширюється на завантаження, чергу брокера,
підпроцеси та виклики створення підписів; переривання зупиняють обробку між відео й ніколи не допускають
відкритого проходження необроблених медіаданих у разі помилки.

Налаштування середовища виконання зберігаються в БД і перевіряються за допомогою Zod:

| Ключ                                | Типове значення | Діапазон / поведінка                                                                                            |
| ----------------------------------- | --------------- | --------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`         | Необов’язкове середовище виконання, вмикається явно                                                             |
| `modalityBridgeVideoAnalysisMode`   | `"full"`        | `full` зберігає загальні підписи; `focused` використовує обмежений, недовірений контекст останнього користувача |
| `modalityBridgeVideoModel`          | `""`            | Успадковує модель Vision Bridge                                                                                 |
| `modalityBridgeVideoFrameCount`     | `8`             | 1–16                                                                                                            |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`     | `uniform`, `scene_aware` або пропорційний `segment_aware`; у разі збою детектора використовується `uniform`     |
| `modalityBridgeVideoMaxVideos`      | `1`             | 1–4                                                                                                             |
| `modalityBridgeVideoTimeout`        | `120000`        | 1000–120000 мс                                                                                                  |

Збережені застарілі значення тайм-ауту Video, що перевищують 120 секунд, обмежуються
кінцевим терміном брокера; нові налаштування зі значеннями вище цієї межі відхиляються.
`GET /api/modality-bridge/video/runtime` перед автентифікацією або перевіркою середовища
виконання вимагає довіреної, позначеної локальності loopback, а потім — автентифікації
керування. Він повертає лише `available`, очищені версії FFmpeg/ffprobe та фіксовану
причину, коли середовище виконання недоступне. Внутрішня кінцева точка видобування не є
публічним API завантаження: переповнення черги повертає `503` разом із `Retry-After`, розрив
з’єднання з боку виклику повертає `499`, а фіксований кінцевий термін брокера повертає `504`. Перетворені відповіді додають
`video->text;model=<visionModel>;parts=<videos>` до центрального
заголовка `x-omniroute-modality-bridge`, не видаляючи сегменти Vision або Audio.

### Маскувальник PII (`piiMasker.ts`)

Виконується на **обох** етапах.

- **`preCall`** клонує корисне навантаження, обходить `system`, `messages`, `input` і
  `prompt` (включно з елементами у вигляді звичайних рядків) та застосовує `processPII()` (з
  `@/shared/utils/inputSanitizer`) до рядкових полів `content`/`text`. Коли
  `PII_REDACTION_ENABLED=true`, виявлені PII редагуються у вихідному
  корисному навантаженні. Це не залежить від `INPUT_SANITIZER_MODE` (який керує лише
  політикою щодо ін’єкцій у промпти). Коли редагування вимкнено, виклик записує кількість
  виявлень, не змінюючи вміст.
- **`postCall`** виконує глибоке клонування відповіді, запускає `sanitizePIIResponse()` разом із
  маскувальником структури Responses API (`maskResponsesOutput` — охоплює
  `output_text` і `output[].content[].text`). Якщо відбувається будь-яке редагування,
  змінена відповідь замінює оригінальну.

Захисний механізм ніколи не блокує; він лише додає анотації (`meta.detections`,
`meta.redacted`) або переписує дані.

#### Вибір за типом, користувацькі шаблони та лічильники виявлень

**Панель керування → Налаштування → Безпека → Маскування PII** визначає, _що_ маскується. Це
не вмикає маскування: за це, як і раніше, відповідають `PII_REDACTION_ENABLED` (запит) і
`PII_RESPONSE_SANITIZATION` (відповідь + SSE), обидва типово вимкнені.

- **Вибір за типом** — вбудовані ідентифікатори наведено у
  `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`). Якщо значення не задано,
  використовуються всі типи (поведінка до появи цього налаштування). Шаблон
  `ssn_us` рушія обробки запитів зіставляється з `ssn`. Шаблони налаштувань (Мінімальний, Стандартний, Фінансовий,
  Бразильський, США, Повний) лише встановлюють прапорці в інтерфейсі.
- **Користувацькі шаблони** — до 20 регулярних виразів або шаблонів із символами підстановки (`*` = до 64
  непробільних символів, `?` = один символ). Збіги перетворюються на `[CUSTOM_REDACTED]`.
  Кожен шаблон проходить через `compilePiiCustomPattern()`
  (`src/shared/utils/piiCustomPatterns.ts`): не більше 500 символів, прапорці обмежено
  до `g i m s u`, він має компілюватися, пройти перевірку `safe-regex` (катастрофічний
  відкат) і не повинен відповідати порожньому рядку або заповнювачу редагування.
  Шаблон, який не проходить перевірку, відхиляється під час збереження й тестування, а збережений рядок,
  що не пройшов перевірку, пропускається під час виконання замість компіляції. Користувацькі шаблони
  виконуються лише тоді, коли маскування ввімкнено.
- **Лічильники виявлень** — кількість за кожним типом (значення збігів ніколи не зберігаються), що утримується в
  пам’яті та скидається після перезапуску (`src/lib/pii/piiDetectionStats.ts`). Лічильники
  збільшуються лише тоді, коли маскування ввімкнено.

Налаштування зберігаються в таблиці `key_value` (простір імен `pii_settings`,
`src/lib/db/piiSettings.ts`) і зчитуються через кеш на 1 с. API:

| Метод  | Шлях                     | Призначення                                                                       |
| ------ | ------------------------ | --------------------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | Стан прапорця, `enabledTypes`, `customPatterns`, лічильники виявлень              |
| `PUT`  | `/api/settings/pii`      | Замінити `enabledTypes` (`null` = усі) та/або `customPatterns`                    |
| `POST` | `/api/settings/pii/test` | Тестовий запуск одного шаблону на зразку розміром до 8 КБ; нічого не зберігається |

Усі три вимагають автентифікації керування та перевіряють тіло за допомогою Zod
(`src/shared/validation/schemas/piiSettings.ts`).

### Ін’єкція у промпт (`promptInjection.ts`)

Виявляє зловмисні структури у вмісті, наданому користувачем, і застосовує
налаштовану політику. Поведінка визначається змінними середовища та параметрами
конструктора:

| Налаштування     | Змінна середовища                                                                                           | Значення за замовчуванням | Ефект                                                                                                                                                                                                 |
| ---------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Увімкнено        | `INPUT_SANITIZER_ENABLED`                                                                                   | `true`                    | Якщо `false`, захисний механізм завершує роботу достроково.                                                                                                                                           |
| Режим            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                             | `warn`                    | Політика щодо ін’єкцій: `block`, `warn` або `log`. (`redact` приймається для зворотної сумісності, але **не** видаляє текст ін’єкції; перезапис PII у запитах контролюється `PII_REDACTION_ENABLED`.) |
| Поріг блокування | параметр `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (псевдонім `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`                    | Мінімальний рівень серйозності, необхідний для блокування. За замовчуванням середній рівень лише відстежується.                                                                                       |

**Пріоритет режимів** (`getMode`): `options.mode` викликувача →
**перевизначення прапорцем функції `INJECTION_GUARD_MODE` у БД** (Панель керування → Налаштування →
Прапорці функцій) → змінна середовища `INJECTION_GUARD_MODE` → змінна середовища `INPUT_SANITIZER_MODE` →
`warn`. Таким чином, перевизначення з панелі керування має пріоритет над змінними середовища, тому
інтерфейс «Прапорці функцій» керує активним захисним механізмом у реальному часі (без перезапуску).
Читання з БД є відмовостійким: у разі помилки захисний механізм повертається до поведінки,
визначеної змінними середовища, а за відсутності перевизначення поведінка ідентична
визначенню лише за змінними середовища.

Джерела виявлення:

1. `sanitizeRequest()` з `@/shared/utils/inputSanitizer` (спільний набір
   детекторів, який використовується в інших частинах конвеєра).
2. Вбудовані `DEFAULT_GUARD_PATTERNS` (наразі `system_override_inline` і
   `markdown_system_block`, обидва з рівнем серйозності `high`).
3. Необов’язкові `customPatterns`, передані через параметри конструктора (рядки, регулярні вирази
   або записи `{ name, pattern, severity }`).

Коли `mode === "block"` **і** принаймні одне виявлення відповідає порогу
серйозності, `preCall` повертає `{ block: true, message: "Request rejected:
suspicious content detected" }`. У режимах `warn`/`log` захисний механізм веде журнал, але
дозволяє виклик. Спільна допоміжна функція `evaluatePromptInjection()` також експортується
для викликувачів, яким потрібно оцінювати підказки без використання реєстру.

**Обмеження сканування (v3.8.20):** детектор перевіряє лише **перші 16 КБ**
об’єднаного тексту підказки — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 байти) у
`src/shared/utils/inputSanitizer.ts`. І `detectInjection()`, і
`evaluatePromptInjection()` виконують `slice(0, MAX_INJECTION_SCAN_BYTES)` перед запуском
циклу шаблонів. Директиви ін’єкцій розташовуються поблизу початку вхідних даних, тому це
обмежує використання CPU/GC регулярними виразами для корисних навантажень розміром у сотні КБ,
не послаблюючи виявлення (див. #3932, #4041).

### Маскувальник облікових даних (`credentialMasker.ts`)

Виконується на **обох** етапах, останнім у стандартному ланцюжку (пріоритет `95`). Редагує
відомі шаблони ключів API / секретних токенів у вихідному корисному навантаженні (вміст
повідомлень, аргументи викликів інструментів, результати інструментів) **і** у відповіді постачальника,
щоб облікові дані, вставлені в підказку (або повторені в результаті інструмента), не потрапили
до зовнішнього постачальника або назад до клієнта.

- **Лише за явного ввімкнення**, за тією самою домовленістю, що й редагування PII (поруч із жорстким правилом №20):
  вимкнено, якщо `settings.credentialRedactionEnabled !== true` **і**
  `CREDENTIAL_REDACTION_ENABLED=true` не задано. Коли функцію вимкнено, захисний механізм нічого не робить —
  він ніколи не блокує та не перезаписує.
- `redactCredentials()` обходить усе дерево корисного навантаження/відповіді (`walkValue()`,
  із захистом від забруднення прототипів і циклів за допомогою `WeakSet`) та замінює збіги
  заповнювачем `[REDACTED:<type>]`, клонуючи лише ті гілки, які фактично
  змінилися.
- `CREDENTIAL_PATTERNS` охоплює ключі постачальників LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), токени VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), платіжні ключі (Stripe, Square), хмарні
  ключі (ключ доступу AWS, Twilio, SendGrid, Mailgun), приватні ключі / JWT,
  рядки підключення, що містять облікові дані (`mongodb://user:pass@...` тощо), а також
  універсальний шаблон значення заголовка `Authorization`/`x-api-key`/`api-key`/`apikey`.
  Ключі, що мають форму заголовків (`authorization`, `x-api-key`, `api-key`,
  `apikey`), редагуються структурно (лише значення, зі збереженням префікса схеми на кшталт
  `Bearer `/`Basic `), а не за допомогою універсального текстового регулярного виразу.
- Захисний механізм ніколи не блокує; він лише перезаписує (`modifiedPayload` /
  `modifiedResponse`) і додає анотації (`meta.credentialsRedacted`, `meta.count`).

Захист від регресій: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовий контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true перериває ланцюжок
  message?: string; // відображається під час блокування
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // повертається preCall для перезапису запиту
  modifiedResponse?: TValue; // повертається postCall для перезапису відповіді
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Захисний механізм сигналізує про «відсутність змін», повертаючи `void`, `{}` або
`{ block: false }`. Повернення `modifiedPayload`/`modifiedResponse` замінює
значення, що передається ланцюжком до наступних захисних механізмів.
`signal?: AbortSignal` передає життєвий цикл виклику до захисних механізмів. Переривання запиту є навмисним винятком із принципу fail-open: медіамости припиняють роботу й виконують очищення, не відновлюючи необроблені медіадані для цільової системи, яка, як відомо, їх не підтримує.

## Реєстр (`registry.ts`)

Синглтон `guardrailRegistry` надає:

- `register(guardrail)` — додає (або замінює за нормалізованим ім'ям) захисний механізм та пересортовує за зростанням `priority`.
- `clear()` / `list()` — допоміжні функції адміністрування.
- `runPreCallHooks(payload, context)` — ітерує активні захисні механізми, пропускає `payload` через `modifiedPayload` і зупиняється на першому `block: true`.
- `runPostCallHooks(response, context)` — той самий потік на стороні відповіді.
- `resetGuardrailsForTests({ registerDefaults })` — очищає стан та, за бажанням, повторно реєструє значення за замовчуванням для чистої ізоляції тестів.

Обидва виконавці повертають `{ blocked, payload|response, results, guardrail?, message? }`, де `results` — це масив записів `GuardrailExecutionResult`, що містять поля `blocked`, `skipped`, `modified`, `error` та `meta` для кожного захисного механізму, корисні для трасування.

### Вимкнення захисних механізмів для кожного запиту

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` агрегує дедуплікований список імен захисних механізмів, які слід пропустити для поточного запиту. Джерела (всі необов'язкові, всі об'єднані):

- `apiKeyInfo.disabledGuardrails`
- Тіло запиту `disabledGuardrails` (верхнього рівня)
- Тіло запиту `metadata.disabledGuardrails`
- Заголовок `x-omniroute-disabled-guardrails` (або застарілий `x-disabled-guardrails`)

Значення можуть бути масивами рядків або рядком, розділеним комами; імена нормалізуються до нижнього регістру в kebab-case (`pii_masker` → `pii-masker`). Результат передається через `context.disabledGuardrails` до реєстру, який пропускає відповідні захисні механізми (`skipped: true` у `results`).

## Порядок виконання

Для кожного запиту, що проходить через `src/sse/handlers/chat.ts` та
`open-sse/handlers/chatCore.ts`:

1.  `resolveDisabledGuardrails(...)` створює список винятків з ключа API, тіла запиту
    та заголовків.
2.  `guardrailRegistry.runPreCallHooks(body, ctx)` запускає захисні механізми у порядку
    зростання пріоритету:
    - Вимкнені захисні механізми записуються як `skipped`.
    - `preCall` кожного захисного механізму може переписати корисне навантаження
      через `modifiedPayload`.
    - Перший `block: true` перериває ланцюжок, і обробник повертає
      відповідь про відхилення захисним механізмом.
3.  (Потенційно переписане) корисне навантаження надходить до комбінованої маршрутизації
    та вихідної диспетчеризації.
4.  Після формування відповіді `guardrailRegistry.runPostCallHooks(...)`
    запускає той самий ланцюжок на відповіді. `block: true` тут відкидає
    вихідну відповідь.

Захисні механізми, які викликають помилку, записуються з `error: <message>` та
реєструються через `logger.warn`, але ланцюжок продовжується — за задумом,
система працює за принципом "відмова-відкриття".

## Конфігурація

Змінні середовища, які читаються вбудованими захисними механізмами:

| Змінна                                | Використовується               | Ефект                                                                                                          |
| :------------------------------------ | :----------------------------- | :------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`             | Встановіть `false`, щоб повністю вимкнути виявлення.                                                           |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`             | Політика ін'єкцій: `warn`, `block` або `log`. Застаріле значення `redact` не переписує текст ін'єкції.         |
| `INJECTION_GUARD_MODE`                | `prompt-injection`             | Режим для захисту від ін'єкцій; також прапорець функції БД, який **перевизначає** змінні середовища (БД > ЗМ). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`             | Мінімальна серйозність, при якій `MODE=block` відхиляє: `high` (за замовчуванням), `medium` або `low`.         |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`             | Застарілий псевдонім для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                    |
| `PII_REDACTION_ENABLED`               | `pii-masker`                   | Якщо `true`, PII запиту редагується (незалежно від режиму ін'єкції).                                           |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (нижче за течією) | Контролює поведінку маскувальника на стороні відповіді.                                                        |

Захисні механізми Modality Bridge читають конфігурацію часу виконання зі сховища
налаштувань на основі БД (`getSettings()`), а не зі змінних середовища.
Основними ключами Vision є `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` та `modalityBridgeCacheMaxEntries`.
Застарілі ключі `visionBridge*` приймаються лише як задокументований
одноцикловий резервний варіант читання; записи на панелі керування
використовують основні ключі. Значення за замовчуванням та резервний
розв'язувач знаходяться в `src/shared/constants/modalityBridgeDefaults.ts`,
а застарілі константи зберігаються в
`src/shared/constants/visionBridgeDefaults.ts`.

Аудіо використовує `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` та `modalityBridgeAudioMaxClips`, а також спільні
налаштування `modalityBridgeCache*`. Аудіо не має резервного варіанту
застарілих ключів, оскільки ці ключі були введені зі схемою Modality Bridge.

Відео використовує `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`, `modalityBridgeVideoFrameCount`,
`modalityBridgeVideoSamplingPolicy`, `modalityBridgeVideoMaxVideos` та
`modalityBridgeVideoTimeout`, а також спільні налаштування `modalityBridgeCache*`.
Він вимкнений за замовчуванням, оскільки FFmpeg/ffprobe є необов'язковими
операційними залежностями, а створення субтитрів кадрів додає затримку та
витрати на модель.

## Користувацькі обмежувачі (Guardrails)

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Кроки:

1.  Створіть `src/lib/guardrails/myGuardrail.ts`, розширюючи `BaseGuardrail`.
2.  Реалізуйте `preCall` та/або `postCall`.
3.  Зареєструйте під час імпорту (виштовхніть з `registerDefaultGuardrails`) або
    викличте `guardrailRegistry.register(...)` під час виконання — реєстр замінює
    будь-який попередній обмежувач з тим самим нормалізованим ім'ям.
4.  Додайте тести до `tests/unit/` (існуючі приклади:
    `tests/unit/guardrails-registry.test.ts`,
    `tests/unit/prompt-injection-guard.test.ts`,
    `tests/unit/guardrails/visionBridge.test.ts`).

## Тестування

Використовуйте `resetGuardrailsForTests()` між тестами, щоб почати з відомого стану.
Передайте `{ registerDefaults: false }`, щоб почати з порожнього реєстру та
зареєструвати лише обмежувачі, що тестуються. Vision Bridge приймає впровадження
залежностей (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge надає
еквівалентні точки для налаштувань, можливостей, вибору моделі STT, перевірок
облікових даних та транскрипції. Таким чином, тести можуть перевіряти обидва
потоки без доступу до БД або мережі.

## Покриття маршрутів захисту від ін'єкцій та червона команда (Фаза 8 · Блок D)

Захист від ін'єкцій (`createInjectionGuard` / `withInjectionGuard`) охоплює всі маршрути,
які приймають підказки користувача. Він враховує `INJECTION_GUARD_MODE` (за замовчуванням `warn` = лише логування;
`block` = повертає HTTP 400 `SECURITY_001`).

| Тип              | Маршрути                                                                                                                                             | Режим за замовчуванням |
| :--------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------- |
| Текст (існуючий) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn                   |
| Генеративний     | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn                   |
| Дані             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn                   |

Вилучення тексту (`extractMessageContents`) охоплює `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Червона команда (нічна, `nightly-llm-security.yml`):** promptfoo перевіряє, що кожен маршрут блокує
корпус OWASP-LLM у режимі `INJECTION_GUARD_MODE=block`; garak запускає зонди (пропускає без секрету).
`moderations` включено для послідовності — оператори в режимі блокування можуть виключити його через
`resolveDisabledGuardrails`.

Нічний робочий процес (`.github/workflows/nightly-llm-security.yml`, cron + ручний
запуск) має два завдання:

- **`promptfoo-guard` (блокування)** — запускає `promptfoo eval -c promptfooconfig.yaml`
  з `INJECTION_GUARD_MODE=block`. Кожен ворожий випадок (наприклад, "ігнорувати всі
  попередні інструкції...", "jailbreaks" у стилі DAN) стверджує, що відповідь містить
  `error.code === "SECURITY_001"`, тобто обмежувач фактично відхилив запит.
- **`garak` (консультативний)** — запускає garak `--probes promptinject,dan,leakreplay`
  проти локального екземпляра OmniRoute (`http://localhost:20128/v1`). Залежить від
  секрету провайдера (`PROMPTFOO_PROVIDER_KEY`); пропускається без помилок і має суфікс
  `|| true`, тому він звітує без збою CI.

Покриття допоміжного обмежувача (`createInjectionGuard` / `withInjectionGuard`)
охоплює кожен маршрут `/v1`, що містить підказки; текст підказки витягується з
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` за допомогою
`extractMessageContents()` у `src/shared/utils/inputSanitizer.ts`.
