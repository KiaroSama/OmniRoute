> **อัปเดตล่าสุด:** 2026-08-29 — v3.8.51 (ที่มาของทรานสคริปต์ Video Bridge ถูกประกาศโดยผู้เรียก
> และยังไม่ได้รับการตรวจสอบโดยเซิร์ฟเวอร์ — ชี้แจงตาม #11661)

Guardrails บังคับใช้มาตรการด้านความปลอดภัย นโยบาย และการแปลงเนื้อหาที่ขอบเขต
ระหว่าง OmniRoute กับผู้ให้บริการต้นทาง Guardrail แต่ละตัวสามารถตรวจสอบ (และ
เลือกที่จะปฏิเสธ แปลง หรือใส่คำอธิบายประกอบ) เพย์โหลดคำขอ (`preCall`) และ
การตอบกลับจากต้นทาง (`postCall`)

ระบบนี้เป็นแบบ **fail-open**: หาก Guardrail เกิดข้อผิดพลาดขณะทำงาน รีจิสทรี
จะบันทึกข้อผิดพลาดและดำเนินการต่อด้วย Guardrail ตัวถัดไป แทนที่จะทำให้
คำขอล้มเหลว การบล็อกต้องเกิดจากการตัดสินใจอย่างชัดเจน (`block: true`) ไม่ใช่เหตุบังเอิญ

### บริดจ์ภาพ (`visionBridge.ts`) — บริดจ์โมดัลลิตี PR-1

สกัดกั้นคำขอที่มีรูปภาพซึ่งส่งไปยัง **โมเดลที่ไม่รองรับภาพ** และดำเนินการอย่างใดอย่างหนึ่ง ได้แก่
เปลี่ยนเส้นทางคำขอทั้งหมดไปยังโมเดลที่รองรับภาพ หรือแทนที่ส่วนรูปภาพ
ด้วยคำอธิบายข้อความที่สร้างโดยโมเดลภาพซึ่งกำหนดค่าได้ ก่อนส่งคำขอ
ไปยังระบบต้นทาง วิธีนี้ช่วยให้ผู้ให้บริการที่รองรับเฉพาะข้อความสามารถจัดการ
เพย์โหลดหลายโมดัลลิตีได้อย่างโปร่งใส

ลำดับการทำงาน:

1. ข้ามหากโมเดลเป้าหมายรองรับภาพอยู่แล้ว (เว้นแต่โมเดลนั้นจะอยู่ใน
   รายการบังคับใช้บริดจ์ `isVisionBridgeForcedModel`)
2. แยกส่วนรูปภาพผ่าน `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`) ซึ่งมอบหมายงานให้กับ **ตัวตรวจจับสื่อแบบรวมศูนย์**
   `detectMediaParts()` ใน `open-sse/utils/mediaParts.ts` — แหล่งข้อมูลจริงเพียงแห่งเดียว
   ที่ใช้ร่วมกับตัวกรองความเข้ากันได้ของคอมโบ การแยกจะจำกัดเฉพาะส่วนระดับบนสุด
   ที่มีรูปแบบซึ่ง `replaceImageParts` สามารถแทรกกลับได้ (สัญญา extract↔replace): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` และ Responses API `input_image` รายการที่พบแบบซ้อนและ
   รูปแบบที่มีเพียงตัวบ่งชี้เป็นเนื้อหาสำหรับตัวกรองคอมโบและจะไม่ถูกแยกออกมา
   ข้ามหากไม่พบรายการใด
3. แก้ไขค่าคอนฟิกรันไทม์ผ่าน `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): คีย์การตั้งค่า `modalityBridge*`
   ใหม่มีลำดับความสำคัญเหนือกว่า ส่วนคีย์ `visionBridge*` แบบเดิมยังคงเป็น
   **ทางเลือกสำรองหนึ่งรอบ** (ช่วงเวลาสำหรับย้อนกลับ) ข้ามก่อนการสำรวจสื่อใดๆ
   เมื่อบริดจ์ถูกปิดใช้งาน
4. ตัวเลือกโหมด (`modalityBridgeVisionMode` ดูตารางด้านล่าง) จะตัดสินใจว่า
   จะเปลี่ยนเส้นทางหรือสร้างคำอธิบาย การเปลี่ยนเส้นทางจะคืนค่า `modifiedPayload`
   โดยสลับเฉพาะ `model` พร้อมเมตา `{ rerouted, fromModel, toModel, imagesKept }`
5. เส้นทางการสร้างคำอธิบาย: จำกัดจำนวนรูปภาพไว้ที่ `maxImages` สร้างพรอมต์ที่รับรู้บริบทของงาน
   ตรวจสอบแคชคำอธิบาย เรียกโมเดลภาพ **แบบขนาน**
   (`Promise.allSettled`) และแทรกส่วนข้อความ `[Image N]: <description>`
   แทนที่รูปภาพเหล่านั้น หากการสร้างคำอธิบายล้มเหลว จะได้ค่า `null` และส่วนรูปภาพเดิมจะถูก
   **เก็บรักษาไว้** (#4012) — ยกเว้นในเส้นทางการสร้างคำอธิบายของคอมโบเมื่อการสร้าง
   คำอธิบายทั้งหมดล้มเหลว ซึ่งระบบต้นทางที่ได้รับการยืนยันว่าไม่รองรับภาพจะได้รับข้อความแทน
   `(unavailable — no vision-capable provider connected)` (#8430)
6. คืนค่า `modifiedPayload` พร้อมเมตา (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`)

#### ตัวเลือกโหมด (`modalityBridgeVisionMode`)

| โหมด       | ค่าเริ่มต้น | ลักษณะการทำงาน                                                                                                                                                                                                                                                                                        |
| ---------- | ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔           | ฮิวริสติกแบบเดิมโดยไม่มีการเปลี่ยนแปลง (#6640/#7204): โมเดลที่ไม่ใช่คอมโบ/`auto/` จะถูกเปลี่ยนเส้นทางไปยังโมเดลภาพที่ดีที่สุด เว้นแต่โมเดลเดิมจะมีข้อมูลประจำตัวที่ใช้งานได้อยู่แล้ว (ในกรณีนั้นจะสร้างคำอธิบาย) ส่วนเป้าหมายแบบคอมโบจะสร้างคำอธิบายเสมอ                                              |
| `describe` |             | สร้างคำอธิบายเสมอ — ข้ามบล็อกการเปลี่ยนเส้นทางทั้งหมด โมเดลที่ผู้ใช้เลือกจะเป็นผู้ตอบเสมอ                                                                                                                                                                                                             |
| `reroute`  |             | บังคับเปลี่ยนเส้นทาง: ข้ามตัวป้องกันที่ให้ใช้โมเดลเดิมซึ่งมีข้อมูลประจำตัวต่อไป อย่างไรก็ตาม ตัวป้องกันข้อมูลประจำตัวของ**เป้าหมาย**การเปลี่ยนเส้นทางยังคงมีผล — เมื่อไม่มีเป้าหมายภาพที่ใช้งานได้ คำขอจะเปลี่ยนไปใช้การสร้างคำอธิบาย เพื่อไม่ให้รูปภาพดิบไปถึงแบ็กเอนด์ที่รองรับเฉพาะข้อความ (#8430) |

โหมดที่บังคับใช้จะลัดวงจร **ก่อน** ที่ฮิวริสติกอัตโนมัติจะทำงาน ส่วนลักษณะการทำงานของ `auto`
จะเหมือนกับการป้องกันก่อน PR-1 ทุกไบต์

#### ขอบเขตคีย์ API (`visionBridgeKeyScope.ts`)

เมื่อคีย์ API ของผู้เรียกจำกัด `allowedConnections` กลุ่มโควตา
(`allowedQuotas`) หรือโมเดล (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) บริดจ์จะเลือกเฉพาะ
โมเดลสำหรับการเปลี่ยนเส้นทางและการสร้างคำอธิบายที่คีย์ดังกล่าวมีสิทธิ์ใช้งาน บนการเชื่อมต่อที่คีย์นั้นมีสิทธิ์ใช้งาน
จากนั้นการเรียกเพื่อสร้างคำอธิบายจะดำเนินการผ่านลูปย้อนกลับเข้าตัวเองของ OmniRoute เสมอ โดยมี
ส่วนหัว `x-omniroute-self-loop-key-id` เพื่อให้คำขอแชตที่รับเข้ามา
บังคับใช้นโยบายการเชื่อมต่อและโมเดลของคีย์นั้นอีกครั้ง `enforceApiKeyPolicy()`
จะยอมรับส่วนหัวดังกล่าวเฉพาะเมื่อใช้ร่วมกับ bearer ของลูปย้อนกลับเข้าตัวเองเท่านั้น ดังนั้นจึงทำได้เพียง
จำกัดการเข้าถึงให้แคบลง และรหัสที่ไม่สามารถแก้ไขได้จะถูกปฏิเสธ

หากไม่มีโมเดลภาพใดที่คีย์ได้รับอนุญาตให้ใช้ เส้นทางการสร้างคำอธิบายจะหลีกทางและ
ปล่อยให้คำขอผ่านไปโดยไม่มีการเปลี่ยนแปลง ซึ่งเป็นพฤติกรรมเปิดให้ผ่านเมื่อเกิดความล้มเหลวเช่นเดียวกับ
การป้องกันที่ถูกปิดใช้งาน (เมตา `{ skipped: true, reason: "no_permitted_vision_model" }`)
คำขอที่ไม่มีคีย์และคีย์ที่ไม่มีข้อจำกัดเหล่านี้จะทำงานเหมือนเดิมทุกประการ

#### พรอมต์การสร้างคำอธิบายที่รับรู้บริบทของงาน (`modalityBridgeVisionTaskAware`)

ค่าเริ่มต้นคือ **true** `composeVisionPrompt()` (`visionBridgeHelpers.ts`) จะผนวก
ข้อความจาก **ข้อความล่าสุดของผู้ใช้** (ตัดให้เหลือไม่เกิน 500 อักขระ) เข้ากับพรอมต์
คำอธิบายพื้นฐาน เพื่อกำหนดทิศทางคำอธิบายให้สอดคล้องกับสิ่งที่ผู้ใช้ถามจริง
(รูปแบบ codex-vision-proxy) และขอให้โมเดลวิชันถอดข้อความที่มองเห็นได้
เมื่อปิดแฟล็กนี้ — หรือไม่มีข้อความจากผู้ใช้ — ระบบจะใช้พรอมต์พื้นฐานโดยไม่มีการแก้ไข

คำขอที่เข้ากันได้กับ OpenAI ของ self-loop สำหรับการอธิบายเอง (`callVisionModelSingle()`
ใน `visionBridgeHelpers.ts`) จะร้องขอ `image_url.detail: "high"` เสมอ —
โดยไม่มีเงื่อนไข สำหรับผู้เรียก/ผู้ให้บริการทุกราย และไม่ขึ้นอยู่กับสัญญาณใดๆ จากไคลเอนต์
การสุ่มตัวอย่างแบบรายละเอียดต่ำลดความแม่นยำของ OCR สำหรับงานถอดข้อความ
ที่พรอมต์นี้ร้องขอโดยตรง ดังนั้นคำขออธิบายเองจึงร้องขอรายละเอียดสูงเสมอ
ไม่ว่าคำขอขาเข้าต้นฉบับจะใช้ระดับรายละเอียดใดก็ตาม การตั้งค่านี้มีผลเฉพาะกับ
เนื้อหาคำขออธิบายภายในเท่านั้น และไม่เปลี่ยนวิธีที่ OmniRoute ส่งต่อ
`image_url.detail` ของผู้เรียกในคำขอหลัก — ค่าเริ่มต้นดังกล่าวถูกใช้แยกต่างหาก
และใช้เฉพาะกับไคลเอนต์ OpenCode ที่ตรวจพบเท่านั้น ใน
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`)
สาขารูปแบบ wire ของ Anthropic ใน self-loop สำหรับการอธิบายไม่มีฟิลด์ `detail`
และไม่ได้รับผลกระทบจากค่าเริ่มต้นทั้งสองรายการ

#### ขีดจำกัดเอาต์พุตคำอธิบาย (`modalityBridgeVisionMaxChars`)

| คีย์                           | ค่าเริ่มต้น | ช่วงค่า            |
| ------------------------------ | ----------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`         | `0` หรือ 100–50000 |

`0` (ค่าเริ่มต้น) หมายถึง **ไม่มีขีดจำกัด** — คำอธิบายที่ส่งคืนโดย
`callVisionModel()` จะถูกส่งผ่านโดยไม่มีการแก้ไข เพื่อคงพฤติกรรมเดิมไว้
ค่าใดๆ ในช่วง 100–50000 จะตัดคำอธิบายและเติมส่วนต่อท้าย `…`
ก่อนนำกลับไปแทรกในรูปแบบ `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` ใน `src/lib/guardrails/visionBridge.ts`)
เพิ่มค่านี้สำหรับงาน OCR ที่มีรายละเอียดมาก ซึ่งโมเดลปลายทางจำเป็นต้องได้รับ
ข้อความถอดเสียงทั้งหมด หรือลดค่าเพื่อจำกัดการใช้โทเค็นของโมเดลวิชันที่สร้างคำอธิบายยาว
ฟิลด์บนแดชบอร์ดอยู่ในแผง Advanced ของแท็บ Vision
(`modality-bridge-max-chars` ใน `ModalityBridgeVisionTab.tsx`) และจะปรับค่าใดๆ
ระหว่าง 1 ถึง 99 ขึ้นเป็นค่าต่ำสุด 100 โดยปล่อยค่า `0` ที่ระบุอย่างชัดเจนไว้ตามเดิม —
`0` เป็นค่า Zod ที่ถูกต้องในตัวมันเอง
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`) ไม่ได้เป็นเพียง
ค่าเริ่มต้นเมื่อ "ไม่ได้ตั้งค่า"

#### แคชคำอธิบาย (`modalityBridge/bridgeCache.ts`)

แคช LRU + TTL ในหน่วยความจำสำหรับเอาต์พุตคำอธิบาย ซึ่งใช้ร่วมกันทั้งโปรเซส
คีย์ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` พร้อม
การจัดเฟรมโดยใช้คำนำหน้าระบุความยาว (ไม่มีการชนกันของขอบเขตฟิลด์) องค์ประกอบโมเดลคือ
โมเดลบริดจ์ที่ **กำหนดค่าไว้** ไม่ใช่โมเดลที่ตอบจริง —
`callVisionModel` อาจใช้โมเดลสำรองภายใน และการสร้างคีย์แยกตามแต่ละครั้งที่พยายาม
จะทำให้แคชแตกกระจาย คำขออธิบายที่ล้มเหลวจะไม่ถูกแคช การตั้งค่า:

| คีย์                            | ค่าเริ่มต้น | ช่วงค่า |
| ------------------------------- | ----------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`      | —       |
| `modalityBridgeCacheTtlMinutes` | `60`        | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`       | 10–5000 |

#### การปรับภาพระยะไกลให้เป็นมาตรฐาน (การดึงข้อมูลแบบ self-loop สำหรับการอธิบาย/base64)

เมื่อบริดจ์ดึงภาพ **ระยะไกล** ด้วยตนเอง — ทั้ง self-call สำหรับการอธิบายของ Anthropic
และการแปลงเป็น base64 ในรูปแบบ wire ของ claude
(`ensureBase64ImagesForClaudeWire`) ซึ่งทั้งคู่ดำเนินการผ่าน
`fetchRemoteImageAsDataUri()` ใน `visionBridgeHelpers.ts` — URI ข้อมูลที่ได้
จะถูกส่งผ่าน `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) ก่อนฝังลงในคำขอของโมเดลวิชัน
ภาพที่มีขนาดใหญ่เกินไปจะถูกย่อให้มี **ด้านยาว 2048px** (ตรงกับขีดจำกัดการปรับขนาด
ที่ OpenAI/Anthropic ใช้ฝั่งเซิร์ฟเวอร์อยู่แล้ว) ซึ่งช่วยลดจำนวนไบต์ที่อัปโหลด/เวลาแฝง
โดยไม่เปลี่ยนสิ่งที่โมเดลวิชันมองเห็น การปรับขนาดใช้ `sharp` ซึ่งโหลดผ่าน dynamic import:
บนแพลตฟอร์มที่ไบนารีแบบเนทีฟของแพ็กเกจโหลดไม่สำเร็จ `normalizeDataUri()`
จะ **ไม่ throw โดยเด็ดขาด** — แต่จะย้อนกลับไปส่งผ่านไบต์ต้นฉบับแทน
เพื่อให้เส้นทางการอธิบาย/แปลงเป็น base64 ยังคงทำงานได้เสมอ ไบต์ที่ไม่ใช่ภาพ
(กรณีการดึงข้อมูลไม่ได้คืนภาพที่ถอดรหัสได้) จะถูกส่งผ่านโดยไม่มีการแก้ไขเช่นกัน
การปรับให้เป็นมาตรฐานนี้จำกัดเฉพาะภาพที่บริดจ์ดึงมาเพื่อใช้ใน self-call ของตนเอง —
จะไม่ถูกนำไปใช้กับเพย์โหลดดิบที่ส่งผ่านจากผู้เรียก ซึ่งสอดคล้องกับหลักการ
แก้ไขเฉพาะเมื่อเลือกใช้เท่านั้น (กฎเคร่งครัดข้อที่ 20)

#### เฮดเดอร์เพื่อความโปร่งใส + สถิติ

การตอบกลับที่ผ่านการแปลงด้วยการอธิบายจะมี
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(สร้างโดย `buildModalityBridgeHeader()` ใน `modalityBridge/bridgeStats.ts`
และประทับโดย `withModalityBridgeHeader()` ใน `src/sse/handlers/chatHelpers.ts`)
คำขอที่ถูกเปลี่ยนเส้นทางจะ **ไม่มี** เฮดเดอร์ — เพย์โหลดไม่ได้ถูกแก้ไข
และการสลับโมเดลสามารถมองเห็นได้อยู่แล้วในฟิลด์ `model` ของเนื้อหาการตอบกลับ

`GET /api/modality-bridge/stats` (ใช้การยืนยันตัวตนสำหรับการจัดการ ระดับเดียวกับ
`GET /api/settings`) ส่งคืนตัวนับแยกตามโมดาลิตีที่เก็บอยู่ในหน่วยความจำ
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` สำหรับ `vision`, `audio` และ
`video` โดย `averageLatencyMs` ใช้ `latencySamples` เป็นตัวหาร ไม่ใช่จำนวนครั้งที่พยายามทั้งหมด
การดำเนินการที่ไม่มีข้อมูลเวลาจะไม่สร้างตัวอย่างที่มีค่าเป็นศูนย์มิลลิวินาทีขึ้นมา
`bridged` ยังคงเป็นนามแฝงที่เข้ากันได้ย้อนหลังสำหรับการแปลงที่สำเร็จ
ความพยายามที่ล้มเหลวจะไม่เพิ่มค่านี้
ตัวนับจะรีเซ็ตเมื่อโปรเซสเริ่มต้นใหม่ตามการออกแบบ
(เป็นเทเลเมทรี ไม่ใช่ระบบบัญชี)

#### การกำหนดค่าแดชบอร์ด

หน้าแดชบอร์ดเฉพาะคือ
`/dashboard/settings/modality-bridge` แท็บ `Vision`, `Audio`
และ `Video` ที่เข้าถึงผ่าน URL ได้จะคงพารามิเตอร์คิวรีไว้ขณะสลับค่า `tab`
แท็บ Vision มีตัวเลือกการเปิดใช้งาน โหมด การเลือกโมเดล (รวมถึงค่าเริ่มต้นแบบอัตโนมัติ)
พรอมป์ตามประเภทงาน ขีดจำกัดขั้นสูงสำหรับเวลาหมดเวลา/รูปภาพ/ความยาวคำอธิบาย/แคช
ตัวนับรันไทม์ และคำขอตัวอย่างที่มีการป้องกัน
แท็บ Audio ใช้งานได้จริงเช่นกัน โดยมีตัวเลือกการเปิดใช้งาน ตัวเลือกโมเดลเฉพาะ STT พร้อม Auto
ขีดจำกัดเวลาหมดเวลา/ความยาวสูงสุดของคลิป ตัวนับเสียง และการทดสอบตัวอย่าง `input_audio`
แท็บ Video ทำงานได้อย่างสมบูรณ์ โดยรายงานสถานะรันไทม์ของ FFmpeg/ffprobe
ซึ่งเป็นหนึ่งในสี่สถานะ UI ที่ระบุไว้อย่างชัดเจน (`unknown` ขณะที่การตรวจสอบกำลังดำเนินอยู่
หรือไม่สามารถดำเนินการให้เสร็จสิ้นได้, `restricted` เมื่อโฮสต์แดชบอร์ดไม่ใช่ loopback
และข้ามการตรวจสอบในฝั่งไคลเอนต์, `unavailable` เมื่อตรวจสอบแล้วและยืนยันว่าไม่มี
หรือ `available` พร้อมเวอร์ชันของ FFmpeg/ffprobe) บันทึกขีดจำกัดการเปิดใช้งาน/โมเดล/เฟรม/วิดีโอ/เวลาหมดเวลา
กรองตัวเลือกโมเดลให้เหลือเฉพาะโมเดลที่รองรับการมองเห็น และแสดงตัวนับวิดีโอ

การ์ด Vision Bridge เดิมภายใต้การตั้งค่า AI เป็นลิงก์สำหรับความเข้ากันได้ไปยัง
หน้าใหม่ โดยไม่ได้เป็นเจ้าของสำเนาที่สองของแบบฟอร์มอีกต่อไป Media Providers ยัง
เชื่อมโยงเวิร์กโฟลว์ Image-to-Text และ Speech-to-Text ไปยังแท็บ Modality
Bridge ที่เกี่ยวข้อง โดยไม่ลบเพลย์กราวด์ Speech-to-Text ที่มีอยู่

**การข้ามการตรวจรับสำหรับ self-loop:** เมื่อการเรียกเพื่อสร้างคำอธิบายกำหนดเส้นทางผ่าน
`/v1` self-loop ของ OmniRoute เอง (โมเดลผู้ให้บริการที่ไม่ใช่มาตรฐาน) คำขอย่อยจะส่ง
`x-omniroute-admission-bypass: internal` และผ่านการยืนยันตัวตนด้วยข้อมูลประจำตัว
self-loop ที่ได้รับการแก้ค่าแล้ว ได้แก่ sentinel `sk_omniroute` ภายในเครื่องเมื่ออยู่ในโหมด local
หรือคีย์ env `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` ที่ผู้ดำเนินการกำหนดค่าไว้ (#1350)
เพื่อให้การติดตั้งใช้งานที่ตั้งค่า `REQUIRE_API_KEY=true` ยังคงเรียกสร้างคำอธิบายได้
การข้ามนี้จะได้รับอนุญาตเฉพาะเมื่อใช้ข้อมูลประจำตัวที่ตรงกันทุกประการเท่านั้น
ไคลเอนต์ภายนอกจึงไม่สามารถใช้ส่วนหัวนี้เพื่อข้ามการตรวจรับได้

ค่าเริ่มต้นแบบเดิมอยู่ใน `src/shared/constants/visionBridgeDefaults.ts`
ส่วนค่าเริ่มต้นใหม่สำหรับโหมด/การรับรู้ประเภทงาน/แคช และตัวแก้ค่าการตั้งค่าอยู่ใน
`src/shared/constants/modalityBridgeDefaults.ts` กลไกป้องกันมีตัวเลือกคอนสตรักเตอร์
`deps` เพื่อให้การทดสอบสามารถแทรกอิมพลีเมนเทชันจำลองของ `getSettings` และ
`callVisionModel` ได้

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

สกัดกั้นคำขอแชตที่มีเสียงก่อนจะไปถึงปลายทางซึ่งไม่ทราบว่ารองรับอินพุตเสียง
ระบบจะไม่เปลี่ยนเส้นทางคำขอแชต โดยส่วนเสียงจะถูกถอดเสียงผ่านเอนด์พอยต์ multipart
ที่เข้ากันได้กับ OpenAI ซึ่งมีอยู่เดิม และโมเดลแชตที่เลือกจะทำงานต่อด้วยข้อความถอดเสียง

ลำดับการทำงาน:

1. แก้ค่า `supportsAudio` ผ่าน `getResolvedModelCapabilities()` โดยเมทาดาทาที่ระบุชัดเจน
   จากรีจิสทรีผู้ให้บริการมีลำดับความสำคัญสูงสุด ตามด้วยเมทาดาทาโมเดลแบบคงที่ และ
   `modalities_input` ที่ซิงค์ไว้ รายการอินพุตที่ประกาศโดยไม่มี `audio` จะมีค่าเป็น `false`
   หากไม่มีหลักฐานด้านความสามารถ ค่าจะยังคงเป็น `null` ทั้ง `false` และ `null`
   จะเปิดใช้งานบริดจ์แบบระมัดระวัง ส่วน `true` จะข้ามบริดจ์
2. แก้ค่าการตั้งค่า `modalityBridgeAudio*` และแยกส่วนเสียงระดับบนสุดที่สามารถตัดต่อได้
   จากทุกข้อความผ่านตัวตรวจจับ `detectMediaParts()` ที่ใช้ร่วมกัน รูปแบบข้อมูลที่รองรับคือ
   `input_audio`, `audio_url` ของ OpenAI และ `source.media_type: "audio/*"`
   ระบบตรวจพบเสียงที่ซ้อนอยู่เพื่อใช้ในการกำหนดเส้นทาง แต่จะไม่ลบออกผ่านเส้นทางการตัดต่อ
   ปริมาณงานถูกจำกัดด้วย `modalityBridgeAudioMaxClips` ส่วนที่อยู่หลังจากขีดจำกัด
   จะยังคงไม่ถูกแก้ไข
3. ใช้ `provider/model` ที่กำหนดค่าไว้ หรือให้ `selectAudioBridgeModel()` ไล่ตรวจสอบ
   `AUDIO_TRANSCRIPTION_PROVIDERS` ตามลำดับแค็ตตาล็อกที่คงที่ และเลือกโมเดลแรก
   ที่มีข้อมูลประจำตัวของผู้ให้บริการที่ใช้งานอยู่และใช้ได้
4. `callAudioTranscription()` แปลงเสียงแบบ base64/data-URI เป็น `file` แบบ multipart
   หรือดาวน์โหลด `audio_url` ระยะไกลผ่านกลไกป้องกันขาออกแบบ public-only
   พร้อมการตรึง DNS และขีดจำกัด 25 MB จากนั้นจะ POST ไฟล์และโมเดลที่เลือกไปยัง
   `/v1/audio/transcriptions` self-loop ภายในเครื่อง โดยยืนยันตัวตนด้วย
   `resolveSelfLoopBearer()` เส้นทางการถอดเสียงที่มีอยู่เดิมจะดำเนินการค้นหาข้อมูลประจำตัว
   การจัดการคูลดาวน์/ขีดจำกัดอัตรา และการส่งต่อไปยังผู้ให้บริการตามปกติ
5. การเรียกที่สำเร็จจะแทนที่ส่วนดังกล่าวด้วย `[Audio N]: <transcript>`
   การเรียกทำงานด้วย `Promise.allSettled` โดยความล้มเหลวแต่ละรายการจะคงส่วนเสียงเดิมนั้นไว้
   (ข้อกำหนด #4012) หากทุกการเรียกล้มเหลวและพิสูจน์แล้วว่าเป้าหมายมี
   `supportsAudio === false` ส่วนต่างๆ จะกลายเป็น
   `[Audio N]: (unavailable — no STT provider connected)` (ข้อกำหนด #8430)
   สำหรับเป้าหมายที่ไม่ทราบความสามารถ (`null`) ผลลัพธ์ที่ล้มเหลวทั้งหมดจะยังคงไม่ถูกแก้ไข
   เป้าหมายที่พิสูจน์แล้วว่ารองรับเฉพาะข้อความและไม่มีข้อมูลประจำตัว STT ที่ใช้ได้
   จะได้รับข้อความแทนที่แบบชัดเจนเดียวกันโดยไม่มีการเรียกเครือข่าย

ข้อความถอดเสียงที่สำเร็จจะใช้แคช LRU/TTL ของ Modality Bridge ที่ใช้ร่วมกันทั้งโปรเซส
คีย์ประกอบด้วยการอ้างอิงเสียง ป้ายกำกับการดำเนินการแบบคงที่ `audio-transcription`
และโมเดล STT ที่เลือก โดยจะไม่แคชความล้มเหลว ความพยายามด้านเสียงจะอัปเดตตัวนับ
`bridged`, `cacheHits`, `failures` และ `lastUsedAt` ที่ใช้ร่วมกัน
การตอบกลับที่ถูกแปลงจะมี
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`
ส่วนคำขอที่ไม่ถูกแก้ไขจะไม่ได้รับเซกเมนต์ Audio Bridge

การตั้งค่ารันไทม์จัดเก็บใน DB และผ่านการตรวจสอบด้วย Zod:

| คีย์                          | ค่าเริ่มต้น | ช่วงค่า               |
| ----------------------------- | ----------- | --------------------- |
| `modalityBridgeAudioEnabled`  | `true`      | —                     |
| `modalityBridgeAudioModel`    | `""`        | อัตโนมัติหรือรหัส STT |
| `modalityBridgeAudioTimeout`  | `60000`     | 1000–300000           |
| `modalityBridgeAudioMaxClips` | `3`         | 1–10                  |

แคชที่ใช้ร่วมกันยังคงควบคุมโดย `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` และ `modalityBridgeCacheMaxEntries`

### บริดจ์วิดีโอ (`videoBridge.ts`, `videoBridgePipeline.ts`)

ดักจับส่วนวิดีโอระดับบนสุดใน `messages` ของ Chat Completions และ `input`
ของ Responses API ก่อนเรียกเป้าหมายที่ไม่ทราบว่ารองรับวิดีโอโดยตรง
รูปแบบที่รองรับ ได้แก่ `input_video`, `video_url`, `video_source`, URL แบบ HTTPS
และ URI ข้อมูล `data:video/*;base64,...` ชื่อไฟล์ธรรมดาที่อยู่ในข้อความจะไม่ถูกพิจารณา
ว่าเป็นวิดีโอ

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) รับผิดชอบการสำรวจคำขอ
การตรวจสอบความสามารถ/นโยบาย การรวบรวมข้อมูลต่อคำขอ และเพย์โหลดการตอบกลับ
งานต่อวิดีโอ—การรับข้อมูล แคชผลลัพธ์ทั้งหมด การอธิบายลำดับเฟรม
(ซึ่งรวมทรานสคริปต์เสียงที่ผู้เรียกประกาศไว้ หากมี) ตลอดจนเมตริก/การยกเลิก/การล้างข้อมูล
ต่อความพยายามหนึ่งครั้ง—ถูกซ่อนไว้เบื้องหลัง `processVideoPart` ใน
`videoBridgePipeline.ts` ซึ่งถูกเรียกหนึ่งครั้งต่อส่วนวิดีโอภายในลูปของ `preCall`
โมดูลดังกล่าวยังกำหนดขอบเขตพอร์ตไว้อย่างชัดเจน ได้แก่ `VideoMediaBrokerPort`
(การรับไบต์และแยกเฟรมตัวอย่าง), `VideoAudioTranscriptionPort`
(การรวมทรานสคริปต์เสียงที่ผู้เรียกประกาศไว้เข้ากับคำบรรยายเฟรมตัวอย่าง) และ
`VideoDrilldownPort` (ขอบเขตการเก็บรักษาข้อมูลการเจาะลึกรายเฟรม ซึ่งยังไม่ได้เชื่อมต่อ
เข้ากับ `processVideoPart`—ปัจจุบันมีเพียงเส้นทาง `/api/modality-bridge/video/drilldown`
ที่แยกต่างหากเท่านั้นที่เขียนรายการข้อมูลการเจาะลึก)

เส้นทางคำขอสาธารณะ `/v1` จะไม่นำเข้าหรือเรียกใช้โพรเซสย่อย
วิดีโอระยะไกลจะถูกดาวน์โหลดภายใต้ขีดจำกัด 50 MiB ส่วนวิดีโอ base64 แบบอินไลน์
มีขีดจำกัดขนาดหลังถอดรหัสต่อวิดีโอแบบเผื่อความปลอดภัยที่ 36 MiB เพื่อให้ซองข้อมูล
ของโมเดล/ข้อความ/การจัดเฟรมยังคงอยู่ภายในขีดจำกัดการรับคำขอ JSON สาธารณะที่ 50 MiB
ระบบจะตรวจสอบความยาวแบบอินไลน์และค่าประมาณขนาดหลังถอดรหัสก่อนการจัดสรรหน่วยความจำ
URL ระยะไกลเริ่มต้นและทุกการเปลี่ยนเส้นทางต้องใช้ HTTPS โดยใช้กลไกป้องกัน
การเชื่อมต่อขาออกเฉพาะสาธารณะที่มีอยู่ พร้อมการตรึง DNS จากนั้นไบต์จะข้ามผ่าน
ขอบเขตโบรกเกอร์ภายใน `POST /api/modality-bridge/video/extract` โดยตรง เส้นทางนี้เป็นทั้ง
`LOCAL_ONLY` และ `SPAWN_CAPABLE` รับเฉพาะคำขอที่ผ่านการยืนยันตัวตนเฉพาะต่อโพรเซส
และมาจากลูปแบ็กที่เชื่อถือได้ และไม่รับ URL, พาธระบบไฟล์, ไฟล์ปฏิบัติการ
หรือรายการอาร์กิวเมนต์โดยเด็ดขาด ไปป์ไลน์ขนาดเนื้อหาของ API และตัวอ่านเนื้อหา
แบบเพิ่มทีละส่วนของตัวจัดการ ต่างบังคับใช้ขีดจำกัดอินพุตโบรกเกอร์ที่ 50 MiB
อย่างเป็นอิสระต่อกัน คิวแบบมีขอบเขตจะดำเนินการแยกข้อมูลครั้งละหนึ่งงาน
อนุญาตให้มีงานรอดำเนินการสี่งาน และจำกัดอินพุตที่รอดำเนินการไว้ที่ 100 MiB

ภายในโบรกเกอร์ `ffprobe` จะอ่านไฟล์ภายในเครื่องแบบส่วนตัว โดยรายการรูปแบบ
ที่อนุญาตแบบตายตัวจะไม่รวมรูปแบบเพลย์ลิสต์และแมนิเฟสต์ สำหรับคอนเทนเนอร์ตระกูล MOV
ที่อนุญาต การอ้างอิงข้อมูล MOV ภายนอกจะยังคงถูกปิดใช้งานโดยค่าเริ่มต้น
และคำสั่งแบบตายตัวจะไม่เลือกเปิดใช้งานคุณสมบัติดังกล่าว ทั้ง `ffprobe` และ `ffmpeg`
ใช้รายการโปรโตคอลที่อนุญาตเฉพาะ `file` ใช้หนึ่งเธรด รายการอาร์กิวเมนต์แบบตายตัว
ไม่มีเชลล์ และใช้ไฟล์ปฏิบัติการที่ค้นหาจาก `PATH` สตรีมภาพหน้าปกแบบแนบ
ไม่ถือเป็นตัวเลือกที่เล่นได้ สตรีมที่เล่นได้ทั้งหมดต้องเป็นไปตามขีดจำกัด
และระบบจะเลือกสตรีมเริ่มต้นที่ระบุไว้อย่างชัดเจนก่อนใช้ตัวเลือกสำรองแบบกำหนดแน่นอน
ที่มีดัชนีต่ำสุด วิดีโอถูกจำกัดไว้ที่ 600 วินาที, 8,192 พิกเซลต่อมิติ
และ 33,554,432 พิกเซลต้นฉบับ FFmpeg จะสุ่มตัวอย่างเฟรม JPEG ณ จุดกึ่งกลางจำนวน 1–16 เฟรม
ปรับลดขนาดด้านยาวให้ไม่เกิน 1,024 พิกเซลโดยไม่ขยายอินพุตที่มีขนาดเล็กกว่า
และจะไม่ได้รับ URL โดยเด็ดขาด ค่าเริ่มต้นของการสุ่มตัวอย่างคือ `uniform`
นโยบาย `scene_aware` ที่เป็นตัวเลือกและ `segment_aware` ที่เป็นการทดลอง
จะดำเนินการ FFmpeg แบบตายตัวเพิ่มอีกหนึ่งรอบกับสตรีมภายในเครื่องที่ตรวจสอบแล้ว
เลือกการประทับเวลาฉาก `showinfo` แบบมีขอบเขต และย้อนกลับไปใช้จุดกึ่งกลางแบบสม่ำเสมอ
ชุดเดิมอย่างกำหนดแน่นอน หากตัวตรวจจับล้มเหลว หมดเวลา ให้เอาต์พุตผิดรูปแบบ
หรือไม่มีชุดตัวเลือก โหมดที่รับรู้เซกเมนต์จะจัดสรรตัวอย่างจุดกึ่งกลาง
ตามสัดส่วนของช่วงฉากที่ตรวจสอบแล้ว หลักฐานของโหมดที่รับรู้เซกเมนต์
และพฤติกรรมการใช้ตัวเลือกสำรองมีรายละเอียดด้านล่าง ขีดจำกัดสูงสุดแบบตายตัวที่ 16 เฟรม
จะถูกใช้หลังการเลือกในทุกนโยบาย เมื่อคำขอแบบรับรู้ฉากมีงบประมาณเพียงหนึ่งเฟรม
ระบบจะใช้จุดกึ่งกลางแบบสม่ำเสมอของวิดีโอเต็มที่กำลังใช้งานหรือหน้าต่างโฟกัส
และรายงาน `policyEffective: uniform` เพราะเฟรมฉากที่เลือกเพียงเฟรมเดียว
ไม่สามารถคงข้อมูลทั้งต้นและปลายของช่วงเวลาไว้ได้ ผู้เรียกอาจระบุ
หน้าต่างโฟกัสที่มีค่าจำกัด (`start`/`end` เป็นวินาที) ได้ โดยขอบเขตจะถูกปรับ
ให้อยู่ภายในระยะเวลาของสื่อ หน้าต่างที่กลับด้านหรือมีค่าไม่จำกัดจะถูกปฏิเสธ
และนโยบายการสุ่มตัวอย่างทั้งหมดจะทำงานเฉพาะภายในช่วงที่ปรับเป็นมาตรฐานแล้ว
หน้าต่างที่ได้จะรวมอยู่ในข้อมูลเมตาของการสุ่มตัวอย่างและคำนำหน้าคำอธิบาย
ที่ไม่น่าเชื่อถือ เพื่อให้โมเดลปลายทางสามารถแยกความแตกต่างระหว่างส่วนตัดที่โฟกัส
กับไทม์ไลน์ทั้งหมดได้

การโฟกัสเชิงความหมายสำหรับคำบรรยายเป็นการตั้งค่าที่แยกต่างหากและระบุไว้อย่างชัดเจน
โหมดการวิเคราะห์เริ่มต้น `full` จะคงพรอมต์เฟรมที่มีอยู่เดิมไว้
และจะไม่ส่งต่อข้อความคำขอไปยังโมเดลคำบรรยาย ในโหมด `focused`
บริดจ์จะอ่านเฉพาะ `text`/`input_text` ล่าสุดที่ไม่ว่างและผู้ใช้เป็นผู้เขียน
จากคอนเทนเนอร์ Chat หรือ Responses เดียวกัน ปรับให้อยู่ในรูปแบบ NFC
ยุบอักขระควบคุมและช่องว่าง และจำกัดไว้ที่ 500 จุดรหัส Unicode
หากผลลัพธ์ว่างเปล่า ระบบจะย้อนกลับไปใช้พรอมต์ `full` ที่ตรงกันทุกประการ
คำใบ้ที่ใช้งานได้จะถูกทำให้เป็นอนุกรมในรูปแบบ JSON ภายในบล็อกบริบทผู้ใช้
ที่ไม่น่าเชื่อถือโดยเฉพาะ และใช้ได้เฉพาะเพื่อจัดลำดับความสำคัญของรายละเอียด
ที่สังเกตได้เท่านั้น โดยไม่สามารถลบล้างคำเตือนแยกต่างหากที่ห้ามปฏิบัติตามคำสั่ง
ซึ่งมองเห็นหรือได้ยินในสื่อ โฟกัสแบบข้อความจะไม่อนุมาน `start`/`end`
หรือเปลี่ยนตัวสุ่มตัวอย่างตามเวลา

#### หลักฐานเซกเมนต์เชิงโครงสร้าง FU-07

`segment_aware` ใช้การวิเคราะห์ล่วงหน้าแบบมีขอบเขตหนึ่งรอบกับสตรีมวิดีโอภายในที่ผ่านการตรวจสอบแล้ว
สายโซ่ตัวกรองแบบตายตัวจะปรับขนาดให้มีความกว้างไม่เกิน 320 พิกเซลก่อน
จากนั้นตรวจจับการเปลี่ยนฉากและช่วงภาพค้าง แล้วสุ่มตัวอย่างที่ 1 เฟรมต่อ
วินาทีเพื่อวัดความเบลอ ค่าลูมาเฉลี่ย และข้อมูลเชิงพื้นที่/เวลา รอบการวิเคราะห์นี้
จำกัดไว้ที่ตัวอย่างเชิงโครงสร้าง 600 ตัวอย่าง ใช้เธรด FFmpeg/ตัวกรองหนึ่งเธรด ใช้
รายการอนุญาตสำหรับโปรโตคอลเฉพาะ `file` และคอนเทนเนอร์ชุดเดิม จำกัดเอาต์พุตของโปรเซสไว้ที่ 1 MiB
และใช้เวลาได้ไม่เกิน 30 วินาทีภายในกรอบการยกเลิก/กำหนดเวลาร่วมของโบรกเกอร์ ระบบจะไม่
รับคำสั่ง ตัวกรอง พาธ หรือ URL จากคำขอโดยเด็ดขาด

ค่าทางโครงสร้างเป็นหลักฐานจากการสุ่มตัวอย่างที่ให้ผลแบบกำหนดแน่นอน ไม่ใช่ความเข้าใจ
เชิงความหมายของวิดีโอ ค่าเหล่านี้ไม่ได้อนุมานบุคคลหรือวัตถุ การกระทำ คำบรรยาย เสียงพูด หรือเจตนา
ของผู้ใช้ ขอบเขตฉากและขอบเขตภาพค้างจะประกอบกันเป็นเซกเมนต์ ส่วนสัดส่วนภาพค้าง ความเบลอ
การรับแสง รายละเอียดเชิงพื้นที่ และการเปลี่ยนแปลงตามเวลามีผลเพียงต่อวิธีจัดสรรงบประมาณ
เฟรม 1–16 เฟรมที่มีอยู่เท่านั้น เซกเมนต์ที่ภาพค้างทั้งหมดจะถูกจำกัดไว้ที่หนึ่งเฟรม
ขณะที่เซกเมนต์ที่ไม่ค้างจะแข่งขันกันเพื่อรับงบประมาณที่เหลือ เมื่อจำนวนขอบเขต
มากกว่าจำนวนเฟรม ระบบจะยังคงครอบคลุมไทม์ไลน์อย่างสม่ำเสมอ เพื่อไม่ให้การตัดฉากอย่างรวดเร็ว
ในช่วงต้นบดบังเซกเมนต์ยาวช่วงท้าย ขอบเขตฉากที่อยู่ภายในความละเอียดการวิเคราะห์ 1 วินาที
จากขอบเขตภาพค้างจะถูกรวมเข้าด้วยกัน

หากตัวกรองขาดหาย หลักฐานผิดรูปแบบ/ว่างเปล่า ตัวตรวจจับเกิดข้อผิดพลาด หรือการวิเคราะห์

งานส่วนนี้ยังไม่ได้เชื่อมต่อ producer ในระบบ production เข้ากับ route และยังไม่มีการเลือก variant แบบหลายความละเอียด ดังนั้นเส้นทางคำขอ Video Bridge แบบโปร่งใสจึงไม่มีภาระงานเพิ่ม ขณะที่การสร้าง principal ที่ผูกกับ tenant และวงจรการทำงานแบบหลายความละเอียดทั้งหมดของ FU-08 ยังคงเป็นงานติดตามผลที่ระบุไว้อย่างชัดเจน แทนที่จะบันทึกไว้ว่าเป็นพฤติกรรมที่เสร็จสมบูรณ์แล้ว

เฟรมจะได้รับคำบรรยายตามลำดับด้วยโมเดล Video ที่กำหนดค่าไว้ ค่า override ของ Video ที่ว่างเปล่าจะสืบทอดการตั้งค่า Vision หากทั้งสองค่าว่างเปล่า auto-router ของ Vision จะเลือกโมเดลที่รองรับการมองเห็นซึ่งมีผลใช้งาน คำบรรยายที่สำเร็จจะแทนที่ส่วนเดิมด้วยคำนำหน้า `[Video description:` ที่คงที่ ซึ่งยังทำเครื่องหมายข้อความว่าเป็นข้อสังเกตจากสื่อที่ไม่น่าเชื่อถือ และแจ้งโมเดลปลายทางไม่ให้ทำตามคำสั่งที่พบในสื่อ คีย์แคชคำบรรยายเฟรมประกอบด้วยไบต์ JPEG พรอมต์ timestamp และโมเดลที่มีผลใช้งาน โดยจะเก็บเฉพาะคำบรรยายที่สำเร็จลงในแคช รายการแคชจะเก็บโมเดล producer ที่ดำเนินการสำเร็จจริง รวมถึงโมเดล fallback ส่วน bridge จะรายงาน `mixed` เมื่อเฟรมต่าง ๆ ถูกสร้างโดยโมเดลคนละตัว เมื่อพบข้อมูลในแคช ระบบจะนำอัตลักษณ์ของ producer นั้นกลับมาใช้ แทนที่จะเปลี่ยนป้ายกำกับให้เป็นแผนการกำหนดเส้นทางที่ร้องขอ แคชผลลัพธ์ของวิดีโอทั้งรายการจะใช้ทุกอินพุตที่เปลี่ยนแปลงเอาต์พุตเป็นคีย์ ได้แก่ พรอมต์ โมเดลที่มีผลใช้งาน นโยบายการสุ่มตัวอย่าง จำนวนเฟรม โหมดการวิเคราะห์เชิงความหมาย fingerprint แบบ SHA-256 ของ focus hint ที่ผ่านการปรับรูปแบบแล้ว ช่วงโฟกัส `transcript` `audioTranscript` และแฟล็ก contact-sheet ดังนั้นการเปลี่ยนแปลงมิติใด ๆ เหล่านี้จะทำให้ไม่พบข้อมูลในแคช และจะไม่มีการนำผลลัพธ์เก่ากลับมาใช้โดยเด็ดขาด เวอร์ชันนโยบายการขจัดภาพซ้ำ เกณฑ์ และจำนวนเฟรมตัวเลือกที่มีขอบเขต ยังถูกระบุอย่างชัดเจนในคีย์และ metadata ของแคชผลลัพธ์ ดังนั้นการเปลี่ยนนโยบายจึงไม่สามารถนำคำอธิบายวิดีโอทั้งรายการที่ล้าสมัยกลับมาใช้ได้ metadata ของแคชผลลัพธ์ v4 จะเก็บโหมดและ fingerprint แต่จะไม่เก็บงานดิบของผู้ใช้ metadata ของ guardrail จะรายงานทั้งโหมดการวิเคราะห์ที่ร้องขอและโหมดที่มีผลใช้งาน หากมีการร้องขอโหมด `focused` โดยไม่มีข้อความผู้ใช้ที่ใช้งานได้ ระบบจะรายงานว่าโหมดที่มีผลใช้งานคือ `full`

guardrail จะดึงทุกส่วนของวิดีโอที่รองรับออกมา แต่จะอธิบายไม่เกิน `modalityBridgeVideoMaxVideos` สำหรับเป้าหมายที่พิสูจน์แล้วว่ามี `supportsVideo === false` วิดีโอที่ล้มเหลวและเกินขีดจำกัดจะถูกแปลงเป็นเครื่องหมายข้อความที่ปลอดภัยอย่างชัดเจน เพื่อไม่ให้มีวิดีโอดิบหลงเหลืออยู่ เมื่อไม่ทราบความสามารถ ส่วนเหล่านั้นจะยังคงตัวนำส่งวิดีโอไว้ ส่วน transcript สำรองใด ๆ จะเป็นไปตามการแปลงข้อความแบบมีขอบเขตข้างต้น เป้าหมายที่มี `supportsVideo === true` จะข้าม bridge สัญญาณยกเลิกคำขอของไคลเอนต์จะถูกส่งต่อผ่านการดาวน์โหลด คิว broker subprocess และการเรียกสร้างคำบรรยาย การยกเลิกจะหยุดการทำงานระหว่างวิดีโอแต่ละรายการ และจะไม่ปล่อยผ่านไปยังสื่อดิบเมื่อเกิดความล้มเหลว

การตั้งค่าขณะรันได้รับการสนับสนุนโดย DB และตรวจสอบความถูกต้องด้วย Zod:

| คีย์                                | ค่าเริ่มต้น | ช่วง / ลักษณะการทำงาน                                                                                       |
| ----------------------------------- | ----------- | ----------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | รันไทม์เสริม ต้องเลือกเปิดใช้งาน                                                                            |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` คงคำบรรยายทั่วไปไว้ ส่วน `focused` ใช้บริบทล่าสุดของผู้ใช้ที่มีขอบเขตจำกัดและไม่น่าเชื่อถือ          |
| `modalityBridgeVideoModel`          | `""`        | สืบทอดโมเดล Vision Bridge                                                                                   |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                        |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware` หรือ `segment_aware` แบบเป็นสัดส่วน; หากตัวตรวจจับล้มเหลวจะย้อนกลับไปใช้ `uniform` |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                         |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                                              |

ค่าการหมดเวลาของวิดีโอแบบเดิมที่บันทึกคงอยู่และเกิน 120 วินาทีจะถูกจำกัดให้เท่ากับ
กำหนดเวลาสิ้นสุดของโบรกเกอร์ ส่วนการเขียนการตั้งค่าใหม่ที่เกินขีดจำกัดดังกล่าวจะถูกปฏิเสธ
`GET /api/modality-bridge/video/runtime` ต้องมีตำแหน่งที่ตั้งแบบลูปแบ็กซึ่งประทับตราว่าเชื่อถือได้
ก่อนดำเนินการตรวจสอบสิทธิ์หรือตรวจสอบรันไทม์ จากนั้นจึงต้องมีการตรวจสอบสิทธิ์ระดับการจัดการ
โดยจะส่งคืนเฉพาะ `available`, เวอร์ชัน FFmpeg/ffprobe ที่ผ่านการทำให้ปลอดภัยแล้ว และเหตุผลแบบคงที่
เมื่อรันไทม์ไม่พร้อมใช้งาน เอนด์พอยต์ภายในสำหรับการแยกข้อมูลไม่ใช่
API อัปโหลดสาธารณะ: เมื่อคิวเต็มจะส่งคืน `503` พร้อม `Retry-After`, เมื่อผู้เรียก
ตัดการเชื่อมต่อจะส่งคืน `499` และเมื่อถึงกำหนดเวลาสิ้นสุดแบบคงที่ของโบรกเกอร์จะส่งคืน `504` การตอบกลับที่แปลงแล้วจะเพิ่ม
`video->text;model=<visionModel>;parts=<videos>` ลงในส่วนหัวส่วนกลาง
`x-omniroute-modality-bridge` โดยไม่ลบส่วนของ Vision หรือ Audio

### ตัวปกปิด PII (`piiMasker.ts`)

ทำงานใน **ทั้งสอง** ขั้นตอน

- **`preCall`** โคลนเพย์โหลด สำรวจ `system`, `messages`, `input` และ
  `prompt` (รวมถึงรายการที่เป็นสตริงล้วน) และใช้ `processPII()` (จาก
  `@/shared/utils/inputSanitizer`) กับฟิลด์ `content`/`text` ที่เป็นสตริง เมื่อ
  `PII_REDACTION_ENABLED=true` ข้อมูล PII ที่ตรวจพบจะถูกปกปิดในเพย์โหลด
  ขาออก การทำงานนี้เป็นอิสระจาก `INPUT_SANITIZER_MODE` (ซึ่งควบคุมเฉพาะ
  นโยบายป้องกันการแทรกพรอมต์) เมื่อปิดการปกปิด การเรียกจะบันทึกจำนวน
  การตรวจพบโดยไม่เขียนเนื้อหาใหม่
- **`postCall`** ทำดีปโคลนการตอบกลับ เรียกใช้ `sanitizePIIResponse()` ร่วมกับ
  ตัวปกปิดสำหรับโครงสร้าง Responses API (`maskResponsesOutput` — ครอบคลุม
  `output_text` และ `output[].content[].text`) หากมีการปกปิดใดๆ เกิดขึ้น
  การตอบกลับที่แก้ไขแล้วจะแทนที่การตอบกลับเดิม

กลไกป้องกันจะไม่บล็อก แต่จะเพิ่มคำอธิบายกำกับ (`meta.detections`,
`meta.redacted`) หรือเขียนข้อมูลใหม่เท่านั้น

#### การเลือกตามประเภท รูปแบบกำหนดเอง และตัวนับการตรวจพบ

**แดชบอร์ด → การตั้งค่า → ความปลอดภัย → การปกปิด PII** ใช้เลือกว่าจะปกปิด _อะไร_
ไม่ได้ใช้เปิดการปกปิด โดยการเปิดใช้งานยังคงควบคุมด้วย `PII_REDACTION_ENABLED` (คำขอ) และ
`PII_RESPONSE_SANITIZATION` (การตอบกลับ + SSE) ซึ่งทั้งคู่ปิดอยู่ตามค่าเริ่มต้น

- **การเลือกตามประเภท** — id ในตัวแสดงอยู่ใน
  `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`) หากไม่ได้กำหนด หมายถึงทุก
  ประเภท (ลักษณะการทำงานก่อนที่จะมีการตั้งค่านี้) รูปแบบ `ssn_us` ของเอนจินคำขอ
  จะแมปไปยัง `ssn` เทมเพลต (Minimal, Standard, Financial,
  Brazilian, USA, Full) มีไว้เพียงเพื่อกรอกช่องทำเครื่องหมายใน UI
- **รูปแบบกำหนดเอง** — รองรับรูปแบบ regex หรือ wildcard สูงสุด 20 รูปแบบ (`*` = อักขระ
  ที่ไม่ใช่ช่องว่างสูงสุด 64 ตัว, `?` = หนึ่งตัว) ข้อมูลที่ตรงกันจะกลายเป็น `[CUSTOM_REDACTED]`
  ทุกรูปแบบจะผ่าน `compilePiiCustomPattern()`
  (`src/shared/utils/piiCustomPatterns.ts`): มีความยาวไม่เกิน 500 อักขระ, แฟล็กจำกัด
  เฉพาะ `g i m s u`, ต้องคอมไพล์ได้, ต้องผ่าน `safe-regex` (การย้อนรอย
  อย่างรุนแรง) และต้องไม่ตรงกับสตริงว่างหรือตัวยึดตำแหน่งสำหรับการปกปิด
  รูปแบบที่ไม่ผ่านจะถูกปฏิเสธทั้งเมื่อบันทึกและเมื่อทดสอบ และแถวที่บันทึกไว้
  ซึ่งไม่ผ่านจะถูกข้ามขณะรันไทม์แทนที่จะนำไปคอมไพล์ รูปแบบกำหนดเองจะทำงาน
  เฉพาะเมื่อเปิดการปกปิดอยู่
- **ตัวนับการตรวจพบ** — จำนวนแยกตามประเภท (ไม่เก็บค่าที่ตรงกัน) ซึ่งเก็บไว้ใน
  หน่วยความจำและรีเซ็ตเมื่อเริ่มระบบใหม่ (`src/lib/pii/piiDetectionStats.ts`) จำนวนดังกล่าว
  จะเพิ่มขึ้นเฉพาะเมื่อเปิดการปกปิดอยู่

การตั้งค่าถูกเก็บไว้ในตาราง `key_value` (เนมสเปซ `pii_settings`,
`src/lib/db/piiSettings.ts`) และอ่านผ่านแคชอายุ 1 วินาที API:

| เมธอด  | พาธ                      | วัตถุประสงค์                                                                 |
| ------ | ------------------------ | ---------------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | สถานะแฟล็ก, `enabledTypes`, `customPatterns`, ตัวนับการตรวจพบ                |
| `PUT`  | `/api/settings/pii`      | แทนที่ `enabledTypes` (`null` = ทั้งหมด) และ/หรือ `customPatterns`           |
| `POST` | `/api/settings/pii/test` | ทดลองเรียกใช้หนึ่งรูปแบบกับตัวอย่างขนาดไม่เกิน 8 KB โดยไม่มีการจัดเก็บข้อมูล |

ทั้งสามรายการต้องมีการตรวจสอบสิทธิ์ระดับการจัดการ และตรวจสอบความถูกต้องของเนื้อหาคำขอด้วย Zod
(`src/shared/validation/schemas/piiSettings.ts`)

### การแทรกพรอมต์ (`promptInjection.ts`)

ตรวจจับโครงสร้างที่มุ่งโจมตีในเนื้อหาที่ผู้ใช้ส่งมา และบังคับใช้
นโยบายที่กำหนดค่าไว้ ลักษณะการทำงานควบคุมด้วยตัวแปรสภาพแวดล้อมและตัวเลือก
ของคอนสตรักเตอร์:

| การตั้งค่า    | ตัวแปรสภาพแวดล้อม                                                                                        | ค่าเริ่มต้น | ผล                                                                                                                                                                                                     |
| ------------- | -------------------------------------------------------------------------------------------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| เปิดใช้งาน    | `INPUT_SANITIZER_ENABLED`                                                                                | `true`      | เมื่อเป็น `false` กลไกป้องกันจะลัดวงจรและหยุดทำงานทันที                                                                                                                                                |
| โหมด          | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                          | `warn`      | นโยบายการป้องกันการแทรกคำสั่ง: `block`, `warn` หรือ `log` (`redact` ยังคงรองรับเพื่อความเข้ากันได้ย้อนหลัง แต่จะ **ไม่** ลบข้อความแทรกคำสั่ง การเขียน PII ในคำขอใหม่ควบคุมโดย `PII_REDACTION_ENABLED`) |
| เกณฑ์การบล็อก | ตัวเลือก `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (นามแฝง `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`      | ระดับความรุนแรงขั้นต่ำที่ต้องมีเพื่อบล็อก โดยค่าเริ่มต้น ระดับปานกลางจะใช้เพื่อสังเกตการณ์เท่านั้น                                                                                                     |

**ลำดับความสำคัญของโหมด** (`getMode`): `options.mode` ของผู้เรียก →
การแทนที่ด้วย **แฟล็กฟีเจอร์ในฐานข้อมูล** ของ `INJECTION_GUARD_MODE` (แดชบอร์ด → การตั้งค่า →
แฟล็กฟีเจอร์) → ตัวแปรสภาพแวดล้อม `INJECTION_GUARD_MODE` → ตัวแปรสภาพแวดล้อม `INPUT_SANITIZER_MODE` →
`warn` ดังนั้น การแทนค่าจากแดชบอร์ดจึงมีลำดับความสำคัญเหนือตัวแปรสภาพแวดล้อม ทำให้ UI ของแฟล็ก
ฟีเจอร์ควบคุมกลไกป้องกันที่กำลังทำงานได้แบบสด ๆ (ไม่ต้องรีสตาร์ต) การอ่านฐานข้อมูลเป็นแบบปลอดภัยเมื่อเกิดข้อผิดพลาด:
หากเกิดข้อผิดพลาด กลไกป้องกันจะย้อนกลับไปใช้พฤติกรรมตามตัวแปรสภาพแวดล้อม และเมื่อไม่ได้ตั้งค่า
การแทนที่ พฤติกรรมจะเหมือนกับการประมวลผลจากตัวแปรสภาพแวดล้อมเพียงอย่างเดียว

1. `sanitizeRequest()` จาก `@/shared/utils/inputSanitizer` (ชุดตัวตรวจจับที่ใช้ร่วมกัน
   ในส่วนอื่นของไปป์ไลน์)
2. `DEFAULT_GUARD_PATTERNS` ที่มีมาให้ในตัว (ปัจจุบันคือ `system_override_inline` และ
   `markdown_system_block` ซึ่งทั้งคู่มีระดับความรุนแรง `high`)
3. `customPatterns` แบบไม่บังคับที่ส่งผ่านตัวเลือกของคอนสตรักเตอร์ (สตริง, regex
   หรือเรคคอร์ด `{ name, pattern, severity }`)

เมื่อ `mode === "block"` **และ** มีการตรวจจับอย่างน้อยหนึ่งรายการที่ถึงเกณฑ์ความรุนแรง
`preCall` จะคืนค่า `{ block: true, message: "Request rejected:
suspicious content detected" }` ในโหมด `warn`/`log` กลไกป้องกันจะบันทึกล็อก แต่
อนุญาตให้เรียกต่อไปได้ นอกจากนี้ยังส่งออกตัวช่วยที่ใช้ร่วมกัน `evaluatePromptInjection()`
สำหรับผู้เรียกที่ต้องการประเมินพรอมต์โดยไม่ผ่านรีจิสทรี

**ขอบเขตการสแกน (v3.8.20):** ตัวตรวจจับจะตรวจสอบเฉพาะ **16 KB แรก** ของ
ข้อความพรอมต์ที่นำมาต่อกัน — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ไบต์) ใน
`src/shared/utils/inputSanitizer.ts` ทั้ง `detectInjection()` และ
`evaluatePromptInjection()` จะเรียก `slice(0, MAX_INJECTION_SCAN_BYTES)` ก่อนดำเนินการ
วนลูปแพตเทิร์น คำสั่งแทรกมักอยู่ใกล้ส่วนต้นของอินพุต ดังนั้นวิธีนี้จึงจำกัดการใช้ CPU/GC ของ regex
สำหรับเพย์โหลดขนาดหลายร้อย KB โดยไม่ลดทอนประสิทธิภาพการตรวจจับ (ดู
#3932, #4041)

### ตัวปกปิดข้อมูลรับรอง (`credentialMasker.ts`)

ทำงานใน **ทั้งสอง** ขั้นตอน และอยู่ลำดับสุดท้ายในเชนเริ่มต้น (ลำดับความสำคัญ `95`) ปกปิด
แพตเทิร์น API key / โทเค็นลับที่เป็นที่รู้จักจากเพย์โหลดขาออก (เนื้อหาข้อความ,
อาร์กิวเมนต์การเรียกเครื่องมือ, ผลลัพธ์จากเครื่องมือ) **และ** การตอบกลับของผู้ให้บริการ เพื่อไม่ให้
ข้อมูลรับรองที่วางลงในพรอมต์ (หรือถูกส่งกลับซ้ำโดยผลลัพธ์จากเครื่องมือ) รั่วไหล
ไปยังผู้ให้บริการต้นทางหรือกลับไปยังไคลเอนต์

- **ต้องเลือกเปิดใช้งานเท่านั้น** โดยใช้แนวทางเดียวกับการปกปิด PII (ใกล้เคียงกับกฎตายตัว #20):
  ปิดใช้งาน เว้นแต่ `settings.credentialRedactionEnabled === true` **หรือ**
  `CREDENTIAL_REDACTION_ENABLED=true` เมื่อปิดอยู่ กลไกป้องกันนี้จะไม่ดำเนินการใด ๆ —
  จะไม่บล็อกและไม่เขียนข้อมูลใหม่
- `redactCredentials()` จะไล่ตรวจสอบทรีทั้งหมดของเพย์โหลด/การตอบกลับ (`walkValue()`,
  ปลอดภัยจาก prototype pollution และปลอดภัยจากวงจรด้วย `WeakSet`) และแทนที่รายการที่ตรงกันด้วย
  ตัวยึดตำแหน่ง `[REDACTED:<type>]` โดยโคลนเฉพาะกิ่งที่มีการเปลี่ยนแปลงจริง
- `CREDENTIAL_PATTERNS` ครอบคลุมคีย์ของผู้ให้บริการ LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), โทเค็น VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), คีย์การชำระเงิน (Stripe, Square), คีย์
  คลาวด์ (คีย์การเข้าถึง AWS, Twilio, SendGrid, Mailgun), คีย์ส่วนตัว / JWT,
  สตริงการเชื่อมต่อที่มีข้อมูลรับรอง (`mongodb://user:pass@...` เป็นต้น) และ
  แพตเทิร์นค่าของเฮดเดอร์ทั่วไป `Authorization`/`x-api-key`/`api-key`/`apikey`
  คีย์ที่มีรูปแบบเป็นเฮดเดอร์ (`authorization`, `x-api-key`, `api-key`,
  `apikey`) จะถูกปกปิดตามโครงสร้าง (เฉพาะค่า โดยคงคำนำหน้าสคีม เช่น
  `Bearer `/`Basic ` ไว้) แทนการใช้ regex ข้อความทั่วไป
- กลไกป้องกันจะไม่บล็อก โดยจะเขียนใหม่เท่านั้น (`modifiedPayload` /
  `modifiedResponse`) และเพิ่มคำอธิบายประกอบ (`meta.credentialsRedacted`, `meta.count`)

ตัวป้องกันการถดถอย: `tests/unit/credential-masker-guardrail.test.ts`

## สัญญาพื้นฐาน (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // ค่า true จะลัดวงจรของเชน
  message?: string; // แสดงเมื่อมีการบล็อก
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // ส่งคืนโดย preCall เพื่อเขียนคำขอใหม่
  modifiedResponse?: TValue; // ส่งคืนโดย postCall เพื่อเขียนการตอบกลับใหม่
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

การ์ดเรลระบุว่า "ไม่มีการเปลี่ยนแปลง" ด้วยการส่งคืน `void`, `{}` หรือ
`{ block: false }` อย่างใดอย่างหนึ่ง การส่งคืน `modifiedPayload`/`modifiedResponse`
จะแทนที่ค่าที่ไหลผ่านเชนสำหรับการ์ดเรลลำดับถัดไป
`signal?: AbortSignal` ส่งต่อวงจรชีวิตของผู้เรียกไปยังการ์ดเรล การยกเลิกคำขอเป็นข้อยกเว้นแบบยอมให้ทำงานต่อโดยเจตนา: บริดจ์สื่อจะหยุดการทำงานและล้างทรัพยากร โดยไม่กู้คืนสื่อดิบไปยังปลายทางที่ทราบว่าไม่รองรับสื่อนั้น

## รีจิสทรี (`registry.ts`)

ซิงเกิลตัน `guardrailRegistry` เปิดเผยเมธอดต่อไปนี้:

- `register(guardrail)` — เพิ่มการ์ดเรล (หรือแทนที่ตามชื่อที่ผ่านการทำให้เป็นมาตรฐาน)
  และเรียงลำดับใหม่ตาม `priority` จากน้อยไปมาก
- `clear()` / `list()` — ตัวช่วยสำหรับการดูแลระบบ
- `runPreCallHooks(payload, context)` — วนซ้ำการ์ดเรลที่ทำงานอยู่ ส่งต่อ
  เพย์โหลดผ่าน `modifiedPayload` และหยุดเมื่อพบ `block: true` ครั้งแรก
- `runPostCallHooks(response, context)` — ใช้โฟลว์เดียวกันกับฝั่งการตอบกลับ
- `resetGuardrailsForTests({ registerDefaults })` — ล้างสถานะและเลือก
  ลงทะเบียนค่าเริ่มต้นใหม่เพื่อแยกการทดสอบอย่างสะอาด

รันเนอร์ทั้งสองส่งคืน `{ blocked, payload|response, results, guardrail?, message? }`
โดย `results` เป็นอาร์เรย์ของเรคคอร์ด `GuardrailExecutionResult` ซึ่งประกอบด้วย
ฟิลด์ `blocked`, `skipped`, `modified`, `error` และ `meta` ของแต่ละการ์ดเรล
ซึ่งมีประโยชน์สำหรับการติดตาม

### การปิดใช้งานการ์ดเรลสำหรับแต่ละคำขอ

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` รวบรวมรายการ
ชื่อการ์ดเรลที่ตัดรายการซ้ำแล้ว ซึ่งควรข้ามสำหรับคำขอปัจจุบัน
แหล่งที่มา (ทั้งหมดเป็นตัวเลือกและนำมารวมกันทั้งหมด):

- `apiKeyInfo.disabledGuardrails`
- `disabledGuardrails` ในเนื้อหาคำขอ (ระดับบนสุด)
- `metadata.disabledGuardrails` ในเนื้อหาคำขอ
- เฮดเดอร์ `x-omniroute-disabled-guardrails` (หรือชื่อเดิม
  `x-disabled-guardrails`)

ค่าอาจเป็นอาร์เรย์ของสตริงหรือสตริงที่คั่นด้วยจุลภาค ชื่อจะถูก
ทำให้เป็นอักษรพิมพ์เล็กในรูปแบบ kebab-case (`pii_masker` → `pii-masker`) ผลลัพธ์
จะถูกส่งผ่าน `context.disabledGuardrails` ไปยังรีจิสทรี ซึ่งจะข้าม
การ์ดเรลที่ตรงกัน (`skipped: true` ใน `results`)

## ลำดับการดำเนินการ

สำหรับแต่ละคำขอที่ไหลผ่าน `src/sse/handlers/chat.ts` และ
`open-sse/handlers/chatCore.ts`:

1. `resolveDisabledGuardrails(...)` สร้างรายการที่ต้องข้ามจาก API key, body
   และ headers
2. `guardrailRegistry.runPreCallHooks(body, ctx)` เรียกใช้ guardrails ตามลำดับ
   priority จากน้อยไปมาก:
   - Guardrails ที่ปิดใช้งานจะถูกบันทึกเป็น `skipped`
   - `preCall` ของแต่ละ guardrail อาจเขียน payload ใหม่ผ่าน `modifiedPayload`
   - รายการแรกที่มี `block: true` จะยุติลำดับการทำงานทันที และ handler จะส่งคืน
     การตอบกลับที่ระบุว่า guardrail ปฏิเสธคำขอ
3. Payload ที่อาจถูกเขียนใหม่จะถูกส่งต่อไปยัง combo routing และการส่งคำขอ
   ไปยัง upstream
4. หลังจากประกอบการตอบกลับแล้ว `guardrailRegistry.runPostCallHooks(...)`
   จะเรียกใช้ลำดับเดิมกับการตอบกลับ หากพบ `block: true` ในขั้นตอนนี้ การตอบกลับ
   จาก upstream จะถูกละทิ้ง

Guardrails ที่ throw ข้อผิดพลาดจะถูกบันทึกด้วย `error: <message>` และเขียน log ผ่าน
`logger.warn` แต่ลำดับการทำงานจะดำเนินต่อไป ซึ่งเป็นการออกแบบแบบ fail-open

## การกำหนดค่า

ตัวแปรสภาพแวดล้อมที่ guardrails ในตัวอ่าน:

| ตัวแปร                                | ใช้โดย                    | ผลกระทบ                                                                                                  |
| ------------------------------------- | ------------------------- | -------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`        | ตั้งค่าเป็น `false` เพื่อปิดใช้งานการตรวจจับทั้งหมด                                                      |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`        | นโยบายการตรวจจับ injection: `warn`, `block` หรือ `log` ค่าเดิม `redact` จะไม่เขียนข้อความ injection ใหม่ |
| `INJECTION_GUARD_MODE`                | `prompt-injection`        | โหมดสำหรับ injection guard และยังเป็น DB feature flag ที่ **มีผลเหนือกว่า** env vars (DB > ENV)          |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`        | ระดับความรุนแรงขั้นต่ำที่ `MODE=block` จะปฏิเสธ: `high` (ค่าเริ่มต้น), `medium` หรือ `low`               |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`        | Alias แบบเดิมสำหรับ `INPUT_SANITIZER_BLOCK_THRESHOLD`                                                    |
| `PII_REDACTION_ENABLED`               | `pii-masker`              | เมื่อเป็น `true` ข้อมูล PII ในคำขอจะถูกปกปิด (ไม่ขึ้นกับโหมด injection)                                  |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (downstream) | ควบคุมลักษณะการทำงานของ masker ฝั่งการตอบกลับ                                                            |

Guardrails ของ Modality Bridge อ่านการกำหนดค่าขณะรันไทม์จาก settings
store ที่มี DB รองรับ (`getSettings()`) ไม่ใช่จาก env vars โดย primary keys ของ Vision คือ
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` และ
`modalityBridgeCacheMaxEntries` ส่วน keys แบบเดิม
`visionBridge*` จะได้รับการยอมรับเฉพาะในฐานะกลไกสำรองสำหรับการอ่านหนึ่งรอบตามที่ระบุไว้
ในเอกสารเท่านั้น การเขียนค่าจาก dashboard จะใช้ primary keys ค่าเริ่มต้นและตัวแก้ไข
fallback อยู่ใน `src/shared/constants/modalityBridgeDefaults.ts` ขณะที่ constants
แบบเดิมยังคงอยู่ใน `src/shared/constants/visionBridgeDefaults.ts`

Audio ใช้ `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` และ `modalityBridgeAudioMaxClips` ร่วมกับ settings
`modalityBridgeCache*` ที่ใช้ร่วมกัน Audio ไม่มีกลไก fallback ไปยัง keys แบบเดิม เนื่องจาก
keys เหล่านี้ถูกนำมาใช้พร้อมกับ schema ของ Modality Bridge

Video ใช้ `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` และ
`modalityBridgeVideoTimeout` ร่วมกับ settings `modalityBridgeCache*` ที่ใช้ร่วมกัน
โดยค่าเริ่มต้นจะปิดใช้งาน เนื่องจาก FFmpeg/ffprobe เป็น operational dependencies
ที่ไม่บังคับ และการสร้างคำบรรยายให้แต่ละ frame จะเพิ่มเวลาแฝงและต้นทุนของโมเดล

## การ์ดเรลแบบกำหนดเอง

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ขั้นตอน:

1. สร้าง `src/lib/guardrails/myGuardrail.ts` โดยสืบทอดจาก `BaseGuardrail`
2. อิมพลีเมนต์ `preCall` และ/หรือ `postCall`
3. ลงทะเบียนขณะนำเข้า (เพิ่มจาก `registerDefaultGuardrails`) หรือ
   เรียก `guardrailRegistry.register(...)` ขณะรันไทม์ — รีจิสทรีจะแทนที่
   การ์ดเรลก่อนหน้าที่มีชื่อหลังการปรับรูปแบบเหมือนกัน
4. เพิ่มการทดสอบภายใต้ `tests/unit/` (ตัวอย่างที่มีอยู่:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`)

## การทดสอบ

ใช้ `resetGuardrailsForTests()` ระหว่างการทดสอบแต่ละรายการเพื่อเริ่มต้นจากสถานะที่ทราบแน่ชัด
ส่ง `{ registerDefaults: false }` เพื่อเริ่มต้นด้วยรีจิสทรีว่างและ
ลงทะเบียนเฉพาะการ์ดเรลที่กำลังทดสอบ Vision Bridge รองรับการฉีดการพึ่งพา
(`deps.getSettings`, `deps.callVisionModel`); Audio Bridge มีจุดเชื่อมต่อ
ที่เทียบเท่ากันสำหรับการตั้งค่า ความสามารถ การเลือกโมเดล STT การตรวจสอบข้อมูลรับรอง
และการถอดเสียง ดังนั้นการทดสอบจึงสามารถตรวจสอบโฟลว์ทั้งสองได้โดยไม่ต้องเข้าถึง DB
หรือเครือข่าย

## ความครอบคลุมของเส้นทางและการทดสอบแบบเรดทีมสำหรับการป้องกันการแทรกคำสั่ง (Phase 8 · Block D)

การป้องกันการแทรกคำสั่ง (`createInjectionGuard` / `withInjectionGuard`) ครอบคลุมทุกเส้นทาง
ที่รับพรอมต์จากผู้ใช้ โดยจะเคารพ `INJECTION_GUARD_MODE` (ค่าเริ่มต้น `warn` = บันทึกล็อกเท่านั้น;
`block` = ส่งคืน HTTP 400 `SECURITY_001`)

| ประเภท         | เส้นทาง                                                                                                                                              | โหมดเริ่มต้น |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| ข้อความ (เดิม) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn         |
| เชิงสร้างสรรค์ | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn         |
| ข้อมูล         | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn         |

การแยกข้อความ (`extractMessageContents`) ครอบคลุม `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`

**เรดทีม (ทุกคืน, `nightly-llm-security.yml`):** promptfoo ตรวจสอบว่าแต่ละเส้นทางบล็อก
คลัง OWASP-LLM ใน `INJECTION_GUARD_MODE=block`; garak เรียกใช้โพรบ (ข้ามหากไม่มีข้อมูลลับ)
`moderations` ถูกรวมไว้เพื่อความสอดคล้อง — ผู้ดูแลระบบที่ใช้โหมดบล็อกสามารถยกเว้นเส้นทางนี้ผ่าน
`resolveDisabledGuardrails`

เวิร์กโฟลว์รายคืน (`.github/workflows/nightly-llm-security.yml`, cron + การสั่งงาน
ด้วยตนเอง) มีสองงาน:

- **`promptfoo-guard` (บล็อกเมื่อไม่ผ่าน)** — เรียกใช้ `promptfoo eval -c promptfooconfig.yaml`
  โดยใช้ `INJECTION_GUARD_MODE=block` กรณีโจมตีแต่ละกรณี (เช่น "เพิกเฉยต่อ
  คำสั่งก่อนหน้าทั้งหมด…", การเจลเบรกแบบ DAN) จะยืนยันว่าการตอบกลับมี
  `error.code === "SECURITY_001"` กล่าวคือ การ์ดได้ปฏิเสธคำขอจริง
- **`garak` (ให้คำแนะนำ)** — เรียกใช้ garak `--probes promptinject,dan,leakreplay`
  กับอินสแตนซ์ OmniRoute ภายในเครื่อง (`http://localhost:20128/v1`) โดยขึ้นอยู่กับ
  ข้อมูลลับของผู้ให้บริการ (`PROMPTFOO_PROVIDER_KEY`); จะข้ามอย่างราบรื่นหากไม่มีข้อมูลดังกล่าว และต่อท้ายด้วย
  `|| true` จึงรายงานผลโดยไม่ทำให้ CI ล้มเหลว

ความครอบคลุมของตัวช่วยการ์ด (`createInjectionGuard` / `withInjectionGuard`)
ครอบคลุมทุกเส้นทาง `/v1` ที่มีพรอมต์; ข้อความพรอมต์จะถูกดึงจาก
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` โดย
`extractMessageContents()` ใน `src/shared/utils/inputSanitizer.ts`
