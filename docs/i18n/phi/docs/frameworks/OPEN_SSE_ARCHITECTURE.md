> **TL;DR**: Ang `open-sse/` ang pangunahing streaming engine na nagpapatakbo sa bawat kahilingan sa LLM sa OmniRoute. Naglalaman ito ng ~1,400 file na nagpapatupad sa pipeline ng kahilingan, mga executor, serbisyo, MCP server, at translation layer. Ipinapaliwanag ng gabay na ito kung paano nagtutugma ang mga bahagi.

**Pinagmulan:** `open-sse/` (workspace package, ~1,440 non-test na `.ts` file)

---

## Bakit Hiwalay na Workspace Package?

Ang `open-sse/` ay isang **standalone workspace** sa OmniRoute monorepo dahil sa ilang kadahilanan:

1. **Muling paggamit** — inilalathala ang `open-sse` bilang `@omniroute/open-sse` sa npm, kaya maaari itong gamitin nang hiwalay ng ibang mga proyekto
2. **Malinaw na mga hangganan** — nakahiwalay ang streaming engine mula sa UI/DB layer na partikular sa OmniRoute
3. **Pagganap** — walang dependency sa Next.js ang engine, kaya mas mabilis ang mga cold start sa mga kontekstong CLI/serverless
4. **Pagbe-version** — maaaring maglabas ng release ang `open-sse` ayon sa sarili nitong iskedyul

```json
// package.json
"workspaces": ["open-sse"]
```

## Ang Pipeline ng Kahilingan

Dumadaan ang bawat kahilingan sa LLM sa isang **5-yugtong pipeline**:

```
                              ┌──────────────┐
   Kahilingang HTTP            │  1. ROUTE    │   paglutas ng combo, pagpili ng model
   (Next.js route)             └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. TRANSLATE│   pag-convert ng format (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. EXECUTE  │   executor ng provider, HTTP, retry, breaker
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. STREAM   │   SSE transformation, backpressure
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. RECORD   │   pagsubaybay sa paggamit, call log, pag-uuri ng error
                              └──────┬───────┘
                                     │
                                     ▼
                              Tugon na HTTP (SSE o JSON)
```

### Yugto 1: Route (services/combo.ts)

**Entry point**: `handleComboChat()` sa `services/combo.ts`

Nireresolba ang kahilingan tungo sa isang kongkretong `(provider, model, account, credentials)` tuple:

- Hanapin ang combo gamit ang ID (o bumuo ng virtual combo para sa mga `auto/*` model)
- Ilapat ang routing strategy (priority, weighted, round-robin, atbp.)
- Salain at alisin ang mga hindi maayos na provider (circuit breaker)
- Piliin ang susunod na maaaring gamiting target

Para sa mga `auto/*` model, ginagawa rin ng yugtong ito ang sumusunod:

- Pinapatakbo ang **16-factor scoring** algorithm (`services/autoCombo/`)
- Pumipili ng pares na `provider+model` batay sa health, gastos, latency, atbp.

### Yugto 2: Translate (translator/)

Kung naiiba ang pinagmulang format (hal., OpenAI) sa target na format (hal., Claude), **isinasalin** ang kahilingan:

- System prompt → system message
- Mga depinisyon ng tool → format ng tool na partikular sa provider
- Mga parameter ng reasoning/thinking → mga katumbas na partikular sa provider
- Normalisasyon ng message role (`developer` → `system` para sa hindi OpenAI)

Inilalantad ng `translator/index.ts` ang:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### Yugto 3: Execute (executors/)

**Entry point**: `getExecutor(providerId).execute(request, options)`

Ginagamit ng lahat ng provider ang `DefaultExecutor` (`executors/default.ts`) sa pamamagitan ng fallback ng `getExecutor()` factory. Ginagawa ng executor ang sumusunod:

- Binubuo ang upstream URL (`buildUrl()`)
- Nagdaragdag ng mga header na partikular sa provider (`buildHeaders()`)
- Tina-transform ang body ng kahilingan (`transformRequest()`)
- Ipinapadala ang kahilingang HTTP na may retry + exponential backoff
- Pinangangasiwaan ang auth refresh kung kinakailangan (mga OAuth provider)

Lahat ng executor ay nag-e-extend sa `BaseExecutor` (`executors/base.ts`, 1170 LOC), na nagbibigay ng:

- Karaniwang retry logic
- Proxy integration
- Circuit breaker integration
- Mga hook sa pagtatala ng paggamit

### Yugto 4: Stream (utils/stream.ts)

Para sa mga streaming response, nagbabalik ang executor ng **ReadableStream**. Ginagawa ng handler ang sumusunod:

- Ipinapadaan sa isang SSE transform (`createSSETransformStreamWithLogger`)
- Naglalapat ng mga heartbeat ping upang matukoy ang mga naputol na koneksyon
- Maayos na pinangangasiwaan ang pag-disconnect ng client (`pipeWithDisconnect`)
- Tina-transform ang SSE → JSON para sa mga non-streaming client

Para sa mga non-streaming response, nagbabalik ang executor ng na-parse na JSON object na ipinapasa nang walang pagbabago.

### Yugto 5: Record (services/usage.ts)

Pagkatapos ng tugon (tagumpay man o kabiguan), itinatala ang paggamit:

- `prompt_tokens`, `completion_tokens`, `cached_tokens` mula sa tugon
- `cost_usd` na kinuwenta mula sa datos ng pagpepresyo
- `latency_ms`, `status`, `error_class` kung nabigo
- Iniimbak sa talahanayang `usage_history`

Ang mga artifact ng log ng tawag (kung naka-enable) ay isinusulat sa `${DATA_DIR}/call_logs/`.

## Masusing Pagsusuri sa Mahahalagang File

### chatCore.ts (5977 linya)

Ang **pangunahing tagapangasiwa ng request**. Sa kabila ng laki nito, mayroon itong malinaw na istruktura:

```ts
// Pseudo-istruktura ng chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Auth + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Pag-validate ng body
  const body = await parseRequestBody(request);

  // 3. Pagtukoy at pagsasalin ng format
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Pag-route ng combo
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Magpatuloy sa susunod na target
    }
  }

  // 5. Pang-emergency na fallback
  return await emergencyFallback(body);
}
```

Sa kabila ng pagiging isang napakalaking function, nakaayos ito sa **mga seksiyong may komento** na tumutugma sa 5-yugtong pipeline.

### combo.ts (4456 LOC)

Ang **routing engine** na nagre-resolve ng isang combo sa mga target na nakaayos ayon sa pagkakasunod-sunod.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("target failed, trying next", { target, err });
    }
  }
  throw new ComboExhaustedError("All targets failed");
}
```

Sinusuportahan ang **19 na routing strategy** (tingnan ang `src/shared/constants/routingStrategies.ts`):

| Strategy            | Gawi                                                                                                            |
| ------------------- | --------------------------------------------------------------------------------------------------------------- |
| `priority`          | Listahang nakaayos na inuuna ang unang target                                                                   |
| `weighted`          | Probabilistiko batay sa timbang ng bawat target                                                                 |
| `round-robin`       | Paikot na dumaan sa mga target ayon sa pagkakasunod-sunod                                                       |
| `context-relay`     | Ipasa ang konteksto sa iba't ibang target                                                                       |
| `fill-first`        | Punuin ang quota bago lumipat sa susunod                                                                        |
| `p2c`               | Kapangyarihan ng dalawang pagpipilian                                                                           |
| `random`            | Pare-parehong random                                                                                            |
| `least-used`        | Piliin ang may pinakakaunting kamakailang paggamit                                                              |
| `cost-optimized`    | Unahin ang pinakamurang maayos na target                                                                        |
| `reset-aware`       | Isinasaalang-alang ang mga reset window ng provider                                                             |
| `reset-window`      | Routing batay sa reset window                                                                                   |
| `headroom`          | Unahin ang may pinakamaraming natitirang puwang sa quota                                                        |
| `strict-random`     | Tunay na pare-pareho (walang quality weighting)                                                                 |
| `auto`              | Gumamit ng 16-factor scoring (`autoCombo/`)                                                                     |
| `lkgp`              | Unahin ang huling provider na napag-alamang maayos                                                              |
| `context-optimized` | Pinakamainam para sa mga request na may mahabang konteksto                                                      |
| `fusion`            | Ipadala nang sabay-sabay sa isang panel, pagkatapos ay i-synthesize sa pamamagitan ng isang judge (`fusion.ts`) |

### base.ts (1170 LOC)

Ang **abstract executor** na ine-extend ng bawat executor class (nang direkta o sa pamamagitan ng `DefaultExecutor` at iba pang subclass). Naglalaman ito ng:

- `buildUrl()` — default na pagbuo ng URL (ino-override ng mga subclass para sa custom na gawi)
- `buildHeaders()` — mga default na header (auth, content-type)
- `transformRequest()` — pass-through bilang default
- `execute()` — ang pangunahing HTTP loop na may retry/backoff/breaker

```ts
// open-sse/executors/default.ts
export class DefaultExecutor extends BaseExecutor {
  // Pinangangasiwaan ang lahat ng provider na compatible sa OpenAI/Anthropic
  // Nagrerehistro ang mga provider ng mga configuration (URL, auth, headers) ngunit iisa ang executor logic na ginagamit
}
```

Ang gawi na partikular sa provider (mga auth header, base URL, mga version header) ay kino-configure sa pamamagitan ng provider registry, hindi ng magkakahiwalay na executor class.

## Mga Executor (150 module)

Karamihan ay tig-isang file bawat provider. Ang lahat ng executor class ay nag-e-extend ng `BaseExecutor` at nag-o-override sa mga bahaging naiiba; ang ibang mga module ay mga helper para sa bawat provider (mga tool schema, fetch/TTS adapter, at quirk handler).

### Mga Karaniwang Pattern

Nire-resolve ang mga provider sa pamamagitan ng `getExecutor(providerId)`, na nagbabalik ng naka-configure na executor. Ginagamit ng mga provider na compatible sa OpenAI/Anthropic ang `DefaultExecutor` (`executors/default.ts`). Kino-configure sa `open-sse/config/providers/` ang gawi na partikular sa provider (base URL, mga auth header, API version), habang pinangangasiwaan sa `open-sse/translator/` ang mga transformation ng request body.

Itinatakda ang **Custom URL** sa pamamagitan ng configuration ng provider:

```ts
// Configuration ng provider sa open-sse/config/providers/
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

Pinangangasiwaan ang **custom auth** sa pamamagitan ng configuration ng authentication sa registry ng provider (API key, OAuth, mga header profile).

Ang mga transformation ng **custom request body** (hal., ang paghihiwalay ng Anthropic sa `system` mula sa `messages`) ay nirerehistro para sa bawat provider sa `open-sse/translator/`.

````

### Ang Executor Factory

Ini-export ng `executors/index.ts` ang `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

Dumadaan ang resolution sa `ExecutorRegistry` (`executors/registry.ts`): idinedeklara ang bawat specialized executor sa built-in na talahanayan ng `executors/index.ts` at nirerehistro sa pamamagitan ng `registerExecutor(alias, instance)` kapag naglo-load ang module; kumokonsulta ang `getExecutor()` sa registry at nagfa-fallback sa isang memoized na `DefaultExecutor` para sa anumang provider na walang specialized entry. Inilalarawan ang kumpletong mapping ng alias → executor ng golden test na `tests/unit/executor-map-golden.test.ts`.

## Mga Tagapagsalin

Magsalin sa pagitan ng **3 format**: OpenAI, Anthropic, Gemini, pati na rin ang bagong Responses API.

### Kailan Isinasagawa ang Pagsasalin

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Mga karaniwang pagsasalin:

- `OpenAI → Anthropic`: hiwalay na `system` field, `x-api-key` header
- `OpenAI → Gemini`: `contents` sa halip na `messages`, `systemInstruction`
- `OpenAI → Responses API`: `input` array, `previous_response_id` state

### Mga Edge Case na Sinusuportahan

- `developer` role → `system` para sa hindi OpenAI
- `system` role → isinasama sa unang mensahe ng user para sa GLM/ERNIE
- `json_schema` → `responseMimeType` + `responseSchema` ng Gemini
- `tools` → format ng tool na partikular sa provider
- Mga parameter ng pag-iisip (o1, Claude) → mga katumbas na partikular sa provider

## MCP Server

Ipinapatupad ng `open-sse/mcp-server/` ang server ng **Model Context Protocol**:

- **110 tool** (pamamahala ng provider, mga combo, memory, cache, compression, proxy, mga skill, gamification, mga plugin, Notion, Obsidian, lokal na corpus)
- **3 transport**: stdio, SSE, Streamable HTTP
- **33 scope** para sa detalyadong awtorisasyon

### Pagpaparehistro ng Tool

Inirerehistro ang mga tool bilang mga hiwalay na file sa `open-sse/mcp-server/tools/`, at bawat isa ay nag-e-export ng pangalan, schema, handler, at scope:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Mga Transport

```ts
// stdio (paggamit sa CLI)
startMcpStdio(server);

// SSE (streaming na nakabatay sa HTTP)
startMcpSse(server, port);

// Streamable HTTP (modernong MCP)
startMcpStreamable(server, port);
```

### Awtorisasyon

Dumaraan ang bawat pagtawag sa tool sa mga pagsusuri ng scope (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## Mga Transformer

Kino-convert ng `open-sse/transformer/` ang mga format sa pagitan ng **Chat Completions** at **Responses API**.

### Bakit May Hiwalay na Transformer?

Ang Responses API ang bagong format ng OpenAI na may **mga stateful na pag-uusap** (`previous_response_id`). Kapag nagpapadala ang isang client ng kahilingan sa Responses, ginagawa ng OmniRoute ang sumusunod:

1. Kino-convert ang Responses → Chat Completions sa loob ng system
2. Ipinapadala sa provider (anumang provider na sumusuporta sa Chat Completions)
3. Kino-convert pabalik sa format ng Responses ang tugon
4. Ini-stream ang na-convert na tugon sa client

Ibinibigay ng transformer (`transformer/responsesTransformer.ts`) ang:

```ts
createResponsesApiTransformStream(): TransformStream
```

Pinangangasiwaan nito ang:

- Mga event na `response.output_item.added`
- Mga event na `response.output_text.delta`
- Event na `response.completed`
- Pagmamapa ng pagtawag sa tool (`function_call` ↔ `tool_calls`)

## Konfigurasyon

Nasa `open-sse/config/` ang layer ng konfigurasyon:

| File                            | Layunin                                                    |
| ------------------------------- | ---------------------------------------------------------- |
| `providerRegistry.ts`           | Registry ng chat model para sa katalogo ng 374 na provider |
| `providerModels.ts`             | Mga alias ng model, pagmamapa ng format                    |
| `constants.ts`                  | Mga timeout, limitasyon, at status code                    |
| `defaultThinkingSignature.ts`   | Default na thinking signature ng Claude                    |
| `modelStrip.ts` (nasa services) | Pag-aalis ng mga field para sa bawat provider              |

### Schema ng Registry ng Provider

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

Tinitiyak ng validation ng Zod sa pag-load ng module na valid ang lahat ng configuration ng provider.

## Mga Limitasyon sa Performance

May mahihigpit na badyet sa performance ang routing engine:

| Operasyon                                   | Target | Pagsukat                               |
| ------------------------------------------- | ------ | -------------------------------------- |
| Pagresolba ng combo                         | <10ms  | Para sa 50 target                      |
| Pagsusuri ng rate limit                     | <1ms   | In-memory na token bucket              |
| Fallback ng model family                    | <5ms   | Mga naka-cache na depinisyon ng family |
| Pag-dispatch ng request routing             | <2ms   | Hot path                               |
| **Walang blocking I/O sa routing hot path** | —      | Lahat ay async                         |

## Mga Anti-Pattern

❌ **Mga synchronous na DB call sa `combo.ts`** — paunang kalkulahin at i-cache
❌ **Retry logic sa mga handler** — gamitin ang `retry()` mula sa resilience service
❌ **Direktang pag-access sa provider config** — gamitin ang mga getter ng `providerRegistry`
❌ **Mga hardcoded na fallback chain** — tukuyin sa `modelFamilyFallback.ts`
❌ **Mga pagbabago sa state sa magkakasabay na request** — gumamit lamang ng request-scoped na context

## Pagdaragdag ng Bagong Component

### Pagdaragdag ng Bagong Service

1. Gumawa ng `open-sse/services/[serviceName].ts` na may nakatuong responsibilidad
2. I-export ang pangunahing handler function at anumang constant
3. Magdagdag ng mga unit test sa `tests/unit/services/[serviceName].test.mjs`
4. Isama sa request pipeline sa `handlers/chatCore.ts` (kung nauugnay sa routing)
5. I-update ang routing logic sa `combo.ts` kung naaapektuhan ng service ang pagpili ng target
6. Idokumento sa file na ito

### Pagdaragdag ng Bagong Executor

1. Gumawa ng `open-sse/executors/[provider].ts` na nag-e-extend sa `BaseExecutor`
2. Irehistro sa `config/providerRegistry.ts`
3. Idagdag sa factory ng `executors/index.ts`
4. Magdagdag ng mga unit test para sa executor
5. Idokumento sa `docs/architecture/ARCHITECTURE.md`

### Pagdaragdag ng Bagong MCP Tool

1. Gumawa o mag-update ng `open-sse/mcp-server/tools/[category]Tools.ts`
2. Tukuyin ang Zod schema para sa mga input
3. Irehistro ang tool sa `mcp-server/index.ts`
4. Idagdag sa scope matrix sa `mcp-server/auth/`
5. Magdagdag ng mga unit test
