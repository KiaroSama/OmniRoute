> **உண்மையின் ஆதாரம்:** `src/lib/guardrails/`
> **கடைசியாகப் புதுப்பிக்கப்பட்டது:** 2026-08-29 — v3.8.51 (Video Bridge உரைமாற்றத்தின் மூலச்சான்று அழைப்பாளரால் அறிவிக்கப்படுகிறது,
> இன்னும் சேவையகத்தால் சரிபார்க்கப்படவில்லை — #11661-இன்படி தெளிவுபடுத்தப்பட்டது)

OmniRoute-க்கும் மேல்நிலை வழங்குநர்களுக்கும் இடையிலான எல்லையில் பாதுகாப்பு, கொள்கை மற்றும் உள்ளடக்க மாற்றங்களை Guardrails செயல்படுத்துகின்றன. ஒவ்வொரு guardrail-உம் கோரிக்கை payload-களை (`preCall`) மற்றும் மேல்நிலை பதில்களை (`postCall`) ஆய்வு செய்து, விருப்பமாக அவற்றை நிராகரிக்கவோ, மாற்றவோ அல்லது குறிப்புரையிடவோ முடியும்.

இந்த அமைப்பு **fail-open** முறையில் இயங்குகிறது: செயல்பாட்டின்போது ஒரு guardrail பிழையை எறிந்தால், registry அந்தப் பிழையைப் பதிவுசெய்துவிட்டு, கோரிக்கையைத் தோல்வியடையச் செய்வதற்குப் பதிலாக அடுத்த guardrail-உடன் தொடரும். தடுத்தல் என்பது எப்போதும் வெளிப்படையான முடிவு (`block: true`); அது ஒருபோதும் தற்செயலாக நிகழாது.

## உள்ளமைக்கப்பட்ட பாதுகாப்புக் கட்டுப்பாடுகள்

இறக்குமதி செய்யும்போது registry, முன்னுரிமை வரிசையில் ஆறு பாதுகாப்புக் கட்டுப்பாடுகளைத் தானாக ஏற்றுகிறது
(`registry.ts` → `registerDefaultGuardrails()`-ஐப் பார்க்கவும்):

| முன்னுரிமை | பெயர்               | கட்டம்(கள்)    | கோப்பு                |
| ---------- | ------------------- | -------------- | --------------------- |
| `5`        | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`        | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`        | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`       | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`       | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`       | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

குறைந்த முன்னுரிமை எண்கள் **முதலில்** இயங்கும்.

### பார்வை இணைப்புப் பாலம் (`visionBridge.ts`) — மோடாலிட்டி இணைப்புப் பாலம் PR-1

**பார்வைத் திறனற்ற மாடல்களை** இலக்காகக் கொண்ட, படங்களைக் கொண்ட கோரிக்கைகளை இடைமறித்து,
முழுக் கோரிக்கையையும் பார்வைத் திறனுள்ள மாடலுக்கு மாற்றி அனுப்புகிறது அல்லது
upstream அழைப்புக்கு முன், உள்ளமைக்கக்கூடிய பார்வை மாடல் உருவாக்கிய உரை விளக்கங்களால்
படப் பகுதிகளை மாற்றுகிறது. இதனால் உரை-மட்டும் வழங்குநர்கள் பன்மோடல்
payload-களை வெளிப்படையாகக் கையாள முடியும்.

செயலோட்டம்:

1. இலக்கு மாடல் ஏற்கெனவே பார்வையை ஆதரித்தால் தவிர்க்கவும் (அது கட்டாய-இணைப்புப்
   பட்டியல் `isVisionBridgeForcedModel`-இல் இடம்பெற்றிருந்தால் தவிர).
2. `extractImageParts(messages)` மூலம் படப் பகுதிகளைப் பிரித்தெடுக்கவும்
   (`visionBridgeHelpers.ts`); இது `open-sse/utils/mediaParts.ts`-இல் உள்ள
   **ஒருங்கிணைந்த ஊடகக் கண்டறிவான** `detectMediaParts()`-க்கு பணியை ஒப்படைக்கிறது —
   இது combo இணக்கத்தன்மை வடிகட்டியுடன் பகிரப்படும் ஒற்றை உண்மை ஆதாரமாகும்.
   `replaceImageParts` மீண்டும் பொருத்தக்கூடிய வடிவங்களின் மேல்நிலைப் பகுதிகளுக்கு
   மட்டுமே பிரித்தெடுத்தல் அனுமதிப்பட்டியலிடப்பட்டுள்ளது (பிரித்தெடுத்தல்↔மாற்றுதல் ஒப்பந்தம்): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, மற்றும் Responses API `input_image`. உள்ளமைந்த பொருத்தங்களும்
   சுட்டி-மட்டும் வடிவங்களும் combo-filter-க்கானவை; அவை ஒருபோதும் பிரித்தெடுக்கப்படாது.
   எதுவும் கிடைக்கவில்லை என்றால் தவிர்க்கவும்.
3. `resolveVisionBridgeRuntimeSettings()` மூலம் இயக்கநேர உள்ளமைவைத் தீர்மானிக்கவும்
   (`src/shared/constants/modalityBridgeDefaults.ts`): புதிய `modalityBridge*`
   அமைப்பு விசைகள் முன்னுரிமை பெறும்; பழைய `visionBridge*` விசைகள் **ஒரு சுழற்சிக்கான
   மாற்று ஏற்பாடாக** (பின்னோக்கிச் செல்லும் காலவாய்ப்பு) தொடர்ந்து இருக்கும்.
   இணைப்புப் பாலம் முடக்கப்பட்டிருக்கும்போது, எந்த ஊடகப் பயணத்திற்கும் முன்பே தவிர்க்கவும்.
4. முறைத் தேர்வி (`modalityBridgeVisionMode`, கீழுள்ள அட்டவணையைப் பார்க்கவும்)
   மாற்றி அனுப்புவதா அல்லது விளக்குவதா என்பதைத் தீர்மானிக்கிறது. மாற்றி அனுப்புதல்,
   `model` மட்டும் மாற்றப்பட்ட `modifiedPayload`-ஐ, meta
   `{ rerouted, fromModel, toModel, imagesKept }` உடன் திருப்பியளிக்கிறது.
5. விளக்கப் பாதை: படங்களை `maxImages` வரை வரம்பிடுகிறது, பணியை உணரும் prompt-ஐ
   உருவாக்குகிறது, விளக்க cache-ஐப் பார்க்கிறது, பார்வை மாடலை **இணையாக**
   (`Promise.allSettled`) அழைக்கிறது, மேலும் அவற்றின் இடத்தில்
   `[Image N]: <description>` உரைப் பகுதிகளைச் செலுத்துகிறது. விளக்குதல் தோல்வியுற்றால்
   `null` கிடைக்கும், மேலும் அசல் படப் பகுதி **பாதுகாக்கப்படும்** (#4012) — ஆனால் combo
   விளக்கப் பாதையில் ஒவ்வொரு விளக்கமும் தோல்வியுற்றால் மட்டும், உறுதிப்படுத்தப்பட்ட பார்வைத்
   திறனற்ற upstream-க்கு அதற்குப் பதிலாக
   `(கிடைக்கவில்லை — பார்வைத் திறனுள்ள வழங்குநர் எதுவும் இணைக்கப்படவில்லை)` stub வழங்கப்படும் (#8430).
6. `modifiedPayload` + meta (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) ஆகியவற்றைத் திருப்பியளிக்கவும்.

#### முறைத் தேர்வி (`modalityBridgeVisionMode`)

| முறை       | இயல்புநிலை | நடத்தை                                                                                                                                                                                                                                                                                                                                          |
| ---------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔          | மாற்றப்படாத பழைய heuristic (#6640/#7204): அசல் மாடலில் ஏற்கத்தக்க credentials ஏற்கெனவே இல்லாவிட்டால், non-combo/`auto/` மாடல்கள் சிறந்த பார்வை மாடலுக்கு மாற்றி அனுப்பப்படும் (அவை இருந்தால் விளக்கப்படும்); combo இலக்குகள் எப்போதும் விளக்கப்படும்.                                                                                           |
| `describe` |            | எப்போதும் விளக்கவும் — மாற்றி அனுப்பும் block முற்றிலுமாகத் தவிர்க்கப்படும்; பயனர் தேர்ந்தெடுத்த மாடலே எப்போதும் பதிலளிக்கும்.                                                                                                                                                                                                                  |
| `reroute`  |            | மாற்றி அனுப்புதலைக் கட்டாயப்படுத்தவும்: credential கொண்ட மாடலை வைத்திருக்கும் guard புறக்கணிக்கப்படும். மாற்றி அனுப்பும்-**இலக்குக்கான** credential guard இன்னும் பொருந்தும் — பயன்படுத்தக்கூடிய பார்வை இலக்கு எதுவும் இல்லாதபோது, கோரிக்கை விளக்கப் பாதைக்குச் செல்லும்; இதனால் மூலப் படங்கள் உரை-மட்டும் backend-ஐ ஒருபோதும் அடையாது (#8430). |

கட்டாய முறைகள், auto heuristic இயங்குவதற்கு **முன்பே** குறுக்கு வழியில் முடிவடைகின்றன;
`auto` நடத்தை PR-1-க்கு முந்தைய பாதுகாப்புக் கட்டுப்பாட்டுடன் byte அளவில் முற்றிலும் ஒரே மாதிரியானது.

#### API-key வரம்பு (`visionBridgeKeyScope.ts`)

அழைப்பவரின் API key, `allowedConnections`, quota pools
(`allowedQuotas`) அல்லது மாடல்களை (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) கட்டுப்படுத்தும்போது, அந்த key
பயன்படுத்தக்கூடிய இணைப்புகளில், அந்த key பயன்படுத்த அனுமதிக்கப்பட்ட மாற்றி அனுப்புதல் மற்றும்
விளக்குதல் மாடல்களை மட்டுமே இணைப்புப் பாலம் தேர்ந்தெடுக்கிறது. பின்னர் விளக்க அழைப்பு எப்போதும்
`x-omniroute-self-loop-key-id` header உடன் OmniRoute self-loop வழியாகச் செல்கிறது;
எனவே பெறும் chat கோரிக்கை, அந்த key-இன் இணைப்பு மற்றும் மாடல் கொள்கையை மீண்டும்
செயல்படுத்துகிறது. self-loop bearer உடன் சேர்ந்து இருந்தால் மட்டுமே அந்த header-ஐ
`enforceApiKeyPolicy()` மதிக்கிறது; எனவே அது அணுகலைக் குறைக்க மட்டுமே முடியும்,
மேலும் தீர்மானிக்க முடியாத id நிராகரிக்கப்படும்.

அந்த key-க்கு எந்தப் பார்வை மாடலும் அனுமதிக்கப்படவில்லை என்றால், விளக்கப் பாதை ஒதுங்கி,
கோரிக்கை மாற்றமின்றி கடந்து செல்லும்; இது முடக்கப்பட்ட பாதுகாப்புக் கட்டுப்பாட்டின் அதே
fail-open நடத்தை ஆகும் (meta `{ skipped: true, reason: "no_permitted_vision_model" }`).
key இல்லாத கோரிக்கைகளும், இந்தக் கட்டுப்பாடுகள் இல்லாத key-களும் முன்பு போலவே
செயல்படும்.

வழிநடத்தப்படுகிறது (codex-vision-proxy முறை), மேலும் காணக்கூடிய உரையைப்
படியெடுக்குமாறு vision model-இடம் கேட்கப்படுகிறது. கொடி முடக்கப்பட்டிருந்தால் —
அல்லது பயனர் உரை இல்லையெனில் — அடிப்படை prompt மாற்றமின்றிப் பயன்படுத்தப்படும்.

Describe self-loop-இன் சொந்த OpenAI-இணக்கமான கோரிக்கை (`callVisionModelSingle()`

#### Describe வெளியீட்டு வரம்பு (`modalityBridgeVisionMaxChars`)

| விசை                           | இயல்புநிலை | வரம்பு               |
| ------------------------------ | ---------- | -------------------- |
| `modalityBridgeVisionMaxChars` | `0`        | `0` அல்லது 100–50000 |

`0` (இயல்புநிலை) என்பது **வரம்பு இல்லை** என்பதைக் குறிக்கிறது —
`callVisionModel()` வழங்கும் விளக்கம் மாற்றமின்றி அனுப்பப்பட்டு, தற்போதுள்ள
நடத்தைப் பாதுகாக்கிறது. 100–50000 வரம்பிலுள்ள எந்த மதிப்பும், விளக்கம்
`[Image N]: <description>` ஆக மீண்டும் செருகப்படுவதற்கு முன் அதை `…`
பின்னொட்டுடன் குறுக்குகிறது (`VisionBridgeGuardrail.preCall()` in
`src/lib/guardrails/visionBridge.ts`). கீழ்நிலை model-க்கு முழுப் படியெடுப்பும்
தேவைப்படும் அதிக விவரமுள்ள OCR பணிகளுக்கு இதை உயர்த்தவும்; அதிகமாகப் பேசும்
vision model-களின் token பயன்பாட்டைக் கட்டுப்படுத்த இதைக் குறைக்கவும்.
Dashboard புலம் Vision tab-இன் Advanced panel-இல் உள்ளது
(`modality-bridge-max-chars` in `ModalityBridgeVisionTab.tsx`); வெளிப்படையாகக்
கொடுக்கப்பட்ட `0`-ஐ மாற்றாமல் விட்டுவிட்டு, 1 முதல் 99 வரையிலான எந்த மதிப்பையும்
குறைந்தபட்சமான 100-க்கு உயர்த்துகிறது — `0` என்பது வெறுமனே "அமைக்கப்படாத"
இயல்புநிலை அல்ல; அது தனித்துவமாகவே செல்லுபடியாகும் Zod மதிப்பு
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`).

#### தொலைநிலைப் பட இயல்பாக்கம் (self-loop describe/base64 fetch)

Bridge தானாகவே ஒரு **தொலைநிலைப்** படத்தைப் பெறும்போது — Anthropic describe
self-call மற்றும் claude-wire-format base64 மாற்றம்
(`ensureBase64ImagesForClaudeWire`) ஆகிய இரண்டும் `visionBridgeHelpers.ts` இல்
உள்ள `fetchRemoteImageAsDataUri()` வழியாக — உருவாகும் data URI, vision-model
கோரிக்கையில் உட்பொதிக்கப்படுவதற்கு முன் `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) வழியாக அனுப்பப்படுகிறது. மிகப்பெரிய படங்கள்
**2048px நீளமான விளிம்புக்கு** அளவு குறைக்கப்படுகின்றன (OpenAI/Anthropic ஏற்கனவே
server-side-இல் பயன்படுத்தும் resize வரம்புடன் பொருந்துமாறு); இதனால் vision
model காண்பது மாறாமல் upload bytes/latency குறைகிறது. அளவு மாற்றம் dynamic
import மூலம் ஏற்றப்படும் `sharp`-ஐப் பயன்படுத்துகிறது: அதன் native binary
ஏற்றத் தவறும் platform-இல், `normalizeDataUri()` **ஒருபோதும் throw செய்யாது** —
அது அசல் bytes-ஐ மாற்றமின்றி அனுப்புவதற்கு fallback செய்வதால்,
describe/base64-conversion பாதை எப்போதும் தொடர்ந்து செயல்படும். படமல்லாத bytes
(குறியீட்டை நீக்கிப் படிக்கக்கூடிய படத்தை வழங்காத fetch) கூட மாற்றமின்றி
அனுப்பப்படுகின்றன. இந்த இயல்பாக்கம் bridge தனது சொந்த self-call-க்காகப் பெறும்
படங்களுக்கு மட்டுமே வரையறுக்கப்பட்டுள்ளது — caller-இன் raw passthrough
payload-க்கு இது ஒருபோதும் பயன்படுத்தப்படாது; இது opt-in-only மாற்றக்
கொள்கையுடன் (Hard Rule #20) ஒத்துப்போகிறது.

மாதிரித் தேர்வி, காலக்கெடு/அதிகபட்சக் கிளிப் வரம்புகள், audio எண்ணிக்கைகள் மற்றும்
`input_audio` மாதிரிச் சோதனை ஆகியவற்றை வழங்குகிறது. Video தாவல் முழுமையாகச்
செயல்படுகிறது: இது FFmpeg/ffprobe இயக்கநேர நிலையைத் தெரிவிக்கிறது — நான்கு
வெளிப்படையான UI நிலைகளில் ஒன்று (ஆய்வு நடந்துகொண்டிருக்கும்போது அல்லது அதை முடிக்க
முடியாதபோது `unknown`, loopback அல்லாத கட்டுப்பாட்டுப் பலகை host-இல் ஆய்வு
client பக்கத்தில் தவிர்க்கப்படும்போது `restricted`, ஆய்வு செய்யப்பட்டு கிடைக்கவில்லை
என்பது உறுதிசெய்யப்பட்டவுடன் `unavailable`, அல்லது FFmpeg/ffprobe பதிப்புகளுடன்
`available`) — இயக்குதல்/மாதிரி/frame/video/காலக்கெடு வரம்புகளை நிலையாகச்
சேமிக்கிறது, மாதிரித் தேர்வியை vision திறனுள்ள மாதிரிகளுக்கு மட்டும்
வடிகட்டுகிறது மற்றும் video எண்ணிக்கைகளை வழங்குகிறது.

AI அமைப்புகளின் கீழிருந்த முந்தைய Vision Bridge அட்டை, புதிய பக்கத்திற்கான
இணக்கத்தன்மை இணைப்பாகும்; அது இனி படிவத்தின் இரண்டாவது நகலைக் கொண்டிருக்காது.
தற்போதுள்ள Speech-to-Text பயிற்சிக் களத்தை அகற்றாமல், Media Providers பகுதியும்
Image-to-Text மற்றும் Speech-to-Text பணிப்பாய்வுகளை அவற்றுடன் தொடர்புடைய Modality
Bridge தாவல்களுடன் இணைக்கிறது.

**சுய-loop அனுமதி புறக்கணிப்பு:** விவரிப்புக் கோரிக்கை OmniRoute-இன் சொந்த
`/v1` சுய-loop வழியாக (தரநிலையற்ற provider மாதிரி) அனுப்பப்படும்போது, துணைக்
கோரிக்கை `x-omniroute-admission-bypass: internal`-ஐ அனுப்புகிறது மற்றும்
தீர்மானிக்கப்பட்ட சுய-loop நற்சான்றுடன் அங்கீகரிக்கப்படுகிறது — local பயன்முறையில்
உள்ளக `sk_omniroute` sentinel அல்லது operator உள்ளமைத்த `OMNIROUTE_API_KEY` /
`ROUTER_API_KEY` env விசை (#1350); இதனால் `REQUIRE_API_KEY=true` deployment-களிலும்
விவரிப்புக் கோரிக்கையை இயக்க முடியும். அந்தத் துல்லியமான நற்சான்றுகளுக்கு மட்டுமே
இந்தப் புறக்கணிப்பு ஏற்கப்படுகிறது; எனவே வெளிப்புற client-கள் அனுமதியைத் தவிர்க்க
இந்த header-ஐப் பயன்படுத்த முடியாது.

மரபுவழி இயல்புநிலைகள் `src/shared/constants/visionBridgeDefaults.ts`-இல் உள்ளன;
புதிய பயன்முறை/பணி சார்ந்த/cache இயல்புநிலைகளும் அமைப்புகள் resolver-உம்
`src/shared/constants/modalityBridgeDefaults.ts`-இல் உள்ளன. சோதனைகள் போலியான
`getSettings` மற்றும் `callVisionModel` செயலாக்கங்களைச் செலுத்தக்கூடிய வகையில்,
guardrail ஒரு `deps` constructor விருப்பத்தை வழங்குகிறது.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Audio உள்ளீட்டை ஏற்றுக்கொள்வதாக அறியப்படாத இலக்கை அடைவதற்கு முன், audio கொண்ட
chat கோரிக்கைகளை இடைமறிக்கிறது. இது chat கோரிக்கையை ஒருபோதும் வேறு வழியில்
அனுப்பாது: தற்போதுள்ள OpenAI-இணக்கமான multipart endpoint வழியாக audio பகுதிகள்
உரையாக மாற்றப்பட்டு, தேர்ந்தெடுக்கப்பட்ட chat மாதிரி உரைப் படியெடுப்புகளுடன்
தொடர்கிறது.

செயலோட்டம்:

1. `getResolvedModelCapabilities()` வழியாக `supportsAudio`-ஐத் தீர்மானிக்கவும்.
   வெளிப்படையான provider-registry metadata-வுக்கு முன்னுரிமை உண்டு; அதைத் தொடர்ந்து
   நிலையான மாதிரி metadata, பின்னர் ஒத்திசைக்கப்பட்ட `modalities_input`.
   `audio` இல்லாத அறிவிக்கப்பட்ட உள்ளீட்டுப் பட்டியல் `false` ஆகும்; திறனுக்கான
   எந்த ஆதாரமும் இல்லையெனில் அது `null` ஆகவே இருக்கும். `false` மற்றும் `null`
   இரண்டுமே பாதுகாப்பான bridge-ஐச் செயல்படுத்தும்; `true` அதைத் தவிர்க்கும்.
2. `modalityBridgeAudio*` அமைப்புகளைத் தீர்மானித்து, பகிரப்பட்ட
   `detectMediaParts()` கண்டறிவியைப் பயன்படுத்தி ஒவ்வொரு செய்தியிலிருந்தும் splice
   செய்யக்கூடிய உயர்நிலை audio பகுதிகளைப் பிரித்தெடுக்கவும். ஆதரிக்கப்படும் wire
   வடிவங்கள் OpenAI `input_audio`, `audio_url`, மற்றும்
   `source.media_type: "audio/*"` ஆகும். உள்ளமை audio routing-க்காகக்
   கண்டறியப்படும், ஆனால் splice பாதையால் அகற்றப்படாது. பணியின் அளவு
   `modalityBridgeAudioMaxClips` மூலம் கட்டுப்படுத்தப்படுகிறது; அதன் பின்னுள்ள
   பகுதிகள் மாற்றப்படாமல் இருக்கும்.
3. உள்ளமைக்கப்பட்ட `provider/model`-ஐப் பயன்படுத்தவும் அல்லது
   `selectAudioBridgeModel()`-ஐ நிலையான catalog வரிசையில்
   `AUDIO_TRANSCRIPTION_PROVIDERS` வழியாகச் சென்று, பயன்படுத்தக்கூடிய செயலில் உள்ள
   provider நற்சான்றைக் கொண்ட முதல் மாதிரியைத் தேர்ந்தெடுக்க அனுமதிக்கவும்.
4. `callAudioTranscription()` base64/data-URI audio-வை multipart `file` ஆக
   மாற்றுகிறது அல்லது DNS pinning மற்றும் 25 MB வரம்புடன், பொது அணுகலுக்கு
   மட்டுமான outbound guard வழியாக தொலைநிலை `audio_url`-ஐப் பதிவிறக்குகிறது.
   பின்னர் அது file-ஐயும் தேர்ந்தெடுக்கப்பட்ட மாதிரியையும் உள்ளக
   `/v1/audio/transcriptions` சுய-loop-க்கு POST செய்கிறது; இது
   `resolveSelfLoopBearer()` மூலம் அங்கீகரிக்கப்படுகிறது. தற்போதுள்ள transcription
   route வழக்கமான நற்சான்றுத் தேடல், cooldown/rate-limit கையாளுதல் மற்றும் provider
   dispatch ஆகியவற்றைச் செய்கிறது.
5. வெற்றிகரமான அழைப்புகள் அவற்றின் பகுதிகளை `[Audio N]: <transcript>` என
   மாற்றுகின்றன. அழைப்புகள் `Promise.allSettled` மூலம் இயங்குகின்றன: தனிப்பட்ட
   தோல்வி அந்த அசல் audio பகுதியைத் தக்கவைக்கும் (#4012 ஒப்பந்தம்). ஒவ்வொரு
   அழைப்பும் தோல்வியடைந்து, இலக்கு `supportsAudio === false` என்பது நிரூபிக்கப்பட்டால்,
   பகுதிகள் `[Audio N]: (கிடைக்கவில்லை — எந்த STT provider-உம் இணைக்கப்படவில்லை)`
   என மாறும் (#8430 ஒப்பந்தம்). அறியப்படாத இலக்குக்கு (`null`), அனைத்தும்
   தோல்வியடைந்த முடிவு மாற்றப்படாமல் இருக்கும். பயன்படுத்தக்கூடிய STT நற்சான்று
   இல்லாத, உரை மட்டும் ஆதரிப்பதாக நிரூபிக்கப்பட்ட இலக்கு, network அழைப்பை
   மேற்கொள்ளாமலே அதே வெளிப்படையான placeholder-ஐப் பெறும்.

வெற்றிகரமான படியெடுப்புகள் செயல்முறை முழுவதற்குமான Modality Bridge LRU/TTL
cache-ஐப் பயன்படுத்துகின்றன. விசையானது audio reference, நிலையான
`audio-transcription` செயல்பாட்டு label மற்றும் தேர்ந்தெடுக்கப்பட்ட STT மாதிரி
ஆகியவற்றை ஒருங்கிணைக்கிறது; தோல்விகள் ஒருபோதும் cache செய்யப்படாது. Audio
முயற்சிகள் பகிரப்பட்ட `bridged`, `cacheHits`, `failures`, மற்றும் `lastUsedAt`
எண்ணிக்கைகளைப் புதுப்பிக்கின்றன. மாற்றப்பட்ட பதில்கள்
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`-ஐக்
கொண்டிருக்கும்; மாற்றப்படாத கோரிக்கைகள் Audio Bridge பகுதியைப் பெறாது.

இயக்கநேர அமைப்புகள் DB ஆதரவுடையவை மற்றும் Zod மூலம் சரிபார்க்கப்படுகின்றன:

| விசை                          | இயல்புநிலை | வரம்பு                  |
| ----------------------------- | ---------- | ----------------------- |
| `modalityBridgeAudioEnabled`  | `true`     | —                       |
| `modalityBridgeAudioModel`    | `""`       | தானியங்கு அல்லது STT ID |
| `modalityBridgeAudioTimeout`  | `60000`    | 1000–300000             |
| `modalityBridgeAudioMaxClips` | `3`        | 1–10                    |

பகிரப்பட்ட தற்காலிகச் சேமிப்பகம் `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, மற்றும் `modalityBridgeCacheMaxEntries`
ஆகியவற்றால் தொடர்ந்து கட்டுப்படுத்தப்படுகிறது.

### வீடியோ இணைப்பி (`videoBridge.ts`, `videoBridgePipeline.ts`)

அறியப்பட்ட இயல்புநிலை வீடியோ ஆதரவு இல்லாத இலக்கு அழைக்கப்படுவதற்கு முன்,
Chat Completions `messages` மற்றும் Responses API `input` ஆகியவற்றில் உள்ள
மேல்நிலை வீடியோப் பகுதிகளை இடைமறிக்கிறது. ஆதரிக்கப்படும் வடிவங்கள்
`input_video`, `video_url`, `video_source`, HTTPS URL-கள் மற்றும்
`data:video/*;base64,...` தரவு URI-கள் ஆகும். உரையில் உள்ள சாதாரண கோப்புப்
பெயர்கள் வீடியோவாகக் கருதப்படாது.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) கோரிக்கை ஊடுருவல்,
திறன்/கொள்கைச் சரிபார்ப்பு, ஒவ்வொரு கோரிக்கைக்குமான திரட்டல் மற்றும்
பதில் payload ஆகியவற்றைக் கையாள்கிறது. ஒவ்வொரு வீடியோவுக்குமான பணிகள் —
பெறுதல், முழு-முடிவு தற்காலிகச் சேமிப்பகம், frame வரிசையை விவரித்தல்
(இதில் அழைப்பாளர் அறிவித்த ஏதேனும் audio transcript ஒருங்கிணைக்கப்படும்),
மற்றும் ஒவ்வொரு முயற்சிக்குமான அளவீடுகள்/இடைநிறுத்தம்/சுத்தப்படுத்தல் —
`videoBridgePipeline.ts`-இல் உள்ள `processVideoPart`-க்குப் பின்னால்
மறைக்கப்பட்டுள்ளன; இது `preCall`-இன் loop-க்குள் ஒவ்வொரு வீடியோப் பகுதிக்கும்
ஒருமுறை அழைக்கப்படுகிறது. அந்த module, `VideoMediaBrokerPort`
(byte-களைப் பெற்று மாதிரி எடுக்கப்பட்ட frame-களைப் பிரித்தெடுப்பது),
`VideoAudioTranscriptionPort` (அழைப்பாளர் அறிவித்த audio transcript-ஐ
மாதிரி எடுக்கப்பட்ட caption-களுடன் ஒருங்கிணைப்பது), மற்றும்
`VideoDrilldownPort` (frame drill-down நிலைத்தன்மை எல்லை; இன்னும்
`processVideoPart`-உடன் இணைக்கப்படவில்லை — தற்போது தனியான
`/api/modality-bridge/video/drilldown` route மட்டுமே drill-down பதிவுகளை
எழுதுகிறது) ஆகிய வெளிப்படையான port எல்லைகளையும் வரையறுக்கிறது.

பொது `/v1` கோரிக்கைப் பாதை ஒருபோதும் subprocess-ஐ import செய்வதோ

அழைப்பாளர்கள் ஏற்கனவே ஒத்திசைக்கப்பட்ட உரையை வைத்திருந்தால், ஆதரிக்கப்படும் வீடியோப் பகுதிக்கு விருப்பத்திற்குரிய `transcript.cues` அணியை இணைக்கலாம். ஒவ்வொரு குறியும் `text`, சோதிக்கப்பட்ட காலஅளவுக்குள் உள்ள வரையறுக்கப்பட்ட `start`/`end` இடைவெளி, மற்றும் அனுமதிப்பட்டியலில் உள்ள `source` (`client`, `embedded`, அல்லது `audio-bridge`) ஆகியவற்றைக் கொண்டிருக்க வேண்டும்; `confidence`-இன் இயல்புநிலை `1`, மேலும் அது `0` மற்றும் `1`-க்கு இடையில் இருக்க வேண்டும். முற்றிலும் ஒரே மாதிரியான நகல் குறிகள் ஒன்றாகச் சுருக்கப்படுகின்றன. இந்த மெட்டாடேட்டாவிலிருந்து OmniRoute ஒருபோதும் உரைமாற்றத்தைத் தொடங்காது: சரிபார்க்கப்பட்ட குறிகள், மூலம், நம்பகத்தன்மை, மற்றும் இடைவெளியுடன் விவரிக்கப்பட்ட முடிவுக்குள் நகலெடுக்கப்பட்டு, ஃபிரேம் தலைப்புரைகளுடன் நம்பத்தகாத அவதானிப்புகளாக வழங்கப்படுகின்றன. செல்லாத, வரம்புக்கு வெளியேயுள்ள, அல்லது மூலச்சான்று இல்லாத உரை, தலைப்புரை ஸ்ட்ரீமில் கலக்கப்படுவதற்குப் பதிலாக நிராகரிக்கப்படுகிறது. சுயமாக உறுதிப்படுத்தப்பட்ட `embedded` அல்லது `audio-bridge` அடையாளங்கள் உட்பட, கோரிக்கை-உடலின் இரு உரைமாற்றச் சேனல்களும் வழங்கப்பட்ட மூலச்சான்றை `client` ஆக இயல்பாக்குகின்றன. சேவையகத்துக்குச் சொந்தமான அடாப்டர் மட்டுமே குறியீடு-மட்டுமான `trustedSource` அளவுருவின் வழியாக அந்த நம்பகமான அடையாளங்களை ஒதுக்க முடியும்; கோரிக்கை JSON புலத்தால் அந்த அளவுருவை அடைய முடியாது. உரைமாற்ற உரை, அதன் மூலச்சான்றைப் பொருட்படுத்தாமல், நம்பத்தகாத ஊடகத்திலிருந்து பெறப்பட்ட உள்ளடக்கமாகவே இருக்கும்; அது ஒருபோதும் அங்கீகாரத்தைத் தீர்மானிக்கக் கூடாது.

### PII மறைப்பான் (`piiMasker.ts`)

**இரண்டு** கட்டங்களிலும் இயங்குகிறது.

- **`preCall`** payload-ஐ நகலெடுத்து, `system`, `messages`, `input`, மற்றும்
  `prompt` (சாதாரண சர உருப்படிகள் உட்பட) ஆகியவற்றைச் சுற்றிச் சென்று, சர வகை

  `processPII()`-ஐப் பயன்படுத்துகிறது. `PII_REDACTION_ENABLED=true` ஆக இருக்கும்போது,
  கண்டறியப்பட்ட PII வெளிச்செல்லும் payload-இல் மறைக்கப்படுகிறது. இது
  `INPUT_SANITIZER_MODE`-இலிருந்து சுயாதீனமானது (அது prompt-injection கொள்கையை
  மட்டுமே கட்டுப்படுத்துகிறது). மறைத்தல் முடக்கப்பட்டிருக்கும்போது, உள்ளடக்கத்தை

  Responses-API-வடிவ மறைப்பானை (`maskResponsesOutput` — `output_text` மற்றும்

(`meta.detections`, `meta.redacted`) அல்லது மீண்டும் எழுதுகிறது.

**Dashboard → Settings → Security → PII masking** எது மறைக்கப்பட வேண்டும் என்பதைத்
தேர்வுசெய்கிறது. இது மறைத்தலை இயக்காது: அதற்கு இன்னும் `PII_REDACTION_ENABLED`
(கோரிக்கை) மற்றும் `PII_RESPONSE_SANITIZATION` (பதில் + SSE) ஆகியவை பயன்படுத்தப்படுகின்றன;
இரண்டும் இயல்பாக முடக்கப்பட்டிருக்கும்.

- **வகை வாரியான தேர்வு** — உள்ளமைக்கப்பட்ட id-கள்
  `src/shared/constants/piiTypes.ts`-இல் (`PII_BUILTIN_TYPES`) பட்டியலிடப்பட்டுள்ளன.
  அமைக்கப்படாதது என்பது ஒவ்வொரு வகையையும் குறிக்கிறது (இந்த அமைப்பு உருவாவதற்கு
  முந்தைய நடத்தை). கோரிக்கை இயந்திரத்தின் `ssn_us` வடிவம் `ssn`-க்கு வரைபடமாகிறது.
  வார்ப்புருக்கள் (Minimal, Standard, Financial, Brazilian, USA, Full) UI-இல் உள்ள
  தேர்வுப்பெட்டிகளை மட்டுமே நிரப்புகின்றன.
- **தனிப்பயன் வடிவங்கள்** — அதிகபட்சம் 20 regex அல்லது wildcard வடிவங்கள்
  (`*` = அதிகபட்சம் 64 இடைவெளியற்ற எழுத்துகள், `?` = ஒன்று). பொருத்தங்கள்
  `[CUSTOM_REDACTED]` ஆகின்றன. ஒவ்வொரு வடிவமும் `compilePiiCustomPattern()`
  (`src/shared/utils/piiCustomPatterns.ts`) வழியாகச் செல்கிறது: அதிகபட்சம் 500
  எழுத்துகள், கொடிகள் `g i m s u` என்பவற்றுக்கு மட்டும் வரம்பிடப்பட்டவை, compile
  ஆக வேண்டும், `safe-regex` சோதனையில் (பேரழிவான backtracking) தேர்ச்சி பெற வேண்டும்,
  மேலும் வெற்று சரம் அல்லது மறைத்தல் placeholder-உடன் பொருந்தக்கூடாது. தோல்வியுறும்
  வடிவம் சேமிக்கும்போதும் சோதிக்கும்போதும் மறுக்கப்படுகிறது; தோல்வியுறும் சேமிக்கப்பட்ட
  வரிசை இயக்கநேரத்தில் compile செய்யப்படுவதற்குப் பதிலாகத் தவிர்க்கப்படுகிறது. மறைத்தல்
  இயக்கப்பட்டிருக்கும்போது மட்டுமே தனிப்பயன் வடிவங்கள் இயங்கும்.
- **கண்டறிதல் எண்ணிகள்** — வகை வாரியான எண்ணிக்கைகள் (பொருந்திய மதிப்புகள் ஒருபோதும்
  அல்ல), நினைவகத்தில் வைக்கப்பட்டு மறுதொடக்கத்தில் மீட்டமைக்கப்படுகின்றன
  (`src/lib/pii/piiDetectionStats.ts`). மறைத்தல் இயக்கப்பட்டிருக்கும்போது மட்டுமே
  அவை அதிகரிக்கும்.

அமைப்புகள் `key_value` அட்டவணையில் (`pii_settings` namespace,
`src/lib/db/piiSettings.ts`) உள்ளன மற்றும் 1 s cache வழியாகப் படிக்கப்படுகின்றன. API:

| முறை   | பாதை                     | நோக்கம்                                                                                       |
| ------ | ------------------------ | --------------------------------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | கொடி நிலை, `enabledTypes`, `customPatterns`, கண்டறிதல் எண்ணிகள்                               |
| `PUT`  | `/api/settings/pii`      | `enabledTypes` (`null` = அனைத்தும்) மற்றும்/அல்லது `customPatterns`-ஐ மாற்றுதல்               |
| `POST` | `/api/settings/pii/test` | அதிகபட்சம் 8 KB மாதிரிக்கு எதிராக ஒரு வடிவத்தைச் சோதனை ஓட்டம் செய்தல்; எதுவும் சேமிக்கப்படாது |

மூன்றிற்கும் மேலாண்மை அங்கீகாரம் தேவைப்படுகிறது; மேலும் Zod மூலம் body
சரிபார்க்கப்படுகிறது (`src/shared/validation/schemas/piiSettings.ts`).

### Prompt Injection (`promptInjection.ts`)

பயனர் வழங்கிய உள்ளடக்கத்தில் உள்ள எதிர்மறைக் கட்டமைப்புகளைக் கண்டறிந்து,
கட்டமைக்கப்பட்ட கொள்கையை அமல்படுத்துகிறது. நடத்தை சூழல் மாறிகள் மற்றும் constructor
விருப்பங்களால் நிர்ணயிக்கப்படுகிறது:

| அமைப்பு             | சூழல் மாறி                                                                                                            | இயல்புநிலை | விளைவு                                                                                                                                                                                                                       |
| ------------------- | --------------------------------------------------------------------------------------------------------------------- | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| செயல்படுத்தப்பட்டது | `INPUT_SANITIZER_ENABLED`                                                                                             | `true`     | `false` ஆக இருக்கும்போது, guardrail உடனடியாக வெளியேறுகிறது.                                                                                                                                                                  |
| பயன்முறை            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                                       | `warn`     | Injection கொள்கை: `block`, `warn`, அல்லது `log`. (பின்தங்கிய இணக்கத்திற்காக `redact` ஏற்கப்படுகிறது, ஆனால் அது injection உரையை அகற்றாது; கோரிக்கையின் PII மறுபதிப்பு `PII_REDACTION_ENABLED` மூலம் கட்டுப்படுத்தப்படுகிறது.) |
| தடுப்பு வரம்பு      | `blockThreshold` விருப்பம் / `INPUT_SANITIZER_BLOCK_THRESHOLD` (`INJECTION_GUARD_BLOCK_THRESHOLD` என்ற மாற்றுப்பெயர்) | `high`     | தடுப்பதற்குத் தேவையான குறைந்தபட்ச தீவிரநிலை. இயல்புநிலையில் நடுத்தரத் தீவிரநிலை கண்காணிப்புக்கு மட்டுமே உரியது.                                                                                                              |

**பயன்முறை முன்னுரிமை** (`getMode`): அழைப்பவரின் `options.mode` →
`INJECTION_GUARD_MODE` **DB அம்சக் கொடி மேலெழுதல்** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` சூழல் மாறி → `INPUT_SANITIZER_MODE` சூழல் மாறி →
`warn`. எனவே Dashboard மேலெழுதல் சூழல் மாறிகளைவிட முன்னுரிமை பெறுகிறது; இதனால் Feature
Flags UI, இயங்கிக்கொண்டிருக்கும் guard-ஐ நேரலையில் கட்டுப்படுத்துகிறது (மறுதொடக்கம் தேவையில்லை). DB வாசிப்பு தோல்வி-பாதுகாப்பானது:
அதில் பிழை ஏற்பட்டால், guard சூழல் மாறி அடிப்படையிலான நடத்தைக்குத் திரும்புகிறது; மேலும் எந்த
மேலெழுதலும் அமைக்கப்படாதபோது, நடத்தை சூழல் மாறி-மட்டும் தீர்மானிப்பதற்கு ஒத்ததாக இருக்கும்.

கண்டறிதல் மூலங்கள்:

1. `@/shared/utils/inputSanitizer`-இலிருந்து `sanitizeRequest()` (pipeline-இன்
   மற்ற பகுதிகளிலும் பயன்படுத்தப்படும் பகிரப்பட்ட detector தொகுப்பு).
2. உள்ளமைந்த `DEFAULT_GUARD_PATTERNS` (தற்போது `system_override_inline` மற்றும்
   `markdown_system_block`, இரண்டும் `high` தீவிரநிலை கொண்டவை).
3. constructor விருப்பங்கள் வழியாக அனுப்பப்படும் விருப்பத் தேர்வான `customPatterns` (சரங்கள், regex,
   அல்லது `{ name, pattern, severity }` பதிவுகள்).

`mode === "block"` ஆக இருந்து, குறைந்தது ஒரு கண்டறிதல் தீவிரநிலை
வரம்பை எட்டும்போது, `preCall` ஆனது `{ block: true, message: "Request rejected:
suspicious content detected" }` என்பதைத் திருப்புகிறது. `warn`/`log` பயன்முறைகளில் guardrail பதிவுசெய்கிறது, ஆனால்
அழைப்பை அனுமதிக்கிறது. registry வழியாகச் செல்லாமல் prompts-ஐ மதிப்பிட வேண்டிய
அழைப்பவர்களுக்காகப் பகிரப்பட்ட helper ஆன `evaluatePromptInjection()`-உம் export செய்யப்படுகிறது.

**ஸ்கேன் வரம்பு (v3.8.20):** இணைக்கப்பட்ட prompt உரையின் **முதல் 16 KB**-ஐ மட்டுமே
detector ஆய்வு செய்கிறது — `src/shared/utils/inputSanitizer.ts`-இல்
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 bytes). Pattern loop-ஐ இயக்குவதற்கு முன்
`detectInjection()` மற்றும் `evaluatePromptInjection()` இரண்டும் `slice(0, MAX_INJECTION_SCAN_BYTES)`-ஐப்
பயன்படுத்துகின்றன. Injection கட்டளைகள் உள்ளீட்டின் தொடக்கத்திற்கு அருகிலேயே இருப்பதால், இது
கண்டறிதலைப் பலவீனப்படுத்தாமல் பல நூறு-KB payload-களில் regex CPU/GC பயன்பாட்டைக்
கட்டுப்படுத்துகிறது (ஒப்பிடுக: #3932, #4041).

### நற்சான்று மறைப்பான் (`credentialMasker.ts`)

**இரண்டு** கட்டங்களிலும், இயல்புநிலை சங்கிலியில் கடைசியாக (முன்னுரிமை `95`) இயங்குகிறது. வெளிச்செல்லும் payload-இலிருந்து (செய்தி
உள்ளடக்கம், tool-call arguments, tool முடிவுகள்) **மற்றும்** provider response-இலிருந்து
நன்கு அறியப்பட்ட API-key / secret-token வடிவங்களை மறைக்கிறது; இதனால் prompt-இல் ஒட்டப்பட்ட
நற்சான்று (அல்லது tool முடிவால் மீண்டும் வெளியிடப்பட்டது) upstream provider-க்கோ client-க்கோ
கசியாது.

- **விருப்பத் தேர்வால் மட்டுமே செயல்படும்**, PII மறைப்பின் அதே நடைமுறை (கடுமையான விதி #20-க்கு அருகிலானது):
  `settings.credentialRedactionEnabled === true` **அல்லது**
  `CREDENTIAL_REDACTION_ENABLED=true` இல்லாவிட்டால் முடக்கப்பட்டிருக்கும். இது அணைக்கப்பட்டிருக்கும்போது, guardrail எந்தச் செயலும் செய்யாது —
  அது ஒருபோதும் தடுக்காது, மறுபதிப்பும் செய்யாது.
- `redactCredentials()` முழு payload/response மரத்திலும் பயணித்து (`walkValue()`,
  prototype pollution-இலிருந்து பாதுகாப்பானது, `WeakSet` மூலம் cycle-இலிருந்து பாதுகாப்பானது), பொருத்தங்களை
  `[REDACTED:<type>]` placeholder-ஆல் மாற்றுகிறது; உண்மையில் மாறிய கிளைகளை மட்டுமே
  clone செய்கிறது.
- `CREDENTIAL_PATTERNS` ஆனது LLM provider keys (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS tokens (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), payment keys (Stripe, Square), cloud
  keys (AWS access key, Twilio, SendGrid, Mailgun), private keys / JWTs,
  நற்சான்றுகளைக் கொண்ட connection strings (`mongodb://user:pass@...`, முதலியவை), மற்றும்
  பொதுவான `Authorization`/`x-api-key`/`api-key`/`apikey` header-value
  வடிவம் ஆகியவற்றை உள்ளடக்குகிறது. Header வடிவிலான keys (`authorization`, `x-api-key`, `api-key`,
  `apikey`) பொதுவான text regex வழியாக அல்லாமல் கட்டமைப்பு ரீதியாக மறைக்கப்படுகின்றன (மதிப்பு மட்டும்; `Bearer `/`Basic ` போன்ற
  scheme prefix பாதுகாக்கப்படும்).
- Guardrail ஒருபோதும் தடுக்காது; அது மறுபதிப்பு (`modifiedPayload` /
  `modifiedResponse`) மற்றும் குறிப்புரை (`meta.credentialsRedacted`, `meta.count`) ஆகியவற்றை மட்டுமே செய்கிறது.

Regression guard: `tests/unit/credential-masker-guardrail.test.ts`.

## அடிப்படை ஒப்பந்தம் (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true சங்கிலியை உடனடியாக நிறுத்துகிறது
  message?: string; // தடுக்கும்போது வெளிப்படுத்தப்படும்
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // கோரிக்கையை மாற்றியமைக்க preCall மூலம் திருப்பி அனுப்பப்படும்
  modifiedResponse?: TValue; // பதிலை மாற்றியமைக்க postCall மூலம் திருப்பி அனுப்பப்படும்
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ஒரு guardrail, `void`, `{}`, அல்லது `{ block: false }` ஆகியவற்றில் ஒன்றைத் திருப்பி அனுப்புவதன் மூலம் "மாற்றம் இல்லை" என்பதைக் குறிக்கிறது. `modifiedPayload`/`modifiedResponse`-ஐத் திருப்பி அனுப்புவது, அடுத்தடுத்த guardrail-களுக்குச் சங்கிலி வழியாகச் செல்லும் மதிப்பை மாற்றுகிறது.
`signal?: AbortSignal`, அழைப்பவரின் வாழ்க்கைச் சுழற்சியை guardrail-களுக்குக் கொண்டு செல்கிறது. ஒரு கோரிக்கை கைவிடப்படுவது திட்டமிட்ட fail-open விதிவிலக்காகும்: இலக்கு மூல ஊடகத்தை ஆதரிக்காது என்று அறியப்பட்டிருந்தால், media bridge-கள் அதை மீட்டமைக்காமல் பணியை நிறுத்தி சுத்தப்படுத்துகின்றன.

## பதிவகம் (`registry.ts`)

singleton `guardrailRegistry` பின்வருவனவற்றை வெளிப்படுத்துகிறது:

- `register(guardrail)` — ஒரு guardrail-ஐச் சேர்க்கிறது (அல்லது இயல்பாக்கப்பட்ட பெயரின் அடிப்படையில் மாற்றுகிறது) மற்றும் ஏறுவரிசை `priority` அடிப்படையில் மீண்டும் வரிசைப்படுத்துகிறது.
- `clear()` / `list()` — நிர்வாக உதவிச் செயல்பாடுகள்.
- `runPreCallHooks(payload, context)` — செயலில் உள்ள guardrail-களை வரிசையாகச் செயல்படுத்தி, `modifiedPayload` வழியாக payload-ஐ அனுப்பி, முதல் `block: true`-இல் நிறுத்துகிறது.
- `runPostCallHooks(response, context)` — பதில் பக்கத்தில் அதே செயலோட்டத்தைப் பயன்படுத்துகிறது.
- `resetGuardrailsForTests({ registerDefaults })` — நிலையை அழித்து, சுத்தமான சோதனைத் தனிமைப்படுத்தலுக்காக விருப்பப்பட்டால் இயல்புநிலைகளை மீண்டும் பதிவு செய்கிறது.

இரண்டு இயக்கிகளும் `{ blocked, payload|response, results, guardrail?, message? }`-ஐத் திருப்பி அனுப்புகின்றன; இதில் `results` என்பது ஒவ்வொரு guardrail-க்கும் உரிய `blocked`, `skipped`, `modified`, `error`, மற்றும் `meta` புலங்களை உள்ளடக்கிய `GuardrailExecutionResult` பதிவுகளின் வரிசையாகும்; இது தடமறிதலுக்குப் பயனுள்ளதாக இருக்கும்.

### ஒவ்வொரு கோரிக்கைக்கும் Guardrail-களை முடக்குதல்

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })`, தற்போதைய கோரிக்கைக்குத் தவிர்க்கப்பட வேண்டிய guardrail பெயர்களின் நகல் நீக்கப்பட்ட பட்டியலைத் தொகுக்கிறது. மூலங்கள் (அனைத்தும் விருப்பமானவை, அனைத்தும் ஒன்றிணைக்கப்படும்):

- `apiKeyInfo.disabledGuardrails`
- கோரிக்கை body-யின் `disabledGuardrails` (மேல்நிலை)
- கோரிக்கை body-யின் `metadata.disabledGuardrails`
- Header `x-omniroute-disabled-guardrails` (அல்லது பழைய
  `x-disabled-guardrails`)

மதிப்புகள் string-களின் array-களாகவோ அல்லது காற்புள்ளியால் பிரிக்கப்பட்ட string ஆகவோ இருக்கலாம்; பெயர்கள் lowercase kebab-case-க்கு இயல்பாக்கப்படுகின்றன (`pii_masker` → `pii-masker`). முடிவு `context.disabledGuardrails` வழியாகப் பதிவகத்திற்கு அனுப்பப்படுகிறது; அது பொருந்தும் guardrail-களைத் தவிர்க்கிறது (`results`-இல் `skipped: true`).

## செயல்படுத்தும் வரிசை

`src/sse/handlers/chat.ts` மற்றும்
`open-sse/handlers/chatCore.ts` வழியாகச் செல்லும் ஒவ்வொரு கோரிக்கைக்கும்:

1. `resolveDisabledGuardrails(...)` ஆனது API விசை, உடல் மற்றும் தலைப்புகளிலிருந்து தவிர்ப்புப் பட்டியலை உருவாக்குகிறது.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ஆனது முன்னுரிமையின் ஏறுவரிசையில் பாதுகாப்புக் கட்டுப்பாடுகளை இயக்குகிறது:
   - முடக்கப்பட்ட பாதுகாப்புக் கட்டுப்பாடுகள் `skipped` எனப் பதிவு செய்யப்படுகின்றன.
   - ஒவ்வொரு பாதுகாப்புக் கட்டுப்பாட்டின் `preCall` ஆனதும் `modifiedPayload` மூலம் தரவுச்சுமையை மாற்றி எழுதலாம்.
   - முதலில் வரும் `block: true`, சங்கிலியின் செயல்பாட்டை உடனடியாக நிறுத்துகிறது; மேலும் கையாளுநர் பாதுகாப்புக் கட்டுப்பாட்டு நிராகரிப்புப் பதிலை வழங்குகிறார்.
3. மாற்றி எழுதப்பட்டிருக்கக்கூடிய தரவுச்சுமை, கூட்டு வழிப்படுத்தல் மற்றும் அப்ஸ்ட்ரீம் அனுப்புதலுக்குள் செல்கிறது.
4. பதில் உருவாக்கப்பட்ட பிறகு, `guardrailRegistry.runPostCallHooks(...)` ஆனது பதிலின் மீது அதே சங்கிலியை இயக்குகிறது. இங்கு `block: true` என்பது அப்ஸ்ட்ரீம் பதிலைக் கைவிடுகிறது.

விதிவிலக்கை எறியும் பாதுகாப்புக் கட்டுப்பாடுகள் `error: <message>` என்பதுடன் பதிவு செய்யப்பட்டு, `logger.warn` மூலம் பதிவேட்டில் எழுதப்படுகின்றன; ஆனால் சங்கிலி தொடர்ந்து இயங்கும் — இது வடிவமைப்பிலேயே தடையின்றித் தொடரும் அணுகுமுறையாகும்.

## தனிப்பயன் பாதுகாப்புத் தடுப்புகள்

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

படிகள்:

1. `BaseGuardrail`-ஐ நீட்டித்து `src/lib/guardrails/myGuardrail.ts`-ஐ உருவாக்கவும்.
2. `preCall` மற்றும்/அல்லது `postCall`-ஐச் செயல்படுத்தவும்.
3. இறக்குமதி செய்யும் நேரத்தில் பதிவுசெய்யவும் (`registerDefaultGuardrails`-இலிருந்து சேர்க்கவும்) அல்லது
   இயக்க நேரத்தில் `guardrailRegistry.register(...)`-ஐ அழைக்கவும் — அதே இயல்பாக்கப்பட்ட பெயரைக்
   கொண்ட முந்தைய பாதுகாப்புத் தடுப்பை பதிவகம் மாற்றிவிடும்.
4. `tests/unit/`-இன் கீழ் சோதனைகளைச் சேர்க்கவும் (தற்போதுள்ள எடுத்துக்காட்டுகள்:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## சோதனை

அறியப்பட்ட நிலையிலிருந்து தொடங்க, சோதனைகளுக்கு இடையே `resetGuardrailsForTests()`-ஐப் பயன்படுத்தவும்.
காலியான பதிவகத்துடன் தொடங்கி, சோதனையின் கீழுள்ள பாதுகாப்புத் தடுப்புகளை மட்டும்
பதிவுசெய்ய `{ registerDefaults: false }`-ஐ அனுப்பவும். Vision Bridge சார்பு
உட்செலுத்தலை (`deps.getSettings`, `deps.callVisionModel`) ஏற்கிறது; Audio Bridge,
அமைப்புகள், திறன்கள், STT மாதிரித் தேர்வு, நற்சான்றுச் சோதனைகள் மற்றும் படியெடுத்தல்
ஆகியவற்றுக்கான இணையான உட்புகும் புள்ளிகளை வழங்குகிறது. எனவே, சோதனைகள் DB அல்லது
பிணைய அணுகல் இல்லாமலேயே இரு ஓட்டங்களையும் பரிசோதிக்க முடியும்.

- `docs/reference/ENVIRONMENT.md` — முழுமையான சூழல் மாறி மேற்கோள்

## Injection-guard வழித்தட உள்ளடக்கம் & red-team (கட்டம் 8 · தொகுதி D)

பயனர் prompts-ஐ ஏற்கும் அனைத்து வழித்தடங்களையும் injection-guard (`createInjectionGuard` / `withInjectionGuard`) உள்ளடக்குகிறது.
இது `INJECTION_GUARD_MODE`-ஐ மதிக்கிறது (இயல்புநிலை `warn` = பதிவு மட்டும்;
`block` = HTTP 400 `SECURITY_001`-ஐத் திருப்பியனுப்பும்).

| வகை                  | வழித்தடங்கள்                                                                                                                                         | இயல்புநிலை பயன்முறை |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| உரை (தற்போதுள்ளது)   | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn                |
| உருவாக்கம் சார்ந்தது | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn                |
| தரவு                 | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn                |

உரைப் பிரித்தெடுத்தல் (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ஆகியவற்றை உள்ளடக்குகிறது.

**Red-team (இரவுதோறும், `nightly-llm-security.yml`):** `INJECTION_GUARD_MODE=block` நிலையில் ஒவ்வொரு வழித்தடமும்
OWASP-LLM corpus-ஐத் தடுக்கிறது என்பதை promptfoo சரிபார்க்கிறது; garak சோதனைத் தேடல்களை இயக்குகிறது (ரகசியம் இல்லாவிட்டால் தவிர்க்கும்).
ஒருமைத்தன்மைக்காக `moderations` சேர்க்கப்பட்டுள்ளது — block-mode-இல் உள்ள இயக்குநர்கள்
`resolveDisabledGuardrails` வழியாக இதற்கு விலக்கு அளிக்கலாம்.

இரவுநேர பணிப்பாய்வு (`.github/workflows/nightly-llm-security.yml`, cron + கைமுறை
dispatch) இரண்டு பணிகளைக் கொண்டுள்ளது:

- **`promptfoo-guard` (தடுக்கும்)** — `INJECTION_GUARD_MODE=block` உடன்
  `promptfoo eval -c promptfooconfig.yaml`-ஐ இயக்குகிறது. ஒவ்வொரு எதிர்மறைச் சோதனை நிலையும்
  (எ.கா. "முந்தைய அனைத்து அறிவுறுத்தல்களையும் புறக்கணிக்கவும்…", DAN-பாணி jailbreaks), பதிலில்
  `error.code === "SECURITY_001"` இருப்பதை உறுதிசெய்கிறது; அதாவது, பாதுகாப்புத் தடுப்பு உண்மையிலேயே கோரிக்கையை நிராகரித்தது.
- **`garak` (ஆலோசனை சார்ந்தது)** — உள்ளக OmniRoute instance-க்கு
  (`http://localhost:20128/v1`) எதிராக garak `--probes promptinject,dan,leakreplay`-ஐ இயக்குகிறது.
  இது வழங்குநர் ரகசியத்தை (`PROMPTFOO_PROVIDER_KEY`) சார்ந்தது; ரகசியம் இல்லாவிட்டால்
  சீராகத் தவிர்க்கப்பட்டு `|| true` பின்னொட்டுடன் இயக்கப்படும், எனவே CI-ஐத் தோல்வியடையச் செய்யாமல் அறிக்கையிடும்.

பாதுகாப்புத் தடுப்பு உதவிக்கருவியின் (`createInjectionGuard` / `withInjectionGuard`)
உள்ளடக்கம் prompt கொண்ட ஒவ்வொரு `/v1` வழித்தடத்தையும் உள்ளடக்குகிறது; prompt உரை
`src/shared/utils/inputSanitizer.ts`-இல் உள்ள `extractMessageContents()` மூலம்
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ஆகியவற்றிலிருந்து பெறப்படுகிறது.
