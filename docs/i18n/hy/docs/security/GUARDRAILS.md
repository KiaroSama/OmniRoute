> **Ճշմարտության աղբյուր՝** `src/lib/guardrails/`
> **Վերջին թարմացումը՝** 2026-08-29 — v3.8.51 (Video Bridge-ի տրանսկրիպտի ծագումը հայտարարում է կանչողը,
> և այն դեռ չի ստուգվում սերվերի կողմից — հստակեցվել է ըստ #11661-ի)

Պաշտպանիչ սահմանափակումներն ապահովում են անվտանգությունը, քաղաքականությունների կիրառումը և բովանդակության փոխակերպումները
OmniRoute-ի ու վերին մակարդակի մատակարարների միջև ընկած սահմանագծում։ Յուրաքանչյուր պաշտպանիչ սահմանափակում կարող է ստուգել (և
ըստ անհրաժեշտության մերժել, փոխակերպել կամ ծանոթագրել) հարցման օգտակար բեռները (`preCall`) և
վերին մակարդակի պատասխանները (`postCall`)։

Համակարգը գործում է **fail-open** սկզբունքով․ եթե պաշտպանիչ սահմանափակման կատարման ընթացքում բացառություն է առաջանում, ռեեստրը
գրանցում է սխալը և հարցումը ձախողելու փոխարեն շարունակում է հաջորդ պաշտպանիչ սահմանափակմամբ։
Արգելափակումը միշտ բացահայտ որոշում է (`block: true`) և երբեք՝ պատահականություն։

## Ներկառուցված պաշտպանիչ մեխանիզմներ

Ներմուծման ժամանակ ռեեստրը առաջնահերթության կարգով ինքնաշխատ բեռնում է վեց պաշտպանիչ մեխանիզմ
(տե՛ս `registry.ts` → `registerDefaultGuardrails()`).

| Առաջնահերթություն | Անուն               | Փուլ(եր)       | Ֆայլ                  |
| ----------------- | ------------------- | -------------- | --------------------- |
| `5`               | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`               | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`               | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`              | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |

| `95`              | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

Ավելի ցածր առաջնահերթության համարները կատարվում են **առաջինը**։

### Տեսողական կամուրջ (`visionBridge.ts`) — Մոդալության կամուրջ PR-1

Ընդհատում է պատկերներ պարունակող՝ **տեսողական հնարավորություններ չունեցող մոդելներին** ուղղված հարցումները և կամ ամբողջ հարցումը վերահասցեավորում է տեսողական հնարավորություններով մոդելի, կամ վերին մակարդակի կանչից առաջ պատկերային մասերը փոխարինում է կարգավորվող տեսողական մոդելի ստեղծած տեքստային նկարագրություններով։ Սա միայն տեքստային մատակարարներին թույլ է տալիս թափանցիկորեն մշակել բազմամոդալ տվյալները։

Ընթացքը՝

1. Բաց թողնել, եթե թիրախային մոդելն արդեն աջակցում է տեսողական մուտքագրումներին (բացառությամբ այն դեպքերի, երբ այն ներառված է հարկադիր կամրջման `isVisionBridgeForcedModel` ցանկում)։
2. Արտահանել պատկերային մասերը `extractImageParts(messages)`-ի միջոցով
   (`visionBridgeHelpers.ts`), որն աշխատանքը պատվիրակում է `open-sse/utils/mediaParts.ts`-ում գտնվող **մեդիայի միասնական հայտնաբերիչին**՝ `detectMediaParts()`-ին։ Այն ճշմարտության միակ աղբյուրն է, որը համատեղ օգտագործվում է կոմբո համատեղելիության զտիչի հետ։ Արտահանումը թույլատրված է միայն վերին մակարդակի այն ձևերի համար, որոնք
   `replaceImageParts`-ը կարող է կրկին տեղադրել (extract↔replace պայմանագիր)՝ OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` և Responses API `input_image`։ Ներդրված համընկնումներն ու
   միայն ցուցիչ պարունակող ձևերը կոմբո զտիչի նյութ են և երբեք չեն արտահանվում։
   Բաց թողնել, եթե ոչինչ չի գտնվել։
3. Աշխատաժամանակային կազմաձևը որոշել `resolveVisionBridgeRuntimeSettings()`-ի միջոցով
   (`src/shared/constants/modalityBridgeDefaults.ts`)՝ նոր `modalityBridge*`
   կարգավորումների բանալիներն ունեն գերակայություն, իսկ հին `visionBridge*` բանալիները մնում են որպես **մեկ շրջափուլի
   պահուստային տարբերակ** (հետշրջման պատուհան)։ Նախքան մեդիայի որևէ շրջանցում՝ բաց թողնել, եթե
   կամուրջն անջատված է։
4. Ռեժիմի ընտրիչը (`modalityBridgeVisionMode`, տե՛ս ստորև բերված աղյուսակը) որոշում է՝
   վերահասցեավորել, թե նկարագրել։ Վերահասցեավորումը վերադարձնում է `modifiedPayload`, որտեղ փոխարինված է միայն `model`-ը,
   ինչպես նաև `{ rerouted, fromModel, toModel, imagesKept }` մետատվյալները։
5. Նկարագրման ուղի՝ պատկերների թիվը սահմանափակել `maxImages`-ով, կազմել առաջադրանքը հաշվի առնող հուշումը,
   ստուգել նկարագրությունների շտեմը, **զուգահեռաբար** կանչել տեսողական մոդելը
   (`Promise.allSettled`) և պատկերների փոխարեն ներարկել `[Image N]: <description>` տեքստային մասերը։
   Ձախողված նկարագրումը տալիս է `null`, իսկ պատկերի սկզբնական մասը
   **պահպանվում է** (#4012)։ Բացառություն է կոմբո նկարագրման ուղին, երբ բոլոր
   նկարագրումները ձախողվել են. այդ դեպքում հաստատապես տեսողական հնարավորություններ չունեցող վերին մակարդակի համակարգն ստանում է
   `(unavailable — no vision-capable provider connected)` փոխարինող տեքստը (#8430)։
6. Վերադարձնել `modifiedPayload`-ը և մետատվյալները (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`)։

#### Ռեժիմի ընտրիչ (`modalityBridgeVisionMode`)

| Ռեժիմ      | Լռելյայն | Վարքագիծ                                                                                                                                                                                                                                                                                                                        |
| ---------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔        | Հին էվրիստիկան՝ անփոփոխ (#6640/#7204). ոչ կոմբո/`auto/` մոդելները վերահասցեավորվում են լավագույն տեսողական մոդելին, եթե սկզբնական մոդելն արդեն չունի օգտագործելի հավատարմագրեր (այդ դեպքում կատարվում է նկարագրում)։ Կոմբո թիրախները միշտ նկարագրվում են։                                                                       |
| `describe` |          | Միշտ նկարագրել. վերահասցեավորման բլոկն ամբողջությամբ բաց է թողնվում, և միշտ պատասխանում է օգտատիրոջ ընտրած մոդելը։                                                                                                                                                                                                              |
| `reroute`  |          | Հարկադիր վերահասցեավորում. հավատարմագրված մոդելը պահպանող սահմանափակումը շրջանցվում է։ Վերահասցեավորման **թիրախի** հավատարմագրերի սահմանափակումը շարունակում է գործել. երբ օգտագործելի տեսողական թիրախ չկա, հարցումն անցնում է նկարագրման ուղուն, որպեսզի չմշակված պատկերները երբեք չհասնեն միայն տեքստային հետնամասին (#8430)։ |

Հարկադիր ռեժիմները կարճ միացմամբ ավարտում են ընտրությունը **մինչև** ավտոմատ էվրիստիկայի գործարկումը։ `auto`-ի վարքագիծը
բայթ առ բայթ նույնական է PR-1-ին նախորդող պաշտպանիչ մեխանիզմի վարքագծին։

#### API բանալու գործողության տիրույթ (`visionBridgeKeyScope.ts`)

Երբ կանչողի API բանալին սահմանափակում է `allowedConnections`-ը, քվոտաների պաշարները
(`allowedQuotas`) կամ մոդելները (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), կամուրջն ընտրում է միայն
այն վերահասցեավորման և նկարագրման մոդելները, որոնք բանալուն թույլատրված է օգտագործել՝ այն կապերի միջոցով, որոնք բանալուն
թույլատրված է օգտագործել։ Այնուհետև նկարագրման կանչը միշտ անցնում է OmniRoute ինքնահղման միջոցով՝
`x-omniroute-self-loop-key-id` վերնագրով, որպեսզի ընդունող զրույցի հարցումը
կրկին կիրառի այդ բանալու կապերի և մոդելների քաղաքականությունը։ `enforceApiKeyPolicy()`-ն
այդ վերնագիրը հաշվի է առնում միայն ինքնահղման bearer-ի հետ միասին, ուստի այն կարող է
միայն նեղացնել հասանելիությունը, իսկ չգտնվող նույնացուցիչը մերժվում է։

Եթե բանալու համար ոչ մի տեսողական մոդել թույլատրված չէ, նկարագրման ուղին մի կողմ է քաշվում, և
հարցումն անցնում է անփոփոխ՝ նույն fail-open վարքագծով, ինչ անջատված
պաշտպանիչ մեխանիզմի դեպքում (մետատվյալներ՝ `{ skipped: true, reason: "no_permitted_vision_model" }`)։
Առանց բանալու հարցումները և այս սահմանափակումները չունեցող բանալիները գործում են ճիշտ այնպես, ինչպես
նախկինում։

#### Առաջադրանքը հաշվի առնող նկարագրման հուշում (`modalityBridgeVisionTaskAware`)

Լռելյայն՝ **true**։ `composeVisionPrompt()`-ը (`visionBridgeHelpers.ts`) հիմնական
նկարագրման հուշմանը կցում է **օգտատիրոջ վերջին հաղորդագրության** տեքստը
(կրճատված մինչև 500 նիշ)՝ նկարագրությունն ուղղորդելով դեպի այն, ինչ իրականում
հարցրել է օգտատերը (codex-vision-proxy ձևանմուշ), և տեսողության մոդելին խնդրելով
արտագրել տեսանելի տեքստը։ Եթե դրոշն անջատված է, կամ օգտատիրոջ տեքստ չկա,
հիմնական հուշումն օգտագործվում է անփոփոխ։

Նկարագրման ինքնաշրջանի սեփական OpenAI-համատեղելի հարցումը (`callVisionModelSingle()`
ֆունկցիան `visionBridgeHelpers.ts`-ում) միշտ պահանջում է
`image_url.detail: "high"`՝ անվերապահորեն, յուրաքանչյուր կանչողի/մատակարարի
համար, առանց հաճախորդի որևէ ազդանշանից կախված լինելու։ Ցածր մանրամասնությամբ
ընտրանքավորումը նվազեցնում է OCR-ի ճշգրտությունը հենց այն տեքստի արտագրման
առաջադրանքի համար, որը պահանջում է այս հուշումը, ուստի նկարագրման կանչն ինքնին
միշտ պահանջում է բարձր մանրամասնություն՝ անկախ սկզբնական մուտքային հարցման
օգտագործած մանրամասնության մակարդակից։ Սա ազդում է միայն ներքին նկարագրման
հարցման մարմնի վրա և չի փոխում այն, թե ինչպես է OmniRoute-ը հիմնական հարցման
ժամանակ փոխանցում կանչողի սեփական `image_url.detail`-ը․ այդ լռելյայն արժեքը
կիրառվում է առանձին և միայն հայտնաբերված OpenCode հաճախորդների համար՝
`defaultImageDetail()`-ում (`open-sse/handlers/chatCore/upstreamBody.ts`)։
Նկարագրման ինքնաշրջանի Anthropic հաղորդալարային ձևաչափի ճյուղը `detail` դաշտ
չունի և այս լռելյայն արժեքներից ոչ մեկի ազդեցությունը չի կրում։

#### Նկարագրման ելքի սահմանաչափ (`modalityBridgeVisionMaxChars`)

| Բանալի                         | Լռելյայն | Միջակայք          |
| ------------------------------ | -------- | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`      | `0` կամ 100–50000 |

`0`-ն (լռելյայն) նշանակում է՝ **սահմանաչափ չկա**․ `callVisionModel()`-ի
վերադարձրած նկարագրությունը փոխանցվում է անփոփոխ՝ պահպանելով առկա վարքագիծը։
100–50000 միջակայքի ցանկացած արժեք կրճատում է նկարագրությունը՝ ավելացնելով `…`
վերջածանց, նախքան այն կրկին `[Image N]: <description>` ձևով տեղադրելը
(`VisionBridgeGuardrail.preCall()`՝ `src/lib/guardrails/visionBridge.ts`-ում)։
Բարձրացրեք այս արժեքը մանրամասներով հարուստ OCR առաջադրանքների համար, երբ
հաջորդ մոդելին անհրաժեշտ է ամբողջական արտագրությունը, իսկ շատախոս տեսողության
մոդելների թոքենների օգտագործումը սահմանափակելու համար՝ նվազեցրեք այն։
Կառավարման վահանակի դաշտը գտնվում է Vision ներդիրի Advanced վահանակում
(`modality-bridge-max-chars`՝ `ModalityBridgeVisionTab.tsx`-ում) և 1-ից 99
միջակայքի ցանկացած արժեք բարձրացնում է մինչև նվազագույն 100-ը՝ միաժամանակ
անփոփոխ թողնելով հստակ նշված `0`-ն։ `0`-ն ինքնին վավեր Zod արժեք է
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), այլ ոչ թե
պարզապես «չսահմանված» լռելյայն արժեք։

#### Նկարագրման քեշ (`modalityBridge/bridgeCache.ts`)

Նկարագրման ելքերի համար հիշողության մեջ պահվող LRU + TTL քեշ, որն ընդհանուր է
ամբողջ գործընթացի համար։
Բանալի = `sha256(imageRef + composedPrompt + configuredBridgeModel)`՝
երկարության նախածանցով շրջանակմամբ (դաշտերի սահմանների բախումներ չկան)։ Մոդելի
բաղադրիչը **կարգաբերված** կամրջային մոդելն է, այլ ոչ թե իրականում պատասխանած
մոդելը․ `callVisionModel`-ը կարող է ներքին կերպով օգտագործել պահուստային տարբերակ,
իսկ յուրաքանչյուր փորձի հիման վրա բանալի ստեղծելը կմասնատի քեշը։ Ձախողված
նկարագրումները երբեք չեն քեշավորվում։ Կարգավորումներ՝

| Բանալի                          | Լռելյայն | Միջակայք |
| ------------------------------- | -------- | -------- |
| `modalityBridgeCacheEnabled`    | `true`   | —        |
| `modalityBridgeCacheTtlMinutes` | `60`     | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`    | 10–5000  |

#### Հեռակա պատկերների նորմալացում (ինքնաշրջանի նկարագրում/base64 առբերում)

Երբ կամուրջն ինքն է առբերում **հեռակա** պատկեր՝ Anthropic նկարագրման ինքնականչի
և claude հաղորդալարային ձևաչափի base64 փոխակերպման
(`ensureBase64ImagesForClaudeWire`) համար, երկու դեպքում էլ
`visionBridgeHelpers.ts`-ի `fetchRemoteImageAsDataUri()`-ի միջոցով, ստացված
տվյալների URI-ն, նախքան տեսողության մոդելի հարցման մեջ ներառվելը, փոխանցվում է
`normalizeDataUri()`-ով (`open-sse/utils/imageNormalize.ts`)։ Չափազանց մեծ
պատկերները փոքրացվում են մինչև **2048px երկար եզր** (համապատասխանելով չափափոխման
այն սահմանաչափին, որն OpenAI-ը/Anthropic-ը արդեն կիրառում են սերվերային կողմում),
ինչը նվազեցնում է վերբեռնվող բայթերի քանակը/ուշացումը՝ առանց փոխելու այն, ինչ
տեսնում է տեսողության մոդելը։ Չափափոխման համար օգտագործվում է `sharp`-ը, որը
բեռնվում է դինամիկ ներմուծման միջոցով․ այն հարթակում, որտեղ դրա բնիկ բինար
ֆայլը չի բեռնվում, `normalizeDataUri()`-ն **երբեք բացառություն չի նետում**․ այն
հետ է անցնում սկզբնական բայթերի անփոփոխ փոխանցմանը, այնպես որ նկարագրման/base64
փոխակերպման ուղին միշտ շարունակում է աշխատել։ Ոչ պատկերային բայթերը (երբ
առբերմամբ չի վերադարձվել ապակոդավորվող պատկեր) նույնպես փոխանցվում են անփոփոխ։
Այս նորմալացումը սահմանափակված է այն պատկերներով, որոնք կամուրջն առբերում է իր
սեփական ինքնականչի համար․ այն երբեք չի կիրառվում կանչողի չմշակված, ուղղակիորեն
փոխանցվող օգտակար բեռի նկատմամբ՝ համաձայն միայն հստակ համաձայնությամբ
փոփոխություններ կատարելու սկզբունքի (Խիստ կանոն #20)։

#### Կարգավորումների սխեմա + միգրացիա

Նոր `modalityBridge*` բանալիները Zod-ով վավերացվում են `updateSettingsSchema`-ում
(`src/shared/validation/settingsSchemas.ts`)՝ `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, `modalityBridgeCache*` եռյակը և Audio Bridge-ի
կողմից օգտագործվող `modalityBridgeAudio*` խումբը։ `141_modality_bridge_settings.sql`
միգրացիան գոյություն ունեցող հին `visionBridge*` արժեքները պատճենում է
համապատասխան նոր բանալիների մեջ (իդեմպոտենտ է և երբեք չի վերագրում օպերատորի
կողմից սահմանված `modalityBridge*` արժեքը)։ Հին բանալիները մեկ թողարկման ցիկլի
ընթացքում շարունակում են ընդունվել որպես ընթերցման պահուստային տարբերակ։

#### Թափանցիկության վերնագիր + վիճակագրություն

Նկարագրմամբ փոխակերպված պատասխանները պարունակում են
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(ստեղծվում է `buildModalityBridgeHeader()`-ի միջոցով
`modalityBridge/bridgeStats.ts`-ում և դրոշմվում է `withModalityBridgeHeader()`-ի
միջոցով `src/sse/handlers/chatHelpers.ts`-ում)։ Վերաուղղորդված հարցումները
**չեն** ստանում վերնագիր․ օգտակար բեռը չի փոփոխվել, իսկ մոդելի փոխարինումն արդեն
տեսանելի է պատասխանի մարմնի `model` դաշտում։

`GET /api/modality-bridge/stats`-ը (կառավարման նույն մակարդակի նույնականացմամբ, ինչ
`GET /api/settings`-ը) վերադարձնում է հիշողության մեջ պահվող՝ ըստ մոդալության հաշվիչները՝
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }`՝ `vision`, `audio` և
`video` մոդալությունների համար։ `averageLatencyMs`-ը որպես հայտարար օգտագործում է
`latencySamples`-ը, այլ ոչ բոլոր փորձերի քանակը․ ժամանակի չափում չունեցող գործողությունը
չի ստեղծում կեղծ՝ զրո միլիվայրկյան տևողությամբ նմուշ։
`bridged`-ը մնում է հաջող փոխակերպումների հետընթաց համատեղելի կեղծանունը․
անհաջող փորձերը չեն ավելացնում դրա արժեքը։
Ըստ նախագծման՝ հաշվիչները զրոյացվում են պրոցեսի վերագործարկման ժամանակ
(հեռաչափություն, ոչ թե հաշվառում)։

#### Վահանակի կազմաձևում

Վահանակի հատուկ էջը գտնվում է
`/dashboard/settings/modality-bridge` հասցեում։ Դրա՝ URL-ով հասցեավորվող `Vision`, `Audio`
և `Video` ներդիրները `tab`-ի արժեքը փոխելիս պահպանում են հարցման պարամետրերը։
Vision ներդիրը հասանելի է դարձնում միացումը, ռեժիմը, մոդելի ընտրությունը (ներառյալ
ինքնաշխատ լռելյայն տարբերակը), առաջադրանքը հաշվի առնող հուշումները, ընդլայնված՝
սպասման ժամանակի/պատկերի/նկարագրության երկարության/քեշի սահմանաչափերը, կատարման
հաշվիչները և պաշտպանված նմուշային հարցումը։ Audio ներդիրը նույնպես գործուն է․ այն հասանելի
է դարձնում միացումը, միայն STT մոդելների ընտրիչը՝ Auto տարբերակով, սպասման ժամանակի/
հոլովակի առավելագույն տևողության սահմանաչափերը, աուդիո հաշվիչները և `input_audio`
նմուշային փորձարկումը։ Video ներդիրը գործունակ է․ այն հաղորդում է FFmpeg/ffprobe-ի
կատարման միջավայրի վիճակը՝ UI-ի չորս հստակ վիճակներից մեկը (`unknown`, քանի դեռ
ստուգումն ընթացքի մեջ է կամ չի կարող ավարտվել, `restricted`՝ վահանակի ոչ loopback
հոսթում, որտեղ ստուգումը բաց է թողնվում հաճախորդի կողմից, `unavailable`՝ ստուգումից և
բացակայության հաստատումից հետո, կամ `available`՝ FFmpeg/ffprobe-ի տարբերակներով),
պահպանում է միացման/մոդելի/կադրերի/տեսանյութի/սպասման ժամանակի սահմանաչափերը,
մոդելի ընտրիչը զտում է՝ թողնելով պատկերների հետ աշխատելու ունակ մոդելները, և հասանելի
է դարձնում տեսանյութի հաշվիչները։

AI-ի կարգավորումների ներքո գտնվող նախկին Vision Bridge քարտը համատեղելիության հղում է
դեպի նոր էջը․ այն այլևս չի պարունակում ձևի երկրորդ պատճենը։ Media Providers-ը նաև
Image-to-Text և Speech-to-Text աշխատանքային հոսքերը կապում է Modality Bridge-ի
համապատասխան ներդիրներին՝ առանց գոյություն ունեցող Speech-to-Text փորձադաշտը հեռացնելու։

**Ինքնահանգույցի ընդունման շրջանցում․** երբ նկարագրման կանչը երթուղավորվում է OmniRoute-ի
սեփական `/v1` ինքնահանգույցով (ոչ ստանդարտ մատակարարի մոդել), ենթահարցումն ուղարկում է
`x-omniroute-admission-bypass: internal` և նույնականացվում է լուծված ինքնահանգույցի
հավաստագրով՝ տեղային ռեժիմում տեղային `sk_omniroute` սենտինելով, կամ օպերատորի կողմից
կազմաձևված `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` միջավայրի բանալիով (#1350), որպեսզի
`REQUIRE_API_KEY=true` տեղակայումները ևս կարողանան կատարել նկարագրման կանչը։ Շրջանցումը
հարգվում է միայն հենց այդ հավաստագրերի համար, ուստի արտաքին հաճախորդները չեն կարող
օգտագործել վերնագիրը՝ ընդունման ստուգումը շրջանցելու համար։

Հին լռելյայն արժեքները գտնվում են `src/shared/constants/visionBridgeDefaults.ts`-ում,
իսկ նոր ռեժիմի/առաջադրանքը հաշվի առնելու/քեշի լռելյայն արժեքներն ու կարգավորումների
լուծիչը՝ `src/shared/constants/modalityBridgeDefaults.ts`-ում։ Պաշտպանիչ սահմանափակիչը
հասանելի է դարձնում `deps` կառուցչի ընտրանքը, որպեսզի թեստերը կարողանան ներարկել կեղծ
`getSettings` և `callVisionModel` իրականացումներ։

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Ընդհատում է աուդիո պարունակող զրույցի հարցումները՝ նախքան դրանք կհասնեն այնպիսի թիրախի,
որի՝ աուդիո մուտք ընդունելու ունակությունը հայտնի չէ։ Այն երբեք չի վերաերթուղավորում
զրույցի հարցումը․ աուդիո մասերը վերծանվում են գոյություն ունեցող՝ OpenAI-ի հետ համատեղելի
բազմամաս վերջնակետի միջոցով, իսկ ընտրված զրույցի մոդելը շարունակում է աշխատանքը
տեքստային վերծանումներով։

Հոսքը՝

1. Լուծել `supportsAudio`-ն `getResolvedModelCapabilities()`-ի միջոցով։ Նախապատվությունը
   տրվում է մատակարարների ռեեստրի հստակ մետատվյալներին, ապա՝ մոդելի ստատիկ
   մետատվյալներին, այնուհետև՝ համաժամեցված `modalities_input`-ին։ Հայտարարված մուտքային
   ցանկը, որը չի պարունակում `audio`, նշանակում է `false`, իսկ կարողության վերաբերյալ
   ապացույցի բացակայության դեպքում արժեքը մնում է `null`։ Թե՛ `false`-ը, թե՛ `null`-ը
   ակտիվացնում են պահպանողական կամուրջը, իսկ `true`-ը շրջանցում է այն։
2. Լուծել `modalityBridgeAudio*` կարգավորումները և յուրաքանչյուր հաղորդագրությունից
   ընդհանուր `detectMediaParts()` հայտնաբերիչի միջոցով առանձնացնել վերադասավորվող
   վերին մակարդակի աուդիո մասերը։ Աջակցվող փոխանցման ձևաչափերն են OpenAI-ի
   `input_audio`-ն, `audio_url`-ը և `source.media_type: "audio/*"`-ը։ Ներդրված աուդիոն
   հայտնաբերվում է երթուղավորման համար, սակայն չի հեռացվում վերադասավորման ուղու
   միջոցով։ Մշակման ծավալը սահմանափակվում է `modalityBridgeAudioMaxClips`-ով․ հաջորդող
   մասերը մնում են անփոփոխ։
3. Հարգել կազմաձևված `provider/model`-ը կամ թույլ տալ, որ `selectAudioBridgeModel()`-ը
   կայուն կատալոգային հերթականությամբ շրջանցի `AUDIO_TRANSCRIPTION_PROVIDERS`-ը և ընտրի
   օգտագործելի, ակտիվ մատակարարի հավաստագիր ունեցող առաջին մոդելը։
4. `callAudioTranscription()`-ը base64/data-URI աուդիոն փոխակերպում է բազմամաս `file`-ի
   կամ հեռակա `audio_url`-ը ներբեռնում է միայն հանրային ելքային պաշտպանի միջոցով՝ DNS
   ամրագրմամբ և 25 MB սահմանաչափով։ Այնուհետև այն ֆայլը և ընտրված մոդելը POST հարցմամբ
   ուղարկում է տեղային `/v1/audio/transcriptions` ինքնահանգույցին՝ նույնականացվելով
   `resolveSelfLoopBearer()`-ով։ Վերծանման գոյություն ունեցող երթուղին իրականացնում է
   հավաստագրերի սովորական որոնում, դադարի/հարցումների հաճախականության սահմանաչափի
   մշակում և մատակարարին փոխանցում։
5. Հաջող կանչերն իրենց մասերը փոխարինում են `[Audio N]: <transcript>`-ով։ Կանչերը
   կատարվում են `Promise.allSettled`-ով․ առանձին ձախողման դեպքում պահպանվում է տվյալ
   սկզբնական աուդիո մասը (#4012 պայմանագիր)։ Եթե բոլոր կանչերը ձախողվեն, և ապացուցված է,
   որ թիրախի `supportsAudio === false`, մասերը դառնում են
   `[Audio N]: (անհասանելի է — STT մատակարար միացված չէ)` (#8430 պայմանագիր)։ Անհայտ
   թիրախի (`null`) դեպքում բոլոր կանչերի ձախողման արդյունքը մնում է անփոփոխ։ Ապացուցված՝
   միայն տեքստ աջակցող թիրախը, որի համար օգտագործելի STT հավաստագիր չկա, ստանում է նույն
   հստակ փոխարինիչը՝ առանց ցանցային կանչ կատարելու։

Հաջող վերծանումներն օգտագործում են ամբողջ պրոցեսի համար ընդհանուր Modality Bridge
LRU/TTL քեշը։ Բանալին համադրում է աուդիո հղումը, կայուն `audio-transcription`
գործողության պիտակը և ընտրված STT մոդելը․ ձախողումները երբեք չեն քեշավորվում։ Աուդիոյի
փորձերը թարմացնում են ընդհանուր `bridged`, `cacheHits`, `failures` և `lastUsedAt`
հաշվիչները։ Փոխակերպված պատասխանները պարունակում են
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`․ անփոփոխ
հարցումները Audio Bridge հատված չեն ստանում։

Կատարման միջավայրի կարգավորումները պահվում են DB-ում և վավերացվում են Zod-ով․

| Բանալի                        | Լռելյայն | Միջակայք        |
| ----------------------------- | -------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`   | —               |
| `modalityBridgeAudioModel`    | `""`     | Auto կամ STT ID |
| `modalityBridgeAudioTimeout`  | `60000`  | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`      | 1–10            |

Ընդհանուր քեշը շարունակում է կառավարվել `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` և `modalityBridgeCacheMaxEntries` պարամետրերով։

### Տեսանյութի կամուրջ (`videoBridge.ts`, `videoBridgePipeline.ts`)

Ընդհատում է Chat Completions-ի `messages`-ում և Responses
API-ի `input`-ում վերին մակարդակի տեսանյութային մասերը՝ նախքան հայտնի ներկառուցված տեսանյութային աջակցություն չունեցող թիրախի կանչը։
Աջակցվող ձևաչափերն են `input_video`, `video_url`, `video_source`, HTTPS URL-ները
և `data:video/*;base64,...` տվյալների URI-ները։ Տեքստում առկա սովորական ֆայլանունները
չեն դիտարկվում որպես տեսանյութ։

`VideoBridgeGuardrail.preCall`-ը (`videoBridge.ts`) պատասխանատու է հարցման շրջանցման,
հնարավորությունների/քաղաքականության ստուգման, յուրաքանչյուր հարցման ագրեգացման և պատասխանի օգտակար բեռի համար։
Յուրաքանչյուր տեսանյութի համար կատարվող աշխատանքը՝ ստացումը, ամբողջական արդյունքի քեշավորումը, կադրերի
հաջորդականության նկարագրումը (որը միավորում է կանչողի կողմից հայտարարված ձայնային վերծանումը) և յուրաքանչյուր փորձի
չափումները/ընդհատումը/մաքրումը, թաքցված է `videoBridgePipeline.ts`-ի
`processVideoPart`-ի հետևում, որը `preCall`-ի ցիկլի ներսում կանչվում է մեկ անգամ՝ յուրաքանչյուր տեսանյութային մասի համար։
Այդ մոդուլը նաև սահմանում է բացահայտ պորտային սահմանները՝ `VideoMediaBrokerPort`
(բայթերի ստացում և նմուշառված կադրերի դուրսբերում), `VideoAudioTranscriptionPort`
(կանչողի կողմից հայտարարված ձայնային վերծանման միավորում նմուշառված ենթագրերի հետ) և
`VideoDrilldownPort` (կադրերի մանրամասն դիտարկման պահպանման սահմանը, որը դեռևս միացված չէ
`processVideoPart`-ին. ներկայումս միայն առանձին `/api/modality-bridge/video/drilldown`
ուղին է գրանցում մանրամասն դիտարկման գրառումները)։

Հանրային `/v1` հարցման ուղին երբեք չի ներմուծում կամ կանչում ենթագործընթաց։
Հեռակա տեսանյութերը ներբեռնվում են 50 MiB սահմանաչափով, իսկ ներկառուցված base64 տեսանյութերի համար կիրառվում է
պահպանողական՝ յուրաքանչյուր տեսանյութի ապակոդավորված տվյալների 36 MiB սահմանաչափ, որպեսզի մոդելի/messages/շրջանակավորման փաթեթը
կարողանա մնալ հանրային JSON հարցումների ընդունման 50 MiB սահմանաչափի ներսում։ Ներկառուցված տվյալների
երկարությունն ու ապակոդավորված չափի գնահատականները ստուգվում են նախքան հիշողության հատկացումը։ HTTPS-ը
պարտադիր է սկզբնական հեռակա URL-ի և յուրաքանչյուր վերահղման համար՝ օգտագործելով առկա
միայն հանրային ելքային հարցումների պաշտպանիչ մեխանիզմը՝ DNS ամրագրմամբ։ Այնուհետև բայթերը հատում են ճշգրիտ ներքին
`POST /api/modality-bridge/video/extract` բրոքերային սահմանը։ Այդ ուղին միաժամանակ
`LOCAL_ONLY` և `SPAWN_CAPABLE` է, ընդունում է միայն տվյալ գործընթացի համար իսկորոշված,
վստահելի loopback հարցում և երբեք չի ընդունում URL, ֆայլային համակարգի ուղի, գործարկվող ֆայլ
կամ արգումենտների ցանկ։ API-ի մարմնի չափի մշակման շղթան և մշակիչի՝ մարմնի փուլային ընթերցիչը
միմյանցից անկախ պարտադրում են բրոքերի մուտքային տվյալների 50 MiB սահմանաչափը։ Դրա սահմանափակ հերթը
միաժամանակ կատարում է մեկ արտահանում, թույլատրում է սպասող չորս առաջադրանք և սպասող մուտքային տվյալները
սահմանափակում է 100 MiB-ով։

Բրոքերի ներսում `ffprobe`-ը կարդում է մասնավոր տեղային ֆայլ, իսկ ձևաչափերի ֆիքսված
թույլատրելի ցանկը բացառում է երգացանկերի և մանիֆեստների ձևաչափերը։ Թույլատրված MOV ընտանիքի
կոնտեյներների համար արտաքին MOV տվյալների հղումները լռելյայն մնում են անջատված, և
ֆիքսված հրամանը չի միացնում դրանք։ Թե՛ `ffprobe`-ը, թե՛ `ffmpeg`-ն օգտագործում են միայն
`file` արձանագրության թույլատրելի ցանկ, մեկ հոսք, արգումենտների ֆիքսված զանգվածներ, առանց shell-ի,
իսկ գործարկվող ֆայլերը որոշվում են `PATH`-ից։ Կցված նկարի կազմի հոսքերը չեն համարվում
նվագարկելի թեկնածուներ։ Բոլոր նվագարկելի հոսքերը պետք է բավարարեն սահմանաչափերը, և
բացահայտ լռելյայն հոսքը նախընտրելի է դետերմինացված՝ ամենացածր ինդեքսով պահուստային տարբերակից։
Տեսանյութերը սահմանափակված են 600 վայրկյանով, յուրաքանչյուր չափության համար՝ 8,192 պիքսելով և
սկզբնաղբյուրի 33,554,432 պիքսելով։ FFmpeg-ը նմուշառում է 1–16 միջնակետային JPEG կադր, փոքրացնում է
երկար եզրը մինչև առավելագույնը 1,024 պիքսել՝ առանց ավելի փոքր մուտքային տվյալները մեծացնելու, և
երբեք URL չի ստանում։ Նմուշառումը լռելյայն `uniform` է։ Ընտրովի
`scene_aware` և փորձարարական `segment_aware` քաղաքականությունները կատարում են մեկ լրացուցիչ
ֆիքսված FFmpeg անցում արդեն վավերացված տեղային հոսքի վրայով, ընտրում են սահմանափակ
`showinfo` տեսարանների ժամանակային նշումներ և դետեկտորի խափանման, ժամանակի սպառման, սխալ ձևաչափված ելքի կամ թեկնածուների դատարկ
բազմության դեպքում դետերմինացված կերպով վերադառնում են նույն հավասարաչափ միջնակետերին։
Հատվածներին իրազեկ ռեժիմը միջնակետային նմուշները բաշխում է վավերացված տեսարանային միջակայքերին համամասնորեն։
Հատվածներին իրազեկ ապացույցները և պահուստային վարքագիծը
մանրամասն նկարագրված են ստորև։ 16 կադրի խիստ սահմանաչափը
բոլոր քաղաքականություններում կիրառվում է ընտրությունից հետո։ Երբ տեսարաններին իրազեկ հարցումն ունի ընդամենը
մեկ կադրի բյուջե, այն օգտագործում է ակտիվ ամբողջական տեսանյութի կամ կենտրոնացման
պատուհանի հավասարաչափ միջնակետը և հաղորդում է `policyEffective: uniform`․ ընտրված մեկ տեսարանային կադրը
չի կարող պահպանել ժամանակային երկու ծայրերը։ Կանչողը կարող է ընտրովի տրամադրել
վերջավոր կենտրոնացման պատուհան (`start`/`end` վայրկյաններով)։ Սահմանները հարմարեցվում են մեդիայի
տևողությանը, հակադարձված կամ ոչ վերջավոր պատուհանները մերժվում են, իսկ նմուշառման
բոլոր քաղաքականությունները կատարվում են միայն նորմալացված միջակայքի ներսում։ Ստացված
պատուհանը ներառվում է նմուշառման մետատվյալներում և չվստահված նկարագրության
նախածանցում, որպեսզի ստորին մակարդակի մոդելները կարողանան տարբերակել կենտրոնացված հատվածն ամբողջական
ժամանակագծից։

Ենթագրերի իմաստային կենտրոնացումը առանձին, բացահայտ կարգավորում է։ Լռելյայն `full`
վերլուծության ռեժիմը պահպանում է կադրի առկա հուշումը և երբեք հարցման տեքստը չի փոխանցում
ենթագրերի մոդելին։ `focused` ռեժիմում կամուրջը նույն Chat կամ Responses
կոնտեյներից կարդում է միայն օգտատիրոջ գրած վերջին ոչ դատարկ `text`/`input_text`-ը,
նորմալացնում է այն NFC-ի, միավորում է կառավարման նիշերն ու բացատները
և սահմանափակում է 500 Unicode կոդային կետով։ Դատարկ արդյունքի դեպքում այն վերադառնում է
ճշգրիտ `full` հուշմանը։ Օգտագործելի հուշումը սերիալացվում է որպես JSON՝
չվստահված օգտատիրոջ համատեքստի առանձին բլոկում և կարող է միայն առաջնահերթություն տալ դիտարկելի
մանրամասներին։ Այն չի կարող շրջանցել մեդիայում տեսանելի կամ լսելի հրահանգներին
չհետևելու առանձին նախազգուշացումը։ Տեքստային կենտրոնացումը երբեք չի ենթադրում `start`/`end` և չի փոխում
ժամանակային նմուշառիչը։

#### FU-07-ի կառուցվածքային հատվածների ապացույցներ

`segment_aware`-ն օգտագործում է արդեն վավերացված տեղային տեսահոսքի մեկ սահմանափակ նախնական վերլուծության անցում։ Ֆիքսված զտիչների շղթան նախ լայնությունը նվազեցնում է առավելագույնը մինչև 320 պիքսել, հայտնաբերում է տեսարանների փոփոխություններն ու սառեցված միջակայքերը, ապա վայրկյանում 1 կադր հաճախականությամբ նմուշառում է լղոզվածությունը, միջին լուսավորությունը և տարածական/ժամանակային տեղեկությունը։ Անցումը սահմանափակված է 600 կառուցվածքային նմուշով, մեկ FFmpeg/զտիչ հոսքով, նույն՝ միայն `file` արձանագրության և կոնտեյներների թույլատրելի ցանկերով, գործընթացի ելքի 1 MiB սահմանաչափով և բրոքերի համատեղ ընդհատման/վերջնաժամկետի շրջանակում առավելագույնը 30 վայրկյանով։ Այն հարցումից երբեք չի ընդունում հրաման, զտիչ, ուղի կամ URL։

Կառուցվածքային արժեքները որոշարկված նմուշառման ապացույցներ են, ոչ թե տեսանյութի իմաստային ըմբռնում։ Դրանք չեն եզրակացնում սուբյեկտները, գործողությունները, ենթագրերը, խոսքը կամ օգտատիրոջ մտադրությունը։ Տեսարանների և սառեցումների սահմանները ձևավորում են հատվածներ․ սառեցման ծածկույթը, լղոզվածությունը, լուսակայումը, տարածական մանրամասնությունը և ժամանակային փոփոխությունն ազդում են միայն այն բանի վրա, թե ինչպես է բաշխվում կադրերի առկա 1–16 բյուջեն։ Ամբողջությամբ սառեցված հատվածը սահմանափակվում է մեկ կադրով, իսկ չսառեցված հատվածները մրցում են մնացած բյուջեի համար։ Երբ սահմանների քանակը գերազանցում է կադրերի քանակը, պահպանվում է ժամանակագծի հավասարաչափ ծածկույթը, որպեսզի սկզբի արագ անցումները չկարողանան թաքցնել երկար եզրափակիչ հատվածը։ Սառեցման սահմանից 1-վայրկյանանոց վերլուծության լուծաչափի սահմաններում գտնվող տեսարանների սահմանները միավորվում են։

Բացակայող զտիչների, սխալ ձևավորված/դատարկ ապացույցների, հայտնաբերիչի սխալի կամ սահմանափակ նախնական վերլուծության ժամանակի սպառման դեպքում համակարգը բաց կերպով հետ է անցնում ճշգրիտ համաչափ միջնակետերի քաղաքականությանը։ Կանչողի ընդհատման կամ բրոքերի վերջնաժամկետի դեպքում բաց հետանցում չի կատարվում․ ընթացիկ ենթագործընթացը դադարեցվում է, հետագա կադրերի արտահանումը կանխվում է, իսկ մասնավոր ժամանակավոր ծառը հեռացվում է `finally`-ում։

`scripts/perf/video-bridge-fu07-eval.ts`-ը ստեղծում է որոշարկված իրական FFmpeg փորձանմուշներ՝ ապակրկնապատկումից հետո ենթագրման կանչերի խնայողության, խիտ շարժման բյուջեի բաշխման, լղոզվածության/լուսակայման/SI-TI ապացույցների, երկար եզրափակիչ հատվածով արագ անցումների և աստիճանական խամրման կեղծ դրական արդյունքների համար։ Այն գրանցում է նախնական վերլուծության իրական անցած ժամանակը և, երբ `/usr/bin/time`-ը հասանելի է, ենթագործընթացի CPU-ն ու RSS-ի գագաթնակետը։ Դրա որակի ստուգումները միայն կառուցվածքային չափորոշիչներ են։ Իրական ենթագրման մոդելի որակը մնում է `HOLD`, քանի որ այս փորձարկման միջավայրը չունի լիազորված վերջնակետ կամ սառեցված գնահատիչ։ Դրամական խնայողությունները նույնպես մնում են `HOLD`, եթե `--caption-cost-per-call-usd`-ը չի տրամադրում մեկ կանչի համար հստակ դրական ծախսային գնահատական․ սկրիպտը երբեք չի հորինում այդ արդյունքներից որևէ մեկը։

Յուրաքանչյուր կադր սահմանափակված է 4 MiB-ով, բոլոր չմշակված կադրերը միասին՝ 23 MiB-ով, իսկ բրոքերի սերիականացված պատասխանը՝ 32 MiB-ով։ Մասնավոր ժամանակավոր գրացուցակը հեռացվում է `finally`-ում։ OmniRoute-ը չի ներառում FFmpeg-ը և չի ընդունում կատարվող ֆայլի հատուկ ուղի։ Ենթագրումից առաջ կամուրջը կիրառում է պահպանողական տեսողական ապակրկնապատկման անցում․ յուրաքանչյուր JPEG վերածվում է 16×16 մոխրագույնի բուֆերի և համեմատվում է միայն վերջին պահպանված կադրի հետ։ Մեկ կադրից մեծ պահանջված ենթագրման բյուջեի դեպքում արտահանումը տրամադրում է թեկնածուների սահմանափակ հավաքածու՝ այդ բյուջեից առավելագույնը երկու անգամ մեծ և երբեք ոչ ավելի, քան 16 կադր։ Պահանջված վերին սահմանը կիրառվում է միայն ապակրկնապատկումից հետո, ընդ որում՝ երբ բյուջեն առնվազն երկու է, վերջնական նոսրացման ընթացքում պահպանվում են ընտրված առաջին և վերջին թեկնածուները։ Տարբերակավորված `grayscale-16x16-mean-cells-v2` քաղաքականությունն օգտագործում է միջին լուսավորության տարբերությունից և այն մանրապատկերի բջիջների հարաբերակցությունից մեծագույնը, որոնց նորմավորված տարբերությունն առնվազն 0.05 է։ Կրկնօրինակի շեմը հաստատուն 0.04-ն է, որն ընտրվել է կանխատեսելիության համար, այլ ոչ թե ներկայացվել որպես կատարման ժամանակի կարգավորում։ Այս երկրորդային բարձր հակադրությամբ ազդանշանը պահպանում է փոքր շարժումներն ու տեսանելի տեքստի փոփոխությունները, որոնք միայն միջինի վրա հիմնված համեմատությունը կարող է թաքցնել։ Համեմատիչի կամ ապակոդավորիչի սխալների դեպքում համակարգը բաց կերպով շարունակում է աշխատանքը և պահպանում ծածկույթը։ Ելքային մետատվյալներն առանձնացնում են արտահանված թեկնածուները, հաջողությամբ օգտագործված կադրերը և հեռացված տեսողական կրկնօրինակները։

Հստակորեն նշված տեսանյութի մասը կարող է պահանջել ժամանակային դրոշմանիշերով կոնտակտային թերթ։ Կամուրջը կառուցում է առավելագույնը 4 սյունակով և 16 կադրով JPEG ցանց։ 512-պիքսելանոց յուրաքանչյուր բջիջ իր սկզբնաղբյուրի ժամանակային դրոշմանիշը դրոշմում է ներքևի բարձր հակադրությամբ շերտի վրա, մինչդեռ նույն ժամանակային դրոշմանիշերը պահպանվում են նաև տեքստային մետատվյալներում՝ հետագա կապակցման և աուդիտի համար։ Ամբողջական JPEG-ը շարունակում է սահմանափակված մնալ 32 MiB-ով։ Եթե `sharp`-ը չի կարող ապակոդավորել կամ կազմել ցանցը, կամուրջը հետ է անցնում առանձին JPEG կադրերին․ հաճախորդի ընդհատումը շարունակում է տարածվել թերթի գործողության միջով։

Առաջխաղացման ապացույցները միտումնավոր առանձնացված են սինթետիկ կազմման միկրոհենանիշից։ `scripts/perf/video-bridge-contact-sheet-eval.ts`-ը սահմանում է սխեմայի տարբերակով A/B փորձարկման միջավայր՝ իրական OpenAI-համատեղելի տեսողական մոդելների համար։ Այն չափում է մատակարարի հաղորդած թոքենները, սկզբից մինչև վերջ իրական ուշացումը՝ ներառյալ թերթի կազմումը, մոդելի կանչերի քանակը և մանիֆեստով սահմանված փաստերի պահպանումը։ Մոդելի չմշակված պատասխանները չեն գրվում հաշվետվության մեջ․ պահպանվում են միայն SHA-256 ամփոփագրերը և համընկած փաստերի ID-ները։ Փորձարկման միջավայրը ցանցային կամ վճարովի մոդելի որևէ կանչ չի կատարում, եթե չի փոխանցվել `--execute-real`-ը և կազմաձևված չեն `--model`-ը, `OMNIROUTE_BASE_URL`-ը և `OMNIROUTE_API_KEY`-ը։ Առանց այդ հստակ իրական գործարկման դրա մեքենայաընթեռնելի վճիռը մնում է `HOLD`․ միայն սինթետիկ օգտակար բեռի/կանչերի քանակի չափումները առաջխաղացման ապացույց չեն։

Կանչողները կարող են աջակցվող տեսանյութի մասին կցել ընտրովի `transcript.cues` զանգված, երբ արդեն ունեն ժամանակով համադրված տեքստ։ Յուրաքանչյուր նշում պետք է պարունակի `text`, հետազոտված տևողության սահմաններում վերջավոր `start`/`end` միջակայք և թույլատրելի ցանկում գտնվող `source` (`client`, `embedded` կամ `audio-bridge`)․ `confidence`-ի լռելյայն արժեքը `1` է, և այն պետք է մնա `0`-ի ու `1`-ի միջև։ Ճշգրիտ կրկնվող նշումները միավորվում են։ OmniRoute-ը երբեք չի սկսում տառադարձում այս մետատվյալներից․ վավերացված նշումները՝ սկզբնաղբյուրով, վստահության մակարդակով և միջակայքով, պատճենվում են նկարագրված արդյունքի մեջ և կադրերի ենթագրերի կողքին ցուցադրվում որպես անվստահելի դիտարկումներ։ Անվավեր, միջակայքից դուրս կամ ծագման տեղեկությունից զուրկ տեքստը մերժվում է՝ ենթագրերի հոսքի մեջ խառնվելու փոխարեն։ Հարցման մարմնի տառադարձման երկու ալիքներն էլ տրամադրված ծագումը նորմավորում են `client`-ի, ներառյալ ինքնուրույն հայտարարված `embedded` կամ `audio-bridge` պիտակները։ Միայն սերվերին պատկանող ադապտերը կարող է այդ վստահելի պիտակները նշանակել միայն կոդով հասանելի `trustedSource` արգումենտի միջոցով․ հարցման JSON դաշտը չի կարող հասնել այդ արգումենտին։ Տառադարձման տեքստը մնում է անվստահելի՝ մեդիայից ստացված բովանդակություն՝ անկախ դրա ծագումից, և երբեք չպետք է որոշի թույլտվությունը։

ստեղծվել են տարբեր մոդելներով։ Քեշի համընկնումը կրկին օգտագործում է այդ producer-ի ինքնությունը՝
այն հարցված routing plan-ի անունով վերանվանելու փոխարեն։ Ամբողջ տեսանյութի արդյունքների
քեշը բանալիավորվում է ելքը փոխող յուրաքանչյուր մուտքով՝ prompt-ով, արդյունավետ
մոդելով, նմուշառման քաղաքականությամբ, կադրերի քանակով, իմաստային վերլուծության ռեժիմով, նորմալացված focus hint-ի SHA-256
մատնահետքով, focus window-ով, `transcript`-ով,
`audioTranscript`-ով և contact-sheet դրոշով, ուստի այդ
չափումներից որևէ մեկի փոփոխությունը քեշի անհամընկնում է, ոչ երբեք հնացած արդյունքի կրկնակի օգտագործում։ Տեսողական dedup քաղաքականության
տարբերակը, շեմը և թեկնածու կադրերի սահմանափակ քանակը նույնպես բացահայտ ներառված են
արդյունքների քեշի բանալու և metadata-ի մեջ. հետևաբար քաղաքականության փոփոխությունը չի կարող կրկին օգտագործել հնացած
ամբողջ տեսանյութի նկարագրություն։ Արդյունքների քեշի v4 metadata-ն պահում է ռեժիմն ու
մատնահետքը, բայց երբեք՝ օգտատիրոջ չմշակված առաջադրանքը։ Guardrail metadata-ն հաղորդում է թե՛
հարցված, թե՛ արդյունավետ վերլուծության ռեժիմները. առանց օգտագործելի օգտատիրոջ տեքստի հարցված `focused` ռեժիմը
հաղորդվում է որպես արդյունավետորեն `full`։

Guardrail-ը դուրս է բերում տեսանյութի բոլոր աջակցվող մասերը, բայց նկարագրում է ոչ ավելի, քան
`modalityBridgeVideoMaxVideos`։ Այն թիրախի դեպքում, որի համար ապացուցված է, որ
`supportsVideo === false`, ձախողված և սահմանաչափը գերազանցող տեսանյութերը վերածվում են բացահայտ անվտանգ
տեքստային նշիչների, որպեսզի ոչ մի չմշակված տեսանյութ չպահպանվի։ Երբ հնարավորությունն անհայտ է, այդ մասերը
պահպանում են իրենց տեսանյութի կրիչը. ցանկացած fallback transcript հետևում է վերոնշյալ սահմանափակ տեքստային
փոխակերպմանը։ `supportsVideo === true` ունեցող թիրախները շրջանցում են bridge-ը։
Հաճախորդի հարցման ընդհատման ազդանշանը տարածվում է ներբեռնման, broker queue-ի,
ենթապրոցեսների և մակագրման կանչերի միջով. ընդհատումները կանգ են առնում տեսանյութերի միջև և երբեք fail-open եղանակով
չեն անցկացնում չմշակված մեդիան։

Runtime կարգավորումները պահվում են DB-ում և վավերացվում են Zod-ով.

| Բանալի                              | Լռելյայն    | Միջակայք / վարքագիծ                                                                                                         |
| ----------------------------------- | ----------- | --------------------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | Ընտրովի գործարկման միջավայր, միացվում է ըստ ցանկության                                                                      |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full`-ը պահպանում է ընդհանուր ենթագրերը, իսկ `focused`-ն օգտագործում է սահմանափակ, անվստահելի՝ վերջին օգտատիրոջ համատեքստը |
| `modalityBridgeVideoModel`          | `""`        | Ժառանգում է Vision Bridge-ի մոդելը                                                                                          |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                                        |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware` կամ համամասնական `segment_aware`. դետեկտորի ձախողման դեպքում օգտագործվում է `uniform`              |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                                         |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 մվ                                                                                                              |

Նախկինում պահպանված՝ 120 վայրկյանից մեծ Video սպասման ժամանակի արժեքները
սահմանափակվում են բրոքերի վերջնաժամկետով, իսկ այդ սահմանաչափը գերազանցող նոր
կարգավորումների գրանցումները մերժվում են։
`GET /api/modality-bridge/video/runtime`-ը նախքան իսկորոշումը կամ գործարկման
միջավայրի ստուգումը պահանջում է վստահելի, դրոշմված loopback տեղայնություն,
այնուհետև՝ կառավարման իսկորոշում։ Այն վերադարձնում է միայն `available`-ը,
մաքրված FFmpeg/ffprobe տարբերակները և ֆիքսված պատճառ, երբ գործարկման միջավայրն
անհասանելի է։ Ներքին արտահանման վերջնակետը հանրային վերբեռնման API չէ․ հերթի
գերբեռնվածությունը վերադարձնում է `503`՝ `Retry-After`-ի հետ, կանչողի
անջատումը՝ `499`, իսկ բրոքերի ֆիքսված վերջնաժամկետը՝ `504`։ Փոխակերպված
պատասխանները կենտրոնական `x-omniroute-modality-bridge` վերնագրին ավելացնում են
`video->text;model=<visionModel>;parts=<videos>`՝ առանց Vision կամ Audio
հատվածները հեռացնելու։

### PII քողարկիչ (`piiMasker.ts`)

Գործարկվում է **երկու** փուլերում։

- **`preCall`**-ը կլոնավորում է օգտակար բեռը, շրջանցում `system`, `messages`,
  `input` և `prompt` դաշտերը (ներառյալ սովորական տողային տարրերը) և տողային
  `content`/`text` դաշտերի նկատմամբ կիրառում է `processPII()`-ը
  (`@/shared/utils/inputSanitizer`-ից)։ Երբ `PII_REDACTION_ENABLED=true`,
  հայտնաբերված PII-ն քողարկվում է ելքային օգտակար բեռում։ Սա անկախ է
  `INPUT_SANITIZER_MODE`-ից (որը կառավարում է միայն հուշման ներարկման
  քաղաքականությունը)։ Երբ քողարկումն անջատված է, կանչը գրանցում է
  հայտնաբերումների քանակները՝ առանց բովանդակությունը վերագրելու։
- **`postCall`**-ը ստեղծում է պատասխանի խորը կլոնը, գործարկում
  `sanitizePIIResponse()`-ը և Responses API-ի կառուցվածքի քողարկիչը
  (`maskResponsesOutput` — ընդգրկում է `output_text`-ը և
  `output[].content[].text`-ը)։ Եթե որևէ քողարկում է կատարվում, փոփոխված
  պատասխանը փոխարինում է սկզբնականին։

Պաշտպանիչ սահմանափակիչը երբեք չի արգելափակում․ այն միայն ծանոթագրում է
(`meta.detections`, `meta.redacted`) կամ վերագրում։

#### Ընտրություն ըստ տեսակի, հատուկ օրինաչափություններ և հայտնաբերման հաշվիչներ

**Վահանակ → Կարգավորումներ → Անվտանգություն → PII քողարկում** բաժինն ընտրում է,
թե _ինչն_ է քողարկվում։ Այն չի միացնում քողարկումը․ դրա համար դեռ օգտագործվում
են `PII_REDACTION_ENABLED`-ը (հարցում) և `PII_RESPONSE_SANITIZATION`-ը
(պատասխան + SSE), որոնք երկուսն էլ լռելյայն անջատված են։

- **Ընտրություն ըստ տեսակի** — ներկառուցված id-ները թվարկված են
  `src/shared/constants/piiTypes.ts`-ում (`PII_BUILTIN_TYPES`)։ Չսահմանված
  արժեքը նշանակում է բոլոր տեսակները (այս կարգավորման ստեղծումից առաջ գործող
  վարքագիծը)։ Հարցումների շարժիչի `ssn_us` օրինաչափությունը համապատասխանում է
  `ssn`-ին։ Ձևանմուշները (Նվազագույն, Ստանդարտ, Ֆինանսական, Բրազիլական,
  ԱՄՆ, Ամբողջական) միայն լրացնում են UI-ի նշատուփերը։
- **Հատուկ օրինաչափություններ** — մինչև 20 regex կամ wildcard
  օրինաչափություն (`*` = մինչև 64 ոչ-բացատային նիշ, `?` = մեկ նիշ)։
  Համընկնումները փոխարինվում են `[CUSTOM_REDACTED]`-ով։ Յուրաքանչյուր
  օրինաչափություն անցնում է `compilePiiCustomPattern()`-ով
  (`src/shared/utils/piiCustomPatterns.ts`)․ առավելագույնը 500 նիշ, դրոշները
  սահմանափակված են `g i m s u`-ով, պետք է հաջողությամբ կազմարկվի, անցնի
  `safe-regex` ստուգումը (աղետալի հետընթաց) և չհամապատասխանի դատարկ տողի կամ
  քողարկման տեղապահի։ Չհաջողված օրինաչափությունը մերժվում է և՛ պահպանելիս,
  և՛ փորձարկելիս, իսկ չհաջողված պահպանված տողը գործարկման ժամանակ բաց է
  թողնվում՝ կազմարկվելու փոխարեն։ Հատուկ օրինաչափությունները գործարկվում են
  միայն այն ժամանակ, երբ քողարկումը միացված է։
- **Հայտնաբերման հաշվիչներ** — քանակներ ըստ տեսակի (երբեք ոչ համընկած
  արժեքները), որոնք պահվում են հիշողությունում և վերակայվում վերագործարկման
  ժամանակ (`src/lib/pii/piiDetectionStats.ts`)։ Դրանք աճում են միայն այն
  ժամանակ, երբ քողարկումը միացված է։

Կարգավորումները գտնվում են `key_value` աղյուսակում (`pii_settings` անվանատարածք,
`src/lib/db/piiSettings.ts`) և ընթերցվում են 1 վրկ քեշի միջոցով։ API․

| Մեթոդ  | Ուղի                     | Նպատակ                                                                                     |
| ------ | ------------------------ | ------------------------------------------------------------------------------------------ |
| `GET`  | `/api/settings/pii`      | Դրոշի վիճակ, `enabledTypes`, `customPatterns`, հայտնաբերման հաշվիչներ                      |
| `PUT`  | `/api/settings/pii`      | Փոխարինել `enabledTypes`-ը (`null` = բոլորը) և/կամ `customPatterns`-ը                      |
| `POST` | `/api/settings/pii/test` | Փորձնական գործարկել մեկ օրինաչափություն առավելագույնը 8 ԿԲ նմուշի վրա․ ոչինչ չի պահպանվում |

Երեքն էլ պահանջում են կառավարման իսկորոշում և մարմինը վավերացնում են Zod-ի
միջոցով (`src/shared/validation/schemas/piiSettings.ts`)։

### Հուշման ներարկում (`promptInjection.ts`)

Հայտնաբերում է օգտատիրոջ տրամադրած բովանդակության հակառակորդային կառուցվածքները
և կիրառում կազմաձևված քաղաքականությունը։ Վարքագիծը կառավարվում է միջավայրի
փոփոխականներով և կոնստրուկտորի ընտրանքներով․

| Կարգավորում      | Միջավայրի փոփոխական                                                                                        | Լռելյայն | Ազդեցություն                                                                                                                                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Միացված          | `INPUT_SANITIZER_ENABLED`                                                                                  | `true`   | Երբ `false` է, պաշտպանիչ մեխանիզմը կարճ միացում է կատարում։                                                                                                                                                                    |
| Ռեժիմ            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                            | `warn`   | Ներարկման քաղաքականություն՝ `block`, `warn` կամ `log`։ (`redact`-ն ընդունվում է հետադարձ համատեղելիության համար, սակայն **չի** հեռացնում ներարկման տեքստը․ հարցման PII-ի վերագրումը կառավարվում է `PII_REDACTION_ENABLED`-ով։) |
| Արգելափակման շեմ | `blockThreshold` ընտրանք / `INPUT_SANITIZER_BLOCK_THRESHOLD` (այլանուն՝ `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`   | Արգելափակման համար պահանջվող նվազագույն լրջությունը։ Լռելյայն կարգավորմամբ միջին մակարդակը միայն դիտարկվում է։                                                                                                                 |

**Ռեժիմի առաջնահերթությունը** (`getMode`)՝ կանչողի `options.mode` →
`INJECTION_GUARD_MODE` **ՏԲ-ի հնարավորության դրոշակի վերասահմանում** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` միջավայրի փոփոխական → `INPUT_SANITIZER_MODE` միջավայրի փոփոխական →
`warn`։ Հետևաբար, կառավարման վահանակի վերասահմանումը գերակայում է միջավայրի փոփոխականներին, ուստի Feature
Flags միջերեսը կառավարում է գործող պաշտպանիչ մեխանիզմը իրական ժամանակում (առանց վերագործարկման)։ ՏԲ-ից ընթերցումը խափանումների նկատմամբ անվտանգ է․
սխալի դեպքում պաշտպանիչ մեխանիզմը վերադառնում է միջավայրի փոփոխականների վրա հիմնված վարքագծին, իսկ երբ
վերասահմանում սահմանված չէ, վարքագիծը նույնական է միայն միջավայրի փոփոխականներով որոշվող վարքագծին։

Հայտնաբերման աղբյուրները՝

1. `sanitizeRequest()`՝ `@/shared/utils/inputSanitizer`-ից (համօգտագործվող հայտնաբերիչների
   հավաքածու, որն օգտագործվում է մշակման շղթայի այլ հատվածներում)։
2. Ներկառուցված `DEFAULT_GUARD_PATTERNS` (ներկայում՝ `system_override_inline` և
   `markdown_system_block`, երկուսն էլ՝ `high` լրջությամբ)։
3. Ընտրովի `customPatterns`, որոնք փոխանցվում են կոնստրուկտորի ընտրանքների միջոցով (տողեր, կանոնավոր արտահայտություններ
   կամ `{ name, pattern, severity }` գրառումներ)։

Երբ `mode === "block"` է, **և** առնվազն մեկ հայտնաբերում համապատասխանում է լրջության
շեմին, `preCall`-ը վերադարձնում է `{ block: true, message: "Request rejected:
suspicious content detected" }`։ `warn`/`log` ռեժիմներում պաշտպանիչ մեխանիզմը գրանցում է իրադարձությունը, սակայն
թույլ է տալիս կանչը։ Համօգտագործվող `evaluatePromptInjection()` օգնականը նույնպես արտահանվում է
այն կանչողների համար, որոնք պետք է գնահատեն հուշումները՝ առանց ռեեստրի միջով անցնելու։

**Սկանավորման սահմանը (v3.8.20)․** հայտնաբերիչը ստուգում է միայն միացված հուշման տեքստի
**առաջին 16 KB-ը**՝ `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 բայթ)
`src/shared/utils/inputSanitizer.ts`-ում։ Ե՛վ `detectInjection()`-ը, և՛
`evaluatePromptInjection()`-ը կատարում են `slice(0, MAX_INJECTION_SCAN_BYTES)`՝ նախքան
ձևանմուշների ցիկլը գործարկելը։ Ներարկման հրահանգները գտնվում են մուտքագրման սկզբնամասում, ուստի սա
սահմանափակում է կանոնավոր արտահայտությունների CPU/GC ծախսը հարյուրավոր KB ծավալով օգտակար բեռների դեպքում՝ առանց հայտնաբերումը թուլացնելու (տե՛ս
#3932, #4041)։

### Հավատարմագրերի քողարկիչ (`credentialMasker.ts`)

Գործարկվում է **երկու** փուլերում էլ՝ լռելյայն շղթայում վերջինը (առաջնահերթություն՝ `95`)։ Քողարկում է
հայտնի API բանալիների / գաղտնի թոքենների ձևանմուշները ելքային օգտակար բեռից (հաղորդագրության
բովանդակություն, գործիքի կանչի արգումենտներ, գործիքի արդյունքներ) **և** մատակարարի պատասխանից, որպեսզի
հուշման մեջ տեղադրված հավատարմագիրը (կամ գործիքի արդյունքի միջոցով հետ վերադարձվածը) չարտահոսի
դեպի վերին մակարդակի մատակարար կամ հետ՝ դեպի հաճախորդ։

- **Միայն ընտրովի ակտիվացմամբ**, նույն սկզբունքով, ինչ PII-ի քողարկումը (կից է Hard Rule #20-ին)․
  անջատված է, եթե `settings.credentialRedactionEnabled === true` չէ **կամ**
  `CREDENTIAL_REDACTION_ENABLED=true` չէ։ Անջատված վիճակում պաշտպանիչ մեխանիզմը ոչինչ չի անում՝
  այն երբեք չի արգելափակում և երբեք չի վերագրում։
- `redactCredentials()`-ը շրջանցում է օգտակար բեռի/պատասխանի ամբողջ ծառը (`walkValue()`,
  պաշտպանված է նախատիպի աղտոտումից, ցիկլերից անվտանգ է `WeakSet`-ի միջոցով) և համընկնումները փոխարինում է
  `[REDACTED:<type>]` տեղապահով՝ կլոնավորելով միայն իրականում
  փոփոխված ճյուղերը։
- `CREDENTIAL_PATTERNS`-ը ներառում է LLM մատակարարների բանալիները (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS թոքենները (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), վճարային բանալիները (Stripe, Square), ամպային
  բանալիները (AWS մուտքի բանալի, Twilio, SendGrid, Mailgun), մասնավոր բանալիները / JWT-ները,
  հավատարմագրեր պարունակող միացման տողերը (`mongodb://user:pass@...` և այլն), ինչպես նաև
  ընդհանուր `Authorization`/`x-api-key`/`api-key`/`apikey` վերնագրի արժեքի
  ձևանմուշը։ Վերնագրի տեսք ունեցող բանալիները (`authorization`, `x-api-key`, `api-key`,
  `apikey`) քողարկվում են կառուցվածքային եղանակով (միայն արժեքը, իսկ սխեմայի նախածանցը, օրինակ՝
  `Bearer `/`Basic `, պահպանվում է), այլ ոչ թե ընդհանուր տեքստային կանոնավոր արտահայտության միջոցով։
- Պաշտպանիչ մեխանիզմը երբեք չի արգելափակում․ այն միայն վերագրում է (`modifiedPayload` /
  `modifiedResponse`) և ավելացնում նշումներ (`meta.credentialsRedacted`, `meta.count`)։

Ռեգրեսիայից պաշտպանություն՝ `tests/unit/credential-masker-guardrail.test.ts`։

## Հիմնական պայմանագիր (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true-ը անմիջապես դադարեցնում է շղթայի կատարումը
  message?: string; // ցուցադրվում է արգելափակման ժամանակ
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // վերադարձվում է preCall-ի կողմից՝ հարցումը վերագրելու համար
  modifiedResponse?: TValue; // վերադարձվում է postCall-ի կողմից՝ պատասխանը վերագրելու համար
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Պաշտպանիչ սահմանափակումը ազդարարում է «փոփոխություն չկա»՝ վերադարձնելով կա՛մ `void`, կա՛մ `{}`, կա՛մ
`{ block: false }`։ `modifiedPayload`/`modifiedResponse` վերադարձնելը փոխարինում է
շղթայով դեպի հաջորդ պաշտպանիչ սահմանափակումներ փոխանցվող արժեքը։
`signal?: AbortSignal`-ը կանչողի կենսացիկլը փոխանցում է պաշտպանիչ սահմանափակումներին։ Հարցման ընդհատումը կանխամտածված fail-open բացառություն է․ մեդիա կամուրջները դադարեցնում են աշխատանքը և մաքրում ռեսուրսները՝ առանց չմշակված մեդիան վերականգնելու այն թիրախի համար, որը, ինչպես հայտնի է, չի աջակցում այն։

## Ռեեստր (`registry.ts`)

`guardrailRegistry` եզակի օրինակը տրամադրում է՝

- `register(guardrail)` — ավելացնում է պաշտպանիչ սահմանափակում (կամ փոխարինում է այն ըստ նորմալացված անվան) և
  վերադասավորում ըստ աճող `priority`-ի։
- `clear()` / `list()` — վարչական օժանդակ մեթոդներ։
- `runPreCallHooks(payload, context)` — հերթով մշակում է ակտիվ պաշտպանիչ սահմանափակումները, փոխանցում է
  payload-ը `modifiedPayload`-ի միջոցով և կանգ է առնում առաջին `block: true`-ի դեպքում։
- `runPostCallHooks(response, context)` — նույն հոսքը պատասխանի կողմում։
- `resetGuardrailsForTests({ registerDefaults })` — մաքրում է վիճակը և, ըստ անհրաժեշտության,
  վերագրանցում է լռելյայնները՝ թեստերի մաքուր մեկուսացման համար։

Երկու գործարկիչներն էլ վերադարձնում են `{ blocked, payload|response, results, guardrail?, message? }`,
որտեղ `results`-ը `GuardrailExecutionResult` գրառումների զանգված է, որոնք ներառում են
յուրաքանչյուր պաշտպանիչ սահմանափակման `blocked`, `skipped`, `modified`, `error` և `meta` դաշտերը,
որոնք օգտակար են հետագծման համար։

### Յուրաքանչյուր հարցման համար պաշտպանիչ սահմանափակումների անջատում

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })`-ը հավաքում է
պաշտպանիչ սահմանափակումների անունների կրկնազերծված ցանկ, որոնք պետք է բաց թողնվեն ընթացիկ
հարցման համար։ Աղբյուրները (բոլորն ընտրովի են, բոլորը միավորվում են)՝

- `apiKeyInfo.disabledGuardrails`
- Հարցման մարմնի `disabledGuardrails` (վերին մակարդակում)
- Հարցման մարմնի `metadata.disabledGuardrails`
- `x-omniroute-disabled-guardrails` վերնագիր (կամ հին
  `x-disabled-guardrails`)

Արժեքները կարող են լինել տողերի զանգվածներ կամ ստորակետերով բաժանված տող․ անունները
նորմալացվում են փոքրատառ kebab-case ձևաչափի (`pii_masker` → `pii-masker`)։ Արդյունքը
`context.disabledGuardrails`-ի միջոցով փոխանցվում է ռեեստրին, որը բաց է թողնում
համապատասխան պաշտպանիչ սահմանափակումները (`skipped: true`՝ `results`-ում)։

## Կատարման հերթականություն

`src/sse/handlers/chat.ts`-ով և
`open-sse/handlers/chatCore.ts`-ով անցնող յուրաքանչյուր հարցման համար՝

1. `resolveDisabledGuardrails(...)`-ը API բանալիից, հարցման մարմնից և
   վերնագրերից կազմում է բաց թողնման ցանկը։
2. `guardrailRegistry.runPreCallHooks(body, ctx)`-ը պաշտպանիչ սահմանափակումները գործարկում է
   առաջնահերթության աճման կարգով՝
   - Անջատված պաշտպանիչ սահմանափակումներն արձանագրվում են որպես `skipped`։
   - Յուրաքանչյուր պաշտպանիչ սահմանափակման `preCall`-ը կարող է վերագրել օգտակար բեռը՝ օգտագործելով `modifiedPayload`։
   - Առաջին `block: true`-ն անմիջապես ընդհատում է շղթան, և մշակիչը վերադարձնում է
     պաշտպանիչ սահմանափակման մերժման պատասխան։
3. Հնարավոր վերագրված օգտակար բեռը փոխանցվում է համակցված երթուղավորմանը և վերին հոսքի
   ուղարկմանը։
4. Պատասխանը կազմելուց հետո `guardrailRegistry.runPostCallHooks(...)`-ը
   պատասխանի վրա գործարկում է նույն շղթան։ Այստեղ `block: true`-ն հեռացնում է վերին հոսքի
   պատասխանը։

Սխալ արձակող պաշտպանիչ սահմանափակումներն արձանագրվում են `error: <message>`-ով և գրանցվում
`logger.warn`-ի միջոցով, սակայն շղթան շարունակվում է. նախագծմամբ կիրառվում է սխալի դեպքում թույլատրելու մոտեցումը։

## Կազմաձևում

Ներկառուցված պաշտպանիչ սահմանափակումների կողմից ընթերցվող միջավայրի փոփոխականները՝

| Փոփոխական                             | Օգտագործվում է             | Ազդեցություն                                                                                                                  |
| ------------------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | Հայտնաբերումն ամբողջությամբ անջատելու համար սահմանեք `false`։                                                                 |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`         | Ներարկման քաղաքականությունը՝ `warn`, `block` կամ `log`։ Հնացած `redact` արժեքը չի վերագրում ներարկման տեքստը։                 |
| `INJECTION_GUARD_MODE`                | `prompt-injection`         | Ներարկման պաշտպանիչի ռեժիմը. նաև ՏԲ-ի գործառույթի դրոշակ է, որը **գերակայում է** միջավայրի փոփոխականների նկատմամբ (DB > ENV)։ |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`         | Նվազագույն խստությունը, որը մերժվում է `MODE=block`-ի դեպքում՝ `high` (լռելյայն), `medium` կամ `low`։                         |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`         | `INPUT_SANITIZER_BLOCK_THRESHOLD`-ի հնացած այլանունը։                                                                         |
| `PII_REDACTION_ENABLED`               | `pii-masker`               | Երբ `true` է, հարցման PII-ը քողարկվում է՝ անկախ ներարկման ռեժիմից։                                                            |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ներքևի հոսք) | Կառավարում է պատասխանի կողմում քողարկիչի վարքագիծը։                                                                           |

Մոդալության կամրջի պաշտպանիչ սահմանափակումները կատարման ժամանակի կազմաձևումն ընթերցում են ՏԲ-ով ապահովվող կարգավորումների
պահոցից (`getSettings()`), ոչ թե միջավայրի փոփոխականներից։ Պատկերի մշակման հիմնական բանալիներն են՝
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` և
`modalityBridgeCacheMaxEntries`։ Հնացած
`visionBridge*` բանալիներն ընդունվում են միայն որպես փաստաթղթավորված՝ մեկ ցիկլի ընթերցման
պահուստային տարբերակ. կառավարման վահանակից գրանցումները կիրառում են հիմնական բանալիները։ Լռելյայն արժեքները և պահուստային
լուծիչը գտնվում են `src/shared/constants/modalityBridgeDefaults.ts`-ում, իսկ հնացած
հաստատունները պահպանվում են `src/shared/constants/visionBridgeDefaults.ts`-ում։

Ձայնի մշակումն օգտագործում է `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` և `modalityBridgeAudioMaxClips`, ինչպես նաև ընդհանուր
`modalityBridgeCache*` կարգավորումները։ Ձայնի մշակման համար հնացած բանալիների պահուստային տարբերակ չկա, քանի որ այս
բանալիները ներդրվել են Մոդալության կամրջի սխեմայի հետ։

Տեսանյութի մշակումն օգտագործում է `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` և
`modalityBridgeVideoTimeout`, ինչպես նաև ընդհանուր `modalityBridgeCache*` կարգավորումները։
Այն լռելյայն անջատված է, քանի որ FFmpeg/ffprobe-ը ոչ պարտադիր գործառնական
կախվածություններ են, իսկ կադրերի նկարագրությունների ստեղծումն ավելացնում է ուշացումն ու մոդելի օգտագործման արժեքը։

## Հատուկ պաշտպանիչ կանոններ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Քայլեր՝

1. Ստեղծեք `src/lib/guardrails/myGuardrail.ts`՝ ընդլայնելով `BaseGuardrail`-ը։
2. Իրագործեք `preCall`-ը և/կամ `postCall`-ը։
3. Կամ գրանցեք ներմուծման պահին (`registerDefaultGuardrails`-ից ավելացնելով), կամ
   գործարկման ընթացքում կանչեք `guardrailRegistry.register(...)`-ը․ ռեեստրը փոխարինում է
   նույն նորմալացված անունն ունեցող ցանկացած նախորդ պաշտպանիչ կանոն։
4. Ավելացրեք թեստեր `tests/unit/`-ում (առկա օրինակներ՝
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`)։

## Թեստավորում

Թեստերի միջև օգտագործեք `resetGuardrailsForTests()`՝ հայտնի վիճակից սկսելու համար։
Փոխանցեք `{ registerDefaults: false }`՝ դատարկ ռեեստրից սկսելու և
միայն թեստավորվող պաշտպանիչ կանոնները գրանցելու համար։ Vision Bridge-ն աջակցում է կախվածությունների
ներմուծմանը (`deps.getSettings`, `deps.callVisionModel`), իսկ Audio Bridge-ը տրամադրում է
համարժեք միջերեսներ՝ կարգավորումների, հնարավորությունների, STT մոդելի ընտրության, հավատարմագրերի
ստուգումների և տրանսկրիպցիայի համար։ Հետևաբար, թեստերը կարող են ստուգել երկու հոսքերն էլ՝ առանց DB-ի
կամ ցանցային հասանելիության։

## Ներարկման պաշտպանիչ կանոնով երթուղիների ծածկույթ և red-team թեստավորում (Փուլ 8 · Բլոկ D)

Ներարկման պաշտպանիչ կանոնը (`createInjectionGuard` / `withInjectionGuard`) ընդգրկում է օգտատիրոջ հուշումներ
ընդունող բոլոր երթուղիները։ Այն հաշվի է առնում `INJECTION_GUARD_MODE`-ը (լռելյայն՝ `warn` = միայն գրանցել մատյանում,
`block` = վերադարձնում է HTTP 400 `SECURITY_001`)։

| Տեսակ        | Երթուղիներ                                                                                                                                           | Լռելյայն ռեժիմ |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| Տեքստ (առկա) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn           |
| Գեներատիվ    | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn           |
| Տվյալներ     | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn           |

Տեքստի արտաբերումը (`extractMessageContents`) ներառում է `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`։

**Red-team (ամեն գիշեր, `nightly-llm-security.yml`)․** promptfoo-ն ստուգում է, որ յուրաքանչյուր երթուղի արգելափակում է
OWASP-LLM կորպուսը `INJECTION_GUARD_MODE=block` ռեժիմում, իսկ garak-ը կատարում է ստուգումներ (գաղտնիքի բացակայության դեպքում՝ բաց է թողնում)։
`moderations`-ը ներառված է հետևողականության համար․ արգելափակման ռեժիմն օգտագործող օպերատորները կարող են այն բացառել
`resolveDisabledGuardrails`-ի միջոցով։

Գիշերային աշխատանքային հոսքը (`.github/workflows/nightly-llm-security.yml`, cron + ձեռքով
գործարկում) ունի երկու առաջադրանք՝

- **`promptfoo-guard` (արգելափակող)** — գործարկում է `promptfoo eval -c promptfooconfig.yaml`-ը
  `INJECTION_GUARD_MODE=block`-ով։ Յուրաքանչյուր հակառակորդային դեպք (օրինակ՝ «անտեսիր բոլոր
  նախորդ հրահանգները…», DAN ոճի jailbreak-ներ) հաստատում է, որ պատասխանը պարունակում է
  `error.code === "SECURITY_001"`, այսինքն՝ պաշտպանիչ կանոնն իսկապես մերժել է հարցումը։
