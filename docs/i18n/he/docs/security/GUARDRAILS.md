> **מקור האמת:** `src/lib/guardrails/`
> **עדכון אחרון:** 2026-08-29 — v3.8.51 (מקור התמליל של Video Bridge מוצהר על ידי הקורא,
> ועדיין אינו מאומת על ידי השרת — הובהר בהתאם ל-#11661)

מנגנוני הגנה אוכפים בטיחות, מדיניות והתמרות תוכן בגבול
שבין OmniRoute לספקים במעלה הזרם. כל מנגנון הגנה יכול לבדוק (ובאופן
אופציונלי לדחות, להתמיר או להוסיף הערות אל) מטעני בקשות (`preCall`) ותגובות
במעלה הזרם (`postCall`).

המערכת פועלת בגישת **fail-open**: אם מנגנון הגנה זורק חריגה במהלך הביצוע, הרישום
מתעד את השגיאה וממשיך למנגנון ההגנה הבא במקום להכשיל את
הבקשה. חסימה היא החלטה מפורשת (`block: true`), ולעולם אינה מתרחשת בטעות.

## מנגנוני הגנה מובנים

הרישום טוען אוטומטית שישה מנגנוני הגנה לפי סדר עדיפות בעת הייבוא
(ראו `registry.ts` → `registerDefaultGuardrails()`):

| עדיפות | שם                  | שלב(ים)        | קובץ                  |
| ------ | ------------------- | -------------- | --------------------- |
| `5`    | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`    | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`    | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`   | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`   | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`   | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

מספרי עדיפות נמוכים יותר מופעלים **ראשונים**.

### גשר ראייה (`visionBridge.ts`) — גשר מודאליות PR-1

מיירט בקשות המכילות תמונות ומיועדות ל**מודלים ללא יכולות ראייה**, ומנתב
מחדש את הבקשה כולה למודל בעל יכולות ראייה, או מחליף את חלקי התמונה
בתיאורים טקסטואליים שמופקים באמצעות מודל ראייה הניתן להגדרה לפני הקריאה
לשירות במעלה הזרם. כך ספקי טקסט בלבד יכולים לטפל באופן שקוף במטענים
מרובי־מודאליות.

זרימה:

1. דילוג אם מודל היעד כבר תומך בראייה (אלא אם הוא מופיע ברשימת
   הגישור הכפוי `isVisionBridgeForcedModel`).
2. חילוץ חלקי תמונה באמצעות `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), שמעבירה את הטיפול ל**גלאי המדיה המאוחד**
   `detectMediaParts()` שב־`open-sse/utils/mediaParts.ts` — מקור האמת
   היחיד המשותף למסנן התאימות המשולב. החילוץ מוגבל באמצעות רשימת היתרים
   לחלקים ברמה העליונה ובצורות ש־`replaceImageParts` יכולה לשלב בחזרה
   (חוזה החילוץ↔ההחלפה): `image_url` של OpenAI,‏ `source.type:"base64"`
   בקידוד base64 של Anthropic,‏ `source.type:"url"` של Anthropic, ו־
   `input_image` של Responses API. התאמות מקוננות וצורות המשמשות
   כאינדיקציה בלבד מיועדות למסנן המשולב ולעולם אינן מחולצות.
   דילוג אם לא נמצאו כאלה.
3. פתרון תצורת זמן הריצה באמצעות `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): מפתחות ההגדרות החדשים
   `modalityBridge*` מקבלים קדימות; מפתחות `visionBridge*` הישנים נשארים
   כ**חלופה למחזור אחד** (חלון חזרה לאחור). דילוג לפני מעבר כלשהו על
   המדיה כאשר הגשר מושבת.
4. בורר המצבים (`modalityBridgeVisionMode`, ראו טבלה להלן) מחליט בין
   ניתוב מחדש לתיאור. ניתוב מחדש מחזיר `modifiedPayload` שבו מוחלף רק
   `model`, יחד עם מטא־נתונים `{ rerouted, fromModel, toModel, imagesKept }`.
5. נתיב התיאור: הגבלת התמונות ל־`maxImages`, הרכבת הנחיה מודעת־משימה,
   בדיקת מטמון התיאורים, קריאה למודל הראייה **במקביל**
   (`Promise.allSettled`), והזרקת חלקי טקסט מסוג
   `[Image N]: <description>` במקומן. תיאור שנכשל מניב `null`, וחלק
   התמונה המקורי **נשמר** (#4012) — למעט בנתיב התיאור המשולב, כאשר כל
   ניסיונות התיאור נכשלו, שבו שירות מאומת ללא יכולות ראייה במעלה הזרם
   מקבל במקום זאת מציין מקום
   `(unavailable — no vision-capable provider connected)` (#8430).
6. החזרת `modifiedPayload` + מטא־נתונים (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### בורר מצבים (`modalityBridgeVisionMode`)

| מצב        | ברירת מחדל | התנהגות                                                                                                                                                                                                                                                        |
| ---------- | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔          | היוריסטיקה הישנה, ללא שינוי (#6640/#7204): מודלים שאינם משולבים או מודלים מסוג `auto/` מנותבים מחדש למודל הראייה הטוב ביותר, אלא אם למודל המקורי כבר יש פרטי אימות שמישים (ואז מתבצע תיאור); יעדים משולבים תמיד משתמשים בתיאור.                                |
| `describe` |            | תמיד לתאר — בלוק הניתוב מחדש נעקף לחלוטין; המודל שבחר המשתמש הוא תמיד זה שמשיב.                                                                                                                                                                                |
| `reroute`  |            | כפיית ניתוב מחדש: מנגנון ההגנה ששומר על מודל בעל פרטי אימות נעקף. מנגנון ההגנה על פרטי האימות של **יעד** הניתוב מחדש עדיין חל — כאשר לא קיים יעד ראייה שמיש, הבקשה עוברת לנתיב התיאור, כך שתמונות גולמיות לעולם אינן מגיעות לשירות עורפי של טקסט בלבד (#8430). |

מצבים כפויים מבצעים קיצור דרך **לפני** הפעלת ההיוריסטיקה האוטומטית;
ההתנהגות של `auto` זהה ברמת הבתים למנגנון ההגנה שלפני PR-1.

#### תחום מפתח API (`visionBridgeKeyScope.ts`)

כאשר מפתח ה־API של הקורא מגביל את `allowedConnections`, מאגרי המכסה
(`allowedQuotas`) או מודלים (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), הגשר בוחר רק
מודלים לניתוב מחדש ולתיאור שבהם המפתח רשאי להשתמש, דרך חיבורים שבהם המפתח
רשאי להשתמש. לאחר מכן קריאת התיאור עוברת תמיד דרך הלולאה העצמית של
OmniRoute עם הכותרת `x-omniroute-self-loop-key-id`, כך שבקשת הצ'אט המקבלת
אוכפת שוב את מדיניות החיבורים והמודלים של אותו מפתח. `enforceApiKeyPolicy()`
מכבדת את הכותרת הזו רק יחד עם אסימון הנושא של הלולאה העצמית, ולכן היא יכולה
רק לצמצם גישה, ומזהה שלא ניתן לפתור נדחה.

אם לא מורשה עבור המפתח אף מודל ראייה, נתיב התיאור מפנה את מקומו והבקשה
מועברת ללא שינוי, באותה התנהגות של כשל פתוח כמו מנגנון הגנה מושבת
(מטא־נתונים `{ skipped: true, reason: "no_permitted_vision_model" }`).
בקשות ללא מפתח, ומפתחות ללא הגבלות אלה, מתנהגים בדיוק כפי שהתנהגו קודם.

#### הנחיית תיאור מודעת־משימה (`modalityBridgeVisionTaskAware`)

ברירת המחדל היא **true**. הפונקציה `composeVisionPrompt()`‏ (`visionBridgeHelpers.ts`) מצרפת
את הטקסט של **הודעת המשתמש האחרונה** (מקוצר ל-500 תווים) להנחיית התיאור
הבסיסית, וכך מכוונת את התיאור למה שהמשתמש ביקש בפועל
(תבנית codex-vision-proxy) ומבקשת ממודל הראייה לתמלל טקסט גלוי.
כאשר הדגל כבוי — או שאין טקסט משתמש — נעשה שימוש בהנחיה הבסיסית ללא שינוי.

הבקשה תואמת-OpenAI של לולאת התיאור העצמית (`callVisionModelSingle()`
בקובץ `visionBridgeHelpers.ts`) תמיד מבקשת `image_url.detail: "high"` —
ללא תנאי, עבור כל קורא/ספק, וללא תלות באות כלשהו מהלקוח.
דגימה ברמת פירוט נמוכה פוגעת בדיוק ה-OCR בדיוק במשימת תמלול הטקסט
שהנחיה זו מבקשת לבצע, ולכן קריאת התיאור עצמה תמיד מבקשת רמת פירוט גבוהה,
ללא קשר לרמת הפירוט שבה השתמשה הבקשה הנכנסת המקורית. הדבר משפיע
רק על גוף בקשת התיאור הפנימית; הוא אינו משנה את האופן שבו
OmniRoute מעביר את `image_url.detail` של הקורא בבקשה הראשית —
ברירת מחדל זו מוחלת בנפרד, ורק עבור לקוחות OpenCode שזוהו, בתוך
`defaultImageDetail()`‏ (`open-sse/handlers/chatCore/upstreamBody.ts`). בענף
פורמט התקשורת של Anthropic בלולאת התיאור העצמית אין שדה `detail`,
ולכן אף אחת מברירות המחדל אינה משפיעה עליו.

#### מגבלת פלט התיאור (`modalityBridgeVisionMaxChars`)

| מפתח                           | ברירת מחדל | טווח             |
| ------------------------------ | ---------- | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`        | `0` או 100–50000 |

`0` (ברירת המחדל) פירושו **ללא מגבלה** — התיאור שמוחזר על ידי
`callVisionModel()` מועבר ללא שינוי, תוך שימור ההתנהגות הקיימת.
כל ערך בטווח 100–50000 מקצר את התיאור ומוסיף לו סיומת
`…` לפני שילובו מחדש בתור `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` בקובץ `src/lib/guardrails/visionBridge.ts`).
הגדילו ערך זה עבור משימות OCR עתירות פרטים שבהן המודל שבהמשך זקוק
לתמלול המלא; הקטינו אותו כדי להגביל את השימוש בטוקנים במודלי ראייה
דברניים. שדה לוח הבקרה נמצא בחלונית המתקדמת של לשונית Vision
(`modality-bridge-max-chars` בקובץ `ModalityBridgeVisionTab.tsx`) ומהדק כל
ערך בין 1 ל-99 כלפי מעלה לרף של 100, תוך השארת `0` מפורש ללא שינוי —
`0` הוא ערך Zod תקין בפני עצמו
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), ולא רק
ברירת המחדל של מצב "לא הוגדר".

#### מטמון התיאור (`modalityBridge/bridgeCache.ts`)

מטמון LRU + TTL בזיכרון עבור פלטי תיאור, המשותף לכל התהליך.
מפתח = `sha256(imageRef + composedPrompt + configuredBridgeModel)` עם
מסגור באמצעות קידומת אורך (ללא התנגשויות בגבולות בין שדות). רכיב המודל
הוא מודל הגשר **שהוגדר**, ולא המודל שענה בפועל —
`callVisionModel` עשוי לעבור פנימית לחלופה, ומפתוח לפי ניסיון היה
מפצל את המטמון. תיאורים שנכשלו לעולם אינם נשמרים במטמון. הגדרות:

| מפתח                            | ברירת מחדל | טווח    |
| ------------------------------- | ---------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`     | —       |
| `modalityBridgeCacheTtlMinutes` | `60`       | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`      | 10–5000 |

#### נרמול תמונות מרוחקות (תיאור בלולאה עצמית/אחזור base64)

כאשר הגשר מאחזר בעצמו תמונה **מרוחקת** — קריאת התיאור העצמית של Anthropic
והמרת base64 עבור פורמט התקשורת של claude
(`ensureBase64ImagesForClaudeWire`), שתיהן באמצעות
`fetchRemoteImageAsDataUri()` בקובץ `visionBridgeHelpers.ts` — ה-URI של הנתונים
שמתקבל מועבר דרך `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) לפני הטמעתו בבקשה למודל הראייה.
גודלן של תמונות גדולות מדי מוקטן כך שהצלע הארוכה תהיה **2048px**
(בהתאם למגבלת שינוי הגודל ש-OpenAI/Anthropic כבר מחילות בצד השרת), דבר
שמפחית את מספר הבתים המועלים ואת זמן ההשהיה מבלי לשנות את מה שמודל
הראייה רואה. שינוי הגודל משתמש ב-`sharp`, שנטען באמצעות ייבוא דינמי:
בפלטפורמה שבה הטעינה של הקובץ הבינארי המקורי שלו נכשלת,
`normalizeDataUri()` **לעולם אינה זורקת חריגה** — היא חוזרת להעברה ללא
שינוי של הבתים המקוריים, כך שנתיב התיאור/המרת ה-base64 ממשיך תמיד
לפעול. גם בתים שאינם תמונה (אחזור שלא החזיר תמונה הניתנת לפענוח)
מועברים ללא שינוי. נרמול זה מוגבל לתמונות שהגשר מאחזר עבור הקריאה
העצמית שלו — הוא לעולם אינו מוחל על מטען ההעברה הגולמי של הקורא,
בהתאם לעיקרון של שינוי בהסכמה מפורשת בלבד (Hard Rule #20).

#### סכמת הגדרות + מיגרציה

מפתחות `modalityBridge*` החדשים מאומתים באמצעות Zod בתוך
`updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, שלישיית `modalityBridgeCache*`, וקבוצת
`modalityBridgeAudio*` שבה משתמש Audio Bridge. המיגרציה
`141_modality_bridge_settings.sql` מעתיקה ערכי `visionBridge*` קיימים
מהמערכת הישנה למפתחות החדשים התואמים (אידמפוטנטית, ולעולם אינה דורסת
ערך `modalityBridge*` שהוגדר על ידי מפעיל); המפתחות הישנים ממשיכים
להתקבל כחלופת קריאה למשך מחזור הפצה אחד.

#### כותרת שקיפות + נתונים סטטיסטיים

תגובות שעברו המרה באמצעות תיאור כוללות
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(נבנית על ידי `buildModalityBridgeHeader()` בקובץ `modalityBridge/bridgeStats.ts`,
ונחתמת על ידי `withModalityBridgeHeader()` בקובץ `src/sse/handlers/chatHelpers.ts`).
בקשות שנותבו מחדש אינן מקבלות **שום** כותרת — המטען לא השתנה והחלפת המודל
כבר גלויה בשדה `model` שבגוף התגובה.

`GET /api/modality-bridge/stats` (אימות ניהולי, באותה רמה כמו
`GET /api/settings`) מחזיר את המונים בזיכרון לכל מודליות
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` עבור `vision`,‏ `audio` ו-
`video`. הערך `averageLatencyMs` משתמש ב-`latencySamples`, ולא בכל הניסיונות, כמכנה;
פעולה ללא מדידת זמן אינה ממציאה דגימה של אפס מילישניות.
`bridged` נשאר הכינוי התואם לאחור להמרות מוצלחות;
ניסיונות שנכשלו אינם מגדילים אותו.
המונים מתאפסים בעת הפעלה מחדש של התהליך, בכוונה תחילה
(טלמטריה, לא הנהלת חשבונות).

#### תצורת לוח הבקרה

הדף הייעודי בלוח הבקרה הוא
`/dashboard/settings/modality-bridge`. הלשוניות `Vision`,‏ `Audio`
ו-`Video`, הניתנות למיעון באמצעות URL, משמרות את פרמטרי השאילתה בעת החלפת הערך `tab`.
הלשונית Vision חושפת הפעלה, מצב, בחירת מודל (כולל ברירת המחדל
האוטומטית), הנחיות תלויות-משימה, מגבלות מתקדמות של זמן קצוב/תמונה/אורך תיאור/מטמון,
מוני זמן ריצה ובקשת דוגמה מוגנת. גם הלשונית Audio פעילה: היא חושפת
הפעלה, בורר מודלים ל-STT בלבד עם Auto, מגבלות זמן קצוב/אורך מרבי של מקטע,
מוני שמע ובדיקת דוגמה מסוג `input_audio`. הלשונית Video מתפקדת: היא מדווחת
על מצב זמן הריצה של FFmpeg/ffprobe — אחד מארבעה מצבי ממשק מפורשים (`unknown` בזמן
שהבדיקה מתבצעת או אם לא ניתן להשלימה, `restricted` במארח לוח בקרה שאינו loopback
שבו הבדיקה מדולגת בצד הלקוח, `unavailable` לאחר שבוצעה בדיקה והיעדרם אומת, או
`available` עם גרסאות FFmpeg/ffprobe) — שומרת באופן מתמשך מגבלות
הפעלה/מודל/פריימים/וידאו/זמן קצוב, מסננת את בורר המודלים למודלים בעלי יכולות ראייה
וחושפת מוני וידאו.

כרטיס Vision Bridge הקודם תחת הגדרות AI הוא קישור תאימות לדף
החדש; הוא אינו מחזיק עוד עותק נוסף של הטופס. Media Providers מקשר גם
תהליכי עבודה של Image-to-Text ו-Speech-to-Text ללשוניות Modality
Bridge המתאימות, מבלי להסיר את סביבת הניסוי הקיימת של Speech-to-Text.

**עקיפת בקרת קבלה בלולאה עצמית:** כאשר קריאת התיאור מנותבת דרך
לולאת `/v1` העצמית של OmniRoute (מודל ספק שאינו תקני), בקשת המשנה שולחת
`x-omniroute-admission-bypass: internal` ומאומתת באמצעות פרטי הגישה שנפתרו
עבור הלולאה העצמית — הסמן המקומי `sk_omniroute` במצב מקומי, או מפתח הסביבה
`OMNIROUTE_API_KEY` / `ROUTER_API_KEY` שהוגדר בידי המפעיל (#1350), כך שגם
פריסות עם `REQUIRE_API_KEY=true` יכולות עדיין להריץ את קריאת התיאור. העקיפה
מכובדת רק עבור פרטי הגישה המדויקים הללו, ולכן לקוחות חיצוניים אינם יכולים להשתמש
בכותרת כדי לדלג על בקרת הקבלה.

ברירות המחדל הישנות נמצאות ב-`src/shared/constants/visionBridgeDefaults.ts`;
ברירות המחדל החדשות עבור מצב/מודעות למשימה/מטמון ופותר ההגדרות נמצאים ב-
`src/shared/constants/modalityBridgeDefaults.ts`. מנגנון ההגנה חושף אפשרות בנאי
`deps`, כדי שבדיקות יוכלו להזריק מימושים מדומים של `getSettings` ושל
`callVisionModel`.

### גשר שמע (`audioBridge.ts`) — Modality Bridge PR-3

מיירט בקשות צ'אט המכילות שמע לפני שהן מגיעות ליעד שלא ידוע כתומך
בקלט שמע. הוא לעולם אינו מנתב מחדש את בקשת הצ'אט: חלקי השמע מתומללים
דרך נקודת הקצה הקיימת, תואמת OpenAI ובפורמט multipart, ומודל הצ'אט
שנבחר ממשיך עם תמלילי טקסט.

זרימה:

1. פתור את `supportsAudio` באמצעות `getResolvedModelCapabilities()`. מטא-נתונים מפורשים
   ממרשם הספקים מקבלים קדימות, לאחר מכן מטא-נתונים סטטיים של המודל, ולאחר מכן
   `modalities_input` מסונכרן. רשימת קלט מוצהרת ללא `audio` היא `false`;
   כאשר אין כל ראיה ליכולת, הערך נשאר `null`. גם `false` וגם `null` מפעילים את
   הגשר השמרני, ואילו `true` עוקף אותו.
2. פתור את הגדרות `modalityBridgeAudio*` וחלץ חלקי שמע הניתנים לשילוב מחדש ברמה העליונה
   מכל הודעה, באמצעות המזהה המשותף `detectMediaParts()`.
   צורות התעבורה הנתמכות הן `input_audio` של OpenAI,‏ `audio_url` ו-
   `source.media_type: "audio/*"`. שמע מקונן מזוהה לצורכי ניתוב, אך אינו
   מוסר בנתיב השילוב מחדש. העבודה מוגבלת באמצעות `modalityBridgeAudioMaxClips`;
   חלקים מאוחרים יותר נשארים ללא שינוי.
3. כבד `provider/model` שהוגדר, או אפשר ל-`selectAudioBridgeModel()` לעבור על
   `AUDIO_TRANSCRIPTION_PROVIDERS` לפי סדר קטלוג יציב ולבחור את המודל הראשון
   שיש לו פרטי גישה פעילים ושמישים של ספק.
4. `callAudioTranscription()` ממיר שמע מסוג base64/data-URI ל-`file` בפורמט multipart,
   או מוריד `audio_url` מרוחק דרך מנגנון ההגנה היוצא המוגבל למשאבים ציבוריים,
   עם הצמדת DNS ומגבלה של 25 MB. לאחר מכן הוא שולח ב-POST את הקובץ ואת המודל שנבחר
   ללולאה העצמית המקומית `/v1/audio/transcriptions`, עם אימות באמצעות
   `resolveSelfLoopBearer()`. נתיב התמלול הקיים מבצע חיפוש רגיל של פרטי גישה,
   טיפול בתקופת צינון/הגבלת קצב ושיגור לספק.
5. קריאות מוצלחות מחליפות את החלקים שלהן ב-`[Audio N]: <transcript>`. הקריאות
   רצות באמצעות `Promise.allSettled`: כשל בודד משמר את חלק השמע המקורי
   (#4012 contract). אם כל הקריאות נכשלות והוכח שהיעד הוא
   `supportsAudio === false`, החלקים הופכים ל-
   `[Audio N]: (unavailable — no STT provider connected)` (#8430 contract). עבור
   יעד לא ידוע (`null`), תוצאה שבה הכול נכשל נשארת ללא שינוי. יעד שהוכח
   כיעד טקסט בלבד ושאין עבורו פרטי גישה שמישים ל-STT מקבל את אותו מציין מקום
   מפורש, מבלי לבצע קריאת רשת.

תמלולים מוצלחים משתמשים במטמון LRU/TTL הכלל-תהליכי של Modality Bridge.
המפתח משלב את הפניית השמע, תווית הפעולה היציבה `audio-transcription`
ומודל ה-STT שנבחר; כשלים לעולם אינם נשמרים במטמון. ניסיונות שמע מעדכנים
את המונים המשותפים `bridged`,‏ `cacheHits`,‏ `failures` ו-`lastUsedAt`.
תגובות שעברו המרה כוללות
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; בקשות
שלא שונו אינן מקבלות מקטע Audio Bridge.

הגדרות זמן הריצה מגובות במסד הנתונים ומאומתות באמצעות Zod:

| מפתח                          | ברירת מחדל | טווח                |
| ----------------------------- | ---------- | ------------------- |
| `modalityBridgeAudioEnabled`  | `true`     | —                   |
| `modalityBridgeAudioModel`    | `""`       | אוטומטי או מזהה STT |
| `modalityBridgeAudioTimeout`  | `60000`    | 1000–300000         |
| `modalityBridgeAudioMaxClips` | `3`        | 1–10                |

המטמון המשותף נותר בשליטת `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` ו-`modalityBridgeCacheMaxEntries`.

### גשר וידאו (`videoBridge.ts`, `videoBridgePipeline.ts`)

מיירט חלקי וידאו ברמה העליונה ב-`messages` של Chat Completions וב-`input` של
Responses API, לפני קריאה ליעד שאין לו תמיכה טבעית ידועה בווידאו.
התבניות הנתמכות הן `input_video`,‏ `video_url`,‏ `video_source`, כתובות URL מסוג HTTPS,
ו-URI של נתונים מסוג `data:video/*;base64,...`. שמות קבצים רגילים בטקסט אינם מטופלים
כווידאו.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) אחראי על מעבר בבקשה, על
בדיקת היכולת/המדיניות, על צבירה לכל בקשה ועל מטען התגובה.
העבודה לכל סרטון — השגה, מטמון התוצאה המלאה, תיאור רצף פריימים
(המשלב כל תמלול שמע שהוצהר על ידי הקורא), ומדדים/ביטול/ניקוי
לכל ניסיון — מוסתרת מאחורי `processVideoPart` בתוך
`videoBridgePipeline.ts`, הנקראת פעם אחת לכל חלק וידאו בתוך הלולאה של `preCall`.
מודול זה מגדיר גם את גבולות הממשק המפורשים `VideoMediaBrokerPort`
(השגת בתים וחילוץ פריימים שנדגמו), `VideoAudioTranscriptionPort`
(שילוב תמלול שמע שהוצהר על ידי הקורא עם הכתוביות שנדגמו), וכן
`VideoDrilldownPort` (גבול ההתמדה של התעמקות בפריימים; הוא עדיין אינו מחובר
ל-`processVideoPart` — כיום רק הנתיב הנפרד `/api/modality-bridge/video/drilldown`
כותב רשומות התעמקות).

נתיב הבקשה הציבורי `/v1` לעולם אינו מייבא או מפעיל תהליך משנה. סרטונים מרוחקים
מורדים תחת מגבלה של 50 MiB; לסרטוני base64 מוטבעים יש מגבלה שמרנית של 36 MiB
לאחר פענוח לכל סרטון, כדי שמעטפת המודל/ההודעות/המסגור תוכל להישאר בתוך מגבלת
הקבלה של בקשות JSON ציבוריות, העומדת על 50 MiB. אורך מוטבע והערכות גודל לאחר
פענוח נבדקים לפני הקצאה. HTTPS נדרש בכתובת ה-URL המרוחקת הראשונית ובכל הפניה,
תוך שימוש בהגנת היציאה הקיימת המוגבלת לכתובות ציבוריות, עם הצמדת DNS. לאחר מכן
הבתים עוברים דרך גבול התיווך הפנימי המדויק `POST /api/modality-bridge/video/extract`.
נתיב זה הוא גם `LOCAL_ONLY` וגם `SPAWN_CAPABLE`, מקבל רק בקשה מאומתת לכל תהליך
מלולאת המשוב המהימנה, ולעולם אינו מקבל כתובת URL, נתיב במערכת הקבצים, קובץ הרצה
או רשימת ארגומנטים. צינור הגבלת גודל הגוף של ה-API וקורא הגוף המצטבר של המטפל
אוכפים באופן בלתי תלוי מגבלת קלט של 50 MiB למתווך. התור התחום שלו מריץ חילוץ
אחד בכל פעם, מאפשר ארבע עבודות ממתינות ומגביל את הקלט הממתין ל-100 MiB.

בתוך המתווך, `ffprobe` קורא קובץ מקומי פרטי; רשימת הפורמטים הקבועה המותרת
מחריגה תבניות של רשימות השמעה ומניפסטים. עבור קונטיינרים מותרים ממשפחת MOV,
הפניות חיצוניות לנתוני MOV נותרות מושבתות כברירת מחדל, והפקודה הקבועה אינה
מאפשרת אותן. גם `ffprobe` וגם `ffmpeg` משתמשים ברשימת פרוטוקולים מותרת המוגבלת
ל-`file`, בתהליכון אחד, במערכי ארגומנטים קבועים, ללא מעטפת, ובקובצי הרצה
המאותרים מתוך `PATH`. זרמי תמונת עטיפה מצורפת אינם מועמדים להפעלה. כל הזרמים
הניתנים להפעלה חייבים לעמוד במגבלות, וזרם ברירת מחדל מפורש מקבל עדיפות לפני
הנסיגה הדטרמיניסטית לזרם בעל האינדקס הנמוך ביותר. סרטונים מוגבלים ל-600 שניות,
ל-8,192 פיקסלים בכל ממד ול-33,554,432 פיקסלים במקור. FFmpeg דוגם 1–16 פריימים
מסוג JPEG בנקודות האמצע, מקטין את הצלע הארוכה ל-1,024 פיקסלים לכל היותר בלי
להגדיל קלטים קטנים יותר, ולעולם אינו מקבל כתובת URL. ברירת המחדל לדגימה היא
`uniform`. המדיניות האופציונלית `scene_aware` והמדיניות הניסיונית
`segment_aware` מבצעות מעבר FFmpeg קבוע נוסף על הזרם המקומי שכבר אומת,
בוחרות חותמות זמן תחומות של סצנות מ-`showinfo`, ונסוגות באופן דטרמיניסטי לאותן
נקודות אמצע אחידות במקרה של כשל בגלאי, פסק זמן, פלט פגום או קבוצת מועמדים ריקה.
מצב מודע למקטעים מקצה דגימות נקודת אמצע באופן יחסי למרווחי הסצנות שאומתו;
הראיות המודעות למקטעים והתנהגות הנסיגה מפורטות להלן. המגבלה הקשיחה של 16 פריימים
מוחלת לאחר הבחירה בכל מדיניות. כאשר לבקשה מודעת לסצנות יש תקציב של פריים אחד
בלבד, היא משתמשת בנקודת האמצע האחידה של חלון הסרטון המלא או חלון המיקוד הפעיל,
ומדווחת `policyEffective: uniform`: פריים יחיד שנבחר מסצנה אינו יכול לשמר את
שני הקצוות הזמניים. הקורא רשאי לספק באופן אופציונלי חלון מיקוד סופי
(`start`/`end` בשניות); הגבולות מוגבלים למשך המדיה, חלונות הפוכים או לא-סופיים
נדחים, וכל מדיניות הדגימה מבוצעת רק בתוך המרווח המנורמל. החלון המתקבל נכלל
במטא-נתוני הדגימה ובקידומת התיאור הבלתי מהימנה, כדי שמודלים בהמשך השרשרת יוכלו
להבחין בין קטע ממוקד לבין ציר הזמן המלא.

מיקוד סמנטי של כתוביות הוא הגדרה נפרדת ומפורשת. מצב הניתוח `full` המוגדר
כברירת מחדל משמר את הנחיית הפריימים הקיימת ולעולם אינו מעביר טקסט מהבקשה למודל
הכתוביות. במצב `focused`, הגשר קורא רק את ה-`text`/`input_text` הלא-ריק האחרון
שנכתב על ידי המשתמש מתוך אותו קונטיינר של Chat או Responses, מנרמל אותו ל-NFC,
מאחד תווי בקרה ורווחים ומגביל אותו ל-500 נקודות קוד של Unicode. תוצאה ריקה
נסוגה להנחיית `full` המדויקת. רמז שמיש עובר סריאליזציה כ-JSON בבלוק ייעודי של
הקשר משתמש בלתי מהימן, ורשאי רק לתעדף פרטים נצפים; הוא אינו יכול לעקוף את
האזהרה הנפרדת שלא לציית להוראות הנראות או הנשמעות במדיה. מיקוד טקסטואלי לעולם
אינו מסיק `start`/`end` ואינו משנה את הדוגם הזמני.

#### ראיות מבניות למקטעים FU-07

`segment_aware` משתמש במעבר קדם-ניתוח תחום יחיד על זרם הווידאו המקומי שכבר אומת. שרשרת המסננים הקבועה מקטינה תחילה את הרוחב ל-320 פיקסלים לכל היותר, מזהה שינויי סצנה ומקטעים קפואים, ולאחר מכן דוגמת בקצב של פריים אחד לשנייה לצורך מדידת טשטוש, לומה ממוצעת ומידע מרחבי/זמני. המעבר מוגבל ל-600 דגימות מבניות, לתהליכון FFmpeg/מסנן אחד, לאותן רשימות היתרים של קונטיינרים ושל פרוטוקול `file` בלבד, למגבלת פלט תהליך של 1 MiB, ולכל היותר 30 שניות במסגרת הביטול/המועד האחרון המשותפים של הברוקר. הוא לעולם אינו מקבל מהבקשה פקודה, מסנן, נתיב או URL.

הערכים המבניים הם ראיות דגימה דטרמיניסטיות, ולא הבנה סמנטית של הווידאו. הם אינם מסיקים נושאים, פעולות, כתוביות, דיבור או כוונת משתמש. גבולות של סצנות וקיפאון יוצרים מקטעים; כיסוי הקיפאון, הטשטוש, החשיפה, הפירוט המרחבי והשינוי הזמני משפיעים רק על אופן הקצאת התקציב הקיים של 1–16 פריימים. מקטע שקפוא במלואו מוגבל לפריים אחד, ואילו מקטעים שאינם קפואים מתחרים על יתרת התקציב. כאשר מספר הגבולות גדול ממספר הפריימים, נשמר כיסוי אחיד של ציר הזמן, כך שחיתוכים מהירים בתחילת הסרטון לא יוכלו להסתיר מקטע סיום ארוך. גבולות סצנה שנמצאים בתוך רזולוציית הניתוח של שנייה אחת מגבול קיפאון מאוחדים.

מסננים חסרים, ראיות פגומות/ריקות, שגיאת גלאי או פסק זמן של קדם-הניתוח התחום גורמים לנסיגה פתוחה אל מדיניות נקודת האמצע האחידה המדויקת. ביטול מצד הקורא או הגעה למועד האחרון של הברוקר אינם גורמים לנסיגה פתוחה: הם מסיימים את תת-התהליך הפעיל, מונעים חילוץ פריימים בהמשך, ועץ הקבצים הזמני הפרטי מוסר ב-`finally`.

`scripts/perf/video-bridge-fu07-eval.ts` מייצר מתקני בדיקה דטרמיניסטיים ואמיתיים של FFmpeg לצורך חיסכון בקריאות ליצירת כתוביות לאחר הסרת כפילויות, הקצאת תקציב לתנועה צפופה, ראיות לטשטוש/חשיפה/SI-TI, חיתוכים מהירים עם מקטע סיום ארוך ותוצאות חיוביות כוזבות של דהייה הדרגתית. הוא מתעד את זמן הקיר של קדם-הניתוח, ובמקומות שבהם `/usr/bin/time` זמין, גם את זמן ה-CPU של תהליך-הבן ואת שיא ה-RSS. בדיקות האיכות שלו הן אורקלים מבניים בלבד. איכות אמיתית של מודל הכתוביות נשארת `HOLD`, משום שלרתמה זו אין נקודת קצה מורשית או שופט מוקפא. גם החיסכון הכספי נשאר `HOLD`, אלא אם `--caption-cost-per-call-usd` מספק אומדן חיובי מפורש של עלות לקריאה; הסקריפט לעולם אינו ממציא אף אחת מהתוצאות.

כל פריים מוגבל ל-4 MiB, כל הפריימים הגולמיים יחד מוגבלים ל-23 MiB, ותגובת הברוקר שעברה סריאליזציה מוגבלת ל-32 MiB. ספרייה זמנית פרטית מוסרת ב-`finally`. OmniRoute אינו כולל את FFmpeg ואינו מקבל נתיב מותאם אישית לקובץ הפעלה. לפני יצירת הכתוביות, הגשר מפעיל מעבר שמרני להסרת כפילויות חזותיות: כל JPEG מצומצם למאגר גווני אפור בגודל 16×16 ומושווה רק לפריים האחרון שנשמר. עבור תקציב כתוביות מבוקש של יותר מפריים אחד, החילוץ מספק מאגר מועמדים תחום של עד פי שניים מהתקציב, ולעולם לא יותר מ-16 פריימים. התקרה המבוקשת מוחלת רק לאחר הסרת הכפילויות, כאשר המועמד הראשון והאחרון שנבחרו נשמרים במהלך הדילול הסופי אם התקציב הוא שניים לפחות. מדיניות
`grayscale-16x16-mean-cells-v2` בעלת ניהול הגרסאות משתמשת בערך הגדול מבין הפרש הלומה הממוצע לבין היחס של תאי התמונה הממוזערת שההפרש המנורמל שלהם הוא לפחות 0.05. סף הכפילויות הוא הקבוע 0.04, שנבחר למען יכולת חיזוי ולא נחשף כהגדרת זמן ריצה. אות משני זה, בעל ניגודיות גבוהה, משמר תנועה קטנה ושינויים בטקסט גלוי שהשוואה המבוססת על ממוצע בלבד עלולה להסתיר. שגיאות במשווה או במפענח גורמות לנסיגה פתוחה ושומרות על הכיסוי. מטא-נתוני הפלט מפרידים בין מועמדים שחולצו, פריימים שנעשה בהם שימוש בהצלחה וכפילויות חזותיות שהושמטו.

חלק וידאו שסומן במפורש רשאי לבקש גיליון תמונות ממוזערות עם חותמות זמן. הגשר יוצר רשת JPEG של עד 4 עמודות ו-16 פריימים. כל תא בגודל 512 פיקסלים מטביע את חותמת הזמן של המקור שלו ברצועה תחתונה בעלת ניגודיות גבוהה, בעוד שאותן חותמות זמן נשארות במטא-נתונים הטקסטואליים לצורך שיוך וביקורת בהמשך. קובץ ה-JPEG המלא עדיין מוגבל ל-32 MiB. אם `sharp` אינו מצליח לפענח או להרכיב את הרשת, הגשר חוזר לפריימי ה-JPEG הנפרדים; ביטול מצד הלקוח עדיין מועבר דרך פעולת הגיליון.

ראיות לקידום מופרדות במכוון ממיקרו-בנצ'מרק ההרכבה הסינתטי. `scripts/perf/video-bridge-contact-sheet-eval.ts` מגדיר רתמת A/B בעלת גרסת סכמה עבור מודלי ראייה אמיתיים התואמים ל-OpenAI. היא מודדת אסימונים שדווחו על ידי הספק, זמן השהיה מקצה לקצה לפי שעון קיר (לרבות הרכבת הגיליון), מספר קריאות המודל ושימור עובדות שהוגדרו במניפסט. תגובות המודל הגולמיות אינן נכתבות לדוח; נשמרים רק תקצירי SHA-256 ומזהי העובדות שנמצאה להם התאמה. הרתמה אינה מבצעת שום קריאת רשת או קריאת מודל בתשלום, אלא אם מועבר `--execute-real` ומוגדרים `--model`,‏ `OMNIROUTE_BASE_URL` ו-`OMNIROUTE_API_KEY`. ללא הרצה אמיתית ומפורשת זו, פסק הדין הקריא למכונה נשאר `HOLD`; מדידות סינתטיות של מטען/מספר קריאות לבדן אינן ראיות לקידום.

קוראים רשאים לצרף מערך `transcript.cues` אופציונלי לחלק וידאו נתמך כאשר כבר מצוי ברשותם טקסט מסונכרן. כל סימן חייב לכלול `text`, מרווח סופי של `start`/`end` בתוך משך הזמן שנבדק, ו-`source` הנמצא ברשימת ההיתרים (`client`,‏ `embedded` או `audio-bridge`); ברירת המחדל של `confidence` היא `1`, ועליו להישאר בין `0` ל-`1`. סימנים כפולים זהים לחלוטין מאוחדים. OmniRoute לעולם אינו מתחיל תמלול על סמך מטא-נתונים אלה: סימנים מאומתים מועתקים לתוצאה המתוארת יחד עם המקור, רמת הביטחון והמרווח שלהם, ומוצגים כתצפיות בלתי מהימנות לצד כתוביות הפריימים. טקסט בלתי תקין, מחוץ לטווח או נטול מקור נדחה במקום להתערבב בזרם הכתוביות. שני ערוצי התמלול בגוף הבקשה מנרמלים את המקור שסופק ל-`client`, לרבות תוויות `embedded` או `audio-bridge` שהוצהרו באופן עצמאי. רק מתאם שבבעלות השרת יכול להקצות תוויות מהימנות אלה באמצעות הארגומנט `trustedSource` הזמין בקוד בלבד; שדה JSON בבקשה אינו יכול להגיע לארגומנט זה. טקסט התמלול נותר תוכן בלתי מהימן שמקורו במדיה, ללא קשר למקורו, ולעולם אסור לו לקבוע הרשאה.

מתקשר מתקדם עשוי לספק רצועת `audioTranscript` עבור אותו סרטון;
היא נחשבת לטקסט שסופק על ידי הלקוח, ולא להוכחה לתמלול בצד השרת.
תפר האיחוד מריץ תצפיות חזותיות וקוליות תחת
מועד אחרון ואות ביטול משותפים, מסדר אותן על ציר זמן משותף, מאחד
כפילויות זהות לחלוטין ומדווח על תוצאה חלקית כאשר רק צד אחד מצליח.
`audioTranscript` לא תקין מוביל לתוצאה חלקית זו — התיאור החזותי
נשמר, והענף הקולי מתעד קוד כשל מסונן — במקום להכשיל את הסרטון כולו.
הזמינות של כל ענף, דגל התוצאה החלקית וקודי הכשל המסוננים נשמרים בתוצאה
המתוארת, במטא-נתונים של מנגנון ההגנה (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), במטא-נתונים של מטמון התוצאות ובמוני האיחוד
של הגשר. נתיב ברירת המחדל של Video Bridge אינו מפעיל המרת דיבור לטקסט
ואינו מוריד עותק מדיה נוסף; ללא אותה רצועה מפורשת, הוא נשאר
מבוסס-וידאו בלבד.

**שמירת תמלילים (#12150 P1).** הדבר חל אוטומטית בכל פעם שבה
Video Bridge (שהפעלתו עצמה דורשת הצטרפות מפורשת) מעבד רמז תמליל — אין דגל
שמירה נפרד. כאשר בקשה מעבדת רמז תמליל כלשהו (`transcript` שהוצהר על ידי
המתקשר או `audioTranscript` מאוחד), מנגנון ההגנה מסמן אותה בתור
`videoBridgeObserved` ומפיק צל מצונזר של תיאור הסרטון —
עיבוד זהה שבו גוף הטקסט החופשי של כל רמז מוחלף ב-
`[redacted-video-transcript]`, שנבנה באמצעות החלפת שדה הרמז המובנה
לפני הרכבת המחרוזת (לעולם לא באמצעות ניתוח הטקסט המשוטח, כך ששום תוכן רמז —
זדוני או רגיל, לרבות גופים המכילים `]` כגון
`[inaudible]`/`[music]` — אינו יכול לשרוד). גוף הבקשה הנשמר ביומן הקריאות מחליף
כל חלק טקסט שמקורו בסרטון באותו צל מצונזר, בהתאמה לפי שוויון תוכן;
עוגן `fullText` נקרא מחדש ממטען מנגנון ההגנה שהושלם לפני הקריאה,
כך שההתאמה עדיין מצליחה לאחר שמנגנוני הגנה מאוחרים יותר בשרשרת (ממסכי PII
ופרטי הזדהות, בעדיפויות 10/95) משכתבים את טקסט התיאור במקום, ולאחר
שהזרקת הנחיית מערכת/העברה/זיכרון מעצבת מחדש את מערך ההודעות. הגוף
שנשלח במעלה הזרם אל המודל אינו משתנה. בקשה שנצפתה גם אינה מאכלסת
Memory מתמשך (חילוץ שמקורו הן בבקשה והן בתגובה מדולג),
כך שהתשובה של המודל עצמו אינה יכולה להדהד טקסט תמליל אל Memory.

**שדות וידאו גולמיים (#12430).** כאשר הגשר מופעל ותמיכה מובנית בווידאו אינה ידועה או חסרה, שדות `transcript`/`audioTranscript` מוגדרים מפעילים גם את `videoBridgeObserved`, אפילו לאחר כשל בתיאור או מגבלת `maxVideos`. ערכי `null` ומחרוזות ריקות נחשבים; שדות חסרים ומטא-נתונים שאינם של וידאו אינם נחשבים. עותקים שמורים מצנזרים שדות אלה או משמיטים את הבקשה, ונעקפים מטמונים/Memory.

בנתיבי נסיגה אלה, רמזים תקינים שסופקו על ידי המתקשר הופכים לחלקי `text`/`input_text`
נתמכים במקום לשדות ספק לא תקניים. שתי הרצועות שסופקו בבקשה
נשארות תצפיות `client` שאינן מהימנות, עם אזהרה מפורשת שהסרטון
לא תואר ושחותמות הזמן לא אומתו מול המדיה. המגבלות הקיימות של
256 רמזים/64-KiB בסך הכול ולכל רמז חלות על שתי הרצועות יחד;
חותמות הזמן חייבות להתאים לתקרה של 600 שניות שהגדיר המתווך ולכל חלון מיקוד
שסופק. רצועות לא תקינות נזרקות ואינן מועברות כטקסט שרירותי; עדיין ניתן
להשתמש ברצועה מקבילה תקינה, אלא אם חורגים יחד מהמגבלה. שדות ריקים/`null`
אינם מוסיפים טקסט. נסיגה זו אינה מוסיפה אחזור מדיה או תמלול.
שדות הרחבת התמליל מוסרים מנשא הווידאו שבנסיגה ומאובייקטי
`video_url`/`source` שלו. רשימת ההרשאות בתעבורת OpenAI נשארת קפדנית; נשאי
וידאו עם תמיכה מובנית לא ידועה נשארים זמינים, ויעדים ידועים התומכים בטקסט בלבד
שומרים על סמנים בטוחים. צללי צנזור מובנים מגינים על טקסט התמליל שנוסף,
בעוד שהבקשה המקורית שבבעלות המתקשר נשארת ללא שינוי. יעדים בעלי תמיכה מובנית
וגשרים מושבתים שומרים על התנהגות העקיפה הקיימת שלהם.

עותקים שמורים נוספים משתמשים באותו אות של בקשה שנצפתה. תמונת המצב הגולמית
של בקשת הלקוח לפני מנגנון ההגנה, הבקשה הממתינה בזיכרון ויומן
הבקשות שנדחו בשלב מוקדם מחליפים באופן מבני שדות תמליל בחלקי וידאו;
הנחיות מחרוזת שנוצרו על ידי שלבי הצינור והעברת הקשר מצונזרות
בנקודת היעד של גוף הבקשה הנשמר. הסמן הנשמר `video_content_removed`
גורם להמשך באמצעות `previous_response_id` להיכשל באופן סגור, במקום לשחזר
טקסט שהושלך במכוון. אם בקשה שנצפתה מאבדת את
צל הצנזור של כל חלק לפני הרישום, או אם אפילו אחד מתוך כמה צללי וידאו
אינו מצליח להתאים לאחר שינויים מאוחרים יותר בבקשה, גוף הבקשה הנשמר
מושמט לחלוטין במקום לשמור תמליל מצונזר חלקית.

עבור בקשה שנצפתה, תגובת מודל עשויה לצטט כל חלק מן
התמליל ללא גבול רמז מובנה. לכן `responseBody` הנשמר ביומן הקריאות
מוחלף בסמן השמטה; פריט הצינור המפורט (שעשוי לכלול גופי
מעלה הזרם/לקוח ומקטעי זרם) אינו נשמר. מטמוני סמנטיקה, אידמפוטנטיות
ושחזור הנמקה עוקפים פעולות קריאה וכתיבה עבור בקשה זו. בקשת הספק
והתגובה הגלויה ללקוח נשארות ללא שינוי. בתי keepalive מוקדמים מנוקזים
מהמאגר הזמני כאשר הפריט המפורט מושמט. אזהרת EventStream הפגום
של Kiro מדווחת רק על מספר הבתים במטען, ולעולם לא על תוכנו או על השגיאה הגולמית
של מנתח JSON.
אין בכך טענה שכל אבחון אחר ולא קשור של ספק/תוסף עבר ביקורת;
סריקת יעדי השמירה הרחבה יותר מנוהלת ב-#11658.

מחזור החיים הפנימי של `/api/modality-bridge/video/drilldown` הוא מצע מטמון נפרד,
המאומת באמצעות loopback/token. כל פעולה דורשת גם מזהה principal אטום וקנוני.
לפני שמאפשרים ללקוח קורא בסביבת ייצור להשתמש בו, עליו לגזור מזהה זה מה-tenant
המאומת, ואסור לו לעולם להעביר ערך שנבחר על ידי הלקוח. מפתחות המטמון קושרים את
ה-principal למזהי session ו-video-reference קנוניים, שומרים רק את המפתחות שלהם
שנגזרו באמצעות SHA-256, ומגבילים הן קריאות והן מחיקה לאותו principal. המטמון
שומר לכל היותר 16 מסגרות JPEG נגזרות בכל רשומה, מפוגג אותן לאחר עשר דקות, ותומך
בקריאות `start`/`end` חסומות או במחיקה מפורשת של session.

כל principal מוגבל ל-16 רשומות ול-64 MiB של נתוני JPEG קנוניים. מגבלות אלה
בלתי תלויות בתקרה הגלובלית של 64 רשומות/256 MiB: לחץ מכסת principal מפנה תחילה
רק את הרשומות של אותו principal שלא נעשה בהן שימוש במשך הזמן הארוך ביותר, לפני
שנשקל פינוי LRU גלובלי. רשומות שפג תוקפן מוסרות הן מחישובי ה-principal והן
מהחישוב הגלובלי בעת פעילות במטמון, בעוד שביטול וכשל אימות אינם מבצעים commit
של החלפה חלקית.

המטמון דוחה Base64 שאינו קנוני, ריפוד עודף, מדיה שאינה JPEG, קובצי JPEG פגומים
או קטועים, וקובצי JPEG שמפיקים אזהרה במהלך פענוח תמונה מלאה וחסום באמצעות
`sharp`. הוא מקודד מחדש כל תמונה שהתקבלה כ-JPEG קנוני, גוזר את הרוחב והגובה
מהבתים המפוענחים במקום לתת אמון בשדות שסיפק הלקוח הקורא, ומשליך בתים עודפים
של polyglot במקום לשמור אותם. רק המאגר הדחוס, הקנוני והחסום מחויב כנגד שתי
המכסות. מגבלת תעבורת ה-JSON כוללת את התקורה של Base64 עבור תקרת הקלט המפוענח
של 32 MiB. כל גזירה שנשמרת מתעדת את פורמט ה-JPEG והרזולוציה המאומתים שלה,
מדיניות הדגימה, גרסת הגזירה, מועד היצירה, גיבוב תוכן שחושב על ידי השרת והפניית
האב המגובבת, לצד גיבוב תוכן האב של הלקוח הקורא המהימן. ביטול נבדק בין שלבי
פענוח וגיבוב אסינכרוניים לפני ה-commit האטומי למטמון.

חטיבה זו עדיין אינה מחברת producer של סביבת ייצור לנתיב ואינה מספקת בחירת
וריאנטים ברזולוציות מרובות. לכן, נתיב הבקשה השקוף של Video Bridge אינו כרוך
בעבודה נוספת, ואילו גזירת principal הקשורה ל-tenant ומחזור החיים המלא
בריבוי רזולוציות של FU-08 נותרו במפורש כעבודת המשך, במקום להיות מתועדים
כהתנהגות שהושלמה.

למסגרות מופקות כתוביות בזו אחר זו באמצעות מודל ה-Video שהוגדר. דריסת Video
ריקה יורשת את הגדרת Vision; אם שתיהן ריקות, הנתב האוטומטי של Vision בוחר את
המודל האפקטיבי בעל יכולות הראייה. כתוביות שהופקו בהצלחה מחליפות את החלק המקורי
בקידומת היציבה `[Video description:`, שגם מסמנת את הטקסט כתצפית בלתי מהימנה
שנגזרה ממדיה ומנחה מודלים בהמשך השרשרת שלא לציית להוראות שנמצאו במדיה.
מפתחות מטמון כתוביות המסגרות כוללים את בתי ה-JPEG, ההנחיה, חותמת הזמן והמודל
האפקטיבי; רק כתוביות שהופקו בהצלחה נשמרות במטמון. רשומות המטמון שומרות את
מודל ה-producer שהצליח בפועל, לרבות מודל fallback; ה-bridge מדווח על `mixed`
כאשר מסגרות שונות הופקו על ידי מודלים שונים. פגיעה במטמון עושה שימוש חוזר
בזהות ה-producer הזו במקום לתייג אותה מחדש כתוכנית הניתוב המבוקשת. מטמון
התוצאות של הסרטון כולו ממופתח לפי כל קלט שמשנה את הפלט — ההנחיה, המודל
האפקטיבי, מדיניות הדגימה, מספר המסגרות, מצב הניתוח הסמנטי, טביעת האצבע
SHA-256 של רמז המיקוד המנורמל, חלון המיקוד, `transcript`,
`audioTranscript` ודגל גיליון התמונות — כך ששינוי בכל אחד מהממדים האלה גורם
להחטאה במטמון, ולעולם לא לשימוש חוזר בתוצאה מיושנת. גם גרסת מדיניות ביטול
הכפילויות החזותי, הסף ומספר מסגרות המועמדות החסום מפורשים במפתח ובמטא-נתונים
של מטמון התוצאות; לכן שינוי מדיניות אינו יכול לעשות שימוש חוזר בתיאור מיושן
של הסרטון כולו. מטא-נתוני v4 של מטמון התוצאות שומרים את המצב ואת טביעת האצבע,
ולעולם לא את משימת המשתמש הגולמית. מטא-נתוני מנגנון ההגנה מדווחים הן על מצב
הניתוח המבוקש והן על המצב האפקטיבי; מצב `focused` שהתבקש ללא טקסט משתמש שמיש
מדווח כאפקטיבית `full`.

מנגנון ההגנה מחלץ כל חלק וידאו נתמך, אך מתאר לא יותר מאשר
`modalityBridgeVideoMaxVideos`. עבור יעד שהוכח כי
`supportsVideo === false`, סרטונים שכשלו או חרגו מהמגבלה הופכים לסמני טקסט
בטוחים ומפורשים, כך שלא נותר שום וידאו גולמי. כאשר היכולת אינה ידועה, חלקים
אלה שומרים על מעטפת הווידאו שלהם; כל תמליל fallback עובר את המרת הטקסט החסומה
שלעיל. יעדים שבהם `supportsVideo === true` עוקפים את ה-bridge. אות הביטול של
בקשת הלקוח מופץ דרך ההורדה, תור ה-broker, תהליכי המשנה וקריאות הכתוביות;
ביטולים עוצרים בין סרטונים ולעולם אינם נכשלים באופן שמאפשר מעבר של מדיה
גולמית.

הגדרות זמן הריצה מגובות במסד נתונים ומאומתות באמצעות Zod:

| מפתח                                | ברירת מחדל  | טווח / התנהגות                                                                     |
| ----------------------------------- | ----------- | ---------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | זמן ריצה אופציונלי, בהצטרפות מפורשת                                                |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` משמר כתוביות כלליות; `focused` משתמש בהקשר מוגבל ולא מהימן של המשתמש האחרון |
| `modalityBridgeVideoModel`          | `""`        | יורש את המודל של Vision Bridge                                                     |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                               |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`,‏ `scene_aware`, או `segment_aware` יחסי; כשל בגלאי חוזר ל-`uniform`     |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                     |

ערכי פסק זמן ישנים ומתמידים של Video, הגבוהים מ-120 שניות, מוגבלים למועד הסופי של
המתווך; כתיבות חדשות של הגדרות מעל מגבלה זו נדחות.
`GET /api/modality-bridge/video/runtime` דורש מיקום loopback מקומי ומהימן עם חותמת
לפני אימות או בדיקת זמן הריצה, ולאחר מכן דורש אימות ניהולי.
הוא מחזיר רק את `available`, גרסאות FFmpeg/ffprobe שעברו טיהור, וסיבה קבועה
כאשר זמן הריצה אינו זמין. נקודת הקצה הפנימית לחילוץ אינה
API ציבורי להעלאה: רוויה של התור מחזירה `503` יחד עם `Retry-After`, ניתוק מצד הקורא
מחזיר `499`, והמועד הסופי הקבוע של המתווך מחזיר `504`. תגובות שהומרו מוסיפות
`video->text;model=<visionModel>;parts=<videos>` לכותרת המרכזית
`x-omniroute-modality-bridge` מבלי להסיר מקטעי Vision או Audio.

### ממסך PII (`piiMasker.ts`)

פועל **בשני** השלבים.

- **`preCall`** משכפל את המטען, עובר על `system`,‏ `messages`,‏ `input` ו-
  `prompt` (כולל פריטי מחרוזת פשוטים), ומחיל `processPII()` (מתוך
  `@/shared/utils/inputSanitizer`) על שדות המחרוזת `content`/`text`. כאשר
  `PII_REDACTION_ENABLED=true`, פרטי PII שזוהו מושחרים במטען
  היוצא. הדבר אינו תלוי ב-`INPUT_SANITIZER_MODE` (השולט רק
  במדיניות הזרקת הנחיות). כאשר ההשחרה כבויה, הקריאה מתעדת את מספר
  הזיהויים מבלי לשכתב את התוכן.
- **`postCall`** משכפל לעומק את התגובה, מפעיל את `sanitizePIIResponse()` יחד עם
  הממסך למבנה של Responses API (`maskResponsesOutput` — מכסה את
  `output_text` ואת `output[].content[].text`). אם מתבצעת השחרה כלשהי,
  התגובה ששונתה מחליפה את המקורית.

מנגנון ההגנה לעולם אינו חוסם; הוא רק מוסיף הערות (`meta.detections`,
`meta.redacted`) או משכתב.

#### בחירה לפי סוג, תבניות מותאמות אישית ומוני זיהוי

**לוח בקרה → הגדרות → אבטחה → מיסוך PII** קובע _מה_ ימוסך. הוא
אינו מפעיל את המיסוך: הדבר עדיין נשלט באמצעות `PII_REDACTION_ENABLED` (בקשה) ו-
`PII_RESPONSE_SANITIZATION` (תגובה + SSE), ושניהם כבויים כברירת מחדל.

- **בחירה לפי סוג** — המזהים המובנים מפורטים בקובץ
  `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`). ערך שאינו מוגדר פירושו כל
  הסוגים (ההתנהגות שהייתה קיימת לפני הוספת הגדרה זו). התבנית
  `ssn_us` של מנוע הבקשות ממופה ל-`ssn`. תבניות מוכנות (מינימלית, רגילה, פיננסית,
  ברזילאית, ארה״ב, מלאה) רק ממלאות את תיבות הסימון בממשק המשתמש.
- **תבניות מותאמות אישית** — עד 20 תבניות של ביטויים רגולריים או תווים כלליים (`*` = עד 64
  תווים שאינם רווח לבן, `?` = תו אחד). התאמות הופכות ל-`[CUSTOM_REDACTED]`.
  כל תבנית עוברת דרך `compilePiiCustomPattern()`
  (`src/shared/utils/piiCustomPatterns.ts`): לכל היותר 500 תווים, דגלים המוגבלים
  ל-`g i m s u`, עליה לעבור הידור, לעבור את `safe-regex` (חזרה לאחור
  קטסטרופלית), ואסור לה להתאים למחרוזת ריקה או למציין מיקום של השחרה.
  תבנית שנכשלת נדחית בעת שמירה ובעת בדיקה, ושורה שמורה
  שנכשלת מדולגת בזמן ריצה במקום לעבור הידור. תבניות מותאמות אישית
  מופעלות רק כאשר המיסוך פעיל.
- **מוני זיהוי** — ספירות לפי סוג (לעולם לא הערכים שהותאמו), הנשמרות
  בזיכרון ומתאפסות בעת הפעלה מחדש (`src/lib/pii/piiDetectionStats.ts`). הן גדלות
  רק כאשר המיסוך פעיל.

ההגדרות נמצאות בטבלה `key_value` (מרחב השמות `pii_settings`,
`src/lib/db/piiSettings.ts`) ונקראות דרך מטמון של 1 שנייה. API:

| שיטה   | נתיב                     | מטרה                                                                 |
| ------ | ------------------------ | -------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | מצב הדגל, `enabledTypes`,‏ `customPatterns`, מוני זיהוי              |
| `PUT`  | `/api/settings/pii`      | החלפת `enabledTypes` (`null` = הכול) ו/או `customPatterns`           |
| `POST` | `/api/settings/pii/test` | הרצה ניסיונית של תבנית אחת מול דוגמה בגודל של עד 8 KB; דבר אינו נשמר |

כל שלוש הפעולות דורשות אימות ניהולי ומאמתות את גוף הבקשה באמצעות Zod
(`src/shared/validation/schemas/piiSettings.ts`).

### הזרקת הנחיות (`promptInjection.ts`)

מזהה מבנים עוינים בתוכן שסופק על ידי המשתמש ואוכף את
המדיניות שהוגדרה. ההתנהגות נקבעת באמצעות משתני סביבה ואפשרויות
הבנאי:

| הגדרה    | משתנה סביבה                                                                                             | ברירת מחדל | השפעה                                                                                                                                                                  |
| -------- | ------------------------------------------------------------------------------------------------------- | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| מופעל    | `INPUT_SANITIZER_ENABLED`                                                                               | `true`     | כאשר הערך הוא `false`, מנגנון ההגנה מסיים את פעולתו באופן מיידי.                                                                                                       |
| מצב      | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                         | `warn`     | מדיניות הזרקה: `block`,‏ `warn` או `log`. (הערך `redact` מתקבל לצורך תאימות לאחור, אך **אינו** מסיר טקסט הזרקה; שכתוב PII בבקשה נשלט באמצעות `PII_REDACTION_ENABLED`.) |
| סף חסימה | האפשרות `blockThreshold` /‏ `INPUT_SANITIZER_BLOCK_THRESHOLD` (כינוי `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`     | דרגת החומרה המזערית הנדרשת לחסימה. כברירת מחדל, דרגה בינונית מיועדת לתצפית בלבד.                                                                                       |

**קדימות המצבים** (`getMode`):‏ `options.mode` של הקורא →
דריסת דגל תכונה **במסד הנתונים** עבור `INJECTION_GUARD_MODE` (לוח הבקרה → הגדרות →
דגלי תכונות) → משתנה הסביבה `INJECTION_GUARD_MODE` → משתנה הסביבה `INPUT_SANITIZER_MODE` →
`warn`. לפיכך, דריסה מלוח הבקרה גוברת על משתני הסביבה, כך שממשק דגלי
התכונות שולט בזמן אמת במנגנון ההגנה הפעיל (ללא הפעלה מחדש). הקריאה ממסד הנתונים בטוחה במקרה של כשל:
אם מתרחשת שגיאה, מנגנון ההגנה חוזר להתנהגות המבוססת על משתני הסביבה, וכאשר לא
מוגדרת דריסה, ההתנהגות זהה לחלוטין לפתרון המבוסס על משתני סביבה בלבד.

מקורות זיהוי:

1. `sanitizeRequest()` מתוך `@/shared/utils/inputSanitizer` (ערכת גלאים משותפת
   המשמשת במקומות נוספים בצינור העיבוד).
2. `DEFAULT_GUARD_PATTERNS` המובנים (נכון לעכשיו `system_override_inline` ו-
   `markdown_system_block`, שניהם בדרגת חומרה `high`).
3. `customPatterns` אופציונליים המועברים דרך אפשרויות הבנאי (מחרוזות, ביטויים רגולריים
   או רשומות `{ name, pattern, severity }`).

כאשר `mode === "block"` **וגם** לפחות זיהוי אחד עומד בסף
החומרה, `preCall` מחזיר `{ block: true, message: "Request rejected:
suspicious content detected" }`. במצבים `warn`/`log`, מנגנון ההגנה כותב ליומן אך
מאפשר את הקריאה. פונקציית העזר המשותפת `evaluatePromptInjection()` מיוצאת גם היא
עבור קוראים שצריכים להעריך הנחיות מבלי לעבור דרך המרשם.

**מגבלת סריקה (v3.8.20):** הגלאי בודק רק את **16 הק״ב הראשונים** של
טקסט ההנחיה המאוחד — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16,384 בתים) בתוך
`src/shared/utils/inputSanitizer.ts`. גם `detectInjection()` וגם
`evaluatePromptInjection()` מפעילות `slice(0, MAX_INJECTION_SCAN_BYTES)` לפני הרצת
לולאת התבניות. הנחיות הזרקה מופיעות סמוך לתחילת הקלט, ולכן הגבלה זו מצמצמת את השימוש של ביטויים רגולריים במעבד/GC במטענים בגודל מאות ק״ב, מבלי להחליש את הזיהוי (ראו
#3932, #4041).

### ממסך פרטי גישה (`credentialMasker.ts`)

פועל **בשני** השלבים, אחרון בשרשרת ברירת המחדל (עדיפות `95`). משחיר
תבניות מוכרות של מפתחות API / אסימונים סודיים במטען היוצא (תוכן
הודעות, ארגומנטים של קריאות כלים ותוצאות כלים) **וכן** בתגובת הספק, כך שפרטי
גישה שהודבקו בהנחיה (או הוחזרו על ידי תוצאת כלי) אינם דולפים
לספק החיצוני או בחזרה ללקוח.

- **בהסכמה מפורשת בלבד**, בהתאם למוסכמה של השחרת PII (בסמוך לכלל מחייב #20):
  מושבת אלא אם `settings.credentialRedactionEnabled === true` **או**
  `CREDENTIAL_REDACTION_ENABLED=true`. כשהאפשרות כבויה, מנגנון ההגנה אינו מבצע דבר —
  הוא לעולם אינו חוסם ולעולם אינו משכתב.
- `redactCredentials()` סורקת את כל עץ המטען/התגובה (`walkValue()`,
  בטוחה מפני זיהום אב־טיפוס ובטוחה מפני מחזורים באמצעות `WeakSet`) ומחליפה התאמות
  במציין מקום `[REDACTED:<type>]`, תוך שכפול רק של הענפים שהשתנו בפועל.
- `CREDENTIAL_PATTERNS` מכסה מפתחות של ספקי LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), אסימוני VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), מפתחות תשלום (Stripe, Square), מפתחות
  ענן (מפתח גישה של AWS,‏ Twilio,‏ SendGrid,‏ Mailgun), מפתחות פרטיים / JWT,
  מחרוזות חיבור המכילות פרטי גישה (`mongodb://user:pass@...` וכדומה), וכן
  תבנית כללית לערכי כותרות `Authorization`/`x-api-key`/`api-key`/`apikey`.
  מפתחות בעלי מבנה של כותרת (`authorization`,‏ `x-api-key`,‏ `api-key`,
  `apikey`) מושחרים באופן מבני (הערך בלבד; קידומת הסכמה, כגון
  `Bearer `/`Basic `, נשמרת) במקום באמצעות ביטוי הטקסט הרגולרי הכללי.
- מנגנון ההגנה לעולם אינו חוסם; הוא רק משכתב (`modifiedPayload` /
  `modifiedResponse`) ומוסיף הערות (`meta.credentialsRedacted`,‏ `meta.count`).

הגנה מפני רגרסיות: `tests/unit/credential-masker-guardrail.test.ts`.

## חוזה בסיס (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true עוצר מיד את השרשרת
  message?: string; // מוצג בעת חסימה
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // מוחזר על ידי preCall כדי לשכתב את הבקשה
  modifiedResponse?: TValue; // מוחזר על ידי postCall כדי לשכתב את התגובה
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

מנגנון הגנה מסמן "ללא שינוי" באמצעות החזרת `void`, `{}`, או
`{ block: false }`. החזרת `modifiedPayload`/`modifiedResponse` מחליפה
את הערך שזורם בשרשרת עבור מנגנוני ההגנה שבהמשך.
`signal?: AbortSignal` מעביר אל מנגנוני ההגנה את מחזור החיים של הקורא. ביטול בקשה הוא החרגת fail-open מכוונת: גשרי מדיה מפסיקים את העבודה ומבצעים ניקוי מבלי לשחזר מדיה גולמית ליעד שידוע כי אינו תומך בה.

## מרשם (`registry.ts`)

היחידון `guardrailRegistry` חושף:

- `register(guardrail)` — מוסיף מנגנון הגנה (או מחליף לפי שם מנורמל) וממיין
  מחדש לפי `priority` בסדר עולה.
- `clear()` / `list()` — כלי עזר ניהוליים.
- `runPreCallHooks(payload, context)` — עובר על מנגנוני ההגנה הפעילים, מעביר את
  המטען דרך `modifiedPayload`, ועוצר ב-`block: true` הראשון.
- `runPostCallHooks(response, context)` — אותה זרימה בצד התגובה.
- `resetGuardrailsForTests({ registerDefaults })` — מנקה את המצב, ולפי הצורך
  רושם מחדש את ברירות המחדל לצורך בידוד נקי של בדיקות.

שני המריצים מחזירים `{ blocked, payload|response, results, guardrail?, message? }`
כאשר `results` הוא מערך של רשומות `GuardrailExecutionResult` הכוללות
את השדות `blocked`, `skipped`, `modified`, `error` ו-`meta` לכל מנגנון הגנה,
ושימושיות למעקב.

### השבתת מנגנוני הגנה לכל בקשה

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` אוסף רשימה
ללא כפילויות של שמות מנגנוני הגנה שיש לדלג עליהם עבור הבקשה הנוכחית.
המקורות (כולם אופציונליים וכולם ממוזגים):

- `apiKeyInfo.disabledGuardrails`
- `disabledGuardrails` בגוף הבקשה (ברמה העליונה)
- `metadata.disabledGuardrails` בגוף הבקשה
- הכותרת `x-omniroute-disabled-guardrails` (או הכותרת הישנה
  `x-disabled-guardrails`)

הערכים יכולים להיות מערכי מחרוזות או מחרוזת מופרדת בפסיקים; השמות
מנורמלים ל-kebab-case באותיות קטנות (`pii_masker` → `pii-masker`). התוצאה
מועברת דרך `context.disabledGuardrails` אל המרשם, שמדלג על
מנגנוני הגנה תואמים (`skipped: true` בתוך `results`).

## סדר הביצוע

עבור כל בקשה שעוברת דרך `src/sse/handlers/chat.ts` ודרך
`open-sse/handlers/chatCore.ts`:

1. `resolveDisabledGuardrails(...)` בונה את רשימת הדילוג ממפתח ה-API, מגוף הבקשה
   ומהכותרות.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` מפעיל את מנגנוני ההגנה לפי סדר
   עדיפויות עולה:
   - מנגנוני הגנה מושבתים מתועדים כ-`skipped`.
   - ה-`preCall` של כל מנגנון הגנה עשוי לשכתב את המטען באמצעות `modifiedPayload`.
   - המופע הראשון של `block: true` עוצר את השרשרת, וה-handler מחזיר
     תגובת דחייה של מנגנון ההגנה.
3. המטען (שייתכן ששוכתב) מועבר לניתוב משולב ולשליחה לשירות שבמעלה הזרם.
4. לאחר הרכבת התגובה, `guardrailRegistry.runPostCallHooks(...)`
   מפעיל את אותה שרשרת על התגובה. `block: true` בשלב זה מבטל את התגובה
   משירות מעלה הזרם.

מנגנוני הגנה שזורקים חריגה מתועדים עם `error: <message>` ונרשמים ביומן באמצעות
`logger.warn`, אך השרשרת ממשיכה — זהו תכנון מסוג fail-open.

## תצורה

משתני סביבה שנקראים על ידי מנגנוני ההגנה המובנים:

| משתנה                                 | בשימוש על ידי             | השפעה                                                                                    |
| ------------------------------------- | ------------------------- | ---------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`        | יש להגדיר `false` כדי להשבית לחלוטין את הזיהוי.                                          |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`        | מדיניות הזרקה: `warn`,‏ `block` או `log`. הערך הישן `redact` אינו משכתב טקסט של הזרקה.   |
| `INJECTION_GUARD_MODE`                | `prompt-injection`        | מצב מגן ההזרקה; משמש גם כדגל תכונה במסד הנתונים אשר **דורס** את משתני הסביבה (DB > ENV). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`        | רמת החומרה המזערית שאותה `MODE=block` דוחה: `high` (ברירת המחדל), `medium` או `low`.     |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`        | כינוי ישן עבור `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                        |
| `PII_REDACTION_ENABLED`               | `pii-masker`              | כאשר הערך הוא `true`, מידע אישי מזהה בבקשה מושחר (ללא תלות במצב ההזרקה).                 |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (במורד הזרם) | שולט בהתנהגות המיסוך בצד התגובה.                                                         |

מנגנוני ההגנה של Modality Bridge קוראים את תצורת זמן הריצה ממאגר ההגדרות
המגובה במסד הנתונים (`getSettings()`), ולא ממשתני סביבה. המפתחות הראשיים של Vision הם
`modalityBridgeVisionEnabled`,‏ `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`,‏ `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`,‏ `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`,‏ `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`,‏ `modalityBridgeCacheTtlMinutes` ו-
`modalityBridgeCacheMaxEntries`. המפתחות הישנים
`visionBridge*` מתקבלים רק כמנגנון הגיבוי המתועד לקריאה במחזור אחד;
כתיבות מלוח הבקרה משתמשות במפתחות הראשיים. ברירות המחדל ופותר מנגנון הגיבוי
נמצאים ב-`src/shared/constants/modalityBridgeDefaults.ts`, בעוד שהקבועים הישנים
נשמרים ב-`src/shared/constants/visionBridgeDefaults.ts`.

אודיו משתמש ב-`modalityBridgeAudioEnabled`,‏ `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` וב-`modalityBridgeAudioMaxClips`, יחד עם הגדרות
`modalityBridgeCache*` המשותפות. לאודיו אין מנגנון גיבוי למפתחות ישנים, משום

הוא מושבת כברירת מחדל משום ש-FFmpeg/ffprobe הם תלויות תפעוליות אופציונליות,
והוספת כיתובים לפריימים מגדילה את זמן ההשהיה ואת עלות המודל.

## מנגנוני הגנה מותאמים אישית

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

שלבים:

1. צרו את `src/lib/guardrails/myGuardrail.ts` כך שירחיב את `BaseGuardrail`.
2. ממשו את `preCall` ו/או את `postCall`.
3. בצעו רישום בזמן הייבוא (הוספה מתוך `registerDefaultGuardrails`) או
   קראו ל-`guardrailRegistry.register(...)` בזמן ריצה — הרישום מחליף
   כל מנגנון הגנה קודם בעל אותו שם מנורמל.
4. הוסיפו בדיקות תחת `tests/unit/` (דוגמאות קיימות:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## בדיקות

השתמשו ב-`resetGuardrailsForTests()` בין הבדיקות כדי להתחיל ממצב ידוע.

תהליך העבודה הלילי (`.github/workflows/nightly-llm-security.yml`, ‏cron + הפעלה ידנית)
כולל שתי משימות:

- **`promptfoo-guard` (חוסמת)** — מריצה את `promptfoo eval -c promptfooconfig.yaml`
  עם `INJECTION_GUARD_MODE=block`. כל מקרה עוין (למשל "התעלם מכל
  ההוראות הקודמות…", פריצות בסגנון DAN) מוודא שהתשובה מכילה
  `error.code === "SECURITY_001"`, כלומר שמנגנון ההגנה אכן דחה את הבקשה.
- **`garak` (מייעצת)** — מריצה את garak עם `--probes promptinject,dan,leakreplay`
  מול מופע OmniRoute מקומי (`http://localhost:20128/v1`). ההרצה מותנית בסוד
  של ספק (`PROMPTFOO_PROVIDER_KEY`); היא מדלגת בצורה תקינה בהיעדרו ומסתיימת בסיומת
  `|| true`, כך שהיא מדווחת מבלי להכשיל את CI.

הכיסוי של פונקציית העזר של מנגנון ההגנה (`createInjectionGuard` / `withInjectionGuard`)
משתרע על כל נתיב `/v1` שמכיל הנחיה; טקסט ההנחיה נשלף מתוך
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` באמצעות
`extractMessageContents()` שב-`src/shared/utils/inputSanitizer.ts`.
