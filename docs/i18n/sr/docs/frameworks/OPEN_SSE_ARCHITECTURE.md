> **Укратко**: `open-sse/` је основни механизам за стримовање који покреће сваки LLM захтев у OmniRoute-у. Садржи око 1.400 датотека које имплементирају ток обраде захтева, извршиоце, сервисе, MCP сервер и слој за превођење. Овај водич објашњава како се ти делови уклапају.

**Извор:** `open-sse/` (пакет радног простора, око 1.440 `.ts` датотека које нису тестови)

## Зашто засебан пакет радног простора?

`open-sse/` је **самосталан радни простор** у OmniRoute монорепозиторијуму из неколико разлога:

1. **Поновна употребљивост** — `open-sse` се објављује као `@omniroute/open-sse` на npm-у, па други пројекти могу да га користе независно
2. **Јасне границе** — механизам за стримовање је одвојен од слоја корисничког интерфејса/базе података специфичног за OmniRoute
3. **Перформансе** — механизам нема Next.js зависности, што омогућава брже хладно покретање у CLI/serverless окружењима
4. **Верзионисање** — `open-sse` може да објављује издања сопственим темпом

```json
// package.json
"workspaces": ["open-sse"]
```

## Ток обраде захтева

Сваки LLM захтев пролази кроз **ток обраде од 5 фаза**:

```
                              ┌──────────────┐
   HTTP захтев                 │  1. УСМЕРИ   │   разрешавање комбинације, избор модела
   (Next.js рута)              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. ПРЕВЕДИ  │   конверзија формата (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. ИЗВРШИ   │   извршилац добављача, HTTP, поновни покушај, прекидач
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. СТРИМУЈ  │   SSE трансформација, повратни притисак
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. ЗАБЕЛЕЖИ │   праћење употребе, дневник позива, класификација грешака
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP одговор (SSE или JSON)
```

### Фаза 1: Усмеравање (services/combo.ts)

**Улазна тачка**: `handleComboChat()` у `services/combo.ts`

Разрешава захтев у конкретну `(provider, model, account, credentials)` n-торку:

- Проналази комбинацију према ID-у (или гради виртуелну комбинацију за `auto/*` моделе)
- Примењује стратегију усмеравања (приоритетну, пондерисану, кружну итд.)
- Филтрира неисправне добављаче (прекидач кола)
- Бира следеће одрживо одредиште

За `auto/*` моделе, ова фаза такође:

- Покреће алгоритам **оцењивања на основу 16 фактора** (`services/autoCombo/`)
- Бира пар `provider+model` на основу исправности, трошкова, кашњења итд.

### Фаза 2: Превођење (translator/)

Ако се изворни формат (нпр. OpenAI) разликује од циљног формата (нпр. Claude), захтев се **преводи**:

- Системски промпт → системска порука
- Дефиниције алата → формат алата специфичан за добављача
- Параметри закључивања/размишљања → еквиваленти специфични за добављача
- Нормализација улога порука (`developer` → `system` за системе који нису OpenAI)

`translator/index.ts` излаже:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### Фаза 3: Извршавање (executors/)

**Улазна тачка**: `getExecutor(providerId).execute(request, options)`

Сви добављачи користе `DefaultExecutor` (`executors/default.ts`) преко резервне опције фабрике `getExecutor()`. Извршилац:

- Гради URL узводног сервиса (`buildUrl()`)
- Додаје заглавља специфична за добављача (`buildHeaders()`)
- Трансформише тело захтева (`transformRequest()`)
- Шаље HTTP захтев уз поновне покушаје и експоненцијално повећавање паузе
- По потреби обавља освежавање аутентификације (OAuth добављачи)

Сви извршиоци проширују `BaseExecutor` (`executors/base.ts`, 1170 линија кода), који обезбеђује:

- Заједничку логику поновних покушаја
- Интеграцију са проксијем
- Интеграцију са прекидачем кола
- Куке за евидентирање употребе

### Фаза 4: Стримовање (utils/stream.ts)

За стримоване одговоре, извршилац враћа **ReadableStream**. Обрађивач:

- Прослеђује податке кроз SSE трансформацију (`createSSETransformStreamWithLogger`)
- Примењује heartbeat пингове ради откривања прекинутих веза
- Коректно обрађује прекид везе са клијентом (`pipeWithDisconnect`)
- Трансформише SSE → JSON за клијенте који не користе стримовање

За одговоре који се не стримују, извршилац враћа рашчлањени JSON објекат који се прослеђује без измена.

### Фаза 5: Евидентирање (services/usage.ts)

Након одговора (успешног или неуспешног), бележе се подаци о коришћењу:

- `prompt_tokens`, `completion_tokens`, `cached_tokens` из одговора
- `cost_usd` израчунат на основу података о ценама
- `latency_ms`, `status`, `error_class` у случају неуспеха
- Чувају се у табели `usage_history`

Артефакти евиденције позива (ако су омогућени) уписују се у `${DATA_DIR}/call_logs/`.

## Detaljan pregled ključnih datoteka

### chatCore.ts (5977 linija)

**Glavni rukovalac zahtevima**. Uprkos veličini, ima jasnu strukturu:

```ts
// Pseudostruktura datoteke chatCore.ts
export async function handleChat(request: NextRequest) {
  // 1. Autentifikacija + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. Validacija tela zahteva
  const body = await parseRequestBody(request);

  // 3. Otkrivanje formata + prevođenje
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. Kombinovano rutiranje
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // Nastavi sa sledećim odredištem
    }
  }

  // 5. Rezervna opcija u hitnim slučajevima
  return await emergencyFallback(body);
}
```

Uprkos tome što je u pitanju jedna ogromna funkcija, organizovana je u **odeljke sa komentarima** koji odgovaraju petostepenom cevovodu.

### combo.ts (4456 linija koda)

**Mehanizam za rutiranje** koji razrešava kombinaciju u uređenu listu odredišta.

```ts
// services/combo.ts
export async function handleComboChat(body, comboId): Promise<ChatResult> {
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      return await handleSingleModel(target, body);
    } catch (err) {
      log.warn("odredište nije uspelo, pokušava se sledeće", { target, err });

  throw new ComboExhaustedError("Sva odredišta nisu uspela");
}
```

````
## Izvršitelji (150 modula)

Uglavnom postoji po jedna datoteka za svakog dobavljača. Sve klase izvršitelja proširuju `BaseExecutor` i redefinišu ono što se razlikuje; ostali moduli predstavljaju pomoćne komponente za pojedinačne dobavljače (šeme alata, fetch/TTS adapteri i obrađivači specifičnosti).

### Uobičajeni obrasci

Dobavljači se razrešavaju pomoću `getExecutor(providerId)`, koji vraća konfigurisani izvršitelj. Dobavljači kompatibilni sa OpenAI/Anthropic koriste `DefaultExecutor` (`executors/default.ts`). Ponašanje specifično za dobavljača (osnovni URL, zaglavlja za autentifikaciju, verzija API-ja) konfiguriše se u `open-sse/config/providers/`, dok se transformacije tela zahteva obrađuju u `open-sse/translator/`.

**Prilagođeni URL** postavlja se putem konfiguracije dobavljača:

```ts
// Konfiguracija dobavljača u open-sse/config/providers/
export default {
````

**Prilagođena autentifikacija** obrađuje se putem konfiguracije autentifikacije registra dobavljača (API ključ, OAuth, profili zaglavlja).

````
### Fabrika izvršitelja

`executors/index.ts` izvozi `getExecutor(providerId)`:

```ts
import { getExecutor } from "@omniroute/open-sse/executors";

const executor = getExecutor("anthropic");
const result = await executor.execute({
  model: "claude-sonnet-4-5",
  messages: [...],
});
````

Razrešavanje se odvija putem `ExecutorRegistry` (`executors/registry.ts`): svaki specijalizovani izvršitelj deklarisan je u ugrađenoj tabeli datoteke `executors/index.ts` i registruje se pomoću `registerExecutor(alias, instance)` pri učitavanju modula; `getExecutor()` proverava registar i, za svakog dobavljača bez specijalizovanog unosa, vraća memorisani `DefaultExecutor` kao rezervnu opciju. Kompletno mapiranje aliasa na izvršitelje opisano je referentnim testom `tests/unit/executor-map-golden.test.ts`.

## Преводиоци

Превођење између **3 формата**: OpenAI, Anthropic, Gemini, као и новог Responses API-ја.

### Када се превођење обавља

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

Уобичајена превођења:

- `OpenAI → Anthropic`: засебно поље `system`, заглавље `x-api-key`
- `OpenAI → Gemini`: `contents` уместо `messages`, `systemInstruction`
- `OpenAI → Responses API`: низ `input`, стање `previous_response_id`

### Обрађени рубни случајеви

- улога `developer` → `system` за системе који нису OpenAI
- улога `system` → спаја се са првом корисничком поруком за GLM/ERNIE
- `json_schema` → Gemini-јеви `responseMimeType` + `responseSchema`
- `tools` → формат алата специфичан за провајдера
- Параметри размишљања (o1, Claude) → еквиваленти специфични за провајдера

## MCP сервер

`open-sse/mcp-server/` имплементира сервер **Model Context Protocol**:

- **110 алата** (управљање провајдерима, комбинације, меморија, кеш, компресија, прокси, вештине, гејмификација, додаци, Notion, Obsidian, локални корпус)
- **3 транспорта**: stdio, SSE, Streamable HTTP
- **33 опсега** за прецизну ауторизацију

### Регистрација алата

Алатке се региструју као самосталне датотеке у `open-sse/mcp-server/tools/`, при чему свака извози назив, шему, обрађивач и опсег:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### Транспорти

```ts
// stdio (употреба преко CLI-ја)
startMcpStdio(server);

// SSE (стримовање засновано на HTTP-у)
startMcpSse(server, port);

// Streamable HTTP (савремени MCP)
startMcpStreamable(server, port);
```

### Ауторизација

Сваки позив алата пролази кроз провере опсега (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## Трансформатори

`open-sse/transformer/` конвертује између формата **Chat Completions** и **Responses API**.

### Зашто засебан трансформатор?

Responses API је нови OpenAI формат са **разговорима са стањем** (`previous_response_id`). Када клијент пошаље Responses захтев, OmniRoute:

1. Интерно конвертује Responses → Chat Completions
2. Шаље провајдеру (било ком провајдеру који подржава Chat Completions)
3. Конвертује одговор назад у Responses формат
4. Стримује конвертовани одговор клијенту

Трансформатор (`transformer/responsesTransformer.ts`) обезбеђује:

```ts
createResponsesApiTransformStream(): TransformStream
```

Овим се обрађују:

- догађаји `response.output_item.added`
- догађаји `response.output_text.delta`
- догађај `response.completed`
- Мапирање позива алата (`function_call` ↔ `tool_calls`)

## Конфигурација

`open-sse/config/` садржи конфигурациони слој:

| Датотека                      | Намена                                                  |
| ----------------------------- | ------------------------------------------------------- |
| `providerRegistry.ts`         | Регистар модела за ћаскање у каталогу од 374 провајдера |
| `providerModels.ts`           | Алијаси модела, мапирање формата                        |
| `constants.ts`                | Временска ограничења, лимити, статусни кодови           |
| `defaultThinkingSignature.ts` | Подразумевани Claude потпис размишљања                  |
| `modelStrip.ts` (у сервисима) | Уклањање поља за сваког провајдера                      |

### Шема регистра провајдера

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

Zod валидација при учитавању модула осигурава да су све конфигурације провајдера важеће.

## Додавање нове компоненте

### Додавање новог сервиса

1. Креирајте `open-sse/services/[serviceName].ts` са јасно усмереном одговорношћу
2. Извезите главну функцију обрађивача и све константе
3. Додајте јединичне тестове у `tests/unit/services/[serviceName].test.mjs`
4. Интегришите у ток обраде захтева у `handlers/chatCore.ts` (ако је повезано са усмеравањем)
5. Ажурирајте логику усмеравања у `combo.ts` ако сервис утиче на избор одредишта
6. Документујте у овој датотеци

### Додавање новог извршиоца

1. Креирајте `open-sse/executors/[provider].ts` који проширује `BaseExecutor`
2. Региструјте у `config/providerRegistry.ts`
3. Додајте у фабрику `executors/index.ts`
4. Додајте јединичне тестове за извршиоца
5. Документујте у `docs/architecture/ARCHITECTURE.md`

### Додавање новог MCP алата

1. Креирајте или ажурирајте `open-sse/mcp-server/tools/[category]Tools.ts`
2. Дефинишите Zod шему за улазне податке
3. Региструјте алат у `mcp-server/index.ts`
4. Додајте у матрицу опсега у `mcp-server/auth/`
5. Додајте јединичне тестове
