> **ბოლოს განახლდა:** 2026-08-29 — v3.8.51 (ვიდეო ხიდის ტრანსკრიპტის წარმომავლობა დეკლარირებულია გამომძახებლის მიერ, ჯერ არ არის სერვერის მიერ დამოწმებული — განმარტებულია #11661-ის მიხედვით)

Guardrails უზრუნველყოფენ უსაფრთხოებას, პოლიტიკას და კონტენტის ტრანსფორმაციებს OmniRoute-სა და upstream პროვაიდერებს შორის საზღვარზე. თითოეულ guardrail-ს შეუძლია შეამოწმოს (და სურვილისამებრ უარყოს, გარდაქმნას ან ანოტირება გაუკეთოს) მოთხოვნის payload-ები (`preCall`) და upstream პასუხები (`postCall`).

სისტემა არის **fail-open**: თუ guardrail-ის შესრულებისას შეცდომა მოხდა, რეგისტრატორი აღრიცხავს შეცდომას და აგრძელებს შემდეგ guardrail-ზე, ნაცვლად მოთხოვნის შეწყვეტისა. დაბლოკვა არის მკაფიო გადაწყვეტილება (`block: true`), არასდროს შემთხვევითობა.

### ხედვის ხიდი (`visionBridge.ts`) — მოდალობის ხიდი PR-1

იჭერს გამოსახულებების შემცველ მოთხოვნებს, რომლებიც მიმართულია **ხედვის მხარდაჭერის არმქონე მოდელებისკენ**, და ან მთელ მოთხოვნას გადაამისამართებს ხედვის მხარდაჭერის მქონე მოდელზე, ან upstream გამოძახებამდე გამოსახულების ნაწილებს ჩაანაცვლებს კონფიგურირებადი ხედვის მოდელის მიერ შექმნილი ტექსტური აღწერებით. ეს მხოლოდ ტექსტზე მომუშავე პროვაიდერებს საშუალებას აძლევს, გამჭვირვალედ დაამუშაონ მულტიმოდალური მონაცემები.

პროცესი:

1. გამოტოვება, თუ სამიზნე მოდელს უკვე აქვს ხედვის მხარდაჭერა (თუ ის იძულებითი ხიდის სიაში `isVisionBridgeForcedModel` არ არის).
2. გამოსახულების ნაწილების ამოღება `extractImageParts(messages)`-ის მეშვეობით
   (`visionBridgeHelpers.ts`), რომელიც დელეგირებას ახდენს **მედიის ერთიან
   დეტექტორზე** `detectMediaParts()` ფაილში `open-sse/utils/mediaParts.ts` —
   ჭეშმარიტების ერთადერთ წყაროზე, რომელსაც combo თავსებადობის ფილტრიც იყენებს.
   ამოღება ნებადართულია მხოლოდ იმ ფორმების ზედა დონის ნაწილებისთვის,
   რომელთა უკან ჩასმაც `replaceImageParts`-ს შეუძლია (ამოღება↔ჩანაცვლების კონტრაქტი): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` და Responses API `input_image`. ჩადგმული დამთხვევები და
   მხოლოდ ინდიკატორის შემცველი ფორმები combo ფილტრისთვისაა განკუთვნილი და არასოდეს ამოიღება.
   გამოტოვება, თუ არცერთი არ მოიძებნა.
3. შესრულების დროის კონფიგურაციის განსაზღვრა `resolveVisionBridgeRuntimeSettings()`-ის მეშვეობით
   (`src/shared/constants/modalityBridgeDefaults.ts`): ახალ `modalityBridge*`
   პარამეტრების გასაღებებს უპირატესობა ენიჭება; ძველი `visionBridge*` გასაღებები რჩება
   **ერთი ციკლის სარეზერვო ვარიანტად** (უკან დაბრუნების ფანჯარა). თუ ხიდი გამორთულია,
   გამოტოვება ხდება ნებისმიერი მედიის დათვალიერებამდე.
4. რეჟიმის ამომრჩევი (`modalityBridgeVisionMode`, იხილეთ ქვემოთ მოცემული ცხრილი)
   განსაზღვრავს გადაამისამართებასა და აღწერას შორის არჩევანს. გადაამისამართება აბრუნებს `modifiedPayload`-ს,
   რომელშიც მხოლოდ `model` არის ჩანაცვლებული, და მეტამონაცემებს `{ rerouted, fromModel, toModel, imagesKept }`.
5. აღწერის გზა: გამოსახულებების რაოდენობის შეზღუდვა `maxImages`-ით, ამოცანაზე მორგებული მოთხოვნის შედგენა,
   აღწერის კეშის შემოწმება, ხედვის მოდელის **პარალელურად**
   გამოძახება (`Promise.allSettled`) და მათ ადგილას `[Image N]: <description>` ტექსტური ნაწილების
   ჩასმა. წარუმატებელი აღწერა იძლევა `null`-ს და გამოსახულების თავდაპირველი ნაწილი
   **შენარჩუნდება** (#4012) — გარდა combo აღწერის გზისა, როდესაც ყველა
   აღწერა წარუმატებელია; ამ შემთხვევაში დადასტურებულად ხედვის მხარდაჭერის არმქონე upstream იღებს
   `(მიუწვდომელია — ხედვის მხარდაჭერის მქონე პროვაიდერი დაკავშირებული არ არის)` ჩანაცვლებით ტექსტს (#8430).
6. `modifiedPayload`-ისა და მეტამონაცემების დაბრუნება (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### API გასაღების მოქმედების არეალი (`visionBridgeKeyScope.ts`)

როდესაც გამომძახებლის API გასაღები ზღუდავს `allowedConnections`-ს, კვოტების ჯგუფებს
(`allowedQuotas`) ან მოდელებს (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), ხიდი
გადაამისამართებისა და აღწერისთვის ირჩევს მხოლოდ იმ მოდელებსა და კავშირებს, რომელთა გამოყენებაც გასაღებს შეუძლია.
შემდეგ აღწერის გამოძახება ყოველთვის გადის OmniRoute-ის თვითმარყუჟით,
`x-omniroute-self-loop-key-id` სათაურის გამოყენებით, რათა მიმღებმა ჩატის მოთხოვნამ
ხელახლა უზრუნველყოს ამ გასაღების კავშირებისა და მოდელების პოლიტიკის აღსრულება. `enforceApiKeyPolicy()`
ამ სათაურს მხოლოდ თვითმარყუჟის bearer-თან ერთად ითვალისწინებს, ამიტომ მას მხოლოდ
წვდომის შეზღუდვა შეუძლია, ხოლო id, რომლის მოძიებაც ვერ ხერხდება, უარყოფილია.

თუ გასაღებისთვის არცერთი ხედვის მოდელი არ არის ნებადართული, აღწერის გზა განზე გადგება და
მოთხოვნა უცვლელად გაივლის — იგივე fail-open ქცევით, როგორც გამორთული
დამცავი მექანიზმის შემთხვევაში (მეტამონაცემები `{ skipped: true, reason: "no_permitted_vision_model" }`).
გასაღების გარეშე გაგზავნილი მოთხოვნები და გასაღებები, რომლებსაც ეს შეზღუდვები არ აქვთ, ზუსტად
ისევე იქცევა, როგორც ადრე.

#### ამოცანაზე მორგებული აღწერის მოთხოვნა (`modalityBridgeVisionTaskAware`)

ნაგულისხმევად **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) საბაზისო აღწერის prompt-ს უმატებს **მომხმარებლის ბოლო შეტყობინების** ტექსტს (შემოკლებულს 500 სიმბოლომდე), რათა აღწერა მიმართოს იმისკენ, რაც მომხმარებელმა რეალურად მოითხოვა (codex-vision-proxy-ის შაბლონი), და vision მოდელს სთხოვს ხილული ტექსტის ტრანსკრიფციას. თუ flag გამორთულია — ან მომხმარებლის ტექსტი არ არსებობს — საბაზისო prompt უცვლელად გამოიყენება.

აღწერის self-loop-ის საკუთარი OpenAI-თან თავსებადი მოთხოვნა (`callVisionModelSingle()`
`visionBridgeHelpers.ts`-ში) ყოველთვის ითხოვს `image_url.detail: "high"` —
უპირობოდ, ყოველი გამომძახებლის/პროვაიდერისთვის და კლიენტის რომელიმე სიგნალზე დამოკიდებულების გარეშე.
დაბალი დეტალიზაციის შერჩევა აუარესებს OCR-ის სიზუსტეს ზუსტად იმ ტექსტის ტრანსკრიფციის
ამოცანისთვის, რომელსაც ეს prompt ითხოვს, ამიტომ თავად აღწერის გამოძახება ყოველთვის ითხოვს მაღალ
დეტალიზაციას, მიუხედავად იმისა, დეტალიზაციის რა დონე გამოიყენა თავდაპირველმა შემომავალმა მოთხოვნამ. ეს
გავლენას ახდენს მხოლოდ შიდა აღწერის მოთხოვნის body-ზე; ის არ ცვლის იმას, თუ როგორ
გადასცემს OmniRoute გამომძახებლის საკუთარ `image_url.detail`-ს ძირითად მოთხოვნაში —
ეს ნაგულისხმევი მნიშვნელობა ცალკე გამოიყენება და მხოლოდ აღმოჩენილი OpenCode კლიენტებისთვის,
`defaultImageDetail()`-ში (`open-sse/handlers/chatCore/upstreamBody.ts`). აღწერის self-loop-ის
Anthropic wire-format-ის განშტოებას `detail` ველი არ აქვს და არცერთი ნაგულისხმევი მნიშვნელობა
მასზე გავლენას არ ახდენს.

#### აღწერის გამომავალი მონაცემების ზღვარი (`modalityBridgeVisionMaxChars`)

| გასაღები                       | ნაგულისხმევი მნიშვნელობა | დიაპაზონი        |
| ------------------------------ | ------------------------ | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`                      | `0` ან 100–50000 |

`0` (ნაგულისხმევი) ნიშნავს, რომ **ზღვარი არ არსებობს** — `callVisionModel()`-ის მიერ
დაბრუნებული აღწერა უცვლელად გადაიცემა, რაც არსებულ ქცევას ინარჩუნებს.
100–50000 დიაპაზონში ნებისმიერი მნიშვნელობა აღწერას ამოკლებს
`…` სუფიქსით, სანამ ის `[Image N]: <description>` სახით უკან ჩაისმება
(`VisionBridgeGuardrail.preCall()` `src/lib/guardrails/visionBridge.ts`-ში).
გაზარდეთ ეს მნიშვნელობა დეტალებით დატვირთული OCR ამოცანებისთვის, სადაც შემდგომ მოდელს
სრული ტრანსკრიფცია სჭირდება; შეამცირეთ იგი მრავალსიტყვიანი vision მოდელების მიერ token-ების
გამოყენების შესაზღუდად. dashboard-ის ველი მდებარეობს Vision ჩანართის Advanced პანელზე
(`modality-bridge-max-chars` `ModalityBridgeVisionTab.tsx`-ში) და 1-დან 99-მდე
ნებისმიერ მნიშვნელობას მინიმალურ ზღვრამდე, 100-მდე, ზრდის, ხოლო ცალსახად მითითებულ `0`-ს
უცვლელად ტოვებს — `0` თავისთავად დასაშვები Zod მნიშვნელობაა
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`) და არა უბრალოდ
„დაუყენებელი“ ნაგულისხმევი მნიშვნელობა.

#### აღწერის cache (`modalityBridge/bridgeCache.ts`)

მეხსიერებაში განთავსებული LRU + TTL cache აღწერის შედეგებისთვის, რომელიც მთელი პროცესის მასშტაბით საზიაროა.
გასაღები = `sha256(imageRef + composedPrompt + configuredBridgeModel)` სიგრძის პრეფიქსით
ჩარჩოებაში (ველების საზღვრების შეჯახებების გარეშე). მოდელის კომპონენტი არის
**კონფიგურირებული** bridge მოდელი და არა მოდელი, რომელმაც რეალურად უპასუხა —
`callVisionModel`-მა შეიძლება შიდა fallback გამოიყენოს, ხოლო თითოეული მცდელობის მიხედვით
გასაღების შექმნა cache-ს დაანაწევრებდა. წარუმატებელი აღწერები cache-ში არასოდეს ინახება. პარამეტრები:

| გასაღები                        | ნაგულისხმევი მნიშვნელობა | დიაპაზონი |
| ------------------------------- | ------------------------ | --------- |
| `modalityBridgeCacheEnabled`    | `true`                   | —         |
| `modalityBridgeCacheTtlMinutes` | `60`                     | 1–1440    |
| `modalityBridgeCacheMaxEntries` | `200`                    | 10–5000   |

#### დისტანციური გამოსახულების ნორმალიზაცია (self-loop აღწერა/base64 მიღება)

როდესაც bridge თავად იღებს **დისტანციურ** გამოსახულებას — Anthropic-ის აღწერის
self-call და claude-wire-format-ის base64 კონვერტაცია
(`ensureBase64ImagesForClaudeWire`), ორივე
`fetchRemoteImageAsDataUri()`-ის მეშვეობით `visionBridgeHelpers.ts`-ში — მიღებული data
URI გადის `normalizeDataUri()`-ში
(`open-sse/utils/imageNormalize.ts`), სანამ vision მოდელის მოთხოვნაში ჩაშენდება.
ზედმეტად დიდი გამოსახულებები მცირდება **2048px სიგრძის წიბომდე** (რაც ემთხვევა
ზომის ლიმიტს, რომელსაც OpenAI/Anthropic უკვე სერვერის მხარეს იყენებენ), რაც ამცირებს
ატვირთვის ბაიტებს/დაყოვნებას vision მოდელის მიერ დანახული მონაცემების შეუცვლელად. ზომის ცვლილება
იყენებს `sharp`-ს, რომელიც dynamic import-ის მეშვეობით იტვირთება: პლატფორმაზე, სადაც მისი native
binary-ის ჩატვირთვა ვერ ხერხდება, `normalizeDataUri()` **არასოდეს აგდებს გამონაკლისს** — ის
fallback-ის სახით თავდაპირველ ბაიტებს უცვლელად ატარებს, ამიტომ აღწერის/base64-კონვერტაციის
გზა ყოველთვის მუშაობას აგრძელებს. არაგამოსახულებითი ბაიტებიც (მიღებული მონაცემები, რომლებიც
დეკოდირებადი გამოსახულება არ აღმოჩნდა) უცვლელად გადაიცემა. ეს ნორმალიზაცია შემოიფარგლება
იმ გამოსახულებებით, რომლებსაც bridge საკუთარი self-call-ისთვის იღებს — ის არასოდეს
გამოიყენება გამომძახებლის პირდაპირ გადაცემულ დაუმუშავებელ payload-ზე, რაც შეესაბამება
მხოლოდ opt-in ცვლილების პრინციპს (Hard Rule #20).

#### გამჭვირვალობის header + სტატისტიკა

აღწერით გარდაქმნილი პასუხები შეიცავს
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`

გადამისამართებული მოთხოვნები header-ს **არ** იღებს — payload უცვლელი იყო, ხოლო მოდელის
ჩანაცვლება უკვე ჩანს პასუხის body-ის `model` ველში.

`GET /api/modality-bridge/stats` (მართვის ავტორიზაცია, იგივე დონე, რაც
`GET /api/settings`-ისთვის) აბრუნებს მეხსიერებაში შენახულ, თითოეული მოდალობის
მთვლელებს:
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` `vision`, `audio` და
`video` მოდალობებისთვის. `averageLatencyMs` მნიშვნელის სახით იყენებს
`latencySamples`-ს და არა ყველა მცდელობას; დროის გაზომვის გარეშე შესრულებული
ოპერაცია ხელოვნურად არ ქმნის ნულმილიწამიან ნიმუშს. `bridged` წარმატებული
კონვერსიებისთვის უკუთავსებად ფსევდონიმად რჩება; წარუმატებელი მცდელობები მას
არ ზრდის.
დიზაინის მიხედვით, მთვლელები პროცესის ხელახლა გაშვებისას ნულდება
(ტელემეტრია და არა აღრიცხვა).

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

აუდიოს შემცველ ჩატის მოთხოვნებს აკავებს მანამ, სანამ ისინი აუდიოშეტანის
მიმღებად უცნობ სამიზნემდე მიაღწევს. ის ჩატის მოთხოვნას არასოდეს გადაამისამართებს:
აუდიოს ნაწილები არსებული OpenAI-თავსებადი multipart საბოლოო წერტილის მეშვეობით
ტრანსკრიბირდება, ხოლო არჩეული ჩატის მოდელი ტექსტური ტრანსკრიპტებით აგრძელებს
მუშაობას.

ნაკადი:

1. ამოხსენით `supportsAudio` `getResolvedModelCapabilities()`-ის მეშვეობით.
   უპირატესობა ენიჭება პროვაიდერთა რეესტრში აშკარად მითითებულ მეტამონაცემებს,
   შემდეგ — მოდელის სტატიკურ მეტამონაცემებს, შემდეგ კი სინქრონიზებულ
   `modalities_input`-ს. გამოცხადებული შეყვანის სია `audio`-ს გარეშე არის
   `false`; შესაძლებლობის დამადასტურებელი მონაცემების არარსებობისას მნიშვნელობა
   რჩება `null`. როგორც `false`, ისე `null` ააქტიურებს კონსერვატიულ ხიდს,
   ხოლო `true` მას გვერდს უვლის.
2. ამოხსენით `modalityBridgeAudio*` პარამეტრები და საზიარო `detectMediaParts()`
   დეტექტორის მეშვეობით თითოეული შეტყობინებიდან ამოიღეთ ზედა დონის აუდიოს
   ნაწილები, რომელთა ამოჭრა და ჩანაცვლებაც შესაძლებელია. მხარდაჭერილი სადენური
   ფორმებია OpenAI `input_audio`, `audio_url` და
   `source.media_type: "audio/*"`. ჩადგმული აუდიო მარშრუტიზაციისთვის
   აღმოჩენილი იქნება, თუმცა ამოჭრის გზით არ წაიშლება. სამუშაოს მოცულობა
   შეზღუდულია `modalityBridgeAudioMaxClips`-ით; მომდევნო ნაწილები უცვლელი რჩება.
3. გამოიყენეთ კონფიგურირებული `provider/model`, ან მიეცით
   `selectAudioBridgeModel()`-ს საშუალება, სტაბილური კატალოგის თანმიმდევრობით
   გაიაროს `AUDIO_TRANSCRIPTION_PROVIDERS` და აირჩიოს პირველი მოდელი, რომელსაც
   აქტიური პროვაიდერის გამოსადეგი ავტორიზაციის მონაცემი აქვს.
4. `callAudioTranscription()` base64/data-URI აუდიოს multipart `file`-ად
   გარდაქმნის, ან დისტანციურ `audio_url`-ს მხოლოდ საჯარო გასასვლელი კავშირის
   დამცავი მექანიზმის გავლით, DNS-ის მიბმითა და 25 MB-იანი ზღვრის დაცვით
   ჩამოტვირთავს. შემდეგ ის ფაილსა და არჩეულ მოდელს POST მოთხოვნით აგზავნის
   ლოკალურ `/v1/audio/transcriptions` თვითმარყუჟში, ავტორიზაციისთვის კი
   `resolveSelfLoopBearer()`-ს იყენებს. არსებული ტრანსკრიფციის მარშრუტი
   ავტორიზაციის მონაცემების ჩვეულებრივ მოძიებას, დაყოვნების/სიხშირის შეზღუდვის
   დამუშავებასა და პროვაიდერთან გადამისამართებას ასრულებს.
5. წარმატებული გამოძახებები თავიანთ ნაწილებს `[Audio N]: <transcript>`-ით
   ანაცვლებს. გამოძახებები `Promise.allSettled`-ით სრულდება: ცალკეული
   წარუმატებლობისას თავდაპირველი აუდიონაწილი შენარჩუნდება (#4012 კონტრაქტი).
   თუ ყველა გამოძახება წარუმატებელია და სამიზნისთვის დადასტურებულია
   `supportsAudio === false`, ნაწილები გარდაიქმნება
   `[Audio N]: (unavailable — no STT provider connected)`-ად (#8430 კონტრაქტი).
   უცნობი სამიზნის (`null`) შემთხვევაში, ყველა გამოძახების წარუმატებლობისას
   მოთხოვნა უცვლელი რჩება. დადასტურებულად მხოლოდ ტექსტის მიმღები სამიზნე,
   რომლისთვისაც გამოსადეგი STT ავტორიზაციის მონაცემი არ არსებობს, იმავე
   აშკარა ჩამნაცვლებელს ქსელური გამოძახების გარეშე მიიღებს.

წარმატებული ტრანსკრიპტები პროცესის მასშტაბით საზიარო Modality Bridge LRU/TTL
ქეშს იყენებს. გასაღები აერთიანებს აუდიომიმართვას, სტაბილურ
`audio-transcription` ოპერაციის ჭდესა და არჩეულ STT მოდელს; წარუმატებლობები
არასოდეს ქეშირდება. აუდიოს დამუშავების მცდელობები განაახლებს საზიარო
`bridged`, `cacheHits`, `failures` და `lastUsedAt` მთვლელებს.
გარდაქმნილ პასუხებს ახლავს
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; უცვლელ
მოთხოვნებს Audio Bridge სეგმენტი არ ემატება.

გაშვების გარემოს პარამეტრები DB-ში ინახება და Zod-ით მოწმდება:

| გასაღები                      | ნაგულისხმევი | დიაპაზონი            |
| ----------------------------- | ------------ | -------------------- |
| `modalityBridgeAudioEnabled`  | `true`       | —                    |
| `modalityBridgeAudioModel`    | `""`         | ავტომატური ან STT ID |
| `modalityBridgeAudioTimeout`  | `60000`      | 1000–300000          |
| `modalityBridgeAudioMaxClips` | `3`          | 1–10                 |

საერთო კეშს კვლავ მართავს `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` და `modalityBridgeCacheMaxEntries`.

### ვიდეოხიდი (`videoBridge.ts`, `videoBridgePipeline.ts`)

URI-ები. ტექსტში არსებული ჩვეულებრივი ფაილის სახელები ვიდეოდ არ განიხილება.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) პასუხისმგებელია მოთხოვნის შემოვლაზე,
შესაძლებლობის/პოლიტიკის შემოწმებაზე, თითოეული მოთხოვნის აგრეგაციასა და პასუხის
სასარგებლო დატვირთვაზე. თითოეულ ვიდეოსთან დაკავშირებული სამუშაო — მიღება,
სრული შედეგის კეში, კადრების თანმიმდევრობის აღწერა (რომელიც აერთიანებს გამომძახებლის
მიერ დეკლარირებულ აუდიოტრანსკრიპტს) და თითოეული მცდელობის
მეტრიკები/შეწყვეტა/გასუფთავება — დაფარულია `processVideoPart`-ის მიღმა
`videoBridgePipeline.ts`-ში, რომელიც `preCall`-ის ციკლში თითოეული ვიდეონაწილისთვის
ერთხელ გამოიძახება. ეს მოდული ასევე განსაზღვრავს პორტების მკაფიო საზღვრებს:
`VideoMediaBrokerPort` (ბაიტების მიღება და შერჩეული კადრების ამოღება),
`VideoAudioTranscriptionPort` (გამომძახებლის მიერ დეკლარირებული აუდიოტრანსკრიპტის
შერჩეული კადრების აღწერებთან გაერთიანება) და `VideoDrilldownPort` (კადრების
დეტალიზაციის შენახვის საზღვარი; ის ჯერ არ არის დაკავშირებული
`processVideoPart`-თან — ამჟამად დეტალიზაციის ჩანაწერებს მხოლოდ ცალკე
`/api/modality-bridge/video/drilldown` მარშრუტი წერს).

საჯარო `/v1` მოთხოვნის გზა არასოდეს ახდენს ქვეპროცესის იმპორტირებას ან გამოძახებას.
დისტანციური ვიდეოები იტვირთება 50 MiB-ის ზღვრის დაცვით; ჩაშენებული base64 ვიდეოებისთვის
მოქმედებს კონსერვატიული, თითო ვიდეოზე 36 MiB-ის დეკოდირებული მონაცემების ლიმიტი,
რათა მოდელის/შეტყობინებების/ჩარჩოების კონვერტი საჯარო JSON მოთხოვნის მიღების
50 MiB-იან ლიმიტში დარჩეს. ჩაშენებული მონაცემების სიგრძე და დეკოდირებული ზომის
შეფასებები მეხსიერების გამოყოფამდე მოწმდება. საწყისი დისტანციური URL-ისა და ყოველი
გადამისამართებისთვის HTTPS სავალდებულოა; გამოიყენება არსებული, მხოლოდ საჯარო
მისამართებზე ორიენტირებული გამავალი კავშირის დაცვა DNS-ის მიბმით. შემდეგ ბაიტები
გადიან ზუსტად განსაზღვრულ შიდა
`POST /api/modality-bridge/video/extract` საბროკერო საზღვარზე. ეს მარშრუტი არის როგორც
`LOCAL_ONLY`, ისე `SPAWN_CAPABLE`, იღებს მხოლოდ პროცესისთვის სპეციფიკური
ავთენტიფიკაციით დაცულ, სანდო loopback-მოთხოვნას და არასოდეს იღებს URL-ს,
ფაილური სისტემის გზას, შესრულებად ფაილს ან არგუმენტების სიას. API-ის სხეულის
ზომის დამუშავების ჯაჭვი და დამმუშავებლის სხეულის ინკრემენტული წამკითხველი
ერთმანეთისგან დამოუკიდებლად უზრუნველყოფენ ბროკერის შემავალი მონაცემების 50 MiB-იან
ლიმიტს. მისი შეზღუდული რიგი ერთდროულად ერთ ამოღებას ასრულებს, ოთხ მომლოდინე

კადრებს სათაურები თანამიმდევრულად ენიჭება კონფიგურირებული Video მოდელით. ცარიელი Video ჩანაცვლება Vision-ის პარამეტრს მემკვიდრეობით იღებს; თუ ორივე ცარიელია, Vision-ის ავტომარშრუტიზატორი ირჩევს ეფექტურ, ხედვის შესაძლებლობის მქონე მოდელს. წარმატებული სათაურები თავდაპირველ ნაწილს ანაცვლებს სტაბილური `[Video description:` პრეფიქსით, რომელიც ტექსტს ასევე აღნიშნავს, როგორც არასანდო, მედიიდან მიღებულ დაკვირვებას, და ქვედა დონის მოდელებს მიუთითებს, არ შეასრულონ მედიაში ნაპოვნი ინსტრუქციები. კადრის სათაურების ქეშის გასაღებები მოიცავს JPEG ბაიტებს, მოთხოვნას, დროის ნიშნულსა და ეფექტურ მოდელს; ქეშდება მხოლოდ წარმატებული სათაურები. ქეშის ჩანაწერები ინარჩუნებს ფაქტობრივ წარმატებულ პროდიუსერ მოდელს, მათ შორის სარეზერვო მოდელს; როდესაც სხვადასხვა კადრი სხვადასხვა მოდელმა შექმნა, bridge აბრუნებს `mixed`-ს. ქეშში დამთხვევა ხელახლა იყენებს ამ პროდიუსერის იდენტობას, ნაცვლად იმისა, რომ მას მოთხოვნილი მარშრუტიზაციის გეგმის იარლიყი მიაკუთვნოს. მთლიანი ვიდეოს შედეგების ქეში ინდექსირდება ყველა იმ შეყვანის მიხედვით, რომელიც შედეგს ცვლის — მოთხოვნა, ეფექტური მოდელი, შერჩევის პოლიტიკა, კადრების რაოდენობა, სემანტიკური ანალიზის რეჟიმი, ნორმალიზებული ფოკუსის მინიშნების SHA-256 ანაბეჭდი, ფოკუსის ფანჯარა, `transcript`, `audioTranscript` და საკონტაქტო ფურცლის დროშა — ამიტომ რომელიმე ამ განზომილების ცვლილება იწვევს ქეშში აცდენას და არა მოძველებული შედეგის ხელახლა გამოყენებას. ვიზუალური დუბლიკატების მოცილების პოლიტიკის ვერსია, ზღვარი და კანდიდატი კადრების შეზღუდული რაოდენობა ასევე აშკარად არის მოცემული შედეგების ქეშის გასაღებსა და მეტამონაცემებში; შესაბამისად, პოლიტიკის ცვლილება ვერ გამოიყენებს მოძველებულ მთლიანი ვიდეოს აღწერას. შედეგების ქეშის v4 მეტამონაცემები ინახავს რეჟიმსა და ანაბეჭდს, მაგრამ არასოდეს — მომხმარებლის დაუმუშავებელ ამოცანას. დამცავი მექანიზმის მეტამონაცემები ასახავს როგორც მოთხოვნილ, ისე ეფექტურ ანალიზის რეჟიმებს; მოთხოვნილი `focused` რეჟიმი გამოსადეგი მომხმარებლის ტექსტის გარეშე ეფექტურად `full` რეჟიმად აისახება.

დამცავი მექანიზმი იღებს ყველა მხარდაჭერილ ვიდეონაწილს, თუმცა აღწერს არაუმეტეს `modalityBridgeVideoMaxVideos` რაოდენობისა. სამიზნისთვის, რომლის `supportsVideo === false` დადასტურებულია, წარუმატებელი და ლიმიტს გადაცილებული ვიდეოები გარდაიქმნება აშკარა უსაფრთხო ტექსტურ მარკერებად, რათა არცერთი დაუმუშავებელი ვიდეო არ დარჩეს. როდესაც შესაძლებლობა უცნობია, ეს ნაწილები ინარჩუნებს საკუთარ ვიდეო-მატარებელს; ნებისმიერი სარეზერვო ტრანსკრიპტი მიჰყვება ზემოთ აღწერილ შეზღუდულ ტექსტურ გარდაქმნას. სამიზნეები, რომელთა `supportsVideo === true`, bridge-ს გვერდს უვლის. კლიენტის მოთხოვნის შეწყვეტის სიგნალი ვრცელდება ჩამოტვირთვაზე, broker-ის რიგზე, ქვეპროცესებსა და სათაურების მინიჭების გამოძახებებზე; შეწყვეტა ვიდეოებს შორის აჩერებს შესრულებას და დაუმუშავებელი მედიის დაშვებით არასოდეს სრულდება.

### PII-ის შემნიღბავი (`piiMasker.ts`)

ეშვება **ორივე** ეტაპზე.

- **`preCall`** ახდენს payload-ის კლონირებას, გაივლის `system`, `messages`, `input` და
  `prompt` ველებს (მათ შორის უბრალო სტრიქონულ ელემენტებს) და სტრიქონულ
  `content`/`text` ველებზე იყენებს `processPII()`-ს (მოდულიდან
  `@/shared/utils/inputSanitizer`). როდესაც `PII_REDACTION_ENABLED=true`, აღმოჩენილი
  PII გამავალი payload-იდან იფარება. ეს დამოუკიდებელია `INPUT_SANITIZER_MODE`-ისგან
  (რომელიც მხოლოდ prompt injection-ის პოლიტიკას აკონტროლებს). როდესაც დაფარვა
  გამორთულია, გამოძახება კონტენტის გადაწერის გარეშე აღრიცხავს აღმოჩენების
  რაოდენობას.
- **`postCall`** ახდენს პასუხის ღრმა კლონირებას, უშვებს `sanitizePIIResponse()`-ს და
  Responses-API-ის ფორმის შემნიღბავს (`maskResponsesOutput` — მოიცავს
  `output_text`-სა და `output[].content[].text`-ს). თუ რაიმე დაფარვა მოხდა,
  შეცვლილი პასუხი ანაცვლებს თავდაპირველს.

დამცავი მექანიზმი არასოდეს ბლოკავს; ის მხოლოდ ანოტაციას ამატებს
(`meta.detections`, `meta.redacted`) ან გადაწერს.

  მნიშვნელობები), ინახება მეხსიერებაში და გადატვირთვისას ნულდება
  (`src/lib/pii/piiDetectionStats.ts`). ისინი მხოლოდ მაშინ იზრდება, როცა
  შენიღბვა ჩართულია.

პარამეტრები ინახება `key_value` ცხრილში (namespace `pii_settings`,
`src/lib/db/piiSettings.ts`) და იკითხება 1 s-იანი კეშის მეშვეობით. API:

| მეთოდი | მისამართი                | დანიშნულება                                                                |
| ------ | ------------------------ | -------------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | ალმის მდგომარეობა, `enabledTypes`, `customPatterns`, აღმოჩენის მრიცხველები |

| `POST` | `/api/settings/pii/test` | ერთი შაბლონის საცდელი გაშვება მაქსიმუმ 8 KB ნიმუშზე; არაფერი ინახება       |

(`src/shared/validation/schemas/piiSettings.ts`).

### Prompt Injection (`promptInjection.ts`)

მომხმარებლის მიერ მოწოდებულ კონტენტში აღმოაჩენს მტრულ სტრუქტურებს და აღასრულებს
კონფიგურირებულ პოლიტიკას. ქცევას გარემოს ცვლადები და კონსტრუქტორის პარამეტრები
განსაზღვრავს:

| პარამეტრი        | გარემოს ცვლადი                                                                                        | ნაგულისხმევი მნიშვნელობა | ეფექტი                                                                                                                                                                                      |
| ---------------- | ----------------------------------------------------------------------------------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ჩართულია         | `INPUT_SANITIZER_ENABLED`                                                                             | `true`                   | როდესაც მნიშვნელობაა `false`, დამცავი მექანიზმი დაუყოვნებლივ ასრულებს მუშაობას.                                                                                                             |
| რეჟიმი           | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`                   | ინექციის პოლიტიკა: `block`, `warn` ან `log`. (`redact` მხარდაჭერილია უკუთავსებადობისთვის, მაგრამ ინექციის ტექსტს **არ** შლის; მოთხოვნაში PII-ის გადაწერას `PII_REDACTION_ENABLED` მართავს.) |
| დაბლოკვის ზღვარი | `blockThreshold` option / `INPUT_SANITIZER_BLOCK_THRESHOLD` (alias `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`                   | დასაბლოკად საჭირო მინიმალური სიმძიმე. ნაგულისხმევი პარამეტრებით საშუალო სიმძიმე მხოლოდ დაკვირვების რეჟიმშია.                                                                                |

**რეჟიმის პრიორიტეტულობა** (`getMode`): გამომძახებლის `options.mode` →
`INJECTION_GUARD_MODE`-ის **DB ფუნქციური ალმით გადაფარვა** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` გარემოს ცვლადი → `INPUT_SANITIZER_MODE` გარემოს ცვლადი →
`warn`. შესაბამისად, მართვის პანელიდან გადაფარვას გარემოს ცვლადებზე უფრო მაღალი
პრიორიტეტი აქვს, ამიტომ Feature Flags UI გაშვებულ დამცავ მექანიზმს რეალურ დროში
მართავს (გადატვირთვის გარეშე). DB-დან წაკითხვა უსაფრთხო მარცხის პრინციპს იყენებს:
შეცდომის შემთხვევაში დამცავი მექანიზმი გარემოს ცვლადებზე დაფუძნებულ ქცევას უბრუნდება,
ხოლო თუ გადაფარვა მითითებული არ არის, ქცევა მხოლოდ გარემოს ცვლადებით განსაზღვრული
ქცევის იდენტურია.

აღმოჩენის წყაროები:

1. `sanitizeRequest()` მოდულიდან `@/shared/utils/inputSanitizer` (საერთო დეტექტორების
   ნაკრები, რომელიც კონვეიერის სხვა ნაწილებშიც გამოიყენება).
2. ჩაშენებული `DEFAULT_GUARD_PATTERNS` (ამჟამად `system_override_inline` და
   `markdown_system_block`, ორივე `high` სიმძიმით).
3. არჩევითი `customPatterns`, რომლებიც კონსტრუქტორის პარამეტრებით გადაეცემა (სტრიქონები, რეგულარული
   გამოსახულებები ან `{ name, pattern, severity }` ჩანაწერები).

როდესაც `mode === "block"` **და** სულ მცირე ერთი აღმოჩენა აკმაყოფილებს სიმძიმის
ზღვარს, `preCall` აბრუნებს `{ block: true, message: "Request rejected:
suspicious content detected" }`. `warn`/`log` რეჟიმებში დამცავი მექანიზმი ქმნის
ჟურნალის ჩანაწერს, თუმცა გამოძახებას უშვებს. საერთო დამხმარე ფუნქცია
`evaluatePromptInjection()` ასევე ექსპორტირებულია იმ გამომძახებლებისთვის, რომლებსაც
მინიშნებების შეფასება რეესტრის გვერდის ავლით სჭირდებათ.

**სკანირების ზღვარი (v3.8.20):** დეტექტორი ამოწმებს მხოლოდ გაერთიანებული მინიშნების
ტექსტის **პირველ 16 KB-ს** — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ბაიტი)
ფაილში `src/shared/utils/inputSanitizer.ts`. როგორც `detectInjection()`, ისე
`evaluatePromptInjection()` შაბლონების ციკლის გაშვებამდე იყენებს
`slice(0, MAX_INJECTION_SCAN_BYTES)`. ინექციის დირექტივები შეყვანილი მონაცემების
დასაწყისთან ახლოს მდებარეობს, ამიტომ ეს ზღუდავს რეგულარული გამოსახულებების CPU/GC
დანახარჯს რამდენიმე ასეული KB-ის მოცულობის დატვირთვებზე, აღმოჩენის ეფექტიანობის
შესუსტების გარეშე (იხ. #3932, #4041).

### ავტორიზაციის მონაცემების დამფარავი (`credentialMasker.ts`)

ეშვება **ორივე** ეტაპზე და ნაგულისხმევ ჯაჭვში ბოლოა (პრიორიტეტი `95`). გამავალ
დატვირთვაში (შეტყობინების შიგთავსი, ინსტრუმენტის გამოძახების არგუმენტები,
ინსტრუმენტის შედეგები) **და** პროვაიდერის პასუხში ფარავს ფართოდ გავრცელებულ
API-გასაღებების / საიდუმლო ტოკენების შაბლონებს, რათა მინიშნებაში ჩასმული
ავტორიზაციის მონაცემები (ან ინსტრუმენტის შედეგში გამეორებული მონაცემები) არც
ზედა დონის პროვაიდერთან და არც კლიენტთან არ გაჟონოს.

- **მხოლოდ აშკარა ჩართვით**, PII-ის დაფარვის იგივე წესის შესაბამისად (Hard Rule #20-ის
  მომიჯნავე): გამორთულია, თუ `settings.credentialRedactionEnabled === true` **ან**
  `CREDENTIAL_REDACTION_ENABLED=true` მითითებული არ არის. გამორთულ მდგომარეობაში
  დამცავი მექანიზმი არაფერს აკეთებს — ის არასდროს ბლოკავს და არასდროს გადაწერს.
- `redactCredentials()` სრულად ამუშავებს დატვირთვის/პასუხის ხეს (`walkValue()`,
  დაცულია პროტოტიპის დაბინძურებისგან და ციკლებისგან `WeakSet`-ის მეშვეობით) და
  დამთხვევებს `[REDACTED:<type>]` ჩამნაცვლებლით ცვლის; კლონირდება მხოლოდ რეალურად
  შეცვლილი განშტოებები.
- `CREDENTIAL_PATTERNS` მოიცავს LLM პროვაიდერების გასაღებებს (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ტოკენებს (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), გადახდის გასაღებებს (Stripe, Square),
  ღრუბლოვანი სერვისების გასაღებებს (AWS access key, Twilio, SendGrid, Mailgun),
  კერძო გასაღებებს / JWT-ებს, ავტორიზაციის მონაცემების შემცველ კავშირის სტრიქონებს
  (`mongodb://user:pass@...` და სხვ.) და ზოგად `Authorization`/`x-api-key`/`api-key`/`apikey`
  სათაურის მნიშვნელობის შაბლონს. სათაურის ფორმის გასაღებები (`authorization`,
  `x-api-key`, `api-key`, `apikey`) ზოგადი ტექსტური რეგულარული გამოსახულების ნაცვლად
  სტრუქტურულად იფარება (მხოლოდ მნიშვნელობა; სქემის პრეფიქსი, როგორიცაა
  `Bearer `/`Basic `, შენარჩუნებულია).
- დამცავი მექანიზმი არასდროს ბლოკავს; ის მხოლოდ გადაწერს (`modifiedPayload` /
  `modifiedResponse`) და ანოტაციას ამატებს (`meta.credentialsRedacted`, `meta.count`).

რეგრესიისგან დაცვა: `tests/unit/credential-masker-guardrail.test.ts`.

## საბაზისო კონტრაქტი (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ჯაჭვის შესრულებას დაუყოვნებლივ წყვეტს
  message?: string; // ნაჩვენებია დაბლოკვისას
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // მოთხოვნის გადასაწერად აბრუნებს preCall
  modifiedResponse?: TValue; // პასუხის გადასაწერად აბრუნებს postCall
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

დამცავი მექანიზმი „ცვლილება არ არის“ მდგომარეობის შესახებ მიანიშნებს `void`-ის, `{}`-ის ან
`{ block: false }`-ის დაბრუნებით. `modifiedPayload`/`modifiedResponse`-ის დაბრუნება
ჩაანაცვლებს ჯაჭვში გამავალ მნიშვნელობას მომდევნო დამცავი მექანიზმებისთვის.
`signal?: AbortSignal` გამომძახებლის სასიცოცხლო ციკლს დამცავ მექანიზმებს გადასცემს. მოთხოვნის შეწყვეტა წინასწარგანზრახული fail-open გამონაკლისია: მედია-ხიდები წყვეტენ მუშაობას და ასუფთავებენ რესურსებს ისე, რომ დაუმუშავებელი მედია არ აღადგინონ სამიზნეზე, რომლის შესახებაც ცნობილია, რომ მას მხარს არ უჭერს.

## რეგისტრატორი (`registry.ts`)

სინგლტონი `guardrailRegistry` აჩვენებს:

- `register(guardrail)` — ამატებს (ან ცვლის ნორმალიზებული სახელით) გარდრეილს და
  ხელახლა ალაგებს ზრდადი `priority`-ის მიხედვით.
- `clear()` / `list()` — ადმინისტრაციული დამხმარეები.
- `runPreCallHooks(payload, context)` — ახდენს აქტიური გარდრეილების იტერაციას,
  გადასცემს `payload`-ს `modifiedPayload`-ის გავლით და ჩერდება პირველ `block: true`-ზე.
- `runPostCallHooks(response, context)` — იგივე ნაკადი პასუხის მხარეს.
- `resetGuardrailsForTests({ registerDefaults })` — ასუფთავებს მდგომარეობას და სურვილისამებრ
  ხელახლა არეგისტრირებს ნაგულისხმევ პარამეტრებს ტესტის სუფთა იზოლაციისთვის.

ორივე რანერი აბრუნებს `{ blocked, payload|response, results, guardrail?, message? }`-ს,
სადაც `results` არის `GuardrailExecutionResult` ჩანაწერების მასივი, რომელიც მოიცავს
თითოეული გარდრეილის `blocked`, `skipped`, `modified`, `error` და `meta` ველებს,
რაც სასარგებლოა ტრეისინგისთვის.

### გარდრეილების გამორთვა თითო მოთხოვნაზე

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` აგროვებს
გარდრეილების სახელების დედუპლიცირებულ სიას, რომლებიც უნდა გამოტოვებულ იქნას
მიმდინარე მოთხოვნისთვის. წყაროები (ყველა არასავალდებულო, ყველა გაერთიანებულია):

- `apiKeyInfo.disabledGuardrails`
- მოთხოვნის სხეული `disabledGuardrails` (ზედა დონის)
- მოთხოვნის სხეული `metadata.disabledGuardrails`
- ჰედერი `x-omniroute-disabled-guardrails` (ან მოძველებული
  `x-disabled-guardrails`)

მნიშვნელობები შეიძლება იყოს სტრიქონების მასივები ან მძიმით გამოყოფილი სტრიქონი;
სახელები ნორმალიზდება პატარა ასოებით kebab-case-ში (`pii_masker` → `pii-masker`).
შედეგი გადაეცემა `context.disabledGuardrails`-ის გავლით რეგისტრატორს,
რომელიც გამოტოვებს შესაბამის გარდრეილებს (`skipped: true` `results`-ში).

## შესრულების თანმიმდევრობა

ყოველი მოთხოვნისთვის, რომელიც გადის `src/sse/handlers/chat.ts`-სა და `open-sse/handlers/chatCore.ts`-ის გავლით:

1.  `resolveDisabledGuardrails(...)` აგებს გამოტოვების სიას API გასაღებიდან, სხეულიდან და სათაურებიდან.
2.  `guardrailRegistry.runPreCallHooks(body, ctx)` ასრულებს დამცავ მექანიზმებს პრიორიტეტის ზრდადი თანმიმდევრობით:
    - გამორთული დამცავი მექანიზმები აღირიცხება როგორც `skipped`.
    - თითოეული დამცავი მექანიზმის `preCall`-მა შეიძლება გადაწეროს მონაცემთა პაკეტი `modifiedPayload`-ის მეშვეობით.
    - პირველი `block: true` წყვეტს ჯაჭვს და დამმუშავებელი აბრუნებს დამცავი მექანიზმის უარყოფის პასუხს.
3.  (პოტენციურად გადაწერილი) მონაცემთა პაკეტი მიედინება კომბინირებულ მარშრუტიზაციასა და ზედა დინების გაგზავნაში.
4.  პასუხის აწყობის შემდეგ, `guardrailRegistry.runPostCallHooks(...)` აწარმოებს იმავე ჯაჭვს პასუხზე. `block: true` აქ აგდებს ზედა დინების პასუხს.

დამცავი მექანიზმები, რომლებიც შეცდომას აგდებენ, აღირიცხება `error: <message>`-ით და აღინიშნება `logger.warn`-ის მეშვეობით, მაგრამ ჯაჭვი გრძელდება — დიზაინით ღიაა წარუმატებლობისთვის.

## კონფიგურაცია

ჩაშენებული დამცავი მექანიზმების მიერ წაკითხული გარემოს ცვლადები:

| ცვლადი                                | გამოიყენება                 | ეფექტი                                                                                                      |
| :------------------------------------ | :-------------------------- | :---------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`          | დააყენეთ `false` გამოვლენის სრულად გამორთვისთვის.                                                           |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`          | ინექციის პოლიტიკა: `warn`, `block`, ან `log`. მოძველებული მნიშვნელობა `redact` არ გადაწერს ინექციის ტექსტს. |
| `INJECTION_GUARD_MODE`                | `prompt-injection`          | რეჟიმი ინექციის დამცავისთვის; ასევე DB ფუნქციის დროშა, რომელიც **გადაფარავს** გარემოს ცვლადებს (DB > ENV).  |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`          | მინიმალური სიმძიმე, რომელსაც `MODE=block` უარყოფს: `high` (ნაგულისხმევი), `medium`, ან `low`.               |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`          | მოძველებული ფსევდონიმი `INPUT_SANITIZER_BLOCK_THRESHOLD`-ისთვის.                                            |
| `PII_REDACTION_ENABLED`               | `pii-masker`                | როდესაც `true`, მოთხოვნის PII რედაქტირდება (ინექციის რეჟიმისგან დამოუკიდებლად).                             |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ქვედა დინება) | აკონტროლებს პასუხის მხარის ნიღბის ქცევას.                                                                   |

Modality Bridge-ის დამცავი მექანიზმები კითხულობენ გაშვების კონფიგურაციას DB-ზე დაფუძნებული პარამეტრების საცავიდან (`getSettings()`), და არა გარემოს ცვლადებიდან. Vision-ის ძირითადი გასაღებებია `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, და `modalityBridgeCacheMaxEntries`. მოძველებული `visionBridge*` გასაღებები მიიღება მხოლოდ როგორც დოკუმენტირებული ერთციკლიანი წაკითხვის სარეზერვო ვარიანტი; დაფის ჩანაწერები იყენებენ ძირითად გასაღებებს. ნაგულისხმევი მნიშვნელობები და სარეზერვო გადამწყვეტი განთავსებულია `src/shared/constants/modalityBridgeDefaults.ts`-ში, მოძველებული კონსტანტები შენარჩუნებულია `src/shared/constants/visionBridgeDefaults.ts`-ში.

აუდიო იყენებს `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`, `modalityBridgeAudioTimeout`, და `modalityBridgeAudioMaxClips`, პლუს გაზიარებულ `modalityBridgeCache*` პარამეტრებს. აუდიოს არ აქვს მოძველებული გასაღების სარეზერვო ვარიანტი, რადგან ეს გასაღებები შემოღებულ იქნა Modality Bridge სქემასთან ერთად.

ვიდეო იყენებს `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`, `modalityBridgeVideoModel`, `modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`, `modalityBridgeVideoMaxVideos`, და `modalityBridgeVideoTimeout`, პლუს გაზიარებულ `modalityBridgeCache*` პარამეტრებს. ის ნაგულისხმევად გამორთულია, რადგან FFmpeg/ffprobe არის არჩევითი ოპერაციული დამოკიდებულებები და კადრების წარწერა ზრდის შეყოვნებასა და მოდელის ღირებულებას.

## მორგებული Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ნაბიჯები:

1.  შექმენით `src/lib/guardrails/myGuardrail.ts`, რომელიც აფართოებს `BaseGuardrail`-ს.
2.  განახორციელეთ `preCall` და/ან `postCall`.
3.  ან დაარეგისტრირეთ იმპორტის დროს (`registerDefaultGuardrails`-დან დამატებით) ან გამოიძახეთ `guardrailRegistry.register(...)` გაშვების დროს — რეესტრი ჩაანაცვლებს ნებისმიერ წინა guardrail-ს იგივე ნორმალიზებული სახელით.
4.  დაამატეთ ტესტები `tests/unit/`-ში (არსებული მაგალითები: `tests/unit/guardrails-registry.test.ts`, `tests/unit/prompt-injection-guard.test.ts`, `tests/unit/guardrails/visionBridge.test.ts`).

## ტესტირება

გამოიყენეთ `resetGuardrailsForTests()` ტესტებს შორის, რათა დაიწყოთ ცნობილი მდგომარეობიდან. გადაეცით `{ registerDefaults: false }`, რათა დაიწყოთ ცარიელი რეესტრით და დაარეგისტრიროთ მხოლოდ ტესტირებადი guardrails. Vision Bridge იღებს დამოკიდებულების ინექციას (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge აჩვენებს ექვივალენტურ წერტილებს პარამეტრებისთვის, შესაძლებლობებისთვის, STT მოდელის არჩევისთვის, სერთიფიკატების შემოწმებისთვის და ტრანსკრიფციისთვის. ამიტომ, ტესტებს შეუძლიათ ორივე ნაკადის შემოწმება მონაცემთა ბაზის ან ქსელზე წვდომის გარეშე.

## ინექციისგან დამცავი მარშრუტების დაფარვა და წითელი გუნდი (ფაზა 8 · ბლოკი D)

ინექციისგან დამცავი მექანიზმი (`createInjectionGuard` / `withInjectionGuard`) მოიცავს ყველა მარშრუტს, რომელიც იღებს მომხმარებლის მოთხოვნებს. ის ითვალისწინებს `INJECTION_GUARD_MODE`-ს (ნაგულისხმევი `warn` = მხოლოდ ჟურნალი; `block` = აბრუნებს HTTP 400 `SECURITY_001`).

| ტიპი            | მარშრუტები                                                                                                                                           | ნაგულისხმევი რეჟიმი |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| Text (existing) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn                |
| Generative      | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn                |
| Data            | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn                |

ტექსტის ამოღება (`extractMessageContents`) მოიცავს `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`-ს.

**წითელი გუნდი (ღამის, `nightly-llm-security.yml`):** promptfoo ამოწმებს, რომ თითოეული მარშრუტი ბლოკავს OWASP-LLM კორპუსს `INJECTION_GUARD_MODE=block` რეჟიმში; garak აწარმოებს ზონდებს (გამოტოვებს საიდუმლოს გარეშე). `moderations` შედის თანმიმდევრულობისთვის — ოპერატორებს ბლოკირების რეჟიმში შეუძლიათ მისი გათავისუფლება `resolveDisabledGuardrails`-ის მეშვეობით.

ღამის სამუშაო პროცესი (`.github/workflows/nightly-llm-security.yml`, cron + ხელით გაშვება) მოიცავს ორ დავალებას:

- **`promptfoo-guard` (ბლოკირება)** — აწარმოებს `promptfoo eval -c promptfooconfig.yaml`-ს `INJECTION_GUARD_MODE=block`-ით. თითოეული მტრული შემთხვევა (მაგ. „უგულებელყავით ყველა წინა ინსტრუქცია…“, DAN-ის სტილის jailbreaks) ადასტურებს, რომ პასუხი შეიცავს `error.code === "SECURITY_001"`, ანუ guard-მა რეალურად უარყო მოთხოვნა.
- **`garak` (საკონსულტაციო)** — აწარმოებს garak `--probes promptinject,dan,leakreplay`-ს ლოკალური OmniRoute ინსტანციის წინააღმდეგ (`http://localhost:20128/v1`). დაცულია პროვაიდერის საიდუმლო გასაღებით (`PROMPTFOO_PROVIDER_KEY`); გამოტოვებს შეცდომის გარეშე და დამატებულია `|| true`, ასე რომ, ის აფიქსირებს CI-ის ჩავარდნის გარეშე.

guard დამხმარის (`createInjectionGuard` / `withInjectionGuard`) დაფარვა მოიცავს ყველა მოთხოვნის შემცველ `/v1` მარშრუტს; მოთხოვნის ტექსტი ამოღებულია `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`-დან `extractMessageContents()` ფუნქციის მიერ `src/shared/utils/inputSanitizer.ts`-ში.
