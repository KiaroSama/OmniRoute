ეს დოკუმენტი OmniRoute-ში CI-ის ხარისხის ყველა ბარიერის ავტორიტეტული ცნობარია.
იგი აღწერს თითოეულ ბარიერს, რას ამოწმებს ის, რომელ CI დავალებაში სრულდება, იყენებს თუ არა
ეტალონის ეტაპობრივი გამკაცრების ან ჩაბარება/ჩავარდნის პოლიტიკას და ბლოკავს თუ არა აგებას, თუ მხოლოდ სარეკომენდაციო ხასიათი აქვს.

მოკლე შეჯამებისა და დაშვებული გამონაკლისების სიის პოლიტიკისთვის იხილეთ სექცია „Quality Gates & Ratchets“
ფაილში `AGENTS.md`. იმავე სისტემის კრიტიკული შეფასების, სიმწიფის კლასიფიკაციისა და კონკრეტულ ხელსაწყოებზე დამოუკიდებელი
გამეორების გეგმისთვის იხილეთ
[ხარისხის ბარიერების სახელმძღვანელო](../ops/QUALITY_GATE_PLAYBOOK.md).

## გეითების ინვენტარი და შესრულების პროფილები

### კანდიდატის დაშვება

CI და Quality Gates სამუშაო პროცესები თითოეული სტაბილურ ვერდიქტს გასცემს: `Gate / CI` და
`Gate / Quality`. მათი ვერსიონირებული დაშვების პოლიტიკა ყველა ზემდგომ დავალებას
სავალდებულოდ ან სარეკომენდაციოდ განსაზღვრავს. შესაბამისი სავალდებულო დავალება წარმატებით
უნდა დასრულდეს: არარსებული, გაუქმებული, გამოტოვებული, მოლოდინის რეჟიმში მყოფი და უცნობი
შედეგები PASS სტატუსს ვერ დაადასტურებს. მხოლოდ დოკუმენტაციასთან ან მხოლოდ კატალოგთან
დაკავშირებული მოქმედი კლასიფიკაციის შემთხვევაში კოდის არხი შეიძლება შეუსაბამოდ ჩაითვალოს;
შავი PR მიღებულ კანდიდატად არ ითვლება. `hotfix` ჭდე მტკიცებულების მოთხოვნას არ აუქმებს.

ორივე სამუშაო პროცესი მოიცავს PR-ებს და main/release განშტოებებში push-ებს, ხელით გაშვებასა
და merge-group მოვლენებს. Push, dispatch და merge-group სრულ შერჩევას ასრულებს. Fork-ები
და merge ჯგუფები განთავსებულ რანერებს იყენებს იმ დავალებებისთვის, რომლებიც სხვა შემთხვევაში
თვითგანთავსებულ რანერებს აირჩევდა; დანერგვამდე უნდა დადასტურდეს განთავსებული გარემოს
საკმარისი სიმძლავრე.

თითოეული JSON ქვითარი განსაზღვრავს ამოღებულ SHA-ს, სამუშაო პროცესის გაშვებასა და მცდელობას.
CLI უარყოფს ამოღებული ვერსიისა და მოვლენის SHA-ების შეუსაბამობას. სამუშაო პროცესის ტესტები
პოლიტიკის წევრობას ვერდიქტის დავალების `needs` სიას უკავშირებს, რათა ახალი ან წაშლილი არხი
შეუმჩნევლად ვერ გაქრეს. ქვითრები მოიცავს საკუთარ სამუშაო პროცესს და არა გამოქვეყნებას,
განთავსებას ან არსებული სარეკომენდაციო სკანერის შიდა მუშაობას. განშტოების წესებში ორივე
შემოწმების სახელის გააქტიურება ცალკე ადმინისტრაციული ცვლილებაა; ამ დავალებების დამატება
თავისთავად არ იცავს განშტოებას.

### სტატიკური სკანირების ინვენტარი

ვერსიონირებული npm-ფსევდონიმების ინვენტარი და სტატიკური სკანირების წევრობა განთავსებულია
`config/quality/gate-manifest.json`-ში. გაუშვით `npm run check:gate-manifest`, რათა
სკრიპტების სახელები და ზუსტი ბრძანებები `package.json`-თან მიმართებით გადაამოწმოთ; დამატებები,
წაშლები და ბრძანებების აცდენა იწვევს როგორც ლოკალური ჰუკის, ისე CI-ში ცვლილებების
კლასიფიკაციის დავალებების წარუმატებლობას. ფსევდონიმი არ არის სამუშაო პროცესის დავალება,
მატრიცის ეგზემპლარი ან სატესტო შემთხვევა: ეს რაოდენობები ურთიერთჩანაცვლებადად არ უნდა იყოს
წარმოდგენილი.

შერჩეული ფსევდონიმების შესრულების გარეშე შესამოწმებლად გამოიყენეთ
`npm run quality:scan -- --list` ან `npm run quality:scan:fast -- --list`.
რანერი npm-ის შესვლის წერტილს იძახებს, ამიტომ მისი შესრულების გარემო (მათ შორის Bun იქ,
სადაც ის კონფიგურირებულია) შენარჩუნებულია. მანიფესტი ამ პროფილებს მიღმა არსებულ
ფსევდონიმებს ცალკე გამოძახებულად აღრიცხავს, ხოლო ტექნიკური მომსახურების ბრძანებები მხოლოდ
წაკითხვის რეჟიმის სკანირების პროფილებში აკრძალულია.

ეს პროფილები მხოლოდ სტატიკურ სკანირებას მოიცავს. ისინი არ ადასტურებს პროდუქტის ტესტებს,
დაფარვას, შეფუთვას, გარე შემოწმებებს ან კანდიდატის გამოშვებისთვის სრულ დაშვებას.
სამუშაო პროცესის დაშვება იყენებს დაკავშირებულ `config/quality/admission-policy.json`-სა და
`scripts/quality/admission-verdict.mjs`-ს. Release-observer პროფილები განცალკევებული რჩება;
მათი შესაბამისი შემოწმებები და ქვითრები დამოუკიდებლად შეამოწმეთ. ქვემოთ მოცემული ტექსტური
ინვენტარი საცნობაროა და არა იმის მტკიცებულება, რომ გეითი ნამდვილად გაეშვა.

სკრიპტები განთავსებულია `scripts/check/`-ში (პოლიტიკის გეითები) და `scripts/quality/`-ში (ratchet ძრავა).
CI-ის ჭეშმარიტების წყაროა `.github/workflows/ci.yml`.

### Release PR-ის სწრაფი გზა (`quality.yml`)

`.github/workflows/quality.yml` ავსებს CI-ს main/release PR-ებისთვის, დაცულ განშტოებებში
push-ებისთვის, dispatch-ისა და merge ჯგუფებისთვის. PR-ები ბილიკების მიხედვით გაფილტრულ
სწრაფ შემოწმებებს იყენებს. მუდმივად გამორთული დუბლირებული აგება წაიშალა; რეალური
აგების/შეფუთვის/ჩატვირთვის შემოწმებები CI-ში რჩება.

#### გამოტოვებული მონათესავე ტესტების ანგარიში

`npm run check:forgotten-sibling-tests` ხელახლა იყენებს იმპორტების გადამწყვეტს, რომელიც ტესტების ზემოქმედების რუკის საფუძველშია.
ყოველი შეცვლილი საწარმოო მოდულისთვის ის დეტერმინისტულ

ტესტი pull-request-ის განსხვავებებში არ არის. Markdown შეჯამება და JSON შედეგი ინახება, როგორც

## Ratchet-ის საბაზისო დონე (`quality-baseline.json`)

Ratchet-ის ძრავა (`scripts/quality/check-quality-ratchet.mjs`) კითხულობს `quality-baseline.json`-ს

მის epsilon-ზე მეტად გაუარესდება, აგების პროცესს წარუმატებლად დაასრულებს.

ამჟამად თვალყურისდევნებული მეტრიკები:

| მეტრიკა               | მიმართულება | მნიშვნელობა                                          |
| --------------------- | ----------- | ---------------------------------------------------- |
| `eslintWarnings`      | `down`      | ESLint-ის გაფრთხილებების რაოდენობა არ უნდა გაიზარდოს |
| `coverage.statements` | `up`        | ინსტრუქციების დაფარვა არ უნდა შემცირდეს              |

მეტრიკას საბაზისო დონის განახლების გარეშე აუმჯობესებს, გამოვლინდება `--require-tighten`-ის მიერ (ფაზა 6A.5,
განხორციელება მოსალოდნელია).

132×-ით (`src/shared/validation/schemas.ts`, 19 სტრიქონი 2,523-იანი ზღვრით);

ერთხელ შესრულდა. ზღვარი, რომელიც მის გამომწვევ კოდზე დიდხანს ცოცხლობს, თითოეულ დასრულებულ
