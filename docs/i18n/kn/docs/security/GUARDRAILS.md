> **ಸತ್ಯದ ಮೂಲ:** `src/lib/guardrails/`
> **ಕೊನೆಯ ನವೀಕರಣ:** 2026-08-29 — v3.8.51 (Video Bridge ಪ್ರತಿಲೇಖದ ಮೂಲವನ್ನು ಕರೆಮಾಡುವವರು ಘೋಷಿಸುತ್ತಾರೆ,
> ಸರ್ವರ್ ಇನ್ನೂ ಅದನ್ನು ಪರಿಶೀಲಿಸುವುದಿಲ್ಲ — #11661 ಪ್ರಕಾರ ಸ್ಪಷ್ಟಪಡಿಸಲಾಗಿದೆ)

Guardrails, OmniRoute ಮತ್ತು ಅಪ್ಸ್ಟ್ರೀಮ್ ಪೂರೈಕೆದಾರರ ನಡುವಿನ ಗಡಿಯಲ್ಲಿ ಸುರಕ್ಷತೆ,
ನೀತಿ ಮತ್ತು ವಿಷಯ ರೂಪಾಂತರಗಳನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ. ಪ್ರತಿಯೊಂದು guardrail ವಿನಂತಿಯ
ಪೇಲೋಡ್ಗಳನ್ನು (`preCall`) ಮತ್ತು ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು (`postCall`)
ಪರಿಶೀಲಿಸಬಹುದು (ಮತ್ತು ಐಚ್ಛಿಕವಾಗಿ ತಿರಸ್ಕರಿಸಬಹುದು, ರೂಪಾಂತರಿಸಬಹುದು ಅಥವಾ ಟಿಪ್ಪಣಿ ಸೇರಿಸಬಹುದು).

ಈ ವ್ಯವಸ್ಥೆಯು **fail-open** ಆಗಿದೆ: ಕಾರ್ಯಗತಗೊಳ್ಳುವಾಗ guardrail ದೋಷವನ್ನು ಎಸೆದರೆ,
registry ಆ ದೋಷವನ್ನು ದಾಖಲಿಸಿ, ವಿನಂತಿಯನ್ನು ವಿಫಲಗೊಳಿಸುವ ಬದಲು ಮುಂದಿನ guardrail
ಜೊತೆಗೆ ಮುಂದುವರಿಯುತ್ತದೆ. ನಿರ್ಬಂಧಿಸುವುದು ಸ್ಪಷ್ಟ ನಿರ್ಧಾರವಾಗಿದೆ (`block: true`),
ಎಂದಿಗೂ ಆಕಸ್ಮಿಕವಲ್ಲ.

## ಅಂತರ್ನಿರ್ಮಿತ ಸುರಕ್ಷತಾ ನಿಯಂತ್ರಣಗಳು

ಆಮದು ಮಾಡುವಾಗ ರಿಜಿಸ್ಟ್ರಿಯು ಆದ್ಯತೆಯ ಕ್ರಮದಲ್ಲಿ ಆರು ಸುರಕ್ಷತಾ ನಿಯಂತ್ರಣಗಳನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಲೋಡ್ ಮಾಡುತ್ತದೆ
(`registry.ts` → `registerDefaultGuardrails()` ನೋಡಿ):

| ಆದ್ಯತೆ | ಹೆಸರು               | ಹಂತ(ಗಳು)       | ಫೈಲ್                  |
| ------ | ------------------- | -------------- | --------------------- |
| `5`    | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`    | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`    | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`   | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`   | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`   | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

ಕಡಿಮೆ ಆದ್ಯತಾ ಸಂಖ್ಯೆಗಳು **ಮೊದಲು** ಚಾಲನೆಯಾಗುತ್ತವೆ.

### ವಿಷನ್ ಬ್ರಿಡ್ಜ್ (`visionBridge.ts`) — ಮಾಡ್ಯಾಲಿಟಿ ಬ್ರಿಡ್ಜ್ PR-1

**ವಿಷನ್ ಬೆಂಬಲಿಸದ ಮಾದರಿಗಳನ್ನು** ಗುರಿಯಾಗಿಸಿಕೊಂಡಿರುವ ಚಿತ್ರಗಳನ್ನು ಒಳಗೊಂಡ ವಿನಂತಿಗಳನ್ನು ತಡೆಹಿಡಿದು, ಸಂಪೂರ್ಣ ವಿನಂತಿಯನ್ನು ವಿಷನ್-ಸಾಮರ್ಥ್ಯವುಳ್ಳ ಮಾದರಿಗೆ ಮರುಮಾರ್ಗಗೊಳಿಸುತ್ತದೆ ಅಥವಾ ಅಪ್ಸ್ಟ್ರೀಮ್ ಕರೆಗೂ ಮೊದಲು ಚಿತ್ರದ ಭಾಗಗಳನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡಬಹುದಾದ ವಿಷನ್ ಮಾದರಿಯಿಂದ ರಚಿಸಲಾದ ಪಠ್ಯ ವಿವರಣೆಗಳಿಂದ ಬದಲಾಯಿಸುತ್ತದೆ. ಇದರಿಂದ ಪಠ್ಯ-ಮಾತ್ರದ ಪೂರೈಕೆದಾರರು ಮಲ್ಟಿಮೋಡಲ್ ಪೇಲೋಡ್ಗಳನ್ನು ಪಾರದರ್ಶಕವಾಗಿ ನಿರ್ವಹಿಸಬಹುದು.

ಹರಿವು:

1. ಗುರಿ ಮಾದರಿಯು ಈಗಾಗಲೇ ವಿಷನ್ ಅನ್ನು ಬೆಂಬಲಿಸಿದರೆ ಬಿಟ್ಟುಬಿಡಿ (ಅದು ಬಲವಂತದ-ಬ್ರಿಡ್ಜ್ ಪಟ್ಟಿ `isVisionBridgeForcedModel`ಯಲ್ಲಿ ಕಾಣಿಸಿಕೊಳ್ಳದಿದ್ದರೆ).
2. `extractImageParts(messages)` ಮೂಲಕ ಚಿತ್ರದ ಭಾಗಗಳನ್ನು ಹೊರತೆಗೆಯಿರಿ
   (`visionBridgeHelpers.ts`); ಇದು `open-sse/utils/mediaParts.ts`ನಲ್ಲಿರುವ **ಏಕೀಕೃತ ಮಾಧ್ಯಮ ಪತ್ತೆಕಾರಕ** `detectMediaParts()`ಗೆ ನಿಯೋಜಿಸುತ್ತದೆ — ಕಾಂಬೊ ಹೊಂದಾಣಿಕೆ ಫಿಲ್ಟರ್ನೊಂದಿಗೆ ಹಂಚಿಕೊಂಡಿರುವ ಏಕೈಕ ಸತ್ಯದ ಮೂಲ.
   ಹೊರತೆಗೆಯುವಿಕೆಯನ್ನು `replaceImageParts` ಮತ್ತೆ ಸೇರಿಸಬಹುದಾದ ಆಕಾರಗಳ ಮೇಲ್ಮಟ್ಟದ ಭಾಗಗಳಿಗೆ ಅನುಮತಿಪಟ್ಟಿಯ ಮೂಲಕ ಸೀಮಿತಗೊಳಿಸಲಾಗಿದೆ (ಹೊರತೆಗೆಯುವಿಕೆ↔ಬದಲಿಸುವಿಕೆ ಒಪ್ಪಂದ): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, ಮತ್ತು Responses API `input_image`. ನೆಸ್ಟ್ ಮಾಡಲಾದ ಹೊಂದಾಣಿಕೆಗಳು ಮತ್ತು ಸೂಚಕ-ಮಾತ್ರದ ಆಕಾರಗಳು ಕಾಂಬೊ-ಫಿಲ್ಟರ್ಗೆ ಸಂಬಂಧಿಸಿದವು ಹಾಗೂ ಅವುಗಳನ್ನು ಎಂದಿಗೂ ಹೊರತೆಗೆಯಲಾಗುವುದಿಲ್ಲ.
   ಯಾವುದೂ ಕಂಡುಬರದಿದ್ದರೆ ಬಿಟ್ಟುಬಿಡಿ.
3. `resolveVisionBridgeRuntimeSettings()` ಮೂಲಕ ರನ್ಟೈಮ್ ಕಾನ್ಫಿಗ್ ಅನ್ನು ನಿರ್ಧರಿಸಿ
   (`src/shared/constants/modalityBridgeDefaults.ts`): ಹೊಸ `modalityBridge*`
   ಸೆಟ್ಟಿಂಗ್ಗಳ ಕೀಗಳು ಮೇಲುಗೈ ಸಾಧಿಸುತ್ತವೆ; ಹಳೆಯ `visionBridge*` ಕೀಗಳು **ಒಂದು-ಚಕ್ರದ ಪರ್ಯಾಯವಾಗಿ** ಉಳಿಯುತ್ತವೆ (ರೋಲ್ಬ್ಯಾಕ್ ವಿಂಡೋ). ಬ್ರಿಡ್ಜ್ ನಿಷ್ಕ್ರಿಯವಾಗಿದ್ದಾಗ ಯಾವುದೇ ಮಾಧ್ಯಮ ಟ್ರಾವರ್ಸಲ್ಗೂ ಮೊದಲು ಬಿಟ್ಟುಬಿಡಿ.
4. ಮೋಡ್ ಆಯ್ಕೆಕಾರಕ (`modalityBridgeVisionMode`, ಕೆಳಗಿನ ಕೋಷ್ಟಕ ನೋಡಿ) ಮರುಮಾರ್ಗಗೊಳಿಸುವಿಕೆ ಅಥವಾ ವಿವರಿಸುವಿಕೆಯ ನಡುವೆ ನಿರ್ಧರಿಸುತ್ತದೆ. ಮರುಮಾರ್ಗಗೊಳಿಸುವಿಕೆಯು `model` ಅನ್ನು ಮಾತ್ರ ಬದಲಾಯಿಸಿದ `modifiedPayload` ಜೊತೆಗೆ ಮೆಟಾ `{ rerouted, fromModel, toModel, imagesKept }` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ.
5. ವಿವರಿಸುವಿಕೆ ಪಥ: ಚಿತ್ರಗಳನ್ನು `maxImages`ಗೆ ಮಿತಿಗೊಳಿಸಿ, ಕಾರ್ಯ-ಅರಿವಿನ ಪ್ರಾಂಪ್ಟ್ ಅನ್ನು ರಚಿಸಿ, ವಿವರಿಸುವಿಕೆ ಕ್ಯಾಶ್ ಅನ್ನು ಪರಿಶೀಲಿಸಿ, ವಿಷನ್ ಮಾದರಿಯನ್ನು **ಸಮಾನಾಂತರವಾಗಿ**
   (`Promise.allSettled`) ಕರೆ ಮಾಡಿ ಹಾಗೂ ಅವುಗಳ ಸ್ಥಾನದಲ್ಲಿ `[Image N]: <description>` ಪಠ್ಯ ಭಾಗಗಳನ್ನು ಸೇರಿಸಿ. ವಿಫಲವಾದ ವಿವರಿಸುವಿಕೆಯು `null` ಅನ್ನು ನೀಡುತ್ತದೆ ಮತ್ತು ಮೂಲ ಚಿತ್ರದ ಭಾಗವನ್ನು **ಉಳಿಸಲಾಗುತ್ತದೆ** (#4012) — ಆದರೆ ಕಾಂಬೊ ವಿವರಿಸುವಿಕೆ ಪಥದಲ್ಲಿ ಪ್ರತಿಯೊಂದು ವಿವರಿಸುವಿಕೆಯೂ ವಿಫಲವಾದಾಗ, ದೃಢೀಕರಿಸಲಾದ ವಿಷನ್ ಬೆಂಬಲಿಸದ ಅಪ್ಸ್ಟ್ರೀಮ್ಗೆ ಬದಲಾಗಿ
   `(ಲಭ್ಯವಿಲ್ಲ — ಯಾವುದೇ ವಿಷನ್-ಸಾಮರ್ಥ್ಯವುಳ್ಳ ಪೂರೈಕೆದಾರ ಸಂಪರ್ಕಗೊಂಡಿಲ್ಲ)` ಸ್ಟಬ್ ನೀಡಲಾಗುತ್ತದೆ (#8430).
6. `modifiedPayload` + ಮೆಟಾ (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) ಅನ್ನು ಹಿಂದಿರುಗಿಸಿ.

#### API-ಕೀ ವ್ಯಾಪ್ತಿ (`visionBridgeKeyScope.ts`)

ಕರೆ ಮಾಡುವವರ API ಕೀಯು `allowedConnections`, ಕೋಟಾ ಪೂಲ್ಗಳು
(`allowedQuotas`) ಅಥವಾ ಮಾದರಿಗಳನ್ನು (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) ನಿರ್ಬಂಧಿಸಿದಾಗ, ಬ್ರಿಡ್ಜ್ ಆ ಕೀ ಬಳಸಬಹುದಾದ ಸಂಪರ್ಕಗಳಲ್ಲಿ ಆ ಕೀ ಬಳಸಬಹುದಾದ ಮರುಮಾರ್ಗಗೊಳಿಸುವಿಕೆ ಮತ್ತು ವಿವರಿಸುವಿಕೆ ಮಾದರಿಗಳನ್ನು ಮಾತ್ರ ಆಯ್ಕೆಮಾಡುತ್ತದೆ. ನಂತರ ವಿವರಿಸುವಿಕೆ ಕರೆಯು ಯಾವಾಗಲೂ
`x-omniroute-self-loop-key-id` ಹೆಡರ್ನೊಂದಿಗೆ OmniRoute ಸ್ವಯಂ-ಲೂಪ್ ಮೂಲಕ ಸಾಗುತ್ತದೆ; ಇದರಿಂದ ಸ್ವೀಕರಿಸುವ ಚಾಟ್ ವಿನಂತಿಯು ಆ ಕೀಯ ಸಂಪರ್ಕ ಮತ್ತು ಮಾದರಿ ನೀತಿಯನ್ನು ಮತ್ತೊಮ್ಮೆ ಜಾರಿಗೊಳಿಸುತ್ತದೆ. `enforceApiKeyPolicy()` ಆ ಹೆಡರ್ ಅನ್ನು ಸ್ವಯಂ-ಲೂಪ್ ಬೇರರ್ ಜೊತೆಗೆ ಮಾತ್ರ ಗೌರವಿಸುತ್ತದೆ, ಆದ್ದರಿಂದ ಅದು ಪ್ರವೇಶವನ್ನು ಕೇವಲ ಮತ್ತಷ್ಟು ಸೀಮಿತಗೊಳಿಸಬಲ್ಲದು; ಪರಿಹರಿಸಲಾಗದ id ಅನ್ನು ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ.

ಕೀಗಾಗಿ ಯಾವುದೇ ವಿಷನ್ ಮಾದರಿಗೆ ಅನುಮತಿ ಇಲ್ಲದಿದ್ದರೆ, ವಿವರಿಸುವಿಕೆ ಪಥವು ಹಿಂದೆ ಸರಿಯುತ್ತದೆ ಮತ್ತು ವಿನಂತಿಯು ಬದಲಾವಣೆಯಿಲ್ಲದೆ ಹಾದುಹೋಗುತ್ತದೆ; ಇದು ನಿಷ್ಕ್ರಿಯ ಸುರಕ್ಷತಾ ನಿಯಂತ್ರಣದಂತೆಯೇ ಅದೇ ವಿಫಲ-ಮುಕ್ತ ವರ್ತನೆಯಾಗಿದೆ (ಮೆಟಾ `{ skipped: true, reason: "no_permitted_vision_model" }`).
ಕೀ ಇಲ್ಲದ ವಿನಂತಿಗಳು ಮತ್ತು ಈ ನಿರ್ಬಂಧಗಳಿಲ್ಲದ ಕೀಗಳು ಹಿಂದಿನಂತೆಯೇ ನಿಖರವಾಗಿ ವರ್ತಿಸುತ್ತವೆ.

ವಿಫಲವಾಗುವ ಪ್ಲಾಟ್ಫಾರ್ಮ್ನಲ್ಲಿ, `normalizeDataUri()` **ಎಂದಿಗೂ throw ಮಾಡುವುದಿಲ್ಲ** —
ಅದು ಮೂಲ ಬೈಟ್ಗಳನ್ನು ಯಥಾವತ್ತಾಗಿ ರವಾನಿಸುವ fallback ಅನ್ನು ಬಳಸುತ್ತದೆ; ಹೀಗಾಗಿ
ವಿವರಣೆ/base64-ಪರಿವರ್ತನೆ ಪಥವು ಸದಾ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿರುತ್ತದೆ. ಚಿತ್ರವಲ್ಲದ ಬೈಟ್ಗಳನ್ನೂ
(ಡಿಕೋಡ್ ಮಾಡಬಹುದಾದ ಚಿತ್ರವನ್ನು ಹಿಂದಿರುಗಿಸದ fetch) ಯಾವುದೇ ಬದಲಾವಣೆಯಿಲ್ಲದೆ
ರವಾನಿಸಲಾಗುತ್ತದೆ. ಈ ಸಾಮಾನ್ಯೀಕರಣವು ಬ್ರಿಡ್ಜ್ ತನ್ನ ಸ್ವಂತ self-callಗಾಗಿ fetch ಮಾಡುವ
ಚಿತ್ರಗಳಿಗೆ ಮಾತ್ರ ಸೀಮಿತವಾಗಿದೆ — ಕರೆ ಮಾಡುವವರ raw passthrough payloadಗೆ ಇದನ್ನು ಎಂದಿಗೂ
ಅನ್ವಯಿಸಲಾಗುವುದಿಲ್ಲ; ಇದು opt-in-only mutation ತತ್ವಕ್ಕೆ (Hard Rule #20) ಅನುಗುಣವಾಗಿದೆ.

#### ಸೆಟ್ಟಿಂಗ್ಗಳ ಸ್ಕೀಮಾ + ಮೈಗ್ರೇಶನ್

ಹೊಸ `modalityBridge*` ಕೀಗಳನ್ನು `updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`) ನಲ್ಲಿ Zod ಮೂಲಕ ಮೌಲ್ಯೀಕರಿಸಲಾಗುತ್ತದೆ:
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCache*` ತ್ರಯ ಮತ್ತು Audio Bridge ಬಳಸುವ `modalityBridgeAudio*` ಗುಂಪು.
ಮೈಗ್ರೇಶನ್ `141_modality_bridge_settings.sql`, ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಹಳೆಯ
`visionBridge*` ಮೌಲ್ಯಗಳನ್ನು ಹೊಂದಿಕೆಯಾಗುವ ಹೊಸ ಕೀಗಳಿಗೆ ನಕಲಿಸುತ್ತದೆ (idempotent ಆಗಿದ್ದು,
ಆಪರೇಟರ್ ಹೊಂದಿಸಿದ `modalityBridge*` ಮೌಲ್ಯವನ್ನು ಎಂದಿಗೂ ತಿದ್ದಿಬರೆಯುವುದಿಲ್ಲ); ಒಂದು
ರಿಲೀಸ್ ಚಕ್ರದವರೆಗೆ ಹಳೆಯ ಕೀಗಳನ್ನು read fallback ಆಗಿ ಸ್ವೀಕರಿಸುವುದು ಮುಂದುವರಿಯುತ್ತದೆ.

#### ಪಾರದರ್ಶಕತೆ ಹೆಡರ್ + ಅಂಕಿಅಂಶಗಳು

ವಿವರಣೆ-ರೂಪಾಂತರಿತ ಪ್ರತಿಕ್ರಿಯೆಗಳು
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
ಅನ್ನು ಹೊಂದಿರುತ್ತವೆ (`modalityBridge/bridgeStats.ts` ನಲ್ಲಿನ
`buildModalityBridgeHeader()` ಮೂಲಕ ನಿರ್ಮಿಸಿ,
`src/sse/handlers/chatHelpers.ts` ನಲ್ಲಿನ `withModalityBridgeHeader()` ಮೂಲಕ
ಲಗತ್ತಿಸಲಾಗುತ್ತದೆ). ಮರುಮಾರ್ಗಗೊಳಿಸಲಾದ ವಿನಂತಿಗಳಿಗೆ **ಯಾವುದೇ** ಹೆಡರ್ ಇರುವುದಿಲ್ಲ —
payload ಅನ್ನು ಬದಲಾಯಿಸಿಲ್ಲ ಮತ್ತು ಮಾಡೆಲ್ ಬದಲಾವಣೆ ಈಗಾಗಲೇ ಪ್ರತಿಕ್ರಿಯೆಯ body ಯಲ್ಲಿನ
`model` ಫೀಲ್ಡ್ನಲ್ಲಿ ಗೋಚರಿಸುತ್ತದೆ.

`GET /api/modality-bridge/stats` (`GET /api/settings` ನಂತೆಯೇ ಅದೇ ಹಂತದ management auth) `vision`, `audio`, ಮತ್ತು `video` ಗಾಗಿ ಮೆಮೊರಿಯಲ್ಲಿರುವ ಪ್ರತಿ-modality ಕೌಂಟರ್ಗಳನ್ನು
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` ಹಿಂತಿರುಗಿಸುತ್ತದೆ. `averageLatencyMs` ತನ್ನ
ಛೇದವಾಗಿ ಎಲ್ಲಾ ಪ್ರಯತ್ನಗಳ ಬದಲು `latencySamples` ಅನ್ನು ಬಳಸುತ್ತದೆ; ಸಮಯ ಮಾಪನವಿಲ್ಲದ ಕಾರ್ಯಾಚರಣೆಯು
ಕೃತಕವಾದ ಶೂನ್ಯ-ಮಿಲಿಸೆಕೆಂಡ್ ಮಾದರಿಯನ್ನು ರಚಿಸುವುದಿಲ್ಲ. ಯಶಸ್ವಿ ಪರಿವರ್ತನೆಗಳಿಗಾಗಿ
ಹಿಂದಿನ ಆವೃತ್ತಿಗಳೊಂದಿಗೆ ಹೊಂದಾಣಿಕೆಯ ಅಲಿಯಾಸ್ ಆಗಿ `bridged` ಉಳಿಯುತ್ತದೆ;
ವಿಫಲ ಪ್ರಯತ್ನಗಳು ಅದನ್ನು ಹೆಚ್ಚಿಸುವುದಿಲ್ಲ.
ವಿನ್ಯಾಸದ ಪ್ರಕಾರ ಪ್ರಕ್ರಿಯೆಯ ಮರುಪ್ರಾರಂಭದ ವೇಳೆ ಕೌಂಟರ್ಗಳು ಮರುಹೊಂದಿಸಲ್ಪಡುತ್ತವೆ
(ಇದು ಟೆಲಿಮೆಟ್ರಿ, ಲೆಕ್ಕಪತ್ರವಲ್ಲ).

#### ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಸಂರಚನೆ

ಮೀಸಲಾದ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಪುಟವು
`/dashboard/settings/modality-bridge` ಆಗಿದೆ. URL ಮೂಲಕ ವಿಳಾಸಿಸಬಹುದಾದ ಅದರ `Vision`, `Audio`,
ಮತ್ತು `Video` ಟ್ಯಾಬ್ಗಳು `tab` ಮೌಲ್ಯವನ್ನು ಬದಲಾಯಿಸುವಾಗ query parameters ಅನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ.
Vision ಟ್ಯಾಬ್ ಸಕ್ರಿಯಗೊಳಿಸುವಿಕೆ, ಮೋಡ್, ಮಾದರಿ ಆಯ್ಕೆ (ಸ್ವಯಂಚಾಲಿತ
ಡೀಫಾಲ್ಟ್ ಸೇರಿದಂತೆ), ಕಾರ್ಯ-ಅರಿವಿನ ಪ್ರಾಂಪ್ಟಿಂಗ್, ಸುಧಾರಿತ timeout/image/description-length/cache
ಮಿತಿಗಳು, runtime ಕೌಂಟರ್ಗಳು ಮತ್ತು ಸುರಕ್ಷಿತಗೊಳಿಸಲಾದ ಮಾದರಿ ವಿನಂತಿಯನ್ನು ಒದಗಿಸುತ್ತದೆ.
Audio ಟ್ಯಾಬ್ ಸಹ ಸಕ್ರಿಯವಾಗಿದೆ: ಇದು ಸಕ್ರಿಯಗೊಳಿಸುವಿಕೆ, Auto ಒಳಗೊಂಡ STT-ಮಾತ್ರದ ಮಾದರಿ ಆಯ್ಕೆಕಾರ,
timeout/max-clip ಮಿತಿಗಳು, audio ಕೌಂಟರ್ಗಳು ಮತ್ತು `input_audio` ಮಾದರಿ ಪರೀಕ್ಷೆಯನ್ನು ಒದಗಿಸುತ್ತದೆ.
Video ಟ್ಯಾಬ್ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ: ಇದು FFmpeg/ffprobe runtime ಸ್ಥಿತಿಯನ್ನು ವರದಿ ಮಾಡುತ್ತದೆ —
ನಾಲ್ಕು ಸ್ಪಷ್ಟ UI ಸ್ಥಿತಿಗಳಲ್ಲಿ ಒಂದು (`unknown`, probe ಪ್ರಗತಿಯಲ್ಲಿರುವಾಗ ಅಥವಾ ಪೂರ್ಣಗೊಳ್ಳಲು
ಸಾಧ್ಯವಾಗದಾಗ; `restricted`, loopback ಅಲ್ಲದ ಡ್ಯಾಶ್ಬೋರ್ಡ್ host ನಲ್ಲಿ probe ಅನ್ನು client-side
ಬಿಟ್ಟುಬಿಟ್ಟಾಗ; `unavailable`, probe ಮಾಡಿದ ನಂತರ ಅದು ಲಭ್ಯವಿಲ್ಲವೆಂದು ದೃಢಪಟ್ಟಾಗ; ಅಥವಾ
FFmpeg/ffprobe ಆವೃತ್ತಿಗಳೊಂದಿಗೆ `available`) — enable/model/frame/video/timeout ಮಿತಿಗಳನ್ನು
ಉಳಿಸುತ್ತದೆ, ಮಾದರಿ ಆಯ್ಕೆಕಾರವನ್ನು vision-ಸಾಮರ್ಥ್ಯವುಳ್ಳ ಮಾದರಿಗಳಿಗೆ ಶೋಧಿಸುತ್ತದೆ ಮತ್ತು video
ಕೌಂಟರ್ಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ.

AI settings ಅಡಿಯಲ್ಲಿದ್ದ ಹಿಂದಿನ Vision Bridge ಕಾರ್ಡ್ ಈಗ ಹೊಸ ಪುಟಕ್ಕೆ ಹೊಂದಾಣಿಕೆ ಲಿಂಕ್ ಆಗಿದೆ;
ಇನ್ನು ಮುಂದೆ ಅದು ಫಾರ್ಮ್ನ ಎರಡನೇ ಪ್ರತಿಯನ್ನು ಹೊಂದಿರುವುದಿಲ್ಲ. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ Speech-to-Text
playground ಅನ್ನು ತೆಗೆದುಹಾಕದೆ, Media Providers ಕೂಡ Image-to-Text ಮತ್ತು Speech-to-Text
ಕಾರ್ಯಪ್ರವಾಹಗಳನ್ನು ಅನುಗುಣವಾದ Modality Bridge ಟ್ಯಾಬ್ಗಳಿಗೆ ಲಿಂಕ್ ಮಾಡುತ್ತದೆ.

**Self-loop admission bypass:** describe ಕರೆ OmniRoute ನ ಸ್ವಂತ `/v1` self-loop ಮೂಲಕ
(non-standard provider model) route ಆದಾಗ, ಉಪ-ವಿನಂತಿಯು
`x-omniroute-admission-bypass: internal` ಅನ್ನು ಕಳುಹಿಸುತ್ತದೆ ಮತ್ತು ನಿರ್ಧರಿಸಲಾದ self-loop
credential ಮೂಲಕ ದೃಢೀಕರಿಸಲ್ಪಡುತ್ತದೆ — local mode ನಲ್ಲಿ ಸ್ಥಳೀಯ `sk_omniroute` sentinel,
ಅಥವಾ operator ಸಂರಚಿಸಿದ `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env key (#1350);
ಇದರಿಂದ `REQUIRE_API_KEY=true` deployments ಕೂಡ describe ಕರೆಯನ್ನು ಚಲಾಯಿಸಬಹುದು.
ಈ ನಿಖರ credentials ಗಳಿಗೆ ಮಾತ್ರ bypass ಅನ್ನು ಗೌರವಿಸಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಬಾಹ್ಯ clients
admission ಅನ್ನು ಬಿಟ್ಟುಹೋಗಲು header ಅನ್ನು ಬಳಸಲಾಗುವುದಿಲ್ಲ.

ಹಳೆಯ ಡೀಫಾಲ್ಟ್ಗಳು `src/shared/constants/visionBridgeDefaults.ts` ನಲ್ಲಿವೆ;
ಹೊಸ mode/task-aware/cache ಡೀಫಾಲ್ಟ್ಗಳು ಮತ್ತು settings resolver
`src/shared/constants/modalityBridgeDefaults.ts` ನಲ್ಲಿವೆ. ಪರೀಕ್ಷೆಗಳು ನಕಲಿ `getSettings`
ಮತ್ತು `callVisionModel` implementations ಅನ್ನು inject ಮಾಡಲು ಸಾಧ್ಯವಾಗುವಂತೆ guardrail
ಒಂದು `deps` constructor option ಅನ್ನು ಒದಗಿಸುತ್ತದೆ.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Audio input ಅನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ ಎಂದು ತಿಳಿದಿಲ್ಲದ target ಅನ್ನು audio ಹೊಂದಿರುವ chat
ವಿನಂತಿಗಳು ತಲುಪುವ ಮೊದಲು ಅವುಗಳನ್ನು intercept ಮಾಡುತ್ತದೆ. ಇದು chat ವಿನಂತಿಯನ್ನು ಎಂದಿಗೂ
ಮರು-route ಮಾಡುವುದಿಲ್ಲ: ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ OpenAI-compatible multipart endpoint ಮೂಲಕ
audio ಭಾಗಗಳನ್ನು ಲಿಪ್ಯಂತರಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಆಯ್ಕೆಮಾಡಿದ chat model ಪಠ್ಯ transcriptಗಳೊಂದಿಗೆ
ಮುಂದುವರಿಯುತ್ತದೆ.

ಪ್ರವಾಹ:

1. `getResolvedModelCapabilities()` ಮೂಲಕ `supportsAudio` ಅನ್ನು resolve ಮಾಡಿ. ಸ್ಪಷ್ಟವಾದ
   provider-registry metadata ಗೆ ಮೊದಲ ಆದ್ಯತೆ, ನಂತರ static model metadata, ನಂತರ sync ಆದ
   `modalities_input`. `audio` ಇಲ್ಲದ ಘೋಷಿತ input list `false` ಆಗಿರುತ್ತದೆ; ಯಾವುದೇ capability
   ಪುರಾವೆ ಇಲ್ಲದಿದ್ದರೆ `null` ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ. `false` ಮತ್ತು `null` ಎರಡೂ conservative bridge
   ಅನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುತ್ತವೆ, ಆದರೆ `true` ಅದನ್ನು bypass ಮಾಡುತ್ತದೆ.
2. `modalityBridgeAudio*` settings ಅನ್ನು resolve ಮಾಡಿ ಮತ್ತು ಹಂಚಿಕೊಂಡ `detectMediaParts()`
   detector ಮೂಲಕ ಪ್ರತಿ message ನಿಂದ splice ಮಾಡಬಹುದಾದ top-level audio ಭಾಗಗಳನ್ನು ಹೊರತೆಗೆಯಿರಿ.
   ಬೆಂಬಲಿತ wire shapes ಎಂದರೆ OpenAI `input_audio`, `audio_url`, ಮತ್ತು
   `source.media_type: "audio/*"`. Routing ಗಾಗಿ nested audio ಅನ್ನು ಪತ್ತೆಮಾಡಲಾಗುತ್ತದೆ, ಆದರೆ
   splice path ಅದನ್ನು ತೆಗೆದುಹಾಕುವುದಿಲ್ಲ. ಕೆಲಸವು `modalityBridgeAudioMaxClips` ನಿಂದ
   ಮಿತಿಗೊಳಿಸಲ್ಪಡುತ್ತದೆ; ನಂತರದ ಭಾಗಗಳು ಬದಲಾಗದೆ ಉಳಿಯುತ್ತವೆ.
3. ಸಂರಚಿಸಲಾದ `provider/model` ಅನ್ನು ಗೌರವಿಸಿ, ಅಥವಾ `selectAudioBridgeModel()` ಗೆ
   `AUDIO_TRANSCRIPTION_PROVIDERS` ಅನ್ನು ಸ್ಥಿರ catalog ಕ್ರಮದಲ್ಲಿ ಪರಿಶೀಲಿಸಿ, ಬಳಸಬಹುದಾದ
   ಸಕ್ರಿಯ provider credential ಹೊಂದಿರುವ ಮೊದಲ model ಅನ್ನು ಆಯ್ಕೆ ಮಾಡಲು ಅವಕಾಶ ನೀಡಿ.
4. `callAudioTranscription()` base64/data-URI audio ಅನ್ನು multipart `file` ಆಗಿ ಪರಿವರ್ತಿಸುತ್ತದೆ,
   ಅಥವಾ DNS pinning ಮತ್ತು 25 MB ಮಿತಿಯೊಂದಿಗೆ public-only outbound guard ಮೂಲಕ remote
   `audio_url` ಅನ್ನು download ಮಾಡುತ್ತದೆ. ನಂತರ ಇದು ಆಯ್ಕೆಮಾಡಿದ model ಮತ್ತು file ಅನ್ನು ಸ್ಥಳೀಯ
   `/v1/audio/transcriptions` self-loop ಗೆ POST ಮಾಡುತ್ತದೆ ಮತ್ತು `resolveSelfLoopBearer()`
   ಮೂಲಕ ದೃಢೀಕರಿಸುತ್ತದೆ. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ transcription route ಸಾಮಾನ್ಯ credential lookup,
   cooldown/rate-limit ನಿರ್ವಹಣೆ ಮತ್ತು provider dispatch ಅನ್ನು ನಿರ್ವಹಿಸುತ್ತದೆ.
5. ಯಶಸ್ವಿ ಕರೆಗಳು ತಮ್ಮ ಭಾಗಗಳನ್ನು `[Audio N]: <transcript>` ನಿಂದ ಬದಲಿಸುತ್ತವೆ. ಕರೆಗಳು
   `Promise.allSettled` ಬಳಸಿ ಚಲಿಸುತ್ತವೆ: ಪ್ರತ್ಯೇಕ ವೈಫಲ್ಯವು ಮೂಲ audio ಭಾಗವನ್ನು ಹಾಗೆಯೇ
   ಉಳಿಸುತ್ತದೆ (#4012 contract). ಪ್ರತಿ ಕರೆಯೂ ವಿಫಲವಾದರೆ ಮತ್ತು target
   `supportsAudio === false` ಎಂದು ಸಾಬೀತಾಗಿದ್ದರೆ, ಭಾಗಗಳು
   `[Audio N]: (unavailable — no STT provider connected)` ಆಗುತ್ತವೆ (#8430 contract).
   ಅಜ್ಞಾತ target (`null`) ಗಾಗಿ, ಎಲ್ಲವೂ ವಿಫಲವಾದ ಫಲಿತಾಂಶವು ಬದಲಾಗದೆ ಉಳಿಯುತ್ತದೆ. ಬಳಸಬಹುದಾದ
   STT credential ಇಲ್ಲದ, ಸಾಬೀತಾದ text-only target ಗೆ network call ಮಾಡದೆಯೇ ಅದೇ ಸ್ಪಷ್ಟ
   stub ದೊರೆಯುತ್ತದೆ.

ಯಶಸ್ವಿ transcriptಗಳು process-wide Modality Bridge LRU/TTL cache ಅನ್ನು ಬಳಸುತ್ತವೆ.
Key, audio reference, ಸ್ಥಿರವಾದ `audio-transcription` operation label ಮತ್ತು ಆಯ್ಕೆಮಾಡಿದ
STT model ಅನ್ನು ಸಂಯೋಜಿಸುತ್ತದೆ; ವೈಫಲ್ಯಗಳನ್ನು ಎಂದಿಗೂ cache ಮಾಡಲಾಗುವುದಿಲ್ಲ. Audio
ಪ್ರಯತ್ನಗಳು ಹಂಚಿಕೊಂಡ `bridged`, `cacheHits`, `failures`, ಮತ್ತು `lastUsedAt` ಕೌಂಟರ್ಗಳನ್ನು
ನವೀಕರಿಸುತ್ತವೆ. ಪರಿವರ್ತಿಸಲಾದ responses ನಲ್ಲಿ
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` ಇರುತ್ತದೆ;

### ವೀಡಿಯೊ ಬ್ರಿಡ್ಜ್ (`videoBridge.ts`, `videoBridgePipeline.ts`)

ತಿಳಿದಿರುವ ಸ್ಥಳೀಯ ವೀಡಿಯೊ ಬೆಂಬಲವನ್ನು ಹೊಂದಿರದ ಗುರಿಯನ್ನು ಕರೆಯುವ ಮೊದಲು, Chat Completions
`messages` ಮತ್ತು Responses API `input` ನಲ್ಲಿರುವ ಉನ್ನತ-ಹಂತದ ವೀಡಿಯೊ ಭಾಗಗಳನ್ನು
ತಡೆಹಿಡಿಯುತ್ತದೆ. ಬೆಂಬಲಿತ ಆಕಾರಗಳೆಂದರೆ `input_video`, `video_url`, `video_source`, HTTPS URLಗಳು,
ಮತ್ತು `data:video/*;base64,...` ಡೇಟಾ URIಗಳು. ಪಠ್ಯದಲ್ಲಿನ ಸರಳ ಫೈಲ್ ಹೆಸರುಗಳನ್ನು
ವೀಡಿಯೊ ಎಂದು ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) ವಿನಂತಿಯ ಟ್ರಾವರ್ಸಲ್,
ಸಾಮರ್ಥ್ಯ/ನೀತಿ ಪರಿಶೀಲನೆ, ಪ್ರತಿ-ವಿನಂತಿಯ ಒಟ್ಟುಗೂಡಿಸುವಿಕೆ, ಮತ್ತು ಪ್ರತಿಕ್ರಿಯೆ ಪೇಲೋಡ್ ಅನ್ನು ನಿರ್ವಹಿಸುತ್ತದೆ.
ಪ್ರತಿ-ವೀಡಿಯೊ ಕೆಲಸ — ಸ್ವಾಧೀನಪಡಿಸಿಕೊಳ್ಳುವಿಕೆ, ಸಂಪೂರ್ಣ-ಫಲಿತಾಂಶದ ಕ್ಯಾಶ್, ಫ್ರೇಮ್
ಅನುಕ್ರಮವನ್ನು ವಿವರಿಸುವುದು (ಇದು ಕರೆಮಾಡುವವರು ಘೋಷಿಸಿದ ಯಾವುದೇ ಆಡಿಯೊ ಪ್ರತಿಲಿಪಿಯನ್ನು ಸಂಯೋಜಿಸುತ್ತದೆ),
ಮತ್ತು ಪ್ರತಿ-ಪ್ರಯತ್ನದ ಮೆಟ್ರಿಕ್ಗಳು/ಸ್ಥಗಿತಗೊಳಿಸುವಿಕೆ/ಸ್ವಚ್ಛಗೊಳಿಸುವಿಕೆ — ಇವೆಲ್ಲವೂ
`videoBridgePipeline.ts` ನಲ್ಲಿನ `processVideoPart` ಹಿಂದೆ ಅಡಗಿವೆ ಮತ್ತು `preCall` ನ ಲೂಪ್ನೊಳಗೆ
ಪ್ರತಿ ವೀಡಿಯೊ ಭಾಗಕ್ಕೆ ಒಮ್ಮೆ ಕರೆಯಲ್ಪಡುತ್ತವೆ. ಆ ಮಾಡ್ಯೂಲ್ ಸ್ಪಷ್ಟ ಪೋರ್ಟ್ ಗಡಿಗಳಾದ
`VideoMediaBrokerPort` (ಬೈಟ್ಗಳನ್ನು ಸ್ವಾಧೀನಪಡಿಸಿಕೊಳ್ಳುವುದು ಮತ್ತು ಮಾದರಿಯಾಗಿ ಆಯ್ದ ಫ್ರೇಮ್ಗಳನ್ನು ಹೊರತೆಗೆಯುವುದು),
`VideoAudioTranscriptionPort` (ಕರೆಮಾಡುವವರು ಘೋಷಿಸಿದ ಆಡಿಯೊ ಪ್ರತಿಲಿಪಿಯನ್ನು ಮಾದರಿ ಶೀರ್ಷಿಕೆಗಳೊಂದಿಗೆ ಸಂಯೋಜಿಸುವುದು), ಮತ್ತು
`VideoDrilldownPort` (ಫ್ರೇಮ್ ಡ್ರಿಲ್-ಡೌನ್ ಸ್ಥಿರತೆ ಗಡಿ; ಇದನ್ನು ಇನ್ನೂ
`processVideoPart` ಗೆ ಜೋಡಿಸಲಾಗಿಲ್ಲ — ಪ್ರಸ್ತುತ ಪ್ರತ್ಯೇಕ `/api/modality-bridge/video/drilldown`
ರೂಟ್ ಮಾತ್ರ ಡ್ರಿಲ್-ಡೌನ್ ನಮೂದುಗಳನ್ನು ಬರೆಯುತ್ತದೆ) ಅನ್ನು ಸಹ ವ್ಯಾಖ್ಯಾನಿಸುತ್ತದೆ.

ಸಾರ್ವಜನಿಕ `/v1` ವಿನಂತಿ ಪಥವು ಉಪಪ್ರಕ್ರಿಯೆಯನ್ನು ಎಂದಿಗೂ ಆಮದು ಮಾಡುವುದಿಲ್ಲ ಅಥವಾ ಆಹ್ವಾನಿಸುವುದಿಲ್ಲ. ದೂರಸ್ಥ
ವೀಡಿಯೊಗಳನ್ನು 50 MiB ಮಿತಿಯೊಳಗೆ ಡೌನ್ಲೋಡ್ ಮಾಡಲಾಗುತ್ತದೆ; ಇನ್ಲೈನ್ base64 ವೀಡಿಯೊಗಳಿಗೆ
ಪ್ರತಿ ವೀಡಿಯೊಗೆ ಸಂಪ್ರದಾಯಬದ್ಧವಾದ 36 MiB ಡಿಕೋಡ್ ಮಿತಿಯಿದೆ, ಇದರಿಂದ ಮಾದರಿ/ಸಂದೇಶಗಳು/ಫ್ರೇಮಿಂಗ್ ಎನ್ವೆಲಪ್
50 MiB ಸಾರ್ವಜನಿಕ JSON ವಿನಂತಿ ಸ್ವೀಕೃತಿ ಮಿತಿಯೊಳಗೆ ಉಳಿಯಬಹುದು. ಇನ್ಲೈನ್
ಉದ್ದ ಮತ್ತು ಡಿಕೋಡ್ ಗಾತ್ರದ ಅಂದಾಜುಗಳನ್ನು ನಿಯೋಜನೆಗೂ ಮೊದಲು ಪರಿಶೀಲಿಸಲಾಗುತ್ತದೆ. ಆರಂಭಿಕ ದೂರಸ್ಥ URL ಮತ್ತು
ಪ್ರತಿ ಮರುನಿರ್ದೇಶನದಲ್ಲಿ HTTPS ಅಗತ್ಯವಿದ್ದು, DNS ಪಿನ್ನಿಂಗ್ನೊಂದಿಗೆ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ
ಸಾರ್ವಜನಿಕ-ಮಾತ್ರ ಹೊರಹೋಗುವ ಗಾರ್ಡ್ ಅನ್ನು ಬಳಸಲಾಗುತ್ತದೆ. ನಂತರ ಬೈಟ್ಗಳು ನಿಖರವಾದ ಆಂತರಿಕ
`POST /api/modality-bridge/video/extract` ಬ್ರೋಕರ್ ಗಡಿಯನ್ನು ದಾಟುತ್ತವೆ. ಆ ರೂಟ್
`LOCAL_ONLY` ಮತ್ತು `SPAWN_CAPABLE` ಎರಡೂ ಆಗಿದ್ದು, ಪ್ರತಿ-ಪ್ರಕ್ರಿಯೆಗೆ ದೃಢೀಕರಿಸಲಾದ,
ವಿಶ್ವಾಸಾರ್ಹ ಲೂಪ್ಬ್ಯಾಕ್ ವಿನಂತಿಯನ್ನು ಮಾತ್ರ ಸ್ವೀಕರಿಸುತ್ತದೆ ಮತ್ತು URL, ಫೈಲ್ಸಿಸ್ಟಮ್ ಪಥ, ಎಕ್ಸಿಕ್ಯೂಟಬಲ್,
ಅಥವಾ ಆರ್ಗ್ಯುಮೆಂಟ್ ಪಟ್ಟಿಯನ್ನು ಎಂದಿಗೂ ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ. API ಬಾಡಿ-ಗಾತ್ರದ ಪೈಪ್ಲೈನ್ ಮತ್ತು ಹ್ಯಾಂಡ್ಲರ್ನ ಕ್ರಮೇಣ ಬಾಡಿ
ರೀಡರ್ ಸ್ವತಂತ್ರವಾಗಿ 50 MiB ಬ್ರೋಕರ್ ಇನ್ಪುಟ್ ಮಿತಿಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ. ಅದರ ಮಿತಿಗೊಳಿಸಲಾದ ಕ್ಯೂ
ಒಂದು ಸಮಯದಲ್ಲಿ ಒಂದು ಹೊರತೆಗೆಯುವಿಕೆಯನ್ನು ನಡೆಸುತ್ತದೆ, ಬಾಕಿಯಿರುವ ನಾಲ್ಕು ಜಾಬ್ಗಳಿಗೆ ಅವಕಾಶ ನೀಡುತ್ತದೆ, ಮತ್ತು ಬಾಕಿಯಿರುವ ಇನ್ಪುಟ್ ಅನ್ನು
100 MiB ಗೆ ಮಿತಿಗೊಳಿಸುತ್ತದೆ.

ಬ್ರೋಕರ್ನೊಳಗೆ, `ffprobe` ಖಾಸಗಿ ಸ್ಥಳೀಯ ಫೈಲ್ ಅನ್ನು ಓದುತ್ತದೆ; ಸ್ಥಿರ ಫಾರ್ಮ್ಯಾಟ್
ಅನುಮತಿ ಪಟ್ಟಿಯು ಪ್ಲೇಲಿಸ್ಟ್ ಮತ್ತು ಮ್ಯಾನಿಫೆಸ್ಟ್ ಫಾರ್ಮ್ಯಾಟ್ಗಳನ್ನು ಹೊರಗಿಡುತ್ತದೆ. ಅನುಮತಿಸಲಾದ MOV-ಕುಟುಂಬದ
ಕಂಟೇನರ್ಗಳಿಗೆ, ಬಾಹ್ಯ MOV ಡೇಟಾ ಉಲ್ಲೇಖಗಳು ಡೀಫಾಲ್ಟ್ ಆಗಿ ನಿಷ್ಕ್ರಿಯವಾಗಿಯೇ ಇರುತ್ತವೆ ಮತ್ತು
ಸ್ಥಿರ ಕಮಾಂಡ್ ಅವುಗಳನ್ನು ಸಕ್ರಿಯಗೊಳಿಸುವುದಿಲ್ಲ. `ffprobe` ಮತ್ತು `ffmpeg` ಎರಡೂ
`file`-ಮಾತ್ರ ಪ್ರೋಟೋಕಾಲ್ ಅನುಮತಿ ಪಟ್ಟಿ, ಒಂದು ಥ್ರೆಡ್, ಸ್ಥಿರ ಆರ್ಗ್ಯುಮೆಂಟ್ ಅರೇಗಳು, ಶೆಲ್ ಇಲ್ಲದೆ,
ಮತ್ತು `PATH` ನಿಂದ ಪರಿಹರಿಸಲಾದ ಎಕ್ಸಿಕ್ಯೂಟಬಲ್ಗಳನ್ನು ಬಳಸುತ್ತವೆ. ಲಗತ್ತಿಸಲಾದ-ಚಿತ್ರದ ಕವರ್ ಸ್ಟ್ರೀಮ್ಗಳು
ಪ್ಲೇ ಮಾಡಬಹುದಾದ ಅಭ್ಯರ್ಥಿಗಳಲ್ಲ. ಪ್ಲೇ ಮಾಡಬಹುದಾದ ಎಲ್ಲ ಸ್ಟ್ರೀಮ್ಗಳು ಮಿತಿಗಳನ್ನು ಪೂರೈಸಬೇಕು ಮತ್ತು
ನಿರ್ಣಾಯಕವಾದ ಅತ್ಯಂತ-ಕಡಿಮೆ-ಸೂಚ್ಯಂಕದ ಫಾಲ್ಬ್ಯಾಕ್ಗೆ ಮೊದಲು ಸ್ಪಷ್ಟವಾದ ಡೀಫಾಲ್ಟ್ ಸ್ಟ್ರೀಮ್ಗೆ ಆದ್ಯತೆ ನೀಡಲಾಗುತ್ತದೆ.
ವೀಡಿಯೊಗಳನ್ನು 600 ಸೆಕೆಂಡುಗಳು, ಪ್ರತಿ ಆಯಾಮಕ್ಕೆ 8,192 ಪಿಕ್ಸೆಲ್ಗಳು, ಮತ್ತು
33,554,432 ಮೂಲ ಪಿಕ್ಸೆಲ್ಗಳಿಗೆ ಮಿತಿಗೊಳಿಸಲಾಗಿದೆ. FFmpeg 1–16 ಮಧ್ಯಬಿಂದು JPEG ಫ್ರೇಮ್ಗಳ ಮಾದರಿಯನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತದೆ,
ಚಿಕ್ಕ ಇನ್ಪುಟ್ಗಳನ್ನು ಮೇಲ್ಮಟ್ಟಕ್ಕೆ ಸ್ಕೇಲ್ ಮಾಡದೆ ಉದ್ದನೆಯ ಅಂಚನ್ನು ಗರಿಷ್ಠ 1,024 ಪಿಕ್ಸೆಲ್ಗಳಿಗೆ ಇಳಿಸುತ್ತದೆ, ಮತ್ತು
ಎಂದಿಗೂ URL ಅನ್ನು ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ. ಮಾದರಿ ಆಯ್ಕೆಯು ಡೀಫಾಲ್ಟ್ ಆಗಿ `uniform` ಆಗಿರುತ್ತದೆ. ಐಚ್ಛಿಕ
`scene_aware` ಮತ್ತು ಪ್ರಾಯೋಗಿಕ `segment_aware` ನೀತಿಗಳು ಈಗಾಗಲೇ ಮೌಲ್ಯೀಕರಿಸಲಾದ ಸ್ಥಳೀಯ ಸ್ಟ್ರೀಮ್ ಮೇಲೆ
ಒಂದು ಹೆಚ್ಚುವರಿ ಸ್ಥಿರ FFmpeg ಪಾಸ್ ಅನ್ನು ನಿರ್ವಹಿಸುತ್ತವೆ, ಮಿತಿಗೊಳಿಸಲಾದ
`showinfo` ದೃಶ್ಯ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ಗಳನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತವೆ, ಮತ್ತು ಡಿಟೆಕ್ಟರ್ ವಿಫಲತೆ, ಕಾಲಮಿತಿ ಮೀರುವಿಕೆ,
ದೋಷಪೂರಿತ ಔಟ್ಪುಟ್, ಅಥವಾ ಖಾಲಿ ಅಭ್ಯರ್ಥಿ ಸೆಟ್ ಸಂದರ್ಭದಲ್ಲಿ ಅದೇ ಏಕರೂಪ ಮಧ್ಯಬಿಂದುಗಳಿಗೆ
ನಿರ್ಣಾಯಕವಾಗಿ ಹಿಂತಿರುಗುತ್ತವೆ. ವಿಭಾಗ-ಅರಿವು ಮೋಡ್, ಮೌಲ್ಯೀಕರಿಸಲಾದ ದೃಶ್ಯ ಮಧ್ಯಂತರಗಳಿಗೆ ಅನುಪಾತದಲ್ಲಿ
ಮಧ್ಯಬಿಂದು ಮಾದರಿಗಳನ್ನು ಹಂಚುತ್ತದೆ; ವಿಭಾಗ-ಅರಿವು ಸಾಕ್ಷ್ಯ ಮತ್ತು ಫಾಲ್ಬ್ಯಾಕ್ ವರ್ತನೆಯನ್ನು
ಕೆಳಗೆ ವಿವರಿಸಲಾಗಿದೆ. ಪ್ರತಿ ನೀತಿಯಲ್ಲೂ ಆಯ್ಕೆಯ ನಂತರ
ಕಠಿಣ 16-ಫ್ರೇಮ್ ಮಿತಿಯನ್ನು ಅನ್ವಯಿಸಲಾಗುತ್ತದೆ. ದೃಶ್ಯ-ಅರಿವು ವಿನಂತಿಯು ಕೇವಲ
ಒಂದು-ಫ್ರೇಮ್ ಬಜೆಟ್ ಹೊಂದಿರುವಾಗ, ಅದು ಸಕ್ರಿಯ ಪೂರ್ಣ-ವೀಡಿಯೊ ಅಥವಾ ಫೋಕಸ್ ವಿಂಡೋದ ಏಕರೂಪ ಮಧ್ಯಬಿಂದುವನ್ನು
ಬಳಸುತ್ತದೆ ಮತ್ತು `policyEffective: uniform` ಎಂದು ವರದಿ ಮಾಡುತ್ತದೆ: ಆಯ್ಕೆಮಾಡಲಾದ ಒಂದೇ ದೃಶ್ಯ ಫ್ರೇಮ್
ಎರಡೂ ಕಾಲಿಕ ತುದಿಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳಲು ಸಾಧ್ಯವಿಲ್ಲ. ಕರೆಮಾಡುವವರು ಐಚ್ಛಿಕವಾಗಿ
ಸೀಮಿತ ಫೋಕಸ್ ವಿಂಡೋವನ್ನು (`start`/`end` ಸೆಕೆಂಡುಗಳು) ಒದಗಿಸಬಹುದು; ಗಡಿಗಳನ್ನು ಮಾಧ್ಯಮದ
ಅವಧಿಗೆ ಸೀಮಿತಗೊಳಿಸಲಾಗುತ್ತದೆ, ಹಿಮ್ಮುಖ ಅಥವಾ ಪರಿಮಿತವಲ್ಲದ ವಿಂಡೋಗಳನ್ನು ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ, ಮತ್ತು ಎಲ್ಲಾ ಮಾದರಿ ಆಯ್ಕೆ
ನೀತಿಗಳನ್ನು ಸಾಮಾನ್ಯೀಕರಿಸಲಾದ ಮಧ್ಯಂತರದೊಳಗೆ ಮಾತ್ರ ನಿರ್ವಹಿಸಲಾಗುತ್ತದೆ. ಫಲಿತಾಂಶದ
ವಿಂಡೋವನ್ನು ಮಾದರಿ ಆಯ್ಕೆ ಮೆಟಾಡೇಟಾ ಮತ್ತು ಅವಿಶ್ವಾಸಾರ್ಹ ವಿವರಣೆ
ಪೂರ್ವಪ್ರತ್ಯಯದಲ್ಲಿ ಸೇರಿಸಲಾಗುತ್ತದೆ, ಇದರಿಂದ ಡೌನ್ಸ್ಟ್ರೀಮ್ ಮಾದರಿಗಳು ಕೇಂದ್ರೀಕೃತ ಆಯ್ದ ಭಾಗವನ್ನು ಪೂರ್ಣ
ಟೈಮ್ಲೈನ್ನಿಂದ ಪ್ರತ್ಯೇಕಿಸಬಹುದು.

ಅರ್ಥಾತ್ಮಕ ಶೀರ್ಷಿಕೆ ಫೋಕಸ್ ಒಂದು ಪ್ರತ್ಯೇಕ, ಸ್ಪಷ್ಟ ಸೆಟ್ಟಿಂಗ್ ಆಗಿದೆ. ಡೀಫಾಲ್ಟ್ `full`
ವಿಶ್ಲೇಷಣಾ ಮೋಡ್ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಫ್ರೇಮ್ ಪ್ರಾಂಪ್ಟ್ ಅನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ ಮತ್ತು ವಿನಂತಿಯ
ಪಠ್ಯವನ್ನು ಶೀರ್ಷಿಕೆ ಮಾದರಿಗೆ ಎಂದಿಗೂ ಫಾರ್ವರ್ಡ್ ಮಾಡುವುದಿಲ್ಲ. `focused` ಮೋಡ್ನಲ್ಲಿ, ಬ್ರಿಡ್ಜ್ ಅದೇ Chat ಅಥವಾ Responses
ಕಂಟೇನರ್ನಿಂದ ಇತ್ತೀಚಿನ ಖಾಲಿಯಲ್ಲದ ಬಳಕೆದಾರ-ರಚಿಸಿದ `text`/`input_text` ಅನ್ನು ಮಾತ್ರ ಓದುತ್ತದೆ,
ಅದನ್ನು NFC ಗೆ ಸಾಮಾನ್ಯೀಕರಿಸುತ್ತದೆ, ನಿಯಂತ್ರಣ ಅಕ್ಷರಗಳು ಮತ್ತು ವೈಟ್ಸ್ಪೇಸ್ ಅನ್ನು ಸಂಕುಚಿಸುತ್ತದೆ,
ಮತ್ತು ಅದನ್ನು 500 Unicode ಕೋಡ್ ಪಾಯಿಂಟ್ಗಳಿಗೆ ಮಿತಿಗೊಳಿಸುತ್ತದೆ. ಖಾಲಿ ಫಲಿತಾಂಶವು ನಿಖರವಾದ
`full` ಪ್ರಾಂಪ್ಟ್ಗೆ ಹಿಂತಿರುಗುತ್ತದೆ. ಉಪಯುಕ್ತ ಸುಳಿವನ್ನು ಮೀಸಲಾದ
ಅವಿಶ್ವಾಸಾರ್ಹ-ಬಳಕೆದಾರ-ಸಂದರ್ಭ ಬ್ಲಾಕ್ನಲ್ಲಿ JSON ಆಗಿ ಸೀರಿಯಲೈಸ್ ಮಾಡಲಾಗುತ್ತದೆ ಮತ್ತು ಅದು ಗಮನಿಸಬಹುದಾದ
ವಿವರಗಳಿಗೆ ಮಾತ್ರ ಆದ್ಯತೆ ನೀಡಬಹುದು; ಮಾಧ್ಯಮದಲ್ಲಿ ಗೋಚರಿಸುವ ಅಥವಾ ಕೇಳಿಸಬಹುದಾದ ಸೂಚನೆಗಳನ್ನು ಅನುಸರಿಸಬಾರದೆಂಬ
ಪ್ರತ್ಯೇಕ ಎಚ್ಚರಿಕೆಯನ್ನು ಅದು ಅತಿಕ್ರಮಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ. ಪಠ್ಯಾತ್ಮಕ ಫೋಕಸ್ ಎಂದಿಗೂ `start`/`end` ಅನ್ನು
ಊಹಿಸುವುದಿಲ್ಲ ಅಥವಾ ಕಾಲಿಕ ಸ್ಯಾಂಪ್ಲರ್ ಅನ್ನು ಬದಲಾಯಿಸುವುದಿಲ್ಲ.

#### FU-07 ರಚನಾತ್ಮಕ ವಿಭಾಗದ ಸಾಕ್ಷ್ಯ

`segment_aware` ಈಗಾಗಲೇ ಮೌಲ್ಯೀಕರಿಸಲಾದ ಸ್ಥಳೀಯ ವೀಡಿಯೊ ಸ್ಟ್ರೀಮ್ ಮೇಲೆ ಒಂದು ಮಿತಿಗೊಳಿಸಲಾದ ಪೂರ್ವ-ವಿಶ್ಲೇಷಣಾ ಪಾಸ್ ಅನ್ನು ಬಳಸುತ್ತದೆ. ಸ್ಥಿರ ಫಿಲ್ಟರ್ ಸರಪಳಿಯು ಮೊದಲು ಅಗಲವನ್ನು ಗರಿಷ್ಠ 320 ಪಿಕ್ಸೆಲ್ಗಳಿಗೆ ಸ್ಕೇಲ್ ಮಾಡುತ್ತದೆ, ದೃಶ್ಯ ಬದಲಾವಣೆಗಳು ಮತ್ತು ಸ್ಥಗಿತಗೊಂಡ ಮಧ್ಯಂತರಗಳನ್ನು ಪತ್ತೆಮಾಡುತ್ತದೆ, ನಂತರ ಮಸುಕು, ಸರಾಸರಿ ಲ್ಯೂಮಾ ಮತ್ತು ಪ್ರಾದೇಶಿಕ/ಕಾಲಿಕ ಮಾಹಿತಿಗಾಗಿ ಪ್ರತಿ ಸೆಕೆಂಡಿಗೆ 1 ಫ್ರೇಮ್ನಂತೆ ಮಾದರಿ ಸಂಗ್ರಹಿಸುತ್ತದೆ. ಈ ಪಾಸ್ ಅನ್ನು 600 ರಚನಾತ್ಮಕ ಮಾದರಿಗಳು, ಒಂದು FFmpeg/ಫಿಲ್ಟರ್ ಥ್ರೆಡ್, ಅದೇ `file`-ಮಾತ್ರದ ಪ್ರೋಟೋಕಾಲ್ ಮತ್ತು ಕಂಟೈನರ್ ಅನುಮತಿ ಪಟ್ಟಿಗಳು, 1 MiB ಪ್ರಕ್ರಿಯೆ-ಔಟ್ಪುಟ್ ಮಿತಿ ಹಾಗೂ ಬ್ರೋಕರ್ನ ಹಂಚಿದ ಸ್ಥಗಿತ/ಗಡುವಿನೊಳಗಿನ ಗರಿಷ್ಠ 30 ಸೆಕೆಂಡುಗಳಿಗೆ ಸೀಮಿತಗೊಳಿಸಲಾಗಿದೆ. ಇದು ವಿನಂತಿಯಿಂದ ಯಾವುದೇ ಕಮಾಂಡ್, ಫಿಲ್ಟರ್, ಪಥ ಅಥವಾ URL ಅನ್ನು ಎಂದಿಗೂ ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ.

ರಚನಾತ್ಮಕ ಮೌಲ್ಯಗಳು ನಿರ್ಧಾರಾತ್ಮಕ ಮಾದರಿ ಸಾಕ್ಷ್ಯವಾಗಿದ್ದು, ವೀಡಿಯೊದ ಅರ್ಥಗ್ರಹಣವಲ್ಲ. ಅವು ವಿಷಯಗಳು, ಕ್ರಿಯೆಗಳು, ಶೀರ್ಷಿಕೆಗಳು, ಮಾತು ಅಥವಾ ಬಳಕೆದಾರರ ಉದ್ದೇಶವನ್ನು ಊಹಿಸುವುದಿಲ್ಲ. ದೃಶ್ಯ ಮತ್ತು ಸ್ಥಗಿತ ಗಡಿಗಳು ಸೆಗ್ಮೆಂಟ್ಗಳನ್ನು ರೂಪಿಸುತ್ತವೆ; ಸ್ಥಗಿತ ವ್ಯಾಪ್ತಿ, ಮಸುಕು, ಎಕ್ಸ್ಪೋಶರ್, ಪ್ರಾದೇಶಿಕ ವಿವರ ಮತ್ತು ಕಾಲಿಕ ಬದಲಾವಣೆಗಳು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ 1–16 ಫ್ರೇಮ್ ಬಜೆಟ್ ಅನ್ನು ಹೇಗೆ ಹಂಚಲಾಗುತ್ತದೆ ಎಂಬುದರ ಮೇಲೆ ಮಾತ್ರ ಪ್ರಭಾವ ಬೀರುತ್ತವೆ. ಸಂಪೂರ್ಣವಾಗಿ ಸ್ಥಗಿತಗೊಂಡ ಸೆಗ್ಮೆಂಟ್ ಅನ್ನು ಒಂದು ಫ್ರೇಮ್ಗೆ ಮಿತಿಗೊಳಿಸಲಾಗುತ್ತದೆ, ಸ್ಥಗಿತಗೊಳ್ಳದ ಸೆಗ್ಮೆಂಟ್ಗಳು ಉಳಿದ ಬಜೆಟ್ಗಾಗಿ ಸ್ಪರ್ಧಿಸುತ್ತವೆ. ಗಡಿಗಳ ಸಂಖ್ಯೆ ಫ್ರೇಮ್ಗಳ ಸಂಖ್ಯೆಯನ್ನು ಮೀರಿದಾಗ, ವೇಗವಾದ ಆರಂಭಿಕ ಕಟ್ಗಳು ದೀರ್ಘವಾದ ಕೊನೆಯ ಸೆಗ್ಮೆಂಟ್ ಅನ್ನು ಮರೆಮಾಡದಂತೆ ಏಕರೂಪ ಟೈಮ್ಲೈನ್ ವ್ಯಾಪ್ತಿಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ. ಸ್ಥಗಿತ ಗಡಿಯ 1-ಸೆಕೆಂಡ್ ವಿಶ್ಲೇಷಣಾ ರೆಸಲ್ಯೂಶನ್ನೊಳಗಿನ ದೃಶ್ಯ ಗಡಿಗಳನ್ನು ಒಗ್ಗೂಡಿಸಲಾಗುತ್ತದೆ.

ಲಭ್ಯವಿಲ್ಲದ ಫಿಲ್ಟರ್ಗಳು, ದೋಷಪೂರಿತ/ಖಾಲಿ ಸಾಕ್ಷ್ಯ, ಡಿಟೆಕ್ಟರ್ ದೋಷ ಅಥವಾ ಮಿತಿಗೊಳಿಸಲಾದ ಪೂರ್ವ-ವಿಶ್ಲೇಷಣೆಯ ಕಾಲಮೀರಿಕೆಯು ನಿಖರವಾದ ಏಕರೂಪ ಮಧ್ಯಬಿಂದು ನೀತಿಗೆ ಮುಕ್ತವಾಗಿ ಹಿಂತಿರುಗುತ್ತದೆ. ಕರೆಮಾಡುವವರ ಸ್ಥಗಿತ ಅಥವಾ ಬ್ರೋಕರ್ ಗಡುವು ಹೀಗೆ ಹಿಂತಿರುಗುವುದಿಲ್ಲ: ಅದು ಚಾಲನೆಯಲ್ಲಿರುವ ಉಪಪ್ರಕ್ರಿಯೆಯನ್ನು ಕೊನೆಗೊಳಿಸುತ್ತದೆ, ನಂತರದ ಫ್ರೇಮ್ ಹೊರತೆಗೆಯುವಿಕೆಯನ್ನು ತಡೆಯುತ್ತದೆ ಮತ್ತು ಖಾಸಗಿ ತಾತ್ಕಾಲಿಕ ಟ್ರೀ ಅನ್ನು `finally` ನಲ್ಲಿ ತೆಗೆದುಹಾಕಲಾಗುತ್ತದೆ.

`scripts/perf/video-bridge-fu07-eval.ts` ನಕಲು ನಿವಾರಣೆಯ ನಂತರದ ಕ್ಯಾಪ್ಶನ್-ಕರೆ ಉಳಿತಾಯ, ದಟ್ಟ-ಚಲನೆಯ ಬಜೆಟ್ ಹಂಚಿಕೆ, ಮಸುಕು/ಎಕ್ಸ್ಪೋಶರ್/SI-TI ಸಾಕ್ಷ್ಯ, ದೀರ್ಘ ಕೊನೆಯ ಭಾಗವಿರುವ ವೇಗದ ಕಟ್ಗಳು ಮತ್ತು ಕ್ರಮೇಣ ಫೇಡ್ನ ತಪ್ಪು ಧನಾತ್ಮಕ ಫಲಿತಾಂಶಗಳಿಗಾಗಿ ನಿರ್ಧಾರಾತ್ಮಕ ನೈಜ FFmpeg ಫಿಕ್ಸ್ಚರ್ಗಳನ್ನು ರಚಿಸುತ್ತದೆ. ಇದು ಪೂರ್ವ-ವಿಶ್ಲೇಷಣೆಯ ವಾಲ್ ಸಮಯವನ್ನು ಮತ್ತು `/usr/bin/time` ಲಭ್ಯವಿರುವಲ್ಲಿ ಚೈಲ್ಡ್ CPU ಹಾಗೂ ಗರಿಷ್ಠ RSS ಅನ್ನು ದಾಖಲಿಸುತ್ತದೆ. ಇದರ ಗುಣಮಟ್ಟ ಪರಿಶೀಲನೆಗಳು ರಚನಾತ್ಮಕ ಓರಾಕಲ್ಗಳು ಮಾತ್ರ. ಈ ಹಾರ್ನೆಸ್ಗೆ ಅಧಿಕೃತ ಎಂಡ್ಪಾಯಿಂಟ್ ಅಥವಾ ಸ್ಥಿರೀಕೃತ ನಿರ್ಣಾಯಕ ಇಲ್ಲದಿರುವುದರಿಂದ ನೈಜ ಕ್ಯಾಪ್ಶನ್-ಮಾದರಿಯ ಗುಣಮಟ್ಟವು `HOLD` ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ. `--caption-cost-per-call-usd` ಪ್ರತಿ ಕರೆಗೆ ಸ್ಪಷ್ಟವಾದ ಧನಾತ್ಮಕ ವೆಚ್ಚದ ಅಂದಾಜನ್ನು ಒದಗಿಸದಿದ್ದರೆ ಹಣಕಾಸಿನ ಉಳಿತಾಯವೂ `HOLD` ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ; ಸ್ಕ್ರಿಪ್ಟ್ ಎರಡೂ ಫಲಿತಾಂಶಗಳಲ್ಲಿ ಯಾವುದನ್ನೂ ಕೃತಕವಾಗಿ ಸೃಷ್ಟಿಸುವುದಿಲ್ಲ.

ಪ್ರತಿ ಫ್ರೇಮ್ ಅನ್ನು 4 MiB ಗೆ, ಎಲ್ಲ ಕಚ್ಚಾ ಫ್ರೇಮ್ಗಳನ್ನು ಒಟ್ಟಾಗಿ 23 MiB ಗೆ ಮತ್ತು ಸೀರಿಯಲೈಸ್ ಮಾಡಿದ ಬ್ರೋಕರ್ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು 32 MiB ಗೆ ಮಿತಿಗೊಳಿಸಲಾಗಿದೆ. ಖಾಸಗಿ ತಾತ್ಕಾಲಿಕ ಡೈರೆಕ್ಟರಿಯನ್ನು `finally` ನಲ್ಲಿ ತೆಗೆದುಹಾಕಲಾಗುತ್ತದೆ. ಸ್ಪಷ್ಟವಾಗಿ ಗುರುತಿಸಲಾದ ವೀಡಿಯೊ ಭಾಗವು ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಹೊಂದಿರುವ ಕಾಂಟ್ಯಾಕ್ಟ್ ಶೀಟ್ ಅನ್ನು ವಿನಂತಿಸಬಹುದು. ಬ್ರಿಡ್ಜ್ ಗರಿಷ್ಠ 4-ಕಾಲಮ್, 16-ಫ್ರೇಮ್ JPEG ಗ್ರಿಡ್ ಅನ್ನು ನಿರ್ಮಿಸುತ್ತದೆ. ಪ್ರತಿ 512-ಪಿಕ್ಸೆಲ್ ಸೆಲ್ ತನ್ನ ಮೂಲ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಅನ್ನು ಹೆಚ್ಚಿನ-ಕಾಂಟ್ರಾಸ್ಟ್ನ ಕೆಳಗಿನ ಪಟ್ಟಿಯಲ್ಲಿ ಅಚ್ಚೊತ್ತುತ್ತದೆ; ಅದೇ ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ಗಳು ನಂತರದ ಸಂಬಂಧ ನಿರ್ಣಯ ಮತ್ತು ಆಡಿಟ್ಗಾಗಿ ಪಠ್ಯ ಮೆಟಾಡೇಟಾದಲ್ಲಿಯೂ ಉಳಿಯುತ್ತವೆ. ಸಂಪೂರ್ಣ JPEG ಅನ್ನು 32 MiB ಗೆ ಮಿತಿಗೊಳಿಸಲಾಗುತ್ತದೆ. `sharp` ಗ್ರಿಡ್ ಅನ್ನು ಡಿಕೋಡ್ ಮಾಡಲು ಅಥವಾ ಸಂಯೋಜಿಸಲು ಸಾಧ್ಯವಾಗದಿದ್ದರೆ, ಬ್ರಿಡ್ಜ್ ಪ್ರತ್ಯೇಕ JPEG ಫ್ರೇಮ್ಗಳಿಗೆ ಹಿಂತಿರುಗುತ್ತದೆ; ಕ್ಲೈಂಟ್ ಸ್ಥಗಿತವು ಆದರೂ ಶೀಟ್ ಕಾರ್ಯಾಚರಣೆಯ ಮೂಲಕ ಪ್ರಸಾರವಾಗುತ್ತದೆ.

ಬಡ್ತಿ ಸಾಕ್ಷ್ಯವನ್ನು ಸಂಶ್ಲೇಷಿತ ಸಂಯೋಜನಾ ಮೈಕ್ರೋಬೆಂಚ್ಮಾರ್ಕ್ನಿಂದ ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಪ್ರತ್ಯೇಕಿಸಲಾಗಿದೆ. `scripts/perf/video-bridge-contact-sheet-eval.ts` ನೈಜ OpenAI-ಹೊಂದಾಣಿಕೆಯ ದೃಶ್ಯ ಮಾದರಿಗಳಿಗಾಗಿ ಸ್ಕೀಮಾ-ಆವೃತ್ತಿಗೊಳಿಸಲಾದ A/B ಹಾರ್ನೆಸ್ ಅನ್ನು ವ್ಯಾಖ್ಯಾನಿಸುತ್ತದೆ. ಇದು ಪೂರೈಕೆದಾರ ವರದಿ ಮಾಡಿದ ಟೋಕನ್ಗಳು, ಅಂತ್ಯದಿಂದ ಅಂತ್ಯದವರೆಗಿನ ವಾಲ್ ವಿಳಂಬ (ಶೀಟ್ ಸಂಯೋಜನೆಯನ್ನೂ ಒಳಗೊಂಡಂತೆ), ಮಾದರಿ-ಕರೆಗಳ ಸಂಖ್ಯೆ ಮತ್ತು ಮ್ಯಾನಿಫೆಸ್ಟ್-ವ್ಯಾಖ್ಯಾನಿತ ವಾಸ್ತವಾಂಶ ಉಳಿಕೆಯನ್ನು ಅಳೆಯುತ್ತದೆ. ಕಚ್ಚಾ ಮಾದರಿ ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು ವರದಿಗೆ ಬರೆಯಲಾಗುವುದಿಲ್ಲ; SHA-256 ಡೈಜೆಸ್ಟ್ಗಳು ಮತ್ತು ಹೊಂದಿಕೆಯಾದ ವಾಸ್ತವಾಂಶ IDಗಳನ್ನು ಮಾತ್ರ ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ. `--execute-real` ಅನ್ನು ರವಾನಿಸಿ, `--model`, `OMNIROUTE_BASE_URL` ಮತ್ತು `OMNIROUTE_API_KEY` ಅನ್ನು ಸಂರಚಿಸದ ಹೊರತು ಹಾರ್ನೆಸ್ ಯಾವುದೇ ನೆಟ್ವರ್ಕ್ ಅಥವಾ ಪಾವತಿಸಲಾದ ಮಾದರಿ ಕರೆಯನ್ನು ಮಾಡುವುದಿಲ್ಲ. ಆ ಸ್ಪಷ್ಟ ನೈಜ ಚಾಲನೆಯಿಲ್ಲದೆ, ಅದರ ಯಂತ್ರ-ಓದಬಹುದಾದ ತೀರ್ಪು `HOLD` ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ; ಸಂಶ್ಲೇಷಿತ ಪೇಲೋಡ್/ಕರೆ-ಸಂಖ್ಯೆ ಅಳತೆಗಳು ಮಾತ್ರ ಬಡ್ತಿ ಸಾಕ್ಷ್ಯವಲ್ಲ.

ಕರೆಮಾಡುವವರು ಈಗಾಗಲೇ ಹೊಂದಾಣಿಕೆಯಾಗಿರುವ ಪಠ್ಯವನ್ನು ಹೊಂದಿದ್ದಾಗ, ಬೆಂಬಲಿತ ವೀಡಿಯೊ ಭಾಗಕ್ಕೆ ಐಚ್ಛಿಕ `transcript.cues` ಅರೇ ಅನ್ನು ಲಗತ್ತಿಸಬಹುದು. ಪ್ರತಿ ಕ್ಯೂ `text`, ಪ್ರೋಬ್ ಮಾಡಿದ ಅವಧಿಯೊಳಗಿನ ಸೀಮಿತ `start`/`end` ಮಧ್ಯಂತರ ಮತ್ತು ಅನುಮತಿ ಪಟ್ಟಿಯಲ್ಲಿರುವ `source` (`client`, `embedded`, ಅಥವಾ `audio-bridge`) ಅನ್ನು ಹೊಂದಿರಬೇಕು; `confidence` ನ ಡೀಫಾಲ್ಟ್ ಮೌಲ್ಯ `1` ಆಗಿದ್ದು, ಅದು `0` ಮತ್ತು `1` ನಡುವೆ ಇರಬೇಕು. ನಿಖರ ನಕಲು ಕ್ಯೂಗಳನ್ನು ಒಗ್ಗೂಡಿಸಲಾಗುತ್ತದೆ. OmniRoute ಈ ಮೆಟಾಡೇಟಾದಿಂದ ಎಂದಿಗೂ ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಶನ್ ಪ್ರಾರಂಭಿಸುವುದಿಲ್ಲ: ಮೌಲ್ಯೀಕರಿಸಿದ ಕ್ಯೂಗಳನ್ನು ಮೂಲ, ವಿಶ್ವಾಸಾರ್ಹತೆ ಮತ್ತು ಮಧ್ಯಂತರದೊಂದಿಗೆ ವಿವರಿಸಲಾದ ಫಲಿತಾಂಶಕ್ಕೆ ನಕಲಿಸಲಾಗುತ್ತದೆ ಹಾಗೂ ಫ್ರೇಮ್ ಕ್ಯಾಪ್ಶನ್ಗಳ ಪಕ್ಕದಲ್ಲಿ ವಿಶ್ವಾಸಾರ್ಹವಲ್ಲದ ವೀಕ್ಷಣೆಗಳಾಗಿ ಪ್ರದರ್ಶಿಸಲಾಗುತ್ತದೆ. ಅಮಾನ್ಯವಾದ, ವ್ಯಾಪ್ತಿಯಿಂದ ಹೊರಗಿರುವ ಅಥವಾ ಮೂಲಾಧಾರವಿಲ್ಲದ ಪಠ್ಯವನ್ನು ಕ್ಯಾಪ್ಶನ್ ಸ್ಟ್ರೀಮ್ಗೆ ಬೆರೆಸುವ ಬದಲು ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ. ಸ್ವಯಂ-ಘೋಷಿತ `embedded` ಅಥವಾ `audio-bridge` ಲೇಬಲ್ಗಳನ್ನೂ ಒಳಗೊಂಡಂತೆ, ವಿನಂತಿ-ಬಾಡಿಯ ಎರಡೂ ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಟ್ ಚಾನಲ್ಗಳು ಒದಗಿಸಲಾದ ಮೂಲಾಧಾರವನ್ನು `client` ಗೆ ಸಾಮಾನ್ಯೀಕರಿಸುತ್ತವೆ. ಸರ್ವರ್ ಸ್ವಾಮ್ಯದ ಅಡಾಪ್ಟರ್ ಮಾತ್ರ ಕೋಡ್-ಮಾತ್ರದ `trustedSource` ಆರ್ಗ್ಯುಮೆಂಟ್ ಮೂಲಕ ಆ ವಿಶ್ವಾಸಾರ್ಹ ಲೇಬಲ್ಗಳನ್ನು ನಿಯೋಜಿಸಬಹುದು; ವಿನಂತಿಯ JSON ಫೀಲ್ಡ್ ಆ ಆರ್ಗ್ಯುಮೆಂಟ್ ಅನ್ನು ತಲುಪಲು ಸಾಧ್ಯವಿಲ್ಲ. ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಟ್ ಪಠ್ಯವು ಅದರ ಮೂಲಾಧಾರ ಏನೇ ಇರಲಿ, ವಿಶ್ವಾಸಾರ್ಹವಲ್ಲದ ಮಾಧ್ಯಮ-ಉತ್ಪನ್ನ ವಿಷಯವಾಗಿಯೇ ಉಳಿಯುತ್ತದೆ ಮತ್ತು ಅದು ಎಂದಿಗೂ ದೃಢೀಕರಣವನ್ನು ನಿರ್ಧರಿಸಬಾರದು.

  ಎಣಿಕೆಗಳನ್ನು ದಾಖಲಿಸುತ್ತದೆ.
- **`postCall`** ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಆಳವಾಗಿ ಕ್ಲೋನ್ ಮಾಡಿ, `sanitizePIIResponse()` ಜೊತೆಗೆ
  Responses-API-ಆಕಾರದ ಮರೆಮಾಚಕವನ್ನು (`maskResponsesOutput` —
  `output_text` ಮತ್ತು `output[].content[].text` ಅನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ) ಚಲಾಯಿಸುತ್ತದೆ.
  ಯಾವುದೇ ಮರೆಮಾಚುವಿಕೆ ಸಂಭವಿಸಿದರೆ, ಮಾರ್ಪಡಿಸಿದ ಪ್ರತಿಕ್ರಿಯೆಯು ಮೂಲ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು
  ಬದಲಿಸುತ್ತದೆ.

ಗಾರ್ಡ್ರೇಲ್ ಎಂದಿಗೂ ನಿರ್ಬಂಧಿಸುವುದಿಲ್ಲ; ಅದು ಕೇವಲ ಟಿಪ್ಪಣಿ ಸೇರಿಸುತ್ತದೆ
(`meta.detections`, `meta.redacted`) ಅಥವಾ ಮರುಬರೆಯುತ್ತದೆ.

#### ಪ್ರತಿ-ಪ್ರಕಾರದ ಆಯ್ಕೆ, ಕಸ್ಟಮ್ ಪ್ಯಾಟರ್ನ್ಗಳು ಮತ್ತು ಪತ್ತೆ ಎಣಿಕೆಗಳು

**ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಸೆಟ್ಟಿಂಗ್ಗಳು → ಭದ್ರತೆ → PII ಮರೆಮಾಚುವಿಕೆ** _ಏನನ್ನು_
ಮರೆಮಾಡಬೇಕು ಎಂಬುದನ್ನು ಆಯ್ಕೆಮಾಡುತ್ತದೆ. ಇದು ಮರೆಮಾಚುವಿಕೆಯನ್ನು ಆನ್ ಮಾಡುವುದಿಲ್ಲ: ಅದನ್ನು ಇನ್ನೂ
`PII_REDACTION_ENABLED` (ವಿನಂತಿ) ಮತ್ತು `PII_RESPONSE_SANITIZATION`
(ಪ್ರತಿಕ್ರಿಯೆ + SSE) ನಿಯಂತ್ರಿಸುತ್ತವೆ; ಎರಡೂ ಡೀಫಾಲ್ಟ್ ಆಗಿ ಆಫ್ ಆಗಿರುತ್ತವೆ.

- **ಪ್ರತಿ-ಪ್ರಕಾರದ ಆಯ್ಕೆ** — ಅಂತರ್ನಿರ್ಮಿತ ಐಡಿಗಳನ್ನು
  `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`) ನಲ್ಲಿ ಪಟ್ಟಿ ಮಾಡಲಾಗಿದೆ.
  ಹೊಂದಿಸದಿದ್ದರೆ ಪ್ರತಿಯೊಂದು ಪ್ರಕಾರವೂ ಆಯ್ಕೆಯಾಗುತ್ತದೆ (ಈ ಸೆಟ್ಟಿಂಗ್ ಅಸ್ತಿತ್ವಕ್ಕೆ ಬರುವ ಮುಂಚಿನ
  ವರ್ತನೆ). ವಿನಂತಿ ಎಂಜಿನ್ನ `ssn_us` ಪ್ಯಾಟರ್ನ್ `ssn` ಗೆ ಮ್ಯಾಪ್ ಆಗುತ್ತದೆ.
  ಟೆಂಪ್ಲೇಟ್ಗಳು (Minimal, Standard, Financial, Brazilian, USA, Full) UI ಯಲ್ಲಿನ
  ಚೆಕ್ಬಾಕ್ಸ್ಗಳನ್ನು ಮಾತ್ರ ತುಂಬುತ್ತವೆ.
- **ಕಸ್ಟಮ್ ಪ್ಯಾಟರ್ನ್ಗಳು** — ಗರಿಷ್ಠ 20 regex ಅಥವಾ ವೈಲ್ಡ್ಕಾರ್ಡ್ ಪ್ಯಾಟರ್ನ್ಗಳು
  (`*` = ಗರಿಷ್ಠ 64 ವೈಟ್ಸ್ಪೇಸ್ ಅಲ್ಲದ ಅಕ್ಷರಗಳು, `?` = ಒಂದು). ಹೊಂದಾಣಿಕೆಗಳು
  `[CUSTOM_REDACTED]` ಆಗುತ್ತವೆ. ಪ್ರತಿಯೊಂದು ಪ್ಯಾಟರ್ನ್
  `compilePiiCustomPattern()` (`src/shared/utils/piiCustomPatterns.ts`) ಮೂಲಕ
  ಹಾದುಹೋಗುತ್ತದೆ: ಗರಿಷ್ಠ 500 ಅಕ್ಷರಗಳು, ಫ್ಲ್ಯಾಗ್ಗಳು `g i m s u` ಗೆ ಸೀಮಿತ,
  ಕಂಪೈಲ್ ಆಗಬೇಕು, `safe-regex` (ವಿನಾಶಕಾರಿ ಬ್ಯಾಕ್ಟ್ರ್ಯಾಕಿಂಗ್) ಅನ್ನು ಪಾಸ್ ಮಾಡಬೇಕು,
  ಮತ್ತು ಖಾಲಿ ಸ್ಟ್ರಿಂಗ್ ಅಥವಾ ಮರೆಮಾಚುವಿಕೆ ಪ್ಲೇಸ್ಹೋಲ್ಡರ್ಗೆ ಹೊಂದಾಣಿಕೆಯಾಗಬಾರದು.
  ವಿಫಲವಾದ ಪ್ಯಾಟರ್ನ್ ಅನ್ನು ಉಳಿಸುವಾಗ ಮತ್ತು ಪರೀಕ್ಷಿಸುವಾಗ ನಿರಾಕರಿಸಲಾಗುತ್ತದೆ; ವಿಫಲವಾದ
  ಸಂಗ್ರಹಿತ ಸಾಲನ್ನು ಕಂಪೈಲ್ ಮಾಡುವ ಬದಲು ರನ್ಟೈಮ್ನಲ್ಲಿ ಬಿಟ್ಟುಬಿಡಲಾಗುತ್ತದೆ. ಮರೆಮಾಚುವಿಕೆ
  ಆನ್ ಆಗಿರುವಾಗ ಮಾತ್ರ ಕಸ್ಟಮ್ ಪ್ಯಾಟರ್ನ್ಗಳು ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತವೆ.
- **ಪತ್ತೆ ಎಣಿಕೆಗಳು** — ಪ್ರತಿ-ಪ್ರಕಾರದ ಎಣಿಕೆಗಳು (ಹೊಂದಾಣಿಕೆಯಾದ ಮೌಲ್ಯಗಳು ಎಂದಿಗೂ ಅಲ್ಲ),
  ಮೆಮೊರಿಯಲ್ಲಿ ಇರಿಸಲ್ಪಡುತ್ತವೆ ಮತ್ತು ಮರುಪ್ರಾರಂಭಿಸಿದಾಗ ಮರುಹೊಂದಿಸಲಾಗುತ್ತದೆ
  (`src/lib/pii/piiDetectionStats.ts`). ಮರೆಮಾಚುವಿಕೆ ಆನ್ ಆಗಿರುವಾಗ ಮಾತ್ರ ಅವು
  ಹೆಚ್ಚಾಗುತ್ತವೆ.

ಸೆಟ್ಟಿಂಗ್ಗಳು `key_value` ಕೋಷ್ಟಕದಲ್ಲಿ (`pii_settings` ನೇಮ್ಸ್ಪೇಸ್,
`src/lib/db/piiSettings.ts`) ಇರುತ್ತವೆ ಮತ್ತು 1 s ಕ್ಯಾಶ್ ಮೂಲಕ ಓದಲಾಗುತ್ತವೆ. API:

| ವಿಧಾನ  | ಪಥ                       | ಉದ್ದೇಶ                                                                          |
| ------ | ------------------------ | ------------------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | ಫ್ಲ್ಯಾಗ್ ಸ್ಥಿತಿ, `enabledTypes`, `customPatterns`, ಪತ್ತೆ ಎಣಿಕೆಗಳು               |
| `PUT`  | `/api/settings/pii`      | `enabledTypes` (`null` = ಎಲ್ಲವೂ) ಮತ್ತು/ಅಥವಾ `customPatterns` ಅನ್ನು ಬದಲಿಸುವುದು   |
| `POST` | `/api/settings/pii/test` | ಗರಿಷ್ಠ 8 KB ಮಾದರಿಯ ವಿರುದ್ಧ ಒಂದು ಪ್ಯಾಟರ್ನ್ನ ಡ್ರೈ-ರನ್; ಏನನ್ನೂ ಸಂಗ್ರಹಿಸಲಾಗುವುದಿಲ್ಲ |

ಮೂರಕ್ಕೂ ನಿರ್ವಹಣಾ ದೃಢೀಕರಣ ಅಗತ್ಯವಿದ್ದು, Zod ಮೂಲಕ ಬಾಡಿಯನ್ನು ಮೌಲ್ಯೀಕರಿಸುತ್ತವೆ
(`src/shared/validation/schemas/piiSettings.ts`).

### ಪ್ರಾಂಪ್ಟ್ ಇಂಜೆಕ್ಷನ್ (`promptInjection.ts`)

ಬಳಕೆದಾರರು ಒದಗಿಸಿದ ವಿಷಯದಲ್ಲಿನ ಪ್ರತಿಕೂಲ ರಚನೆಗಳನ್ನು ಪತ್ತೆಮಾಡಿ, ಸಂರಚಿಸಲಾದ
ನೀತಿಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತದೆ. ವರ್ತನೆಯನ್ನು ಪರಿಸರ ವೇರಿಯೇಬಲ್ಗಳು ಮತ್ತು ಕನ್ಸ್ಟ್ರಕ್ಟರ್
ಆಯ್ಕೆಗಳು ನಿಯಂತ್ರಿಸುತ್ತವೆ:

| ಸೆಟ್ಟಿಂಗ್         | ಪರಿಸರ ಚರ                                                                                                        | ಡೀಫಾಲ್ಟ್ | ಪರಿಣಾಮ                                                                                                                                                                                                                               |
| ----------------- | --------------------------------------------------------------------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ಸಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆ | `INPUT_SANITIZER_ENABLED`                                                                                       | `true`   | `false` ಆಗಿರುವಾಗ, ಗಾರ್ಡ್ರೇಲ್ ಶಾರ್ಟ್-ಸರ್ಕ್ಯೂಟ್ ಆಗುತ್ತದೆ.                                                                                                                                                                              |
| ಮೋಡ್              | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                                 | `warn`   | ಇಂಜೆಕ್ಷನ್ ನೀತಿ: `block`, `warn`, ಅಥವಾ `log`. (ಹಿಂದಿನ ಆವೃತ್ತಿಗಳ ಹೊಂದಾಣಿಕೆಗಾಗಿ `redact` ಅನ್ನು ಸ್ವೀಕರಿಸಲಾಗುತ್ತದೆ, ಆದರೆ ಅದು ಇಂಜೆಕ್ಷನ್ ಪಠ್ಯವನ್ನು ತೆಗೆದುಹಾಕುವುದಿಲ್ಲ; ವಿನಂತಿಯ PII ಮರುಬರವಣಿಗೆಯನ್ನು `PII_REDACTION_ENABLED` ನಿಯಂತ್ರಿಸುತ್ತದೆ.) |
| ನಿರ್ಬಂಧಿಸುವ ಮಿತಿ  | `blockThreshold` ಆಯ್ಕೆ / `INPUT_SANITIZER_BLOCK_THRESHOLD` (`INJECTION_GUARD_BLOCK_THRESHOLD` ಎಂಬ ಪರ್ಯಾಯ ಹೆಸರು) | `high`   | ನಿರ್ಬಂಧಿಸಲು ಅಗತ್ಯವಿರುವ ಕನಿಷ್ಠ ತೀವ್ರತೆ. ಡೀಫಾಲ್ಟ್ ಆಗಿ ಮಧ್ಯಮ ತೀವ್ರತೆಯು ವೀಕ್ಷಣೆಗೆ ಮಾತ್ರ ಸೀಮಿತವಾಗಿದೆ.                                                                                                                                     |

**ಮೋಡ್ ಆದ್ಯತೆಯ ಕ್ರಮ** (`getMode`): ಕಾಲರ್ನ `options.mode` →
`INJECTION_GUARD_MODE` **DB ವೈಶಿಷ್ಟ್ಯ-ಫ್ಲ್ಯಾಗ್ ಅತಿಕ್ರಮಣ** (ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಸೆಟ್ಟಿಂಗ್ಗಳು →
ವೈಶಿಷ್ಟ್ಯ ಫ್ಲ್ಯಾಗ್ಗಳು) → `INJECTION_GUARD_MODE` ಪರಿಸರ ಚರ → `INPUT_SANITIZER_MODE` ಪರಿಸರ ಚರ →
`warn`. ಆದ್ದರಿಂದ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಅತಿಕ್ರಮಣವು ಪರಿಸರ ಚರಗಳಿಗಿಂತ ಆದ್ಯತೆ ಪಡೆಯುತ್ತದೆ, ಹೀಗಾಗಿ ವೈಶಿಷ್ಟ್ಯ
ಫ್ಲ್ಯಾಗ್ಗಳ UI ಚಾಲನೆಯಲ್ಲಿರುವ ಗಾರ್ಡ್ ಅನ್ನು ನೇರವಾಗಿ ನಿಯಂತ್ರಿಸುತ್ತದೆ (ಮರುಪ್ರಾರಂಭ ಅಗತ್ಯವಿಲ್ಲ). DB ಓದುವಿಕೆ ವಿಫಲ-ಸುರಕ್ಷಿತವಾಗಿದೆ:
ಅದು ದೋಷಗೊಂಡರೆ, ಗಾರ್ಡ್ ಪರಿಸರ ಚರ-ಆಧಾರಿತ ವರ್ತನೆಗೆ ಹಿಂತಿರುಗುತ್ತದೆ ಮತ್ತು ಯಾವುದೇ
ಅತಿಕ್ರಮಣವನ್ನು ಹೊಂದಿಸದಿದ್ದಾಗ ಅದರ ವರ್ತನೆಯು ಪರಿಸರ ಚರ-ಮಾತ್ರದ ನಿರ್ಧಾರಕ್ಕೆ ಸಮಾನವಾಗಿರುತ್ತದೆ.

ಪತ್ತೆ ಮೂಲಗಳು:

1. `@/shared/utils/inputSanitizer` ನಲ್ಲಿನ `sanitizeRequest()` (ಪೈಪ್ಲೈನ್ನ
   ಇತರ ಭಾಗಗಳಲ್ಲಿಯೂ ಬಳಸಲಾಗುವ ಹಂಚಿಕೆಯ ಪತ್ತೆಕಾರಕಗಳ ಸಮೂಹ).
2. ಅಂತರ್ನಿರ್ಮಿತ `DEFAULT_GUARD_PATTERNS` (ಪ್ರಸ್ತುತ `system_override_inline` ಮತ್ತು
   `markdown_system_block`, ಎರಡೂ `high` ತೀವ್ರತೆಯವು).
3. ಕನ್ಸ್ಟ್ರಕ್ಟರ್ ಆಯ್ಕೆಗಳ ಮೂಲಕ ರವಾನಿಸಲಾದ ಐಚ್ಛಿಕ `customPatterns` (ಸ್ಟ್ರಿಂಗ್ಗಳು, ರೆಜೆಕ್ಸ್,
   ಅಥವಾ `{ name, pattern, severity }` ದಾಖಲೆಗಳು).

`mode === "block"` ಆಗಿರುವಾಗ **ಮತ್ತು** ಕನಿಷ್ಠ ಒಂದು ಪತ್ತೆಯು ತೀವ್ರತೆಯ
ಮಿತಿಯನ್ನು ಪೂರೈಸಿದಾಗ, `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ. `warn`/`log` ಮೋಡ್ಗಳಲ್ಲಿ ಗಾರ್ಡ್ರೇಲ್ ಲಾಗ್ ಮಾಡುತ್ತದೆ, ಆದರೆ
ಕರೆಗೆ ಅನುಮತಿಸುತ್ತದೆ. ರಿಜಿಸ್ಟ್ರಿಯ ಮೂಲಕ ಹೋಗದೆ ಪ್ರಾಂಪ್ಟ್ಗಳನ್ನು ಮೌಲ್ಯಮಾಪನ ಮಾಡಬೇಕಾದ
ಕಾಲರ್ಗಳಿಗಾಗಿ ಹಂಚಿಕೆಯ ಸಹಾಯಕ `evaluatePromptInjection()` ಅನ್ನೂ ಎಕ್ಸ್ಪೋರ್ಟ್ ಮಾಡಲಾಗಿದೆ.

**ಸ್ಕ್ಯಾನ್ ಮಿತಿ (v3.8.20):** ಪತ್ತೆಕಾರಕವು ಜೋಡಿಸಲಾದ ಪ್ರಾಂಪ್ಟ್ ಪಠ್ಯದ **ಮೊದಲ 16 KB** ಅನ್ನು
ಮಾತ್ರ ಪರಿಶೀಲಿಸುತ್ತದೆ — `src/shared/utils/inputSanitizer.ts` ನಲ್ಲಿ
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ಬೈಟ್ಗಳು). ಪ್ಯಾಟರ್ನ್ ಲೂಪ್ ಅನ್ನು ಚಲಾಯಿಸುವ ಮೊದಲು
`detectInjection()` ಮತ್ತು `evaluatePromptInjection()` ಎರಡೂ `slice(0, MAX_INJECTION_SCAN_BYTES)` ಅನ್ನು ಬಳಸುತ್ತವೆ.
ಇಂಜೆಕ್ಷನ್ ನಿರ್ದೇಶನಗಳು ಇನ್ಪುಟ್ನ ಮೇಲ್ಭಾಗದ ಸಮೀಪದಲ್ಲಿರುತ್ತವೆ, ಆದ್ದರಿಂದ ಇದು ಪತ್ತೆ ಸಾಮರ್ಥ್ಯವನ್ನು ದುರ್ಬಲಗೊಳಿಸದೆ
ನೂರಾರು-KB ಪೇಲೋಡ್ಗಳಲ್ಲಿ ರೆಜೆಕ್ಸ್ CPU/GC ಬಳಕೆಗೆ ಮಿತಿ ವಿಧಿಸುತ್ತದೆ (ನೋಡಿ
#3932, #4041).

### ಕ್ರೆಡೆನ್ಶಿಯಲ್ ಮಾಸ್ಕರ್ (`credentialMasker.ts`)

ಡೀಫಾಲ್ಟ್ ಸರಣಿಯಲ್ಲಿ ಕೊನೆಯದಾಗಿ (ಆದ್ಯತೆ `95`), **ಎರಡೂ** ಹಂತಗಳಲ್ಲಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ. ಔಟ್ಬೌಂಡ್ ಪೇಲೋಡ್ನಿಂದ (ಸಂದೇಶದ
ವಿಷಯ, ಟೂಲ್-ಕಾಲ್ ಆರ್ಗ್ಯುಮೆಂಟ್ಗಳು, ಟೂಲ್ ಫಲಿತಾಂಶಗಳು) **ಹಾಗೂ** ಪೂರೈಕೆದಾರರ ಪ್ರತಿಕ್ರಿಯೆಯಿಂದ
ಸುಪರಿಚಿತ API-ಕೀ / ರಹಸ್ಯ-ಟೋಕನ್ ಪ್ಯಾಟರ್ನ್ಗಳನ್ನು ಮರೆಮಾಡುತ್ತದೆ. ಇದರಿಂದ ಪ್ರಾಂಪ್ಟ್ನಲ್ಲಿ ಅಂಟಿಸಲಾದ ಕ್ರೆಡೆನ್ಶಿಯಲ್
(ಅಥವಾ ಟೂಲ್ ಫಲಿತಾಂಶದಿಂದ ಪ್ರತಿಧ್ವನಿಸಲಾದದ್ದು) ಅಪ್ಸ್ಟ್ರೀಮ್ ಪೂರೈಕೆದಾರರಿಗೆ ಅಥವಾ ಕ್ಲೈಂಟ್ಗೆ ಮರಳಿ ಸೋರಿಕೆಯಾಗುವುದಿಲ್ಲ.

- PII ಮರೆಮಾಡುವಿಕೆಯಂತೆಯೇ **ಆಯ್ಕೆ ಮಾಡಿಕೊಂಡಾಗ ಮಾತ್ರ ಸಕ್ರಿಯವಾಗುತ್ತದೆ** (ಕಠಿಣ ನಿಯಮ #20 ಗೆ ಸಂಬಂಧಿತ):
  `settings.credentialRedactionEnabled === true` **ಅಥವಾ**
  `CREDENTIAL_REDACTION_ENABLED=true` ಆಗಿರದ ಹೊರತು ನಿಷ್ಕ್ರಿಯವಾಗಿರುತ್ತದೆ. ಇದು ಆಫ್ ಆಗಿರುವಾಗ ಗಾರ್ಡ್ರೇಲ್ ಯಾವುದೇ ಕಾರ್ಯ ಮಾಡುವುದಿಲ್ಲ —
  ಅದು ಎಂದಿಗೂ ನಿರ್ಬಂಧಿಸುವುದಿಲ್ಲ ಮತ್ತು ಎಂದಿಗೂ ಮರುಬರೆಯುವುದಿಲ್ಲ.
- `redactCredentials()` ಸಂಪೂರ್ಣ ಪೇಲೋಡ್/ಪ್ರತಿಕ್ರಿಯೆ ಟ್ರೀಯನ್ನು ಪರಿಶೀಲಿಸುತ್ತದೆ (`walkValue()`,
  ಪ್ರೋಟೋಟೈಪ್-ಪಲ್ಯೂಷನ್ನಿಂದ ಸುರಕ್ಷಿತ, `WeakSet` ಮೂಲಕ ಸೈಕಲ್-ಸುರಕ್ಷಿತ) ಮತ್ತು ಹೊಂದಾಣಿಕೆಗಳನ್ನು
  `[REDACTED:<type>]` ಪ್ಲೇಸ್ಹೋಲ್ಡರ್ನಿಂದ ಬದಲಾಯಿಸುತ್ತದೆ; ನಿಜವಾಗಿಯೂ ಬದಲಾದ ಶಾಖೆಗಳನ್ನು ಮಾತ್ರ
  ಕ್ಲೋನ್ ಮಾಡುತ್ತದೆ.
- `CREDENTIAL_PATTERNS` LLM ಪೂರೈಕೆದಾರರ ಕೀಗಳು (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ಟೋಕನ್ಗಳು (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), ಪಾವತಿ ಕೀಗಳು (Stripe, Square), ಕ್ಲೌಡ್
  ಕೀಗಳು (AWS ಪ್ರವೇಶ ಕೀ, Twilio, SendGrid, Mailgun), ಖಾಸಗಿ ಕೀಗಳು / JWTಗಳು,
  ಕ್ರೆಡೆನ್ಶಿಯಲ್ಗಳನ್ನು ಹೊಂದಿರುವ ಸಂಪರ್ಕ ಸ್ಟ್ರಿಂಗ್ಗಳು (`mongodb://user:pass@...`, ಇತ್ಯಾದಿ), ಮತ್ತು
  ಸಾಮಾನ್ಯ `Authorization`/`x-api-key`/`api-key`/`apikey` ಹೆಡರ್-ಮೌಲ್ಯ
  ಪ್ಯಾಟರ್ನ್ ಅನ್ನು ಒಳಗೊಂಡಿದೆ. ಹೆಡರ್ ಸ್ವರೂಪದ ಕೀಗಳನ್ನು (`authorization`, `x-api-key`, `api-key`,
  `apikey`) ಸಾಮಾನ್ಯ ಪಠ್ಯ ರೆಜೆಕ್ಸ್ ಮೂಲಕವಲ್ಲದೆ ರಚನಾತ್ಮಕವಾಗಿ ಮರೆಮಾಡಲಾಗುತ್ತದೆ (ಮೌಲ್ಯ ಮಾತ್ರ;
  `Bearer `/`Basic ` ನಂತಹ ಸ್ಕೀಮ್ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಉಳಿಸಲಾಗುತ್ತದೆ).
- ಗಾರ್ಡ್ರೇಲ್ ಎಂದಿಗೂ ನಿರ್ಬಂಧಿಸುವುದಿಲ್ಲ; ಅದು ಮರುಬರೆಯುತ್ತದೆ (`modifiedPayload` /
  `modifiedResponse`) ಮತ್ತು ಟಿಪ್ಪಣಿ ಸೇರಿಸುತ್ತದೆ (`meta.credentialsRedacted`, `meta.count`).

ರಿಗ್ರೆಷನ್ ಗಾರ್ಡ್: `tests/unit/credential-masker-guardrail.test.ts`.

## ಮೂಲ ಒಪ್ಪಂದ (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ಸರಪಳಿಯನ್ನು ತಕ್ಷಣವೇ ಸ್ಥಗಿತಗೊಳಿಸುತ್ತದೆ
  message?: string; // ನಿರ್ಬಂಧಿಸುವಾಗ ಪ್ರದರ್ಶಿಸಲಾಗುತ್ತದೆ
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // ವಿನಂತಿಯನ್ನು ಮರುಬರೆಯಲು preCall ಮೂಲಕ ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತದೆ
  modifiedResponse?: TValue; // ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಮರುಬರೆಯಲು postCall ಮೂಲಕ ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತದೆ
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

`void`, `{}`, ಅಥವಾ `{ block: false }` ಇವುಗಳಲ್ಲಿ ಯಾವುದನ್ನಾದರೂ ಹಿಂತಿರುಗಿಸುವ ಮೂಲಕ guardrail "ಯಾವುದೇ ಬದಲಾವಣೆ ಇಲ್ಲ" ಎಂದು ಸೂಚಿಸುತ್ತದೆ. `modifiedPayload`/`modifiedResponse` ಅನ್ನು ಹಿಂತಿರುಗಿಸುವುದರಿಂದ, ನಂತರದ guardrailಗಳಿಗಾಗಿ ಸರಪಳಿಯ ಮೂಲಕ ಹರಿಯುವ ಮೌಲ್ಯವನ್ನು ಅದು ಬದಲಿಸುತ್ತದೆ.
`signal?: AbortSignal` ಕಾಲರ್ನ ಜೀವನಚಕ್ರವನ್ನು guardrailಗಳಿಗೆ ಒಯ್ಯುತ್ತದೆ. ವಿನಂತಿಯ ರದ್ದತಿಯು ಉದ್ದೇಶಪೂರ್ವಕ fail-open ಅಪವಾದವಾಗಿದೆ: media bridgeಗಳು ಕೆಲಸವನ್ನು ನಿಲ್ಲಿಸಿ cleanup ಮಾಡುತ್ತವೆ ಮತ್ತು ಅದನ್ನು ಬೆಂಬಲಿಸುವುದಿಲ್ಲ ಎಂದು ತಿಳಿದಿರುವ ಗುರಿಗೆ raw media ಅನ್ನು ಮರುಸ್ಥಾಪಿಸುವುದಿಲ್ಲ.

## ರಿಜಿಸ್ಟ್ರಿ (`registry.ts`)

singleton `guardrailRegistry` ಈ ಕೆಳಗಿನವುಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ:

- `register(guardrail)` — guardrail ಅನ್ನು ಸೇರಿಸುತ್ತದೆ (ಅಥವಾ normalized name ಆಧಾರದಲ್ಲಿ ಬದಲಿಸುತ್ತದೆ) ಮತ್ತು ಏರಿಕೆ ಕ್ರಮದ `priority` ಪ್ರಕಾರ ಮರು-ವಿಂಗಡಿಸುತ್ತದೆ.
- `clear()` / `list()` — ಆಡಳಿತಾತ್ಮಕ ಸಹಾಯಕಗಳು.
- `runPreCallHooks(payload, context)` — ಸಕ್ರಿಯ guardrailಗಳ ಮೂಲಕ ಪುನರಾವರ್ತಿಸುತ್ತದೆ, `modifiedPayload` ಮೂಲಕ payload ಅನ್ನು ಮುಂದಕ್ಕೆ ಕೊಂಡೊಯ್ಯುತ್ತದೆ ಮತ್ತು ಮೊದಲ `block: true` ದೊರೆತಾಗ ನಿಲ್ಲುತ್ತದೆ.
- `runPostCallHooks(response, context)` — response ಭಾಗದಲ್ಲಿಯೂ ಇದೇ ಹರಿವನ್ನು ಅನುಸರಿಸುತ್ತದೆ.
- `resetGuardrailsForTests({ registerDefaults })` — ಸ್ಥಿತಿಯನ್ನು ತೆರವುಗೊಳಿಸುತ್ತದೆ ಮತ್ತು ಸ್ವಚ್ಛ test isolationಗಾಗಿ ಐಚ್ಛಿಕವಾಗಿ defaults ಅನ್ನು ಮರು-ನೋಂದಾಯಿಸುತ್ತದೆ.

ಎರಡೂ runnerಗಳು `{ blocked, payload|response, results, guardrail?, message? }` ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತವೆ, ಇಲ್ಲಿ `results` ಎಂಬುದು ಪ್ರತಿಯೊಂದು guardrailಗೆ ಸಂಬಂಧಿಸಿದ `blocked`, `skipped`, `modified`, `error`, ಮತ್ತು `meta` ಕ್ಷೇತ್ರಗಳನ್ನು ಒಳಗೊಂಡಿರುವ `GuardrailExecutionResult` recordಗಳ array ಆಗಿದ್ದು, tracingಗೆ ಉಪಯುಕ್ತವಾಗಿದೆ.

### ಪ್ರತಿ ವಿನಂತಿಗೆ Guardrailಗಳನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವುದು

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` ಪ್ರಸ್ತುತ ವಿನಂತಿಗಾಗಿ ಬಿಟ್ಟುಬಿಡಬೇಕಾದ guardrail ಹೆಸರುಗಳ duplicate ತೆಗೆದುಹಾಕಿದ ಪಟ್ಟಿಯನ್ನು ಒಟ್ಟುಗೂಡಿಸುತ್ತದೆ. ಮೂಲಗಳು (ಎಲ್ಲವೂ ಐಚ್ಛಿಕ, ಎಲ್ಲವನ್ನೂ ವಿಲೀನಗೊಳಿಸಲಾಗುತ್ತದೆ):

- `apiKeyInfo.disabledGuardrails`
- ವಿನಂತಿಯ bodyಯಲ್ಲಿನ `disabledGuardrails` (top-level)
- ವಿನಂತಿಯ bodyಯಲ್ಲಿನ `metadata.disabledGuardrails`
- Header `x-omniroute-disabled-guardrails` (ಅಥವಾ ಹಳೆಯ
  `x-disabled-guardrails`)

ಮೌಲ್ಯಗಳು stringಗಳ array ಆಗಿರಬಹುದು ಅಥವಾ comma-separated string ಆಗಿರಬಹುದು; ಹೆಸರುಗಳನ್ನು lowercase kebab-caseಗೆ normalize ಮಾಡಲಾಗುತ್ತದೆ (`pii_masker` → `pii-masker`). ಫಲಿತಾಂಶವನ್ನು `context.disabledGuardrails` ಮೂಲಕ registryಗೆ ರವಾನಿಸಲಾಗುತ್ತದೆ, ಅದು ಹೊಂದಿಕೆಯಾಗುವ guardrailಗಳನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ (`results` ನಲ್ಲಿ `skipped: true`).

## ಕಾರ್ಯಗತಗೊಳಿಸುವ ಕ್ರಮ

`src/sse/handlers/chat.ts` ಮತ್ತು
`open-sse/handlers/chatCore.ts` ಮೂಲಕ ಹರಿಯುವ ಪ್ರತಿ ವಿನಂತಿಗಾಗಿ:

1. `resolveDisabledGuardrails(...)` API ಕೀ, ಬಾಡಿ ಮತ್ತು ಹೆಡರ್ಗಳಿಂದ ಬಿಟ್ಟುಬಿಡುವ ಪಟ್ಟಿಯನ್ನು ರಚಿಸುತ್ತದೆ.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ಗಾರ್ಡ್ರೇಲ್ಗಳನ್ನು ಆದ್ಯತೆಯ ಆರೋಹಣ ಕ್ರಮದಲ್ಲಿ ಚಲಾಯಿಸುತ್ತದೆ:
   - ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾದ ಗಾರ್ಡ್ರೇಲ್ಗಳನ್ನು `skipped` ಎಂದು ದಾಖಲಿಸಲಾಗುತ್ತದೆ.
   - ಪ್ರತಿ ಗಾರ್ಡ್ರೇಲ್ನ `preCall`, `modifiedPayload` ಮೂಲಕ ಪೇಲೋಡ್ ಅನ್ನು ಮರುಬರೆಯಬಹುದು.
   - ಮೊದಲ `block: true` ಸರಪಳಿಯನ್ನು ಅಲ್ಲಿಯೇ ನಿಲ್ಲಿಸುತ್ತದೆ ಮತ್ತು ಹ್ಯಾಂಡ್ಲರ್ ಗಾರ್ಡ್ರೇಲ್ ನಿರಾಕರಣೆಯ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ.
3. (ಸಂಭಾವ್ಯವಾಗಿ ಮರುಬರೆಯಲಾದ) ಪೇಲೋಡ್ ಕಾಂಬೊ ರೂಟಿಂಗ್ ಮತ್ತು ಅಪ್ಸ್ಟ್ರೀಮ್ ಡಿಸ್ಪ್ಯಾಚ್ಗೆ ಹರಿಯುತ್ತದೆ.
4. ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಜೋಡಿಸಿದ ನಂತರ, `guardrailRegistry.runPostCallHooks(...)` ಪ್ರತಿಕ್ರಿಯೆಯ ಮೇಲೆ ಅದೇ ಸರಪಳಿಯನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. ಇಲ್ಲಿ `block: true` ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಕೈಬಿಡುತ್ತದೆ.

ದೋಷ ಎಸೆಯುವ ಗಾರ್ಡ್ರೇಲ್ಗಳನ್ನು `error: <message>` ಜೊತೆಗೆ ದಾಖಲಿಸಲಾಗುತ್ತದೆ ಮತ್ತು
`logger.warn` ಮೂಲಕ ಲಾಗ್ ಮಾಡಲಾಗುತ್ತದೆ, ಆದರೆ ಸರಪಳಿ ಮುಂದುವರಿಯುತ್ತದೆ — ವಿನ್ಯಾಸದ ಪ್ರಕಾರ ದೋಷ ಸಂಭವಿಸಿದಾಗಲೂ ಅನುಮತಿಸಲಾಗುತ್ತದೆ.

| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`          | `MODE=block` ನಿರಾಕರಿಸುವ ಕನಿಷ್ಠ ತೀವ್ರತೆ: `high` (ಡೀಫಾಲ್ಟ್), `medium`, ಅಥವಾ `low`.                        |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`          | `INPUT_SANITIZER_BLOCK_THRESHOLD` ಗಾಗಿನ ಹಳೆಯ ಅಲಿಯಾಸ್.                                                   |
| `PII_REDACTION_ENABLED`               | `pii-masker`                | `true` ಆಗಿದ್ದಾಗ, ವಿನಂತಿಯ PII ಅನ್ನು ಮರೆಮಾಡಲಾಗುತ್ತದೆ (ಇಂಜೆಕ್ಷನ್ ಮೋಡ್ನಿಂದ ಸ್ವತಂತ್ರವಾಗಿ).                   |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ಡೌನ್ಸ್ಟ್ರೀಮ್) | ಪ್ರತಿಕ್ರಿಯೆ-ಬದಿಯ ಮಾಸ್ಕರ್ ವರ್ತನೆಯನ್ನು ನಿಯಂತ್ರಿಸುತ್ತದೆ.                                                   |

Modality Bridge ಗಾರ್ಡ್ರೇಲ್ಗಳು ಪರಿಸರ ಚರಗಳ ಬದಲಾಗಿ DB-ಬೆಂಬಲಿತ ಸೆಟ್ಟಿಂಗ್ಗಳ
ಸ್ಟೋರ್ನಿಂದ (`getSettings()`) ರನ್ಟೈಮ್ ಸಂರಚನೆಯನ್ನು ಓದುತ್ತವೆ. Vision ನ ಪ್ರಾಥಮಿಕ ಕೀಗಳು
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, ಮತ್ತು
`modalityBridgeCacheMaxEntries`. ಹಳೆಯ
`visionBridge*` ಕೀಗಳನ್ನು ದಾಖಲಿಸಲಾದ ಒಂದು-ಚಕ್ರದ ಓದು ಫಾಲ್ಬ್ಯಾಕ್ ಆಗಿ ಮಾತ್ರ
ಸ್ವೀಕರಿಸಲಾಗುತ್ತದೆ; ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಬರಹಗಳು ಪ್ರಾಥಮಿಕ ಕೀಗಳನ್ನು ಬಳಸುತ್ತವೆ. ಡೀಫಾಲ್ಟ್ಗಳು ಮತ್ತು ಫಾಲ್ಬ್ಯಾಕ್
ರಿಸಾಲ್ವರ್ `src/shared/constants/modalityBridgeDefaults.ts` ನಲ್ಲಿ ಇವೆ; ಹಳೆಯ
ಸ್ಥಿರಾಂಕಗಳನ್ನು `src/shared/constants/visionBridgeDefaults.ts` ನಲ್ಲಿ ಉಳಿಸಿಕೊಳ್ಳಲಾಗಿದೆ.

Audio, `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout`, ಮತ್ತು `modalityBridgeAudioMaxClips` ಜೊತೆಗೆ ಹಂಚಿಕೊಂಡ
`modalityBridgeCache*` ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು ಬಳಸುತ್ತದೆ. ಈ ಕೀಗಳನ್ನು Modality Bridge ಸ್ಕೀಮಾ ಜೊತೆಗೆ
ಪರಿಚಯಿಸಿದ್ದರಿಂದ Audioಗೆ ಹಳೆಯ ಕೀಗಳ ಫಾಲ್ಬ್ಯಾಕ್ ಇಲ್ಲ.

Video, `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos`, ಮತ್ತು
`modalityBridgeVideoTimeout` ಜೊತೆಗೆ ಹಂಚಿಕೊಂಡ `modalityBridgeCache*` ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು ಬಳಸುತ್ತದೆ.
FFmpeg/ffprobe ಐಚ್ಛಿಕ ಕಾರ್ಯಾಚರಣಾ ಅವಲಂಬನೆಗಳಾಗಿರುವುದರಿಂದ ಮತ್ತು ಫ್ರೇಮ್ ಕ್ಯಾಪ್ಷನಿಂಗ್ ವಿಳಂಬ ಹಾಗೂ ಮಾದರಿ ವೆಚ್ಚವನ್ನು ಹೆಚ್ಚಿಸುವುದರಿಂದ
ಇದು ಡೀಫಾಲ್ಟ್ ಆಗಿ ನಿಷ್ಕ್ರಿಯಗೊಂಡಿರುತ್ತದೆ.

## ಕಸ್ಟಮ್ ಗಾರ್ಡ್ರೈಲ್ಗಳು

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ಹಂತಗಳು:

1. `BaseGuardrail` ಅನ್ನು ವಿಸ್ತರಿಸುವ `src/lib/guardrails/myGuardrail.ts` ಅನ್ನು ರಚಿಸಿ.
2. `preCall` ಮತ್ತು/ಅಥವಾ `postCall` ಅನ್ನು ಅನುಷ್ಠಾನಗೊಳಿಸಿ.
3. ಇಂಪೋರ್ಟ್ ಸಮಯದಲ್ಲಿಯೇ ನೋಂದಾಯಿಸಿ (`registerDefaultGuardrails` ನಿಂದ ಪುಶ್ ಮಾಡಿ) ಅಥವಾ
   ರನ್ಟೈಮ್ನಲ್ಲಿ `guardrailRegistry.register(...)` ಅನ್ನು ಕರೆ ಮಾಡಿ — ಅದೇ ಸಾಮಾನ್ಯೀಕರಿಸಿದ
   ಹೆಸರನ್ನು ಹೊಂದಿರುವ ಯಾವುದೇ ಹಿಂದಿನ ಗಾರ್ಡ್ರೈಲ್ ಅನ್ನು ರಿಜಿಸ್ಟ್ರಿ ಬದಲಿಸುತ್ತದೆ.
4. `tests/unit/` ಅಡಿಯಲ್ಲಿ ಪರೀಕ್ಷೆಗಳನ್ನು ಸೇರಿಸಿ (ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಉದಾಹರಣೆಗಳು:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## ಪರೀಕ್ಷೆ

ತಿಳಿದಿರುವ ಸ್ಥಿತಿಯಿಂದ ಪ್ರಾರಂಭಿಸಲು ಪರೀಕ್ಷೆಗಳ ನಡುವೆ `resetGuardrailsForTests()` ಅನ್ನು ಬಳಸಿ.
ಖಾಲಿ ರಿಜಿಸ್ಟ್ರಿಯೊಂದಿಗೆ ಪ್ರಾರಂಭಿಸಲು `{ registerDefaults: false }` ಅನ್ನು ಪಾಸ್ ಮಾಡಿ ಮತ್ತು
ಪರೀಕ್ಷೆಯಲ್ಲಿರುವ ಗಾರ್ಡ್ರೈಲ್ಗಳನ್ನು ಮಾತ್ರ ನೋಂದಾಯಿಸಿ. Vision Bridge ಡಿಪೆಂಡೆನ್ಸಿ
ಇಂಜೆಕ್ಷನ್ ಅನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge,
ಸೆಟ್ಟಿಂಗ್ಗಳು, ಸಾಮರ್ಥ್ಯಗಳು, STT ಮಾದರಿ ಆಯ್ಕೆ, ಕ್ರೆಡೆನ್ಶಿಯಲ್ ಪರಿಶೀಲನೆಗಳು ಮತ್ತು
ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಷನ್ಗಾಗಿ ಸಮಾನವಾದ ಸೀಮ್ಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ. ಆದ್ದರಿಂದ ಪರೀಕ್ಷೆಗಳು DB
ಅಥವಾ ನೆಟ್ವರ್ಕ್ ಪ್ರವೇಶವಿಲ್ಲದೆಯೇ ಎರಡೂ ಫ್ಲೋಗಳನ್ನು ಪರೀಕ್ಷಿಸಬಹುದು.

## ಇಂಜೆಕ್ಷನ್-ಗಾರ್ಡ್ ರೂಟ್ ವ್ಯಾಪ್ತಿ ಮತ್ತು ರೆಡ್-ಟೀಮ್ (ಹಂತ 8 · ಬ್ಲಾಕ್ D)

ಇಂಜೆಕ್ಷನ್-ಗಾರ್ಡ್ (`createInjectionGuard` / `withInjectionGuard`) ಬಳಕೆದಾರರ
ಪ್ರಾಂಪ್ಟ್ಗಳನ್ನು ಸ್ವೀಕರಿಸುವ ಎಲ್ಲಾ ರೂಟ್ಗಳನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ. ಇದು `INJECTION_GUARD_MODE`
ಅನ್ನು ಗೌರವಿಸುತ್ತದೆ (ಡೀಫಾಲ್ಟ್ `warn` = ಲಾಗ್ ಮಾತ್ರ; `block` = HTTP 400 `SECURITY_001` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ).

| ಪ್ರಕಾರ                     | ರೂಟ್ಗಳು                                                                                                                                              | ಡೀಫಾಲ್ಟ್ ಮೋಡ್ |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| ಪಠ್ಯ (ಅಸ್ತಿತ್ವದಲ್ಲಿರುವುದು) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn          |
| ಜನರೇಟಿವ್                   | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn          |
| ಡೇಟಾ                       | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn          |

ಪಠ್ಯ ಹೊರತೆಗೆಯುವಿಕೆ (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ಅನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ.

**ರೆಡ್-ಟೀಮ್ (ಪ್ರತಿ ರಾತ್ರಿ, `nightly-llm-security.yml`):** `INJECTION_GUARD_MODE=block`
ನಲ್ಲಿ ಪ್ರತಿಯೊಂದು ರೂಟ್, `OWASP-LLM` ಕಾರ್ಪಸ್ ಅನ್ನು ನಿರ್ಬಂಧಿಸುತ್ತದೆ ಎಂಬುದನ್ನು promptfoo
ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ; garak ಪ್ರೋಬ್ಗಳನ್ನು ಚಲಾಯಿಸುತ್ತದೆ (ಸೀಕ್ರೆಟ್ ಇಲ್ಲದಿದ್ದರೆ ಬಿಟ್ಟುಬಿಡುತ್ತದೆ).
ಸ್ಥಿರತೆಗಾಗಿ `moderations` ಅನ್ನು ಸೇರಿಸಲಾಗಿದೆ — ಬ್ಲಾಕ್-ಮೋಡ್ನಲ್ಲಿರುವ ಆಪರೇಟರ್ಗಳು
`resolveDisabledGuardrails` ಮೂಲಕ ಅದಕ್ಕೆ ವಿನಾಯಿತಿ ನೀಡಬಹುದು.

ಪ್ರತಿ ರಾತ್ರಿಯ ವರ್ಕ್ಫ್ಲೋ (`.github/workflows/nightly-llm-security.yml`, cron + ಮ್ಯಾನುಯಲ್
ಡಿಸ್ಪ್ಯಾಚ್) ಎರಡು ಜಾಬ್ಗಳನ್ನು ಹೊಂದಿದೆ:

- **`promptfoo-guard` (ನಿರ್ಬಂಧಿಸುವುದು)** — `INJECTION_GUARD_MODE=block` ಜೊತೆಗೆ
  `promptfoo eval -c promptfooconfig.yaml` ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. ಪ್ರತಿಯೊಂದು ಪ್ರತಿಕೂಲ
  ಪ್ರಕರಣವು (ಉದಾ. "ಹಿಂದಿನ ಎಲ್ಲಾ ಸೂಚನೆಗಳನ್ನು ನಿರ್ಲಕ್ಷಿಸಿ…", DAN-ಶೈಲಿಯ ಜೈಲ್ಬ್ರೇಕ್ಗಳು)
  ಪ್ರತಿಕ್ರಿಯೆಯು `error.code === "SECURITY_001"` ಅನ್ನು ಹೊಂದಿದೆ ಎಂದು ದೃಢೀಕರಿಸುತ್ತದೆ,
  ಅಂದರೆ ಗಾರ್ಡ್ ನಿಜವಾಗಿಯೂ ವಿನಂತಿಯನ್ನು ತಿರಸ್ಕರಿಸಿದೆ.
- **`garak` (ಸಲಹಾತ್ಮಕ)** — ಸ್ಥಳೀಯ OmniRoute ಇನ್ಸ್ಟನ್ಸ್
  (`http://localhost:20128/v1`) ವಿರುದ್ಧ garak `--probes promptinject,dan,leakreplay`
  ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. ಇದು ಪ್ರೊವೈಡರ್ ಸೀಕ್ರೆಟ್ (`PROMPTFOO_PROVIDER_KEY`) ಮೇಲೆ
  ಅವಲಂಬಿತವಾಗಿದೆ; ಸೀಕ್ರೆಟ್ ಇಲ್ಲದಿದ್ದರೆ ಸರಾಗವಾಗಿ ಬಿಟ್ಟುಬಿಡುತ್ತದೆ ಮತ್ತು `|| true`
  ಪ್ರತ್ಯಯವನ್ನು ಹೊಂದಿರುತ್ತದೆ, ಆದ್ದರಿಂದ CI ವಿಫಲಗೊಳಿಸದೆಯೇ ವರದಿ ಮಾಡುತ್ತದೆ.

ಗಾರ್ಡ್ ಹೆಲ್ಪರ್ನ (`createInjectionGuard` / `withInjectionGuard`) ವ್ಯಾಪ್ತಿಯು ಪ್ರಾಂಪ್ಟ್
ಹೊಂದಿರುವ ಪ್ರತಿಯೊಂದು `/v1` ರೂಟ್ಗೆ ವಿಸ್ತರಿಸುತ್ತದೆ; ಪ್ರಾಂಪ್ಟ್ ಪಠ್ಯವನ್ನು
`src/shared/utils/inputSanitizer.ts` ನಲ್ಲಿರುವ `extractMessageContents()` ಮೂಲಕ
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ನಿಂದ
ಪಡೆಯಲಾಗುತ್ತದೆ.
