> **Источник истины:** `src/lib/guardrails/`
> **Последнее обновление:** 2026-08-29 — v3.8.51 (Происхождение стенограммы Video Bridge объявляется вызывающей стороной,
> еще не проверено сервером — уточнено согласно #11661)

Защитные механизмы (guardrails) обеспечивают безопасность, соблюдение политик и преобразования контента на границе между OmniRoute и вышестоящими провайдерами. Каждый защитный механизм может проверять (и опционально отклонять, преобразовывать или аннотировать) полезные данные запросов (`preCall`) и ответы вышестоящих систем (`postCall`).

Система является **открытой при сбое (fail-open)**: если защитный механизм выдает ошибку во время выполнения, реестр записывает ошибку и продолжает работу со следующим защитным механизмом, вместо того чтобы отклонять запрос. Блокировка — это явное решение (`block: true`), а не случайность.

## Встроенные защитные механизмы

При импорте реестр автоматически загружает шесть защитных механизмов в порядке приоритета
(см. `registry.ts` → `registerDefaultGuardrails()`):

| Приоритет | Имя                 | Этап(ы)        | Файл                  |
| --------- | ------------------- | -------------- | --------------------- |
| `5`       | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`       | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`       | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`      | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`      | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`      | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

Меньшие значения приоритета выполняются **первыми**.

### Мост для изображений (`visionBridge.ts`) — мост модальностей PR-1

Перехватывает запросы с изображениями, направленные **моделям без поддержки изображений**, и либо перенаправляет весь запрос модели с поддержкой изображений, либо перед вызовом вышестоящего сервиса заменяет части с изображениями текстовыми описаниями, созданными настраиваемой моделью обработки изображений. Благодаря этому провайдеры, работающие только с текстом, могут прозрачно обрабатывать мультимодальные полезные нагрузки.

Последовательность:

1. Пропустить обработку, если целевая модель уже поддерживает изображения (если только она не присутствует в списке принудительного использования моста `isVisionBridgeForcedModel`).
2. Извлечь части с изображениями с помощью `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), которая делегирует работу **унифицированному детектору
   медиа** `detectMediaParts()` в `open-sse/utils/mediaParts.ts` — единому
   источнику истины, совместно используемому с фильтром совместимости комбо.
   Извлечение ограничено разрешённым списком частей верхнего уровня тех форм,
   которые `replaceImageParts` может вставить обратно (контракт extract↔replace): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` и Responses API `input_image`. Вложенные совпадения и
   формы, содержащие только индикаторы, предназначены для комбо-фильтра и никогда не извлекаются.
   Пропустить обработку, если ничего не найдено.
3. Определить конфигурацию среды выполнения с помощью `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): новые ключи настроек `modalityBridge*`
   имеют приоритет; устаревшие ключи `visionBridge*` остаются в качестве **резервного
   варианта на один цикл** (окно отката). Если мост отключён, пропустить обработку до
   любого обхода медиа.
4. Селектор режима (`modalityBridgeVisionMode`, см. таблицу ниже) выбирает
   перенаправление или описание. Перенаправление возвращает `modifiedPayload`, в котором
   заменено только поле `model`, а также метаданные `{ rerouted, fromModel, toModel, imagesKept }`.
5. Путь описания: ограничить количество изображений значением `maxImages`, составить
   учитывающий задачу промпт, проверить кэш описаний, вызвать модель обработки изображений
   **параллельно** (`Promise.allSettled`) и вставить вместо изображений текстовые части
   `[Image N]: <description>`. Если создать описание не удалось, возвращается `null`, а исходная
   часть с изображением **сохраняется** (#4012) — кроме пути описания для комбо, когда
   не удалось создать ни одного описания: в этом случае для подтверждённо не поддерживающего
   изображения вышестоящего сервиса вместо изображения используется заглушка
   `(недоступно — не подключён ни один провайдер с поддержкой изображений)` (#8430).
6. Вернуть `modifiedPayload` и метаданные (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### Селектор режима (`modalityBridgeVisionMode`)

| Режим      | По умолчанию | Поведение                                                                                                                                                                                                                                                                                                                                                                                    |
| ---------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔            | Устаревшая эвристика без изменений (#6640/#7204): модели, не являющиеся комбо, и модели `auto/` перенаправляются лучшей модели с поддержкой изображений, если у исходной модели нет пригодных учётных данных (в противном случае создаётся описание); для целей-комбо всегда создаётся описание.                                                                                             |
| `describe` |              | Всегда создавать описание — блок перенаправления полностью пропускается; ответ всегда даёт выбранная пользователем модель.                                                                                                                                                                                                                                                                   |
| `reroute`  |              | Принудительное перенаправление: проверка сохранения модели с учётными данными обходится. Проверка учётных данных **целевой** модели перенаправления по-прежнему применяется — если нет пригодной целевой модели с поддержкой изображений, запрос переходит к созданию описания, чтобы необработанные изображения никогда не попадали в серверную часть, работающую только с текстом (#8430). |

Принудительные режимы завершают выбор **до** запуска автоматической эвристики;
поведение `auto` побайтно идентично защитному механизму до PR-1.

#### Область действия API-ключа (`visionBridgeKeyScope.ts`)

Когда API-ключ вызывающей стороны ограничивает `allowedConnections`, пулы квот
(`allowedQuotas`) или модели (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), мост выбирает для
перенаправления и описания только те модели и подключения, которые разрешено
использовать ключу. Затем вызов создания описания всегда проходит через петлю
самовызова OmniRoute с заголовком `x-omniroute-self-loop-key-id`, чтобы принимающий
чат-запрос повторно применил политику подключений и моделей этого ключа.
`enforceApiKeyPolicy()` учитывает этот заголовок только вместе с bearer-токеном
петли самовызова, поэтому он может лишь сужать доступ; идентификатор, который не
удаётся разрешить, отклоняется.

Если ключу не разрешена ни одна модель с поддержкой изображений, путь описания
не вмешивается, и запрос проходит без изменений — это то же открытое при сбое
поведение, что и у отключённого защитного механизма (метаданные
`{ skipped: true, reason: "no_permitted_vision_model" }`).
Запросы без ключа и ключи без этих ограничений обрабатываются точно так же, как
раньше.

#### Учитывающий задачу промпт описания (`modalityBridgeVisionTaskAware`)

По умолчанию **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) добавляет
текст **последнего сообщения пользователя** (обрезанный до 500 символов) к базовому
промпту описания, направляя описание на то, о чём фактически спросил пользователь
(паттерн codex-vision-proxy), и просит визуальную модель расшифровать видимый
текст. Если флаг отключён или пользовательский текст отсутствует, базовый промпт
используется без изменений.

Собственный OpenAI-совместимый запрос цикла самоописания (`callVisionModelSingle()`
в `visionBridgeHelpers.ts`) всегда запрашивает `image_url.detail: "high"` —
безусловно, для каждого вызывающего кода/провайдера, независимо от каких-либо
сигналов клиента. Выборка с низкой детализацией ухудшает точность OCR именно для
задачи расшифровки текста, которую задаёт этот промпт, поэтому сам вызов описания
всегда запрашивает высокую детализацию независимо от уровня детализации исходного
входящего запроса. Это влияет только на тело внутреннего запроса описания; это не
изменяет способ, которым OmniRoute передаёт собственное значение
`image_url.detail` вызывающей стороны в основном запросе — это значение по
умолчанию применяется отдельно и только для обнаруженных клиентов OpenCode в
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). Ветка
цикла самоописания с форматом передачи Anthropic не имеет поля `detail` и не
затрагивается ни одним из этих значений по умолчанию.

#### Ограничение вывода описания (`modalityBridgeVisionMaxChars`)

| Ключ                           | По умолчанию | Диапазон          |
| ------------------------------ | ------------ | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`          | `0` или 100–50000 |

`0` (по умолчанию) означает **без ограничения** — описание, возвращённое
`callVisionModel()`, передаётся без изменений, сохраняя существующее
поведение. Любое значение в диапазоне 100–50000 обрезает описание, добавляя
суффикс `…`, прежде чем оно будет вставлено обратно в виде
`[Image N]: <description>` (`VisionBridgeGuardrail.preCall()` в
`src/lib/guardrails/visionBridge.ts`). Увеличьте это значение для задач OCR с
большим количеством деталей, где последующей модели требуется полная
расшифровка; уменьшите его, чтобы ограничить расход токенов многословными
визуальными моделями. Поле панели мониторинга находится на панели Advanced
вкладки Vision (`modality-bridge-max-chars` в `ModalityBridgeVisionTab.tsx`) и
повышает любое значение от 1 до 99 до минимального значения 100, оставляя явно
указанный `0` без изменений — `0` сам по себе является допустимым значением Zod
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не просто
значением по умолчанию для состояния «не задано».

#### Кеш описаний (`modalityBridge/bridgeCache.ts`)

Внутрипроцессный кеш LRU + TTL для результатов описания, общий для всего
процесса. Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` с
кадрированием посредством префиксов длины (без коллизий на границах полей).
Компонент модели — это **настроенная** модель моста, а не модель, которая
фактически ответила: `callVisionModel` может внутренне переключиться на
резервный вариант, а создание ключа для каждой попытки фрагментировало бы кеш.
Неудачные описания никогда не кешируются. Настройки:

| Ключ                            | По умолчанию | Диапазон |
| ------------------------------- | ------------ | -------- |
| `modalityBridgeCacheEnabled`    | `true`       | —        |
| `modalityBridgeCacheTtlMinutes` | `60`         | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`        | 10–5000  |

#### Нормализация удалённых изображений (самоописание/получение base64)

Когда мост самостоятельно получает **удалённое** изображение — для внутреннего
вызова описания Anthropic и преобразования в base64 для формата передачи claude
(`ensureBase64ImagesForClaudeWire`), в обоих случаях через
`fetchRemoteImageAsDataUri()` в `visionBridgeHelpers.ts`, — полученный URI данных
перед встраиванием в запрос визуальной модели пропускается через
`normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`). Слишком большие
изображения уменьшаются до **2048px по длинной стороне** (в соответствии с
ограничением изменения размера, которое OpenAI/Anthropic уже применяют на
стороне сервера), что сокращает объём загружаемых данных и задержку, не изменяя
то, что видит визуальная модель. Для изменения размера используется `sharp`,
загружаемый через динамический импорт: на платформе, где его нативный бинарный
файл не удаётся загрузить, `normalizeDataUri()` **никогда не выбрасывает
исключение** — он возвращается к передаче исходных байтов без изменений, поэтому
путь описания/преобразования в base64 всегда продолжает работать. Байты, не
являющиеся изображением (если при получении не было возвращено декодируемое
изображение), также передаются без изменений. Эта нормализация применяется
только к изображениям, которые мост получает для собственного внутреннего
вызова, и никогда не применяется к необработанной полезной нагрузке вызывающей
стороны, что соответствует принципу изменения только при явном согласии
(жёсткое правило №20).

#### Схема настроек + миграция

Новые ключи `modalityBridge*` проверяются с помощью Zod в
`updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`):
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, тройка
`modalityBridgeCache*` и группа `modalityBridgeAudio*`, используемая Audio
Bridge. Миграция `141_modality_bridge_settings.sql` копирует существующие
устаревшие значения `visionBridge*` в соответствующие новые ключи
(идемпотентно, никогда не перезаписывая значение `modalityBridge*`, заданное
оператором); устаревшие ключи остаются допустимыми в качестве резервного
источника при чтении в течение одного цикла выпуска.

#### Заголовок прозрачности + статистика

Преобразованные посредством описания ответы содержат
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(формируется `buildModalityBridgeHeader()` в `modalityBridge/bridgeStats.ts`,
добавляется `withModalityBridgeHeader()` в `src/sse/handlers/chatHelpers.ts`).
Перенаправленные запросы **не** получают заголовок — полезная нагрузка не
изменялась, а замена модели уже видна в поле `model` тела ответа.

`GET /api/modality-bridge/stats` (авторизация управления, тот же уровень, что и у
`GET /api/settings`) возвращает хранящиеся в памяти счетчики по каждой модальности
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` и
`video`. В качестве знаменателя `averageLatencyMs` использует `latencySamples`,
а не все попытки; операция без измерения времени не создает искусственный
образец с нулевой длительностью. `bridged` остается обратно совместимым
псевдонимом для успешных преобразований; неудачные попытки не увеличивают его.
Счетчики намеренно сбрасываются при перезапуске процесса
(это телеметрия, а не учет).

#### Конфигурация панели управления

Специализированная страница панели управления находится по адресу
`/dashboard/settings/modality-bridge`. Ее вкладки `Vision`, `Audio` и
`Video`, доступные по URL, при переключении сохраняют параметры запроса,
изменяя значение `tab`. Вкладка Vision предоставляет включение функции, выбор
режима и модели (включая автоматический вариант по умолчанию), формирование
промптов с учетом задачи, расширенные ограничения для тайм-аута, изображения,
длины описания и кэша, счетчики среды выполнения, а также защищенный тестовый
запрос. Вкладка Audio также полностью работает: она предоставляет включение
функции, средство выбора только STT-моделей с вариантом Auto, ограничения
тайм-аута и максимальной длительности клипа, счетчики аудио и тестовый запрос
`input_audio`. Вкладка Video функциональна: она отображает состояние среды
выполнения FFmpeg/ffprobe — одно из четырех явных состояний интерфейса (`unknown`,
пока проверка выполняется или не может быть завершена, `restricted` для хоста
панели управления, не являющегося loopback-хостом, где проверка пропускается
на стороне клиента, `unavailable`, когда проверка завершена и отсутствие
подтверждено, либо `available` с версиями FFmpeg/ffprobe), — сохраняет настройки
включения, модели, кадров, видео и тайм-аута, фильтрует средство выбора моделей,
оставляя только модели с поддержкой изображений, и предоставляет счетчики видео.

Прежняя карточка Vision Bridge в настройках ИИ теперь служит ссылкой
совместимости на новую страницу; она больше не содержит вторую копию формы.
Media Providers также связывает рабочие процессы Image-to-Text и Speech-to-Text
с соответствующими вкладками Modality Bridge, не удаляя существующую
тестовую среду Speech-to-Text.

**Обход проверки допуска для self-loop:** когда вызов описания маршрутизируется
через собственный self-loop OmniRoute `/v1` (модель нестандартного провайдера),
подзапрос отправляет `x-omniroute-admission-bypass: internal` и проходит
аутентификацию с помощью разрешенных учетных данных self-loop — локального
маркера `sk_omniroute` в локальном режиме либо настроенного оператором ключа
окружения `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350), благодаря чему
развертывания с `REQUIRE_API_KEY=true` по-прежнему могут выполнять вызов
описания. Обход разрешается только для этих точных учетных данных, поэтому
внешние клиенты не могут использовать этот заголовок для пропуска проверки
допуска.

Устаревшие значения по умолчанию находятся в
`src/shared/constants/visionBridgeDefaults.ts`; новые значения по умолчанию для
режима, учета задачи и кэша, а также обработчик настроек находятся в
`src/shared/constants/modalityBridgeDefaults.ts`. Защитный механизм предоставляет
параметр конструктора `deps`, чтобы тесты могли внедрять фиктивные реализации
`getSettings` и `callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Перехватывает содержащие аудио запросы чата до того, как они достигнут целевой
системы, для которой не подтверждена поддержка аудиоввода. Он никогда не
перенаправляет запрос чата: аудиофрагменты транскрибируются через существующую
OpenAI-совместимую multipart-конечную точку, после чего выбранная модель чата
продолжает работу с текстовыми расшифровками.

Процесс:

1. Определить `supportsAudio` с помощью `getResolvedModelCapabilities()`.
   Явные метаданные реестра провайдеров имеют приоритет, затем идут статические
   метаданные модели, а после них — синхронизированные `modalities_input`.
   Объявленный список входных данных без `audio` дает `false`; при отсутствии
   данных о возможностях остается `null`. И `false`, и `null` активируют
   консервативный мост, тогда как `true` обходит его.
2. Определить настройки `modalityBridgeAudio*` и извлечь пригодные для вставки
   аудиофрагменты верхнего уровня из каждого сообщения с помощью общего
   детектора `detectMediaParts()`. Поддерживаемые форматы передачи: OpenAI
   `input_audio`, `audio_url` и `source.media_type: "audio/*"`. Вложенное аудио
   обнаруживается для маршрутизации, но не удаляется при вставке. Объем работы
   ограничивается `modalityBridgeAudioMaxClips`; последующие фрагменты остаются
   без изменений.
3. Использовать настроенное значение `provider/model` или позволить
   `selectAudioBridgeModel()` пройти по `AUDIO_TRANSCRIPTION_PROVIDERS` в
   стабильном порядке каталога и выбрать первую модель с пригодными активными
   учетными данными провайдера.
4. `callAudioTranscription()` преобразует аудио в формате base64/data-URI в
   multipart-файл `file` либо загружает удаленный `audio_url` через защитный
   механизм исходящих подключений только к публичным адресам с фиксацией DNS
   и ограничением в 25 МБ. Затем он отправляет файл и выбранную модель методом
   POST в локальный self-loop `/v1/audio/transcriptions`, аутентифицированный
   с помощью `resolveSelfLoopBearer()`. Существующий маршрут транскрибирования
   выполняет стандартный поиск учетных данных, обработку периодов ожидания и
   ограничений частоты запросов, а также диспетчеризацию провайдера.
5. Успешные вызовы заменяют соответствующие фрагменты на
   `[Audio N]: <transcript>`. Вызовы выполняются через `Promise.allSettled`:
   сбой отдельного вызова сохраняет исходный аудиофрагмент (контракт #4012).
   Если все вызовы завершились неудачно и для целевой системы доказано
   `supportsAudio === false`, фрагменты заменяются на
   `[Audio N]: (unavailable — no STT provider connected)` (контракт #8430).
   Для неизвестной целевой системы (`null`) при сбое всех вызовов содержимое
   остается без изменений. Целевая система, для которой доказано, что она
   поддерживает только текст, при отсутствии пригодных учетных данных STT
   получает ту же явную заглушку без выполнения сетевого вызова.

Успешные расшифровки используют общий для всего процесса LRU/TTL-кэш Modality
Bridge. Ключ объединяет ссылку на аудио, стабильную метку операции
`audio-transcription` и выбранную STT-модель; сбои никогда не кэшируются.
Попытки обработки аудио обновляют общие счетчики `bridged`, `cacheHits`,
`failures` и `lastUsedAt`. Преобразованные ответы содержат
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`;
неизмененные запросы не получают сегмент Audio Bridge.

Настройки среды выполнения хранятся в БД и проверяются с помощью Zod:

| Ключ                          | По умолчанию | Диапазон        |
| ----------------------------- | ------------ | --------------- |
| `modalityBridgeAudioEnabled`  | `true`       | —               |
| `modalityBridgeAudioModel`    | `""`         | Auto или ID STT |
| `modalityBridgeAudioTimeout`  | `60000`      | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`          | 1–10            |

Общий кеш по-прежнему управляется параметрами `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` и `modalityBridgeCacheMaxEntries`.

### Мост для видео (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехватывает части верхнего уровня с видео в `messages` Chat Completions и
`input` API Responses до вызова целевой модели без известной встроенной поддержки
видео. Поддерживаются форматы `input_video`, `video_url`, `video_source`, URL-адреса HTTPS
и URI данных `data:video/*;base64,...`. Обычные имена файлов в тексте не считаются
видео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) отвечает за обход запроса,
проверку возможностей и политик, агрегацию в рамках запроса и полезную нагрузку ответа.
Обработка каждого видео — получение данных, кеширование полного результата, описание
последовательности кадров (с объединением любой объявленной вызывающей стороной
транскрипции аудио), а также метрики, прерывание и очистка для каждой попытки —
скрыта за `processVideoPart` в `videoBridgePipeline.ts`, которая вызывается один раз
для каждой части с видео внутри цикла `preCall`. Этот модуль также определяет явные
границы портов `VideoMediaBrokerPort` (получение байтов и извлечение выбранных кадров),
`VideoAudioTranscriptionPort` (объединение объявленной вызывающей стороной транскрипции
аудио с подписями выбранных кадров) и `VideoDrilldownPort` (граница сохранения данных
детализации кадров; пока не подключена к `processVideoPart` — в настоящее время записи
детализации создаёт только отдельный маршрут `/api/modality-bridge/video/drilldown`).

Публичный путь запросов `/v1` никогда не импортирует и не запускает подпроцесс. Удалённые
видео загружаются с ограничением в 50 МиБ; для встроенных видео в формате base64 действует
консервативное ограничение в 36 МиБ декодированных данных на одно видео, чтобы оболочка
модели, сообщений и фрейминга укладывалась в публичный лимит приёма JSON-запросов,
равный 50 МиБ. Длина встроенных данных и оценка декодированного размера проверяются до
выделения памяти. HTTPS обязателен как для исходного удалённого URL-адреса, так и для
каждого перенаправления; при этом используется существующее ограничение исходящих
подключений только к публичным адресам с фиксацией DNS. Затем байты передаются через
точную внутреннюю границу брокера `POST /api/modality-bridge/video/extract`. Этот маршрут
одновременно является `LOCAL_ONLY` и `SPAWN_CAPABLE`, принимает только аутентифицированные
на уровне процесса доверенные запросы через loopback-интерфейс и никогда не принимает
URL-адрес, путь в файловой системе, исполняемый файл или список аргументов. Конвейер
ограничения размера тела API и инкрементальный обработчик чтения тела независимо друг
от друга применяют ограничение входных данных брокера в 50 МиБ. Ограниченная очередь
выполняет по одному извлечению за раз, допускает четыре ожидающих задания и ограничивает
общий объём ожидающих входных данных 100 МиБ.

Внутри брокера `ffprobe` считывает закрытый локальный файл; фиксированный список
разрешённых форматов исключает форматы плейлистов и манифестов. Для разрешённых
контейнеров семейства MOV внешние ссылки на данные MOV по умолчанию остаются отключёнными,
и фиксированная команда их не включает. И `ffprobe`, и `ffmpeg` используют список
разрешённых протоколов только с `file`, один поток, фиксированные массивы аргументов,
не используют оболочку, а исполняемые файлы разрешаются через `PATH`. Потоки обложек
типа attached-picture не считаются кандидатами для воспроизведения. Все воспроизводимые
потоки должны соответствовать ограничениям; явно заданный поток по умолчанию имеет
приоритет перед детерминированным резервным выбором потока с наименьшим индексом.
Продолжительность видео ограничена 600 секундами, размер каждого измерения — 8 192
пикселями, а общее количество исходных пикселей — 33 554 432. FFmpeg выбирает 1–16
JPEG-кадров в средних точках, уменьшает длинную сторону максимум до 1 024 пикселей,
не увеличивая изображения меньшего размера, и никогда не получает URL-адрес.
По умолчанию используется стратегия выборки `uniform`. Необязательная стратегия
`scene_aware` и экспериментальная стратегия `segment_aware` выполняют один
дополнительный фиксированный проход FFmpeg по уже проверенному локальному потоку,
выбирают ограниченный набор временных меток сцен `showinfo` и детерминированно
возвращаются к тем же равномерным средним точкам при сбое детектора, истечении времени
ожидания, некорректном выводе или пустом наборе кандидатов. В режиме с учётом сегментов
выборки в средних точках распределяются пропорционально проверенным интервалам сцен;
свидетельства для режима с учётом сегментов и резервное поведение подробно описаны
ниже. Жёсткое ограничение в 16 кадров применяется после выбора при любой стратегии.
Если для запроса с учётом сцен доступен бюджет только в один кадр, используется
равномерная средняя точка активного окна всего видео или окна фокусировки, а в
результате указывается `policyEffective: uniform`: один выбранный кадр сцены не может
охватить обе временные границы. Вызывающая сторона может при необходимости указать
конечное окно фокусировки (`start`/`end` в секундах); границы ограничиваются
продолжительностью медиаданных, окна с обратным порядком границ или нечисловыми
конечными значениями отклоняются, а все стратегии выборки применяются только внутри
нормализованного интервала. Полученное окно включается в метаданные выборки и в
недоверенный префикс описания, чтобы последующие модели могли отличить выделенный
фрагмент от полной временной шкалы.

Семантическая фокусировка подписей — это отдельная явно задаваемая настройка. Режим
анализа `full`, используемый по умолчанию, сохраняет существующий запрос для кадров
и никогда не передаёт текст запроса модели подписей. В режиме `focused` мост считывает
только последний непустой пользовательский `text`/`input_text` из того же контейнера
Chat или Responses, нормализует его в NFC, сворачивает управляющие символы и пробельные
последовательности и ограничивает длину 500 кодовыми точками Unicode. Пустой результат
приводит к возврату к точному запросу `full`. Пригодная подсказка сериализуется как JSON
в специальном блоке недоверенного пользовательского контекста и может только задавать
приоритет наблюдаемым деталям; она не может переопределить отдельное предупреждение
о запрете следовать инструкциям, видимым или слышимым в медиаданных. Текстовая
фокусировка никогда не выводит `start`/`end` и не изменяет временной семплер.

#### FU-07 структурные свидетельства сегментов

`segment_aware` использует один ограниченный проход предварительного анализа уже проверенного
локального видеопотока. Фиксированная цепочка фильтров сначала уменьшает ширину
до не более чем 320 пикселей, обнаруживает смены сцен и интервалы неподвижности,
а затем выполняет выборку с частотой 1 кадр в секунду для оценки размытия, средней
яркости, а также пространственной и временной информации. Проход ограничен
600 структурными выборками, одним потоком FFmpeg/фильтра, теми же списками
разрешённых контейнеров и протоколом только `file`, ограничением вывода процесса
в 1 МиБ и не более чем 30 секундами в рамках общего механизма прерывания/крайнего
срока брокера. Он никогда не принимает из запроса команду, фильтр, путь или URL.

Структурные значения представляют собой детерминированные данные выборки, а не
семантическое понимание видео. Они не определяют объекты, действия, субтитры,
речь или намерения пользователя. Границы сцен и неподвижных интервалов формируют
сегменты; покрытие неподвижных интервалов, размытие, экспозиция, пространственная
детализация и временные изменения влияют только на распределение существующего
бюджета в 1–16 кадров. Полностью неподвижный сегмент ограничивается одним кадром,
а неподвижные сегменты конкурируют за оставшийся бюджет. Когда количество границ
превышает количество кадров, сохраняется равномерное покрытие временной шкалы,
чтобы быстрые ранние склейки не могли скрыть длинный заключительный сегмент.
Границы сцен, находящиеся в пределах 1-секундного разрешения анализа от границы
неподвижного интервала, объединяются.

Отсутствующие фильтры, некорректные/пустые данные, ошибка детектора или истечение
времени ограниченного предварительного анализа приводят к открытому отказу с
переходом к точной политике равномерных средних точек. Прерывание вызывающей
стороной или крайний срок брокера не приводят к открытому отказу: они завершают
выполняющийся подпроцесс, предотвращают последующее извлечение кадров, а приватное
временное дерево удаляется в `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` создаёт детерминированные реальные
тестовые данные FFmpeg для оценки сокращения количества вызовов создания описаний
после дедупликации, распределения бюджета при интенсивном движении, данных о
размытии/экспозиции/SI-TI, быстрых склеек с длинным заключительным сегментом и
ложноположительных результатов при постепенном затухании. Скрипт регистрирует
фактическое время предварительного анализа, а при наличии `/usr/bin/time` —
процессорное время дочернего процесса и пиковое значение RSS. Его проверки
качества являются только структурными оракулами. Оценка качества реальной модели
создания описаний остаётся `HOLD`, поскольку у этого тестового стенда нет
авторизованной конечной точки или зафиксированного оценщика. Оценка денежной
экономии также остаётся `HOLD`, если только `--caption-cost-per-call-usd` не
задаёт явную положительную оценку стоимости одного вызова; скрипт никогда не
выдумывает ни один из этих результатов.

Размер каждого кадра ограничен 4 МиБ, совокупный размер всех необработанных
кадров — 23 МиБ, а размер сериализованного ответа брокера — 32 МиБ. Приватный
временный каталог удаляется в `finally`. OmniRoute не включает FFmpeg в комплект
поставки и не принимает пользовательский путь к исполняемому файлу. Перед
созданием описаний мост применяет консервативный проход визуальной дедупликации:
каждый JPEG уменьшается до буфера оттенков серого 16×16 и сравнивается только
с последним сохранённым кадром. Если запрошенный бюджет описаний превышает один
кадр, при извлечении формируется ограниченный пул кандидатов размером не более
чем вдвое больше этого бюджета и никогда не превышающий 16 кадров. Запрошенное
ограничение применяется только после дедупликации; при окончательном прореживании
первый и последний выбранные кандидаты сохраняются, если бюджет составляет не
менее двух кадров. Версионированная политика
`grayscale-16x16-mean-cells-v2` использует большее из двух значений: средней
дельты яркости и доли ячеек миниатюры, нормализованная дельта которых составляет
не менее 0.05. Порог дубликата равен константе 0.04, выбранной ради
предсказуемости, а не предоставляемой в виде настройки времени выполнения. Этот
вторичный высококонтрастный сигнал сохраняет небольшие движения и изменения
видимого текста, которые может скрыть сравнение только по среднему значению.
Ошибки компаратора или декодера приводят к открытому отказу и сохранению
покрытия. Метаданные вывода раздельно указывают извлечённых кандидатов, успешно
использованные кадры и отброшенные визуальные дубликаты.

Явно отмеченная часть видео может запрашивать контактный лист с временными
метками. Мост создаёт JPEG-сетку не более чем из 4 столбцов и 16 кадров.
В каждую 512-пиксельную ячейку временная метка исходного кадра впечатывается
на высококонтрастную полосу внизу, при этом те же временные метки сохраняются
в текстовых метаданных для последующего сопоставления и аудита. Размер полного
JPEG остаётся ограниченным 32 МиБ. Если `sharp` не может декодировать или
скомпоновать сетку, мост возвращается к отдельным JPEG-кадрам; прерывание
клиентом по-прежнему распространяется на операцию с контактным листом.

Данные для продвижения намеренно отделены от синтетического микротеста
компоновки. `scripts/perf/video-bridge-contact-sheet-eval.ts` определяет
версионированный по схеме A/B-тестовый стенд для реальных моделей компьютерного
зрения, совместимых с OpenAI. Он измеряет указанное провайдером количество
токенов, сквозную фактическую задержку (включая компоновку контактного листа),
количество вызовов модели и сохранение фактов, определённых в манифесте.
Необработанные ответы модели не записываются в отчёт; сохраняются только
SHA-256-дайджесты и идентификаторы совпавших фактов. Тестовый стенд не выполняет
сетевых вызовов или вызовов платной модели, если не передан параметр
`--execute-real` и не настроены `--model`, `OMNIROUTE_BASE_URL` и
`OMNIROUTE_API_KEY`. Без такого явно запрошенного реального запуска его
машиночитаемый вердикт остаётся `HOLD`; одних лишь синтетических измерений
полезной нагрузки/количества вызовов недостаточно для продвижения.

Вызывающие стороны могут прикрепить необязательный массив `transcript.cues`
к поддерживаемой части видео, если у них уже есть синхронизированный текст.
Каждая реплика должна содержать `text`, конечный интервал `start`/`end` в
пределах определённой длительности и `source` из списка разрешённых значений
(`client`, `embedded` или `audio-bridge`); значение `confidence` по умолчанию
равно `1` и должно оставаться в диапазоне от `0` до `1`. Полностью совпадающие
реплики сворачиваются. OmniRoute никогда не запускает транскрибирование на
основании этих метаданных: проверенные реплики копируются в описанный результат
вместе с источником, уверенностью и интервалом и отображаются как ненадёжные
наблюдения рядом с описаниями кадров. Некорректный текст, текст за пределами
допустимого диапазона или текст без указания происхождения отклоняется, а не
смешивается с потоком описаний. Оба канала расшифровки в теле запроса нормализуют
предоставленное происхождение до `client`, включая самостоятельно заявленные
метки `embedded` или `audio-bridge`. Только принадлежащий серверу адаптер может
назначать эти доверенные метки через доступный только из кода аргумент
`trustedSource`; поле JSON запроса не может передаваться в этот аргумент. Текст
расшифровки остаётся ненадёжным содержимым, полученным из мультимедиа, независимо
от его происхождения, и никогда не должен определять авторизацию.

Опытный вызывающий код может предоставить дорожку `audioTranscript` для того же видео;
она рассматривается как предоставленный клиентом текст, а не как подтверждение серверной транскрипции.
Узел объединения выполняет визуальные и аудионаблюдения с единым
крайним сроком и сигналом прерывания, упорядочивает их на общей временной шкале, сворачивает
точные дубликаты и возвращает частичный результат, если успешно обработана только одна сторона.
Недопустимый `audioTranscript` приводит к такому частичному результату — визуальное
описание сохраняется, а аудиоветвь записывает очищенный код ошибки —
вместо сбоя обработки всего видео. Доступность каждой ветви, флаг частичного результата
и очищенные коды ошибок сохраняются в описанном результате, в метаданных
защитного механизма (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), в метаданных кэша результатов и в счётчиках
объединения моста. Стандартный путь Video Bridge не вызывает преобразование речи в текст
и не загружает вторую копию медиафайла; без явно предоставленной дорожки он остаётся
только видеорежимом.

**Хранение транскриптов (#12150 P1).** Это применяется автоматически всякий раз, когда
Video Bridge (который сам по себе включается отдельно) отображает реплику транскрипта — отдельного
флага хранения нет. Когда запрос отображает любую реплику транскрипта (объявленный вызывающей стороной
`transcript` или объединённый `audioTranscript`), защитный механизм помечает его как
`videoBridgeObserved` и создаёт редактированную теневую копию описания видео —
идентичное представление, в котором произвольный текст каждой реплики заменён на
`[redacted-video-transcript]`; она создаётся посредством подстановки в структурированное поле реплики
до сборки строки (а не путём разбора сведённого текста, поэтому никакое содержимое
реплики — вредоносное или обычное, включая текст с символом `]`, например
`[inaudible]`/`[music]`, — не может сохраниться). В теле запроса, сохраняемом в журнале вызовов,
каждая текстовая часть, полученная из видео, заменяется соответствующей редактированной теневой копией
путём сопоставления по равенству содержимого; опорное значение `fullText` повторно считывается из завершённых
данных защитного механизма перед вызовом, поэтому сопоставление по-прежнему успешно после того, как последующие
защитные механизмы цепочки (маскировщики персональных данных и учётных данных с приоритетами 10/95)
изменят текст описания на месте, а внедрение системного промпта, передачи управления и памяти
изменит структуру массива сообщений. Тело, отправляемое модели, остаётся неизменным. Наблюдаемый
запрос также не заполняет долговременную Memory (извлечение как из запроса, так и из ответа
пропускается), поэтому собственный ответ модели не может скопировать текст транскрипта в Memory.

**Необработанные поля видео (#12430).** Когда мост включён, а наличие нативной поддержки видео неизвестно или она отсутствует, заданные поля `transcript`/`audioTranscript` также активируют `videoBridgeObserved`, даже после сбоя описания или при достижении ограничения `maxVideos`. Значения `null` и пустые строки учитываются; отсутствующие поля и метаданные, не относящиеся к видео, не учитываются. В сохраняемых копиях эти поля редактируются либо запрос не сохраняется, а кэши/Memory обходятся.

На этих резервных путях допустимые реплики, предоставленные вызывающей стороной, преобразуются в поддерживаемые
части `text`/`input_text`, а не в нестандартные поля провайдера. Обе предоставленные в запросе дорожки
остаются недоверенными наблюдениями `client` с явным предупреждением о том, что видео
не было описано, а временные метки не сверялись с медиафайлом. Существующие ограничения
в 256 реплик/64 КиБ суммарно и на каждую реплику применяются к обеим дорожкам вместе;
временные метки должны укладываться в 600-секундный предел брокера и в любое заданное
фокусное окно. Недопустимые дорожки отбрасываются, а не пересылаются как произвольный текст;
допустимая парная дорожка всё ещё может использоваться, если не превышен их совокупный лимит.
Поля со значением null или пустой строкой не добавляют текст. Этот резервный механизм не добавляет
получение медиафайла или транскрипцию. Поля расширения транскрипта удаляются из резервного
контейнера видео и его объектов `video_url`/`source`. Список разрешённых полей OpenAI остаётся
строгим; контейнеры видео с неизвестной нативной поддержкой остаются доступными, а известные
цели, поддерживающие только текст, сохраняют безопасные маркеры. Структурированные редактированные
теневые копии защищают добавленный текст транскрипта, тогда как исходный запрос, принадлежащий
вызывающей стороне, остаётся неизменным. Цели с нативной поддержкой и отключённые мосты
сохраняют существующее поведение обхода.

Дополнительные сохраняемые копии используют тот же сигнал наблюдаемого запроса. В необработанном
снимке клиентского запроса до применения защитных механизмов, ожидающем запросе в памяти и журнале
рано отклонённого запроса поля транскрипта в видеочастях структурно заменяются;
строковые промпты, синтезированные этапами конвейера и передачей контекста, редактируются
в точке сохранения тела запроса. Сохранённый маркер `video_content_removed`
заставляет продолжение через `previous_response_id` завершаться безопасным отказом вместо восстановления
текста, который был намеренно удалён. Если наблюдаемый запрос теряет свою
теневую копию для редактирования отдельной части до журналирования или хотя бы одна из нескольких теневых
копий видео не совпадает после последующих изменений запроса, сохраняемое тело запроса
полностью исключается вместо сохранения частично отредактированного транскрипта.

Для наблюдаемого запроса ответ модели может цитировать любую часть
транскрипта без структурированной границы реплики. Поэтому его сохраняемое в журнале вызовов
поле `responseBody` заменяется маркером исключения; подробный
артефакт конвейера (который может содержать тела запросов и ответов вышестоящего сервиса/клиента, а также фрагменты потока)
не сохраняется. Семантический кэш, кэш идемпотентности и кэш воспроизведения рассуждений
не читаются и не записываются для такого запроса. Запрос к провайдеру и видимый клиенту
ответ остаются неизменными. Ранние байты keepalive удаляются из временного
буфера, когда подробный артефакт исключается. Предупреждение Kiro о некорректном EventStream
сообщает только количество байтов полезной нагрузки, но никогда не её содержимое или необработанную ошибку
JSON-парсера.
Это не означает, что были проверены все несвязанные диагностические сообщения провайдеров/плагинов;
более широкий аудит мест сохранения отслеживается в #11658.

Внутренний жизненный цикл `/api/modality-bridge/video/drilldown` представляет собой отдельную кэш-подсистему с обратным подключением и аутентификацией по токену. Для каждой операции также требуется канонический непрозрачный идентификатор принципала. Прежде чем предоставить производственному вызывающему компоненту доступ, он должен сформировать этот идентификатор на основе аутентифицированного арендатора и ни при каких обстоятельствах не передавать значение, выбранное клиентом. Ключи кэша связывают этого принципала с каноническими идентификаторами сеанса и ссылки на видео, хранят только их ключи, производные от SHA-256, и ограничивают как чтение, так и удаление одним и тем же принципалом. В каждой записи кэш хранит не более 16 производных кадров JPEG, удаляет их через десять минут и поддерживает ограниченное чтение с параметрами `start`/`end` либо явное удаление сеанса.

Для каждого принципала действует ограничение в 16 записей и 64 МиБ канонических данных JPEG. Эти ограничения не зависят от глобального предела в 64 записи/256 МиБ: при исчерпании квоты принципала сначала вытесняются только записи этого принципала, использовавшиеся наиболее давно, и лишь затем рассматривается глобальное вытеснение по LRU. Истёкшие записи удаляются из учёта как принципала, так и глобального кэша при активности кэша, а отмена и ошибка валидации не приводят к фиксации частичной замены.

Кэш отклоняет неканонический Base64, избыточное заполнение, данные не в формате JPEG, повреждённые или усечённые JPEG, а также JPEG, при ограниченном полном декодировании которых с помощью `sharp` возникает предупреждение. Каждое принятое изображение повторно кодируется в канонический JPEG; его ширина и высота определяются по декодированным байтам без доверия к полям вызывающей стороны, а все завершающие полиглотные байты отбрасываются, а не сохраняются. В обеих квотах учитывается только ограниченный канонический сжатый буфер. Ограничение для JSON в проводном формате учитывает накладные расходы Base64 для предельного размера декодированных входных данных в 32 МиБ. Для каждого
сохранённого производного результата записываются валидированные формат и разрешение JPEG, политика выборки, версия алгоритма формирования, время создания, вычисленный сервером хэш содержимого, хэшированная родительская ссылка, а также хэш родительского содержимого от доверенной вызывающей стороны. Отмена проверяется между асинхронными этапами декодирования и хэширования до атомарной фиксации в кэше.

На этом этапе производственный источник ещё не подключён к маршруту, а выбор вариантов с несколькими разрешениями не поддерживается. Поэтому прозрачный путь запроса Video Bridge не несёт дополнительных затрат, а формирование привязанного к арендатору принципала и полный жизненный цикл FU-08 с несколькими разрешениями остаются явно обозначенными последующими задачами и не документируются как уже реализованное поведение.

Кадры последовательно снабжаются подписями с помощью настроенной модели Video. Пустое переопределение Video наследует настройку Vision; если обе настройки пусты, автоматический маршрутизатор Vision выбирает подходящую модель с поддержкой обработки изображений. Успешно созданные подписи заменяют исходную часть текстом со стабильным префиксом `[Video description:`, который также помечает текст как недоверенное наблюдение, полученное из медиаданных, и предписывает последующим моделям не выполнять инструкции, обнаруженные в медиаданных. Ключи кэша подписей кадров включают байты JPEG, запрос, временную метку и фактически используемую модель; кэшируются только успешно созданные подписи. Записи кэша сохраняют фактическую модель, успешно создавшую результат, включая резервную модель; мост сообщает `mixed`, если разные кадры были обработаны разными моделями. При попадании в кэш повторно используется идентификатор этого создателя, а не обозначение запрошенного плана маршрутизации. Ключ кэша результата для всего видео формируется из всех входных данных, влияющих на результат: запроса, фактически используемой модели, политики выборки, количества кадров, режима семантического анализа, SHA-256-отпечатка нормализованной подсказки фокуса, окна фокуса, `transcript`, `audioTranscript` и флага контактного листа. Поэтому изменение любого из этих параметров приводит к промаху кэша, а не к повторному использованию устаревшего результата. Версия политики визуальной дедупликации, порог и ограниченное количество кадров-кандидатов также явно включаются в ключ и метаданные кэша результатов; следовательно, изменение политики не позволяет повторно использовать устаревшее описание всего видео. Метаданные кэша результатов версии v4 сохраняют режим и отпечаток, но никогда не сохраняют необработанную пользовательскую задачу. Метаданные защитного механизма содержат как запрошенный, так и фактический режим анализа; запрошенный режим `focused` без пригодного пользовательского текста отражается как фактически работающий в режиме `full`.

Защитный механизм извлекает все поддерживаемые части видео, но описывает не более `modalityBridgeVideoMaxVideos`. Для целевого компонента, для которого подтверждено `supportsVideo === false`, неудачно обработанные и превышающие лимит видео преобразуются в явные безопасные текстовые маркеры, чтобы необработанное видео не сохранялось. Если возможность неизвестна, такие части сохраняют свой видеоконтейнер; любой резервный транскрипт проходит описанное выше ограниченное преобразование в текст. Целевые компоненты с `supportsVideo === true` обходят мост. Сигнал отмены клиентского запроса распространяется на скачивание, очередь брокера, подпроцессы и вызовы создания подписей; отмена останавливает обработку между видео и никогда не приводит к небезопасному пропуску необработанных медиаданных.

Параметры среды выполнения хранятся в БД и валидируются с помощью Zod:

| Ключ                                | Значение по умолчанию | Диапазон / поведение                                                                                                               |
| ----------------------------------- | --------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`               | Необязательная среда выполнения, включаемая явно                                                                                   |
| `modalityBridgeVideoAnalysisMode`   | `"full"`              | `full` сохраняет универсальные описания; `focused` использует ограниченный недоверенный контекст последнего сообщения пользователя |
| `modalityBridgeVideoModel`          | `""`                  | Наследует модель Vision Bridge                                                                                                     |
| `modalityBridgeVideoFrameCount`     | `8`                   | 1–16                                                                                                                               |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`           | `uniform`, `scene_aware` или пропорциональный `segment_aware`; при сбое детектора используется `uniform`                           |
| `modalityBridgeVideoMaxVideos`      | `1`                   | 1–4                                                                                                                                |
| `modalityBridgeVideoTimeout`        | `120000`              | 1000–120000 мс                                                                                                                     |

Сохранённые устаревшие значения тайм-аута Video свыше 120 секунд ограничиваются
предельным сроком брокера; новые значения настроек, превышающие этот предел,
отклоняются. `GET /api/modality-bridge/video/runtime` перед аутентификацией или
проверкой среды выполнения требует доверенной подтверждённой локальности
loopback, а затем — управленческой аутентификации. Эндпоинт возвращает только
`available`, очищенные версии FFmpeg/ffprobe и фиксированную причину
недоступности среды выполнения. Внутренний эндпоинт извлечения не является
публичным API для загрузки: при переполнении очереди возвращаются `503` и
`Retry-After`, при отключении вызывающей стороны — `499`, а при достижении
фиксированного предельного срока брокера — `504`. Преобразованные ответы
добавляют `video->text;model=<visionModel>;parts=<videos>` в центральный
заголовок `x-omniroute-modality-bridge`, не удаляя сегменты Vision или Audio.

### Маскирование PII (`piiMasker.ts`)

Выполняется на **обоих** этапах.

- **`preCall`** клонирует полезную нагрузку, обходит `system`, `messages`,
  `input` и `prompt` (включая элементы в виде обычных строк) и применяет
  `processPII()` (из `@/shared/utils/inputSanitizer`) к строковым полям
  `content`/`text`. Когда `PII_REDACTION_ENABLED=true`, обнаруженные PII
  редактируются в исходящей полезной нагрузке. Это не зависит от
  `INPUT_SANITIZER_MODE` (который управляет только политикой защиты от
  инъекций в промпт). Когда редактирование отключено, вызов регистрирует
  количество обнаружений без изменения содержимого.
- **`postCall`** выполняет глубокое клонирование ответа, запускает
  `sanitizePIIResponse()` вместе с маскированием структуры Responses API
  (`maskResponsesOutput` — охватывает `output_text` и
  `output[].content[].text`). Если происходит какое-либо редактирование,
  изменённый ответ заменяет исходный.

Защитный механизм никогда не блокирует; он лишь добавляет аннотации
(`meta.detections`, `meta.redacted`) или изменяет содержимое.

#### Выбор по типам, пользовательские шаблоны и счётчики обнаружений

**Панель управления → Настройки → Безопасность → Маскирование PII** определяет,
_что_ маскируется. Эта настройка не включает маскирование: за это по-прежнему
отвечают `PII_REDACTION_ENABLED` (запрос) и `PII_RESPONSE_SANITIZATION`
(ответ + SSE), оба по умолчанию отключены.

- **Выбор по типам** — встроенные идентификаторы перечислены в
  `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`). Если значение не
  задано, используются все типы (как и до появления этой настройки). Шаблон
  `ssn_us` механизма обработки запросов сопоставляется с `ssn`. Шаблоны
  (Минимальный, Стандартный, Финансовый, Бразильский, США, Полный) лишь
  устанавливают флажки в пользовательском интерфейсе.
- **Пользовательские шаблоны** — до 20 регулярных выражений или шаблонов с
  подстановочными знаками (`*` = до 64 непробельных символов, `?` = один).
  Совпадения заменяются на `[CUSTOM_REDACTED]`. Каждый шаблон проходит через
  `compilePiiCustomPattern()` (`src/shared/utils/piiCustomPatterns.ts`): не
  более 500 символов, флаги ограничены `g i m s u`, выражение должно
  компилироваться, проходить проверку `safe-regex` (катастрофический
  бэктрекинг) и не должно совпадать с пустой строкой или заполнителем
  редактирования. Шаблон, не прошедший проверку, отклоняется при сохранении и
  тестировании, а сохранённая строка с некорректным шаблоном пропускается во
  время выполнения вместо компиляции. Пользовательские шаблоны применяются
  только при включённом маскировании.
- **Счётчики обнаружений** — количество по каждому типу (сами совпавшие
  значения никогда не сохраняются), хранящееся в памяти и сбрасываемое при
  перезапуске (`src/lib/pii/piiDetectionStats.ts`). Счётчики увеличиваются
  только при включённом маскировании.

Настройки хранятся в таблице `key_value` (пространство имён `pii_settings`,
`src/lib/db/piiSettings.ts`) и считываются через кэш с длительностью 1 с. API:

| Метод  | Путь                     | Назначение                                                                             |
| ------ | ------------------------ | -------------------------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | Состояние флагов, `enabledTypes`, `customPatterns`, счётчики обнаружений               |
| `PUT`  | `/api/settings/pii`      | Замена `enabledTypes` (`null` = все) и/или `customPatterns`                            |
| `POST` | `/api/settings/pii/test` | Пробный запуск одного шаблона на образце размером не более 8 КБ; ничего не сохраняется |

Все три эндпоинта требуют управленческой аутентификации и проверяют тело запроса
с помощью Zod (`src/shared/validation/schemas/piiSettings.ts`).

### Инъекция в промпт (`promptInjection.ts`)

Обнаруживает вредоносные структуры в предоставленном пользователем содержимом
и применяет настроенную политику. Поведение определяется переменными окружения
и параметрами конструктора:

| Настройка        | Переменная окружения                                                                                        | По умолчанию | Эффект                                                                                                                                                                                                                                   |
| ---------------- | ----------------------------------------------------------------------------------------------------------- | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Включено         | `INPUT_SANITIZER_ENABLED`                                                                                   | `true`       | При значении `false` защитный механизм немедленно завершает работу.                                                                                                                                                                      |
| Режим            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                             | `warn`       | Политика обработки инъекций: `block`, `warn` или `log`. (`redact` поддерживается для обратной совместимости, но **не** удаляет текст инъекции; перезапись персональных данных в запросе управляется параметром `PII_REDACTION_ENABLED`.) |
| Порог блокировки | параметр `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (псевдоним `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`       | Минимальная степень серьёзности, необходимая для блокировки. При значении по умолчанию средняя степень используется только для наблюдения.                                                                                               |

**Приоритет режима** (`getMode`): `options.mode`, заданный вызывающей стороной →
**переопределение функциональным флагом из БД** `INJECTION_GUARD_MODE` (Панель управления → Настройки →
Функциональные флаги) → переменная окружения `INJECTION_GUARD_MODE` → переменная окружения `INPUT_SANITIZER_MODE` →
`warn`. Таким образом, переопределение через панель управления имеет приоритет над переменными окружения, поэтому интерфейс
функциональных флагов управляет работающим защитным механизмом в реальном времени (без перезапуска). Чтение из БД отказоустойчиво:
при ошибке защитный механизм возвращается к поведению, основанному на переменных окружения, а при отсутствии
переопределения поведение идентично разрешению только через переменные окружения.

Источники обнаружения:

1. `sanitizeRequest()` из `@/shared/utils/inputSanitizer` (общий набор детекторов,
   используемый в других частях конвейера).
2. Встроенные `DEFAULT_GUARD_PATTERNS` (в настоящее время `system_override_inline` и
   `markdown_system_block`, оба со степенью серьёзности `high`).
3. Необязательные `customPatterns`, передаваемые через параметры конструктора (строки, регулярные выражения
   или записи `{ name, pattern, severity }`).

Когда `mode === "block"` **и** хотя бы одно обнаружение соответствует порогу
серьёзности, `preCall` возвращает `{ block: true, message: "Request rejected:
suspicious content detected" }`. В режимах `warn`/`log` защитный механизм записывает событие в журнал, но
разрешает вызов. Общая вспомогательная функция `evaluatePromptInjection()` также экспортируется
для вызывающих сторон, которым необходимо проверять промпты без использования реестра.

**Ограничение сканирования (v3.8.20):** детектор проверяет только **первые 16 КБ**
объединённого текста промпта — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 байта) в
`src/shared/utils/inputSanitizer.ts`. И `detectInjection()`, и
`evaluatePromptInjection()` вызывают `slice(0, MAX_INJECTION_SCAN_BYTES)` перед запуском
цикла по шаблонам. Директивы инъекций находятся ближе к началу входных данных, поэтому это
ограничивает нагрузку регулярных выражений на ЦП и сборщик мусора для полезных нагрузок размером в сотни КБ, не ослабляя обнаружение (см.
#3932, #4041).

### Маскирование учётных данных (`credentialMasker.ts`)

Выполняется на **обоих** этапах и последним в цепочке по умолчанию (приоритет `95`). Редактирует
известные шаблоны API-ключей и секретных токенов в исходящей полезной нагрузке (содержимое
сообщений, аргументы вызовов инструментов, результаты инструментов) **и** в ответе провайдера, чтобы
учётные данные, вставленные в промпт (или возвращённые результатом инструмента), не утекли
вышестоящему провайдеру или обратно клиенту.

- **Только с явным включением**, по тому же принципу, что и редактирование персональных данных (смежно с жёстким правилом №20):
  отключено, если `settings.credentialRedactionEnabled !== true` **и**
  `CREDENTIAL_REDACTION_ENABLED` не равно `true`. Когда функция отключена, защитный механизм ничего не делает —
  он никогда не блокирует и не изменяет данные.
- `redactCredentials()` обходит всё дерево полезной нагрузки/ответа (`walkValue()`,
  с защитой от загрязнения прототипа и циклов посредством `WeakSet`) и заменяет совпадения
  заполнителем `[REDACTED:<type>]`, клонируя только фактически изменённые
  ветви.
- `CREDENTIAL_PATTERNS` охватывает ключи провайдеров LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), токены VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), платёжные ключи (Stripe, Square), облачные
  ключи (ключ доступа AWS, Twilio, SendGrid, Mailgun), закрытые ключи / JWT,
  строки подключения, содержащие учётные данные (`mongodb://user:pass@...` и т. д.), а также
  универсальный шаблон значений заголовков `Authorization`/`x-api-key`/`api-key`/`apikey`.
  Ключи, имеющие форму заголовков (`authorization`, `x-api-key`, `api-key`,
  `apikey`), редактируются структурно (только значение, при этом префикс схемы вроде
  `Bearer `/`Basic ` сохраняется), а не с помощью универсального текстового регулярного выражения.
- Защитный механизм никогда не блокирует; он только изменяет (`modifiedPayload` /
  `modifiedResponse`) и аннотирует (`meta.credentialsRedacted`, `meta.count`).

Защита от регрессий: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовый контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // значение true прерывает цепочку
  message?: string; // отображается при блокировке
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // возвращается методом preCall для изменения запроса
  modifiedResponse?: TValue; // возвращается методом postCall для изменения ответа
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Защитный механизм сообщает об отсутствии изменений, возвращая `void`, `{}` или
`{ block: false }`. Возврат `modifiedPayload`/`modifiedResponse` заменяет
значение, передаваемое по цепочке последующим защитным механизмам.
`signal?: AbortSignal` передаёт жизненный цикл вызывающей стороны защитным механизмам. Прерывание запроса является намеренным исключением из принципа fail-open: медиамосты прекращают работу и выполняют очистку, не восстанавливая необработанные медиаданные для целевой системы, которая заведомо их не поддерживает.

## Реестр (`registry.ts`)

Синглтон `guardrailRegistry` предоставляет:

- `register(guardrail)` — добавляет (или заменяет по нормализованному имени) защитный механизм и
  повторно сортирует по возрастанию `priority`.
- `clear()` / `list()` — вспомогательные функции администрирования.
- `runPreCallHooks(payload, context)` — итерирует активные защитные механизмы, пропускает
  полезную нагрузку через `modifiedPayload` и останавливается на первом `block: true`.
- `runPostCallHooks(response, context)` — тот же поток на стороне ответа.
- `resetGuardrailsForTests({ registerDefaults })` — очищает состояние и опционально
  повторно регистрирует значения по умолчанию для чистой изоляции тестов.

Оба запускатора возвращают `{ blocked, payload|response, results, guardrail?, message? }`,
где `results` — это массив записей `GuardrailExecutionResult`, которые включают
поля `blocked`, `skipped`, `modified`, `error` и `meta` для каждого защитного механизма,
полезные для трассировки.

### Отключение защитных механизмов для каждого запроса

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` агрегирует
дедуплицированный список имен защитных механизмов, которые должны быть пропущены для текущего
запроса. Источники (все опциональные, все объединенные):

- `apiKeyInfo.disabledGuardrails`
- Тело запроса `disabledGuardrails` (верхний уровень)
- Тело запроса `metadata.disabledGuardrails`
- Заголовок `x-omniroute-disabled-guardrails` (или устаревший
  `x-disabled-guardrails`)

Значения могут быть массивами строк или строкой, разделенной запятыми; имена
нормализуются в нижний регистр kebab-case (`pii_masker` → `pii-masker`). Результат
передается через `context.disabledGuardrails` в реестр, который пропускает
соответствующие защитные механизмы (`skipped: true` в `results`).

## Порядок выполнения

Для каждого запроса, проходящего через `src/sse/handlers/chat.ts` и
`open-sse/handlers/chatCore.ts`:

1.  `resolveDisabledGuardrails(...)` формирует список исключений из ключа API, тела запроса
    и заголовков.
2.  `guardrailRegistry.runPreCallHooks(body, ctx)` запускает защитные механизмы в порядке
    возрастания приоритета:
    - Отключенные защитные механизмы записываются как `skipped`.
    - Метод `preCall` каждого защитного механизма может переписывать полезную нагрузку через `modifiedPayload`.
    - Первый `block: true` прерывает цепочку, и обработчик возвращает
      ответ об отклонении защитным механизмом.
3.  (Потенциально переписанная) полезная нагрузка поступает в комбинированную маршрутизацию и
    диспетчеризацию вышестоящему сервису.
4.  После сборки ответа `guardrailRegistry.runPostCallHooks(...)`
    запускает ту же цепочку для ответа. `block: true` здесь отбрасывает
    ответ вышестоящего сервиса.

Защитные механизмы, которые выбрасывают исключения, записываются с `error: <message>` и
логируются через `logger.warn`, но цепочка продолжается — по замыслу, система
открыта к сбоям.

## Конфигурация

Переменные окружения, считываемые встроенными защитными механизмами:

| Переменная                            | Используется                  | Эффект                                                                                                                 |
| :------------------------------------ | :---------------------------- | :--------------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`            | Установите `false`, чтобы полностью отключить обнаружение.                                                             |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`            | Политика инъекций: `warn`, `block` или `log`. Устаревшее значение `redact` не переписывает текст инъекции.             |
| `INJECTION_GUARD_MODE`                | `prompt-injection`            | Режим для защиты от инъекций; также флаг функции БД, который **переопределяет** переменные окружения (БД > ОКРУЖЕНИЕ). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`            | Минимальная серьезность, при которой `MODE=block` отклоняет: `high` (по умолчанию), `medium` или `low`.                |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`            | Устаревший псевдоним для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                            |
| `PII_REDACTION_ENABLED`               | `pii-masker`                  | Если `true`, PII запроса скрывается (независимо от режима инъекции).                                                   |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ниже по потоку) | Управляет поведением маскировщика на стороне ответа.                                                                   |

Защитные механизмы Modality Bridge считывают конфигурацию времени выполнения из хранилища настроек,
поддерживаемого БД (`getSettings()`), а не из переменных окружения. Основные ключи Vision:
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` и
`modalityBridgeCacheMaxEntries`. Устаревшие ключи
`visionBridge*` принимаются только в качестве документированного одноциклового
резервного чтения; записи с панели управления используют основные ключи. Значения по умолчанию и
резервный резолвер находятся в `src/shared/constants/modalityBridgeDefaults.ts`,
при этом устаревшие константы сохранены в `src/shared/constants/visionBridgeDefaults.ts`.

Аудио использует `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` и `modalityBridgeAudioMaxClips`, а также общие
настройки `modalityBridgeCache*`. У Аудио нет резервного варианта для устаревших ключей,
поскольку эти ключи были введены со схемой Modality Bridge.

Видео использует `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` и
`modalityBridgeVideoTimeout`, а также общие настройки `modalityBridgeCache*`.
По умолчанию оно отключено, поскольку FFmpeg/ffprobe являются необязательными
операционными зависимостями, а создание подписей к кадрам увеличивает задержку и
стоимость модели.

## Пользовательские Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Шаги:

1.  Создайте `src/lib/guardrails/myGuardrail.ts`, расширяющий `BaseGuardrail`.
2.  Реализуйте `preCall` и/или `postCall`.
3.  Либо зарегистрируйте во время импорта (push из `registerDefaultGuardrails`), либо
    вызовите `guardrailRegistry.register(...)` во время выполнения — реестр заменяет
    любой предыдущий guardrail с тем же нормализованным именем.
4.  Добавьте тесты в `tests/unit/` (существующие примеры:
    `tests/unit/guardrails-registry.test.ts`,
    `tests/unit/prompt-injection-guard.test.ts`,
    `tests/unit/guardrails/visionBridge.test.ts`).

## Тестирование

Используйте `resetGuardrailsForTests()` между тестами, чтобы начать с известного состояния.
Передайте `{ registerDefaults: false }`, чтобы начать с пустого реестра и
зарегистрировать только тестируемые guardrails. Vision Bridge принимает внедрение зависимостей
(`deps.getSettings`, `deps.callVisionModel`); Audio Bridge предоставляет эквивалентные точки расширения
для настроек, возможностей, выбора модели STT, проверки учетных данных и транскрипции.
Таким образом, тесты могут проверять оба потока без доступа к БД или сети.

## Покрытие маршрутов защитой от инъекций и red-team (Фаза 8 · Блок D)

Защита от инъекций (`createInjectionGuard` / `withInjectionGuard`) охватывает все маршруты,
которые принимают пользовательские промпты. Она учитывает `INJECTION_GUARD_MODE` (по умолчанию `warn` = только логирование;
`block` = возвращает HTTP 400 `SECURITY_001`).

| Тип                  | Маршруты                                                                                                                                             | Режим по умолчанию |
| :------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------- |
| Текст (существующий) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn               |
| Генеративный         | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn               |
| Данные               | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn               |

Извлечение текста (`extractMessageContents`) охватывает `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Red-team (ночной, `nightly-llm-security.yml`):** promptfoo проверяет, что каждый маршрут блокирует
корпус OWASP-LLM в режиме `INJECTION_GUARD_MODE=block`; garak запускает зонды (пропускает без секрета).
`moderations` включен для согласованности — операторы в режиме блокировки могут исключить его через
`resolveDisabledGuardrails`.

Ночной рабочий процесс (`.github/workflows/nightly-llm-security.yml`, cron + ручной
запуск) состоит из двух задач:

- **`promptfoo-guard` (блокирующий)** — запускает `promptfoo eval -c promptfooconfig.yaml`
  с `INJECTION_GUARD_MODE=block`. Каждый adversarial-кейс (например, "игнорировать все
  предыдущие инструкции...", джейлбрейки в стиле DAN) подтверждает, что ответ содержит
  `error.code === "SECURITY_001"`, то есть защита фактически отклонила запрос.
- **`garak` (консультативный)** — запускает garak `--probes promptinject,dan,leakreplay`
  против локального экземпляра OmniRoute (`http://localhost:20128/v1`). Ограничен
  секретом провайдера (`PROMPTFOO_PROVIDER_KEY`); корректно пропускается и имеет суффикс
  `|| true`, поэтому он сообщает о результатах, не приводя к сбою CI.

Покрытие вспомогательной функции защиты (`createInjectionGuard` / `withInjectionGuard`)
охватывает каждый маршрут `/v1`, содержащий промпты; текст промпта извлекается из
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` с помощью
`extractMessageContents()` в `src/shared/utils/inputSanitizer.ts`.
