> **સત્યનો અધિકૃત સ્રોત:** `src/lib/guardrails/`
> **છેલ્લે અપડેટ કરેલું:** 2026-08-29 — v3.8.51 (Video Bridge ટ્રાન્સક્રિપ્ટનું મૂળ કૉલર દ્વારા જાહેર કરવામાં આવે છે,
> હજી સર્વર દ્વારા ચકાસાયેલું નથી — #11661 અનુસાર સ્પષ્ટ કરવામાં આવ્યું)

Guardrails, OmniRoute અને અપસ્ટ્રીમ પ્રદાતાઓ વચ્ચેની સીમા પર સુરક્ષા, નીતિ અને કન્ટેન્ટ રૂપાંતરણો લાગુ કરે છે. દરેક guardrail વિનંતીના payloads (`preCall`) અને અપસ્ટ્રીમ પ્રતિસાદો (`postCall`)નું નિરીક્ષણ કરી શકે છે (અને વૈકલ્પિક રીતે તેમને નકારી, રૂપાંતરિત અથવા ઍનોટેટ કરી શકે છે).

સિસ્ટમ **fail-open** છે: જો કોઈ guardrail કાર્યરત હોય ત્યારે અપવાદ ફેંકે, તો registry ભૂલ નોંધે છે અને વિનંતીને નિષ્ફળ કરવાને બદલે આગામી guardrail સાથે ચાલુ રહે છે. બ્લૉક કરવું હંમેશાં સ્પષ્ટ નિર્ણય (`block: true`) હોય છે, ક્યારેય આકસ્મિક ઘટના નહીં.

## બિલ્ટ-ઇન ગાર્ડરેલ્સ

રજિસ્ટ્રીને ઇમ્પોર્ટ કરવામાં આવે ત્યારે તે પ્રાથમિકતા ક્રમમાં છ ગાર્ડરેલ્સને આપમેળે લોડ કરે છે
(`registry.ts` → `registerDefaultGuardrails()` જુઓ):

| પ્રાથમિકતા | નામ                 | તબક્કો(ઓ)      | ફાઇલ                  |
| ---------- | ------------------- | -------------- | --------------------- |
| `5`        | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`        | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`        | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`       | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`       | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`       | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

ઓછી પ્રાથમિકતા સંખ્યાઓ **પહેલા** ચાલે છે.

### વિઝન બ્રિજ (`visionBridge.ts`) — મોડાલિટી બ્રિજ PR-1

**નોન-વિઝન મોડલ્સ** માટેના ઇમેજ ધરાવતા રિક્વેસ્ટ્સને ઇન્ટરસેપ્ટ કરે છે અને કાં તો
સમગ્ર રિક્વેસ્ટને વિઝન-સક્ષમ મોડલ તરફ ફરી રૂટ કરે છે અથવા અપસ્ટ્રીમ કૉલ પહેલાં
ઇમેજ ભાગોને કૉન્ફિગર કરી શકાય તેવા વિઝન મોડલ દ્વારા બનાવવામાં આવેલા ટેક્સ્ટ વર્ણનો
સાથે બદલે છે. આનાથી માત્ર ટેક્સ્ટ સપોર્ટ કરતા પ્રોવાઇડર્સ મલ્ટિમોડલ પેલોડ્સને
પારદર્શક રીતે હેન્ડલ કરી શકે છે.

પ્રવાહ:

1. જો લક્ષ્ય મોડલ પહેલેથી જ વિઝનને સપોર્ટ કરતું હોય, તો તેને સ્કિપ કરો (સિવાય કે તે
   ફરજિયાત-બ્રિજ યાદી `isVisionBridgeForcedModel`માં હોય).
2. `extractImageParts(messages)` મારફતે ઇમેજ ભાગો એક્સ્ટ્રેક્ટ કરો
   (`visionBridgeHelpers.ts`), જે `open-sse/utils/mediaParts.ts`માં રહેલા
   **એકીકૃત મીડિયા ડિટેક્ટર** `detectMediaParts()`ને કાર્ય સોંપે છે — આ
   કૉમ્બો સુસંગતતા ફિલ્ટર સાથે શેર થતો સત્યનો એકમાત્ર સ્રોત છે.
   એક્સ્ટ્રેક્શન એવા ટોપ-લેવલ ભાગોના આકારો સુધી allowlist કરેલું છે જેને
   `replaceImageParts` પાછા સ્પ્લાઇસ કરી શકે છે (extract↔replace કરાર): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, અને Responses API `input_image`. નેસ્ટેડ મેચો અને
   માત્ર-સૂચક આકારો કૉમ્બો-ફિલ્ટર માટેની સામગ્રી છે અને ક્યારેય એક્સ્ટ્રેક્ટ થતા નથી.
   જો કંઈ ન મળે તો સ્કિપ કરો.
3. `resolveVisionBridgeRuntimeSettings()` મારફતે રનટાઇમ કૉન્ફિગ ઉકેલો
   (`src/shared/constants/modalityBridgeDefaults.ts`): નવી `modalityBridge*`
   સેટિંગ્સ કીઝને પ્રાથમિકતા મળે છે; જૂની `visionBridge*` કીઝ **એક-સાઇકલ
   ફૉલબૅક** (રોલબૅક વિન્ડો) તરીકે રહે છે. જ્યારે બ્રિજ ડિસેબલ હોય ત્યારે કોઈપણ
   મીડિયા ટ્રાવર્સલ પહેલાં સ્કિપ કરો.
4. મોડ સિલેક્ટર (`modalityBridgeVisionMode`, નીચેનું કોષ્ટક જુઓ) ફરી રૂટ કરવું
   કે વર્ણન કરવું તે નક્કી કરે છે. રિરાઉટ માત્ર `model` સ્વૅપ કરીને
   `modifiedPayload` તથા meta `{ rerouted, fromModel, toModel, imagesKept }`
   પરત કરે છે.
5. વર્ણન પાથ: ઇમેજોની સંખ્યા `maxImages` સુધી મર્યાદિત કરો, કાર્ય-સજાગ પ્રોમ્પ્ટ
   તૈયાર કરો, વર્ણન કૅશ તપાસો, વિઝન મોડલને **સમાંતરમાં** કૉલ કરો
   (`Promise.allSettled`), અને ઇમેજોના સ્થાને `[Image N]: <description>` ટેક્સ્ટ
   ભાગો ઇન્જેક્ટ કરો. નિષ્ફળ વર્ણન `null` આપે છે અને મૂળ ઇમેજ ભાગ
   **જાળવી રાખવામાં આવે છે** (#4012) — સિવાય કે કૉમ્બો વર્ણન પાથ પર દરેક
   વર્ણન નિષ્ફળ ગયું હોય; તે સ્થિતિમાં પુષ્ટિ થયેલા નોન-વિઝન અપસ્ટ્રીમને તેના
   બદલે `(અનુપલબ્ધ — કોઈ વિઝન-સક્ષમ પ્રોવાઇડર કનેક્ટેડ નથી)` સ્ટબ મળે છે (#8430).
6. `modifiedPayload` + meta (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) પરત કરો.

#### મોડ સિલેક્ટર (`modalityBridgeVisionMode`)

| મોડ        | ડિફૉલ્ટ | વર્તન                                                                                                                                                                                                                                                                                                                |
| ---------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔       | લેગસી હ્યુરિસ્ટિક, અપરિવર્તિત (#6640/#7204): જો મૂળ મોડલ પાસે પહેલેથી ઉપયોગ કરી શકાય તેવા ક્રેડેન્શિયલ્સ ન હોય, તો નોન-કૉમ્બો/`auto/` મોડલ્સ શ્રેષ્ઠ વિઝન મોડલ તરફ ફરી રૂટ થાય છે (ક્રેડેન્શિયલ્સ હોય તો વર્ણન કરે છે); કૉમ્બો લક્ષ્યો હંમેશાં વર્ણન કરે છે.                                                         |
| `describe` |         | હંમેશાં વર્ણન કરો — રિરાઉટ બ્લૉક સંપૂર્ણપણે સ્કિપ થાય છે; વપરાશકર્તાએ પસંદ કરેલું મોડલ હંમેશાં જવાબ આપે છે.                                                                                                                                                                                                          |
| `reroute`  |         | રિરાઉટ ફરજિયાત કરો: ક્રેડેન્શિયલ ધરાવતું મોડલ જાળવી રાખવાનો ગાર્ડ બાયપાસ થાય છે. રિરાઉટ-**લક્ષ્ય** ક્રેડેન્શિયલ ગાર્ડ હજી પણ લાગુ પડે છે — જ્યારે કોઈ ઉપયોગ કરી શકાય તેવું વિઝન લક્ષ્ય અસ્તિત્વમાં ન હોય, ત્યારે રિક્વેસ્ટ વર્ણન તરફ આગળ વધે છે જેથી કાચી ઇમેજો ક્યારેય માત્ર-ટેક્સ્ટ બૅકએન્ડ સુધી ન પહોંચે (#8430). |

ફરજિયાત મોડ્સ `auto` હ્યુરિસ્ટિક ચાલે તે **પહેલાં** જ શૉર્ટ-સર્કિટ થાય છે;
`auto`નું વર્તન PR-1 પહેલાના ગાર્ડરેલ સાથે બાઇટ-દર-બાઇટ સમાન છે.

#### API-કીનો વ્યાપ (`visionBridgeKeyScope.ts`)

જ્યારે કૉલરની API કી `allowedConnections`, ક્વોટા પૂલ્સ
(`allowedQuotas`) અથવા મોડલ્સ (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`)ને પ્રતિબંધિત કરે છે,
ત્યારે બ્રિજ માત્ર એવા રિરાઉટ અને વર્ણન મોડલ્સ પસંદ કરે છે જેનો ઉપયોગ કી કરી શકે,
અને એવા કનેક્શન્સ પર કરે છે જેનો ઉપયોગ કી કરી શકે. ત્યારબાદ વર્ણન કૉલ હંમેશાં
`x-omniroute-self-loop-key-id` હેડર સાથે OmniRoute સેલ્ફ-લૂપ મારફતે જાય છે,
જેથી પ્રાપ્ત કરતો ચેટ રિક્વેસ્ટ તે કીની કનેક્શન અને મોડલ નીતિને ફરીથી લાગુ કરે છે.
`enforceApiKeyPolicy()` એ હેડરને માત્ર સેલ્ફ-લૂપ bearer સાથે જ માન્ય રાખે છે,
તેથી તે માત્ર ઍક્સેસને વધુ મર્યાદિત કરી શકે છે, અને ઉકેલી ન શકાય તેવી idને
નકારવામાં આવે છે.

જો કી માટે કોઈ વિઝન મોડલની પરવાનગી ન હોય, તો વર્ણન પાથ બાજુએ થઈ જાય છે અને
રિક્વેસ્ટ કોઈ ફેરફાર વિના પસાર થાય છે, જે ડિસેબલ કરેલા ગાર્ડરેલ જેટલું જ
fail-open વર્તન છે (meta `{ skipped: true, reason: "no_permitted_vision_model" }`).
કી વિનાના રિક્વેસ્ટ્સ અને આવા પ્રતિબંધો વિનાની કીઝનું વર્તન પહેલાં જેવું જ રહે છે.

#### કાર્ય-સજાગ વર્ણન પ્રોમ્પ્ટ (`modalityBridgeVisionTaskAware`)

ડિફૉલ્ટ **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) મૂળભૂત
વર્ણન પ્રોમ્પ્ટમાં **છેલ્લા વપરાશકર્તા સંદેશા**નું લખાણ (500 અક્ષરો સુધી ટૂંકાવેલું)
ઉમેરે છે, જેથી વર્ણન વપરાશકર્તાએ ખરેખર જે પૂછ્યું છે તે તરફ દોરાય
(codex-vision-proxy પેટર્ન) અને વિઝન મોડેલને દૃશ્યમાન લખાણનું ટ્રાન્સક્રિપ્શન કરવા
કહે છે. ફ્લૅગ બંધ હોય — અથવા વપરાશકર્તાનું કોઈ લખાણ ન હોય — તો મૂળભૂત પ્રોમ્પ્ટ
કોઈ ફેરફાર વિના વપરાય છે.

વર્ણન સેલ્ફ-લૂપની પોતાની OpenAI-સુસંગત વિનંતી (`callVisionModelSingle()`
`visionBridgeHelpers.ts`માં) હંમેશાં `image_url.detail: "high"`ની વિનંતી કરે છે —
બિનશરતી રીતે, દરેક કૉલર/પ્રદાતા માટે, કોઈપણ ક્લાયન્ટ સંકેત પર આધારિત રાખ્યા વિના.
આ પ્રોમ્પ્ટ જે ટેક્સ્ટ-ટ્રાન્સક્રિપ્શન કાર્ય માટે કહે છે, તેના માટે ઓછી-વિગતવાળું
સેમ્પલિંગ OCRની ચોકસાઈ ઘટાડે છે, તેથી મૂળ ઇનબાઉન્ડ વિનંતીમાં ગમે તે વિગત સ્તર
વપરાયું હોય, વર્ણન કૉલ પોતે હંમેશાં ઉચ્ચ વિગતની વિનંતી કરે છે. આ માત્ર આંતરિક
વર્ણન વિનંતીના બૉડીને અસર કરે છે; પ્રાથમિક વિનંતી પર OmniRoute કૉલરના પોતાના
`image_url.detail`ને કેવી રીતે ફોરવર્ડ કરે છે તે બદલાતું નથી — તે ડિફૉલ્ટ અલગથી
લાગુ થાય છે, અને માત્ર શોધાયેલા OpenCode ક્લાયન્ટ્સ માટે,
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`)માં.
વર્ણન સેલ્ફ-લૂપની Anthropic વાયર-ફૉર્મેટ શાખામાં કોઈ `detail` ફીલ્ડ નથી અને
બંનેમાંથી કોઈપણ ડિફૉલ્ટથી તે પ્રભાવિત થતી નથી.

#### વર્ણન આઉટપુટ મર્યાદા (`modalityBridgeVisionMaxChars`)

| કી                             | ડિફૉલ્ટ | શ્રેણી             |
| ------------------------------ | ------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`     | `0` અથવા 100–50000 |

`0` (ડિફૉલ્ટ)નો અર્થ **કોઈ મર્યાદા નહીં** — `callVisionModel()` દ્વારા પરત કરાયેલું
વર્ણન કોઈ ફેરફાર વિના આગળ મોકલાય છે, જેથી હાલનું વર્તન જળવાય છે. 100–50000ની
શ્રેણીમાંનું કોઈપણ મૂલ્ય, વર્ણનને `[Image N]: <description>` તરીકે પાછું જોડવામાં
આવે તે પહેલાં `…` પ્રત્યય સાથે ટૂંકાવે છે
(`VisionBridgeGuardrail.preCall()` `src/lib/guardrails/visionBridge.ts`માં).
વિગત-સઘન OCR કાર્યોમાં, જ્યાં ડાઉનસ્ટ્રીમ મોડેલને સંપૂર્ણ ટ્રાન્સક્રિપ્શનની જરૂર
હોય, ત્યાં આ મૂલ્ય વધારો; વધુ વાતોડિયા વિઝન મોડેલ્સના ટોકન વપરાશને મર્યાદિત કરવા
તે ઘટાડો. ડૅશબોર્ડ ફીલ્ડ Vision ટૅબની Advanced પૅનલમાં છે
(`modality-bridge-max-chars` `ModalityBridgeVisionTab.tsx`માં) અને 1થી 99 વચ્ચેના
કોઈપણ મૂલ્યને 100ની લઘુતમ મર્યાદા સુધી વધારી દે છે, જ્યારે સ્પષ્ટ `0`ને અસ્પર્શિત
રાખે છે — `0` માત્ર "સેટ ન કરેલું" ડિફૉલ્ટ નથી, પરંતુ પોતાની રીતે માન્ય Zod મૂલ્ય છે
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`).

#### વર્ણન કૅશ (`modalityBridge/bridgeCache.ts`)

વર્ણન આઉટપુટ્સ માટે ઇન-મેમરી LRU + TTL કૅશ, સમગ્ર પ્રોસેસમાં સહિયારું.
કી = `sha256(imageRef + composedPrompt + configuredBridgeModel)` સાથે
લેન્થ-પ્રીફિક્સ ફ્રેમિંગ (ફીલ્ડની સીમાઓ વચ્ચે કોઈ અથડામણ નહીં). મોડેલ ઘટક
**કન્ફિગર કરેલું** બ્રિજ મોડેલ છે, વાસ્તવમાં જવાબ આપનાર મોડેલ નહીં —
`callVisionModel` આંતરિક રીતે ફૉલબૅક કરી શકે છે અને દરેક પ્રયાસ પ્રમાણે કી બનાવવાથી
કૅશ વિખંડિત થઈ જાય. નિષ્ફળ વર્ણનો ક્યારેય કૅશ થતા નથી. સેટિંગ્સ:

| કી                              | ડિફૉલ્ટ | શ્રેણી  |
| ------------------------------- | ------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`  | —       |
| `modalityBridgeCacheTtlMinutes` | `60`    | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`   | 10–5000 |

#### રિમોટ ઇમેજ સામાન્યીકરણ (સેલ્ફ-લૂપ વર્ણન/base64 ફેચ)

જ્યારે બ્રિજ પોતે **રિમોટ** ઇમેજ ફેચ કરે છે — Anthropic વર્ણન સેલ્ફ-કૉલ અને
claude-વાયર-ફૉર્મેટ base64 રૂપાંતરણ (`ensureBase64ImagesForClaudeWire`), બંને
`visionBridgeHelpers.ts`માંના `fetchRemoteImageAsDataUri()` મારફતે — ત્યારે
પરિણામી ડેટા URIને વિઝન-મોડેલ વિનંતીમાં એમ્બેડ કરતા પહેલાં
`normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`)માંથી પસાર કરવામાં આવે છે.
મર્યાદાથી મોટી ઇમેજને **2048px લાંબી ધાર** સુધી ડાઉનસ્કેલ કરવામાં આવે છે (OpenAI/Anthropic
પહેલેથી સર્વર-સાઇડ પર લાગુ કરે છે તે રીસાઇઝ મર્યાદાને અનુરૂપ), જે વિઝન મોડેલ શું
જુએ છે તેમાં ફેરફાર કર્યા વિના અપલોડ બાઇટ્સ/લેટન્સી ઘટાડે છે. રીસાઇઝિંગ `sharp`નો
ઉપયોગ કરે છે, જે ડાયનામિક ઇમ્પોર્ટ દ્વારા લોડ થાય છે: જે પ્લૅટફૉર્મ પર તેનું નેટિવ
બાઇનરી લોડ થવામાં નિષ્ફળ જાય, ત્યાં `normalizeDataUri()` **ક્યારેય થ્રો કરતું નથી**
— તે મૂળ બાઇટ્સને યથાવત્ પસાર કરવાના ફૉલબૅક પર જાય છે, જેથી વર્ણન/base64-રૂપાંતરણ
પાથ હંમેશાં કાર્યરત રહે છે. બિન-ઇમેજ બાઇટ્સ (એવો ફેચ જેણે ડિકોડ કરી શકાય તેવી ઇમેજ
પરત ન કરી હોય) પણ અસ્પર્શિત રીતે પસાર થાય છે. આ સામાન્યીકરણ ફક્ત બ્રિજ પોતાના
સેલ્ફ-કૉલ માટે ફેચ કરે છે તે ઇમેજ સુધી મર્યાદિત છે — તે કૉલરના કાચા પાસથ્રૂ પેલોડ
પર ક્યારેય લાગુ થતું નથી, જે ફક્ત સ્પષ્ટ પસંદગી હોય ત્યારે જ ફેરફાર કરવાના સિદ્ધાંત
(Hard Rule #20) સાથે સુસંગત છે.

#### પારદર્શિતા હેડર + આંકડા

વર્ણન દ્વારા રૂપાંતરિત પ્રતિસાદોમાં
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
હોય છે (`modalityBridge/bridgeStats.ts`માં `buildModalityBridgeHeader()` દ્વારા
બનાવેલું, `src/sse/handlers/chatHelpers.ts`માં `withModalityBridgeHeader()` દ્વારા
સ્ટૅમ્પ કરેલું). રીરાઉટ કરેલી વિનંતીઓને **કોઈ** હેડર મળતું નથી — પેલોડ અસ્પર્શિત
હતું અને મોડેલની અદલાબદલી પ્રતિસાદ બૉડીના `model` ફીલ્ડમાં પહેલેથી જ દૃશ્યમાન છે.

`GET /api/modality-bridge/stats` (મેનેજમેન્ટ ઑથ, `GET /api/settings` જેવું જ સ્તર)
`vision`, `audio`, અને `video` માટે ઇન-મેમરી પ્રતિ-મોડાલિટી કાઉન્ટર્સ
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` પરત કરે છે. `averageLatencyMs` તેના
છેદ તરીકે બધા attemptsનો નહીં, પરંતુ `latencySamples`નો ઉપયોગ કરે છે; ટાઇમિંગ
વિનાનું ઑપરેશન શૂન્ય-મિલિસેકન્ડનો નકલી સેમ્પલ બનાવતું નથી. `bridged` સફળ
રૂપાંતરો માટે બૅકવર્ડ-કમ્પેટિબલ ઉપનામ તરીકે રહે છે; નિષ્ફળ attempts તેને
વધારતા નથી.
ડિઝાઇન મુજબ પ્રોસેસ રીસ્ટાર્ટ થતાં કાઉન્ટર્સ રીસેટ થાય છે
(ટેલિમેટ્રી, હિસાબ-કિતાબ નહીં).

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

ઑડિયો ધરાવતી ચૅટ રિક્વેસ્ટ્સ એવા ટાર્ગેટ સુધી પહોંચે તે પહેલાં ઇન્ટરસેપ્ટ કરે છે,
જે ઑડિયો ઇનપુટ સ્વીકારવા માટે જાણીતું નથી. તે ચૅટ રિક્વેસ્ટને ક્યારેય ફરીથી રૂટ
કરતું નથી: ઑડિયો પાર્ટ્સ હાલના OpenAI-કમ્પેટિબલ મલ્ટિપાર્ટ એન્ડપોઇન્ટ મારફતે
ટ્રાન્સક્રાઇબ થાય છે અને પસંદ કરેલું ચૅટ મૉડલ ટેક્સ્ટ ટ્રાન્સક્રિપ્ટ્સ સાથે ચાલુ રહે છે.

પ્રવાહ:

1. `getResolvedModelCapabilities()` મારફતે `supportsAudio` રિઝૉલ્વ કરો. સ્પષ્ટ
   provider-registry મેટાડેટાને પ્રાથમિકતા મળે છે, ત્યારબાદ સ્ટેટિક મૉડલ મેટાડેટા અને પછી
   સિંક કરેલું `modalities_input`. `audio` વિનાની જાહેર કરેલી ઇનપુટ સૂચિનું મૂલ્ય
   `false` છે; કોઈ ક્ષમતા પુરાવો ન હોય તો મૂલ્ય `null` રહે છે. `false` અને `null`
   બંને કન્ઝર્વેટિવ બ્રિજને સક્રિય કરે છે, જ્યારે `true` તેને બાયપાસ કરે છે.
2. `modalityBridgeAudio*` સેટિંગ્સ રિઝૉલ્વ કરો અને શેર કરેલા `detectMediaParts()`
   ડિટેક્ટર મારફતે દરેક મેસેજમાંથી સ્પ્લાઇસ કરી શકાય તેવા ટૉપ-લેવલ ઑડિયો પાર્ટ્સ
   એક્સટ્રેક્ટ કરો. સપોર્ટેડ વાયર શેપ્સ OpenAI `input_audio`, `audio_url`, અને
   `source.media_type: "audio/*"` છે. નેસ્ટેડ ઑડિયો રૂટિંગ માટે શોધાય છે, પરંતુ
   સ્પ્લાઇસ પાથ દ્વારા દૂર થતો નથી. કાર્ય `modalityBridgeAudioMaxClips` દ્વારા
   મર્યાદિત છે; ત્યારપછીના પાર્ટ્સ અપરિવર્તિત રહે છે.
3. કૉન્ફિગર કરેલા `provider/model`ને માન આપો, અથવા `selectAudioBridgeModel()`ને
   સ્થિર કૅટલૉગ ક્રમમાં `AUDIO_TRANSCRIPTION_PROVIDERS`માંથી પસાર થઈને ઉપયોગી
   સક્રિય પ્રોવાઇડર ક્રેડેન્શિયલ ધરાવતું પ્રથમ મૉડલ પસંદ કરવા દો.
4. `callAudioTranscription()` base64/data-URI ઑડિયોને મલ્ટિપાર્ટ `file`માં
   રૂપાંતરિત કરે છે, અથવા DNS પિનિંગ અને 25 MB મર્યાદા ધરાવતા માત્ર-પબ્લિક
   આઉટબાઉન્ડ ગાર્ડ મારફતે રિમોટ `audio_url` ડાઉનલોડ કરે છે. ત્યારબાદ તે ફાઇલ અને
   પસંદ કરેલા મૉડલને લોકલ `/v1/audio/transcriptions` સેલ્ફ-લૂપ પર POST કરે છે,
   જે `resolveSelfLoopBearer()` વડે ઑથેન્ટિકેટ થયેલું હોય છે. હાલનો
   ટ્રાન્સક્રિપ્શન રૂટ સામાન્ય ક્રેડેન્શિયલ લુકઅપ, કૂલડાઉન/રેટ-લિમિટ હૅન્ડલિંગ અને
   પ્રોવાઇડર ડિસ્પૅચ કરે છે.
5. સફળ કૉલ્સ તેમના પાર્ટ્સને `[Audio N]: <transcript>`થી બદલે છે. કૉલ્સ
   `Promise.allSettled` વડે ચાલે છે: કોઈ વ્યક્તિગત નિષ્ફળતા મૂળ ઑડિયો પાર્ટને
   જાળવી રાખે છે (#4012 કૉન્ટ્રેક્ટ). જો દરેક કૉલ નિષ્ફળ જાય અને ટાર્ગેટ માટે
   `supportsAudio === false` સાબિત થયેલું હોય, તો પાર્ટ્સ
   `[Audio N]: (unavailable — no STT provider connected)` બને છે (#8430 કૉન્ટ્રેક્ટ).
   અજ્ઞાત ટાર્ગેટ (`null`) માટે, બધી કૉલ્સની નિષ્ફળતાનું પરિણામ અપરિવર્તિત રહે છે.
   કોઈ ઉપયોગી STT ક્રેડેન્શિયલ ન ધરાવતા સાબિત થયેલા માત્ર-ટેક્સ્ટ ટાર્ગેટને નેટવર્ક
   કૉલ કર્યા વિના એ જ સ્પષ્ટ સ્ટબ મળે છે.

સફળ ટ્રાન્સક્રિપ્ટ્સ પ્રોસેસ-વ્યાપી Modality Bridge LRU/TTL કૅશનો ઉપયોગ કરે છે.
કી ઑડિયો રેફરન્સ, સ્થિર `audio-transcription` ઑપરેશન લેબલ અને પસંદ કરેલા STT
મૉડલને જોડે છે; નિષ્ફળતાઓ ક્યારેય કૅશ થતી નથી. ઑડિયો attempts શેર કરેલા
`bridged`, `cacheHits`, `failures`, અને `lastUsedAt` કાઉન્ટર્સ અપડેટ કરે છે.
ટ્રાન્સફોર્મ થયેલા રિસ્પોન્સિસમાં
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` હોય છે;
અપરિવર્તિત રિક્વેસ્ટ્સને Audio Bridge સેગમેન્ટ મળતું નથી.

રનટાઇમ સેટિંગ્સ DB-બૅક્ડ અને Zod-વૅલિડેટેડ છે:

| ----------------------------- | ------- | -------------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —                    |
| `modalityBridgeAudioModel`    | `""`    | સ્વચાલિત અથવા STT ID |

| `modalityBridgeAudioMaxClips` | `3`     | 1–10                 |

સહિયારા કૅશનું નિયંત્રણ હજી પણ `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, અને `modalityBridgeCacheMaxEntries` દ્વારા થાય છે.

### વિડિયો બ્રિજ (`videoBridge.ts`, `videoBridgePipeline.ts`)

જાણીતી મૂળભૂત વિડિયો સપોર્ટ ક્ષમતા વિનાના લક્ષ્યને કૉલ કરવામાં આવે તે પહેલાં, Chat Completionsના `messages` અને Responses
APIના `input`માં ટોચના સ્તરના વિડિયો ભાગોને આંતરે છે.
સપોર્ટેડ સ્વરૂપો `input_video`, `video_url`, `video_source`, HTTPS URLs,
અને `data:video/*;base64,...` ડેટા URIs છે. ટેક્સ્ટમાં આપેલાં સાદાં ફાઇલનામોને
વિડિયો તરીકે ગણવામાં આવતાં નથી.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) વિનંતીનું ટ્રાવર્સલ,
ક્ષમતા/નીતિની તપાસ, પ્રતિ-વિનંતી એકત્રીકરણ અને પ્રતિસાદ પેલોડનું સંચાલન કરે છે.
પ્રતિ-વિડિયો કાર્ય — પ્રાપ્તિકરણ, સંપૂર્ણ-પરિણામ કૅશ, ફ્રેમ
ક્રમનું વર્ણન કરવું (જે કૉલર દ્વારા જાહેર કરાયેલા કોઈપણ ઑડિયો ટ્રાન્સક્રિપ્ટને સંયોજિત કરે છે), અને પ્રતિ-પ્રયાસ
મેટ્રિક્સ/રદ્દીકરણ/સફાઈ — `videoBridgePipeline.ts`માં `processVideoPart`ની પાછળ
છુપાયેલું છે, જેને `preCall`ના લૂપમાં દરેક વિડિયો ભાગ માટે એક વખત કૉલ કરવામાં આવે છે.
તે મોડ્યુલ સ્પષ્ટ પોર્ટ સીમાઓ `VideoMediaBrokerPort`
(બાઇટ્સ પ્રાપ્ત કરવી અને નમૂનારૂપ ફ્રેમ્સ કાઢવી), `VideoAudioTranscriptionPort`
(કૉલર દ્વારા જાહેર કરાયેલા ઑડિયો ટ્રાન્સક્રિપ્ટને નમૂનારૂપ કૅપ્શન્સ સાથે સંયોજિત કરવું), અને
`VideoDrilldownPort` (ફ્રેમ ડ્રિલ-ડાઉન સ્થાયિત્વ સીમા; હજી
`processVideoPart` સાથે જોડાયેલ નથી — હાલમાં માત્ર અલગ `/api/modality-bridge/video/drilldown`
રૂટ ડ્રિલ-ડાઉન એન્ટ્રીઓ લખે છે) પણ વ્યાખ્યાયિત કરે છે.

#### FU-07 માળખાકીય સેગમેન્ટ પુરાવા

`segment_aware` પહેલેથી માન્ય કરાયેલા સ્થાનિક વિડિયો સ્ટ્રીમ પર એક મર્યાદિત પૂર્વ-વિશ્લેષણ પાસનો ઉપયોગ કરે છે. નિશ્ચિત ફિલ્ટર ચેઇન પહેલાં પહોળાઈને વધુમાં વધુ 320 પિક્સેલ સુધી સ્કેલ કરે છે, દૃશ્ય પરિવર્તનો અને સ્થિર અંતરાલો શોધે છે, અને પછી ધૂંધળાશ, સરેરાશ લ્યુમા તથા અવકાશી/કાલિક માહિતી માટે પ્રતિ સેકન્ડ 1 ફ્રેમનું સેમ્પલિંગ કરે છે. આ પાસ 600 માળખાકીય સેમ્પલ, એક FFmpeg/ફિલ્ટર થ્રેડ, સમાન માત્ર-`file` પ્રોટોકોલ અને કન્ટેનર અનુમતિ-સૂચિઓ, 1 MiB પ્રક્રિયા-આઉટપુટ મર્યાદા તથા બ્રોકરના વહેંચાયેલા રદકરણ/સમયમર્યાદાની અંદર વધુમાં વધુ 30 સેકન્ડ સુધી મર્યાદિત છે. તે વિનંતીમાંથી ક્યારેય કોઈ કમાન્ડ, ફિલ્ટર, પાથ અથવા URL સ્વીકારતું નથી.

માળખાકીય મૂલ્યો નિર્ધારિત સેમ્પલિંગ પુરાવા છે, વિડિયોની અર્થસંબંધિત સમજ નથી. તેઓ વિષયો, ક્રિયાઓ, કૅપ્શનો, વાણી અથવા વપરાશકર્તાના હેતુનું અનુમાન કરતા નથી. દૃશ્ય અને ફ્રીઝ સીમાઓ સેગમેન્ટ બનાવે છે; ફ્રીઝ આવરણ, ધૂંધળાશ, એક્સપોઝર, અવકાશી વિગતો અને કાલિક પરિવર્તન માત્ર હાલના 1–16 ફ્રેમના બજેટની ફાળવણીને પ્રભાવિત કરે છે. સંપૂર્ણપણે સ્થિર સેગમેન્ટને વધુમાં વધુ એક ફ્રેમ મળે છે, જ્યારે સ્થિર ન હોય તેવા સેગમેન્ટ બાકી બજેટ માટે સ્પર્ધા કરે છે. જ્યારે સીમાઓની સંખ્યા ફ્રેમ કરતાં વધુ હોય, ત્યારે સમયરેખાનું સમાન આવરણ જાળવવામાં આવે છે જેથી શરૂઆતના ઝડપી કટ લાંબા અંતિમ સેગમેન્ટને છુપાવી ન શકે. ફ્રીઝ સીમાના 1-સેકન્ડના વિશ્લેષણ રિઝોલ્યુશનની અંદર આવેલી દૃશ્ય સીમાઓને એકત્રિત કરવામાં આવે છે.

પ્રમોશન પુરાવાને સિન્થેટિક કમ્પોઝિશન માઇક્રોબેન્ચમાર્કથી ઇરાદાપૂર્વક અલગ રાખવામાં આવે છે. `scripts/perf/video-bridge-contact-sheet-eval.ts` વાસ્તવિક OpenAI-સુસંગત વિઝન મોડલ માટે સ્કીમા-સંસ્કરણિત A/B હાર્નેસ વ્યાખ્યાયિત કરે છે. તે પ્રદાતા દ્વારા અહેવાલ કરાયેલા ટોકન, શરૂઆતથી અંત સુધીની વાસ્તવિક વિલંબતા (શીટ કમ્પોઝિશન સહિત), મોડલ-કૉલની સંખ્યા અને મેનિફેસ્ટ દ્વારા વ્યાખ્યાયિત તથ્યોની જાળવણી માપે છે. કાચા મોડલ પ્રતિસાદ અહેવાલમાં લખવામાં આવતા નથી; માત્ર SHA-256 ડાઇજેસ્ટ અને મેળ ખાતી તથ્ય ID જાળવવામાં આવે છે. જ્યાં સુધી `--execute-real` પાસ કરવામાં ન આવે અને `--model`, `OMNIROUTE_BASE_URL` તથા `OMNIROUTE_API_KEY` કૉન્ફિગર ન કરેલાં હોય, ત્યાં સુધી હાર્નેસ કોઈ નેટવર્ક અથવા ચૂકવણીવાળો મોડલ કૉલ કરતું નથી. આવી સ્પષ્ટ વાસ્તવિક રન વિના, તેનો મશીન-વાંચનીય ચુકાદો `HOLD` રહે છે; માત્ર સિન્થેટિક પેલોડ/કૉલ-સંખ્યા માપન પ્રમોશન પુરાવો નથી.

કૉલર, જ્યારે તેમની પાસે પહેલેથી જ સંરેખિત ટેક્સ્ટ હોય, ત્યારે સમર્થિત વિડિયો ભાગમાં વૈકલ્પિક `transcript.cues` ઍરે જોડી શકે છે. દરેક ક્યુમાં `text`, તપાસેલી અવધિની અંદરનો સીમિત `start`/`end` અંતરાલ અને અનુમતિ-સૂચિબદ્ધ `source` (`client`, `embedded` અથવા `audio-bridge`) હોવા આવશ્યક છે; `confidence`નું ડિફૉલ્ટ મૂલ્ય `1` છે અને તે `0`થી `1` વચ્ચે જ રહેવું જોઈએ. બરાબર સમાન ડુપ્લિકેટ ક્યુને એકત્રિત કરવામાં આવે છે. OmniRoute આ મેટાડેટામાંથી ક્યારેય ટ્રાન્સક્રિપ્શન શરૂ કરતું નથી: માન્ય કરાયેલા ક્યુને સ્રોત, વિશ્વાસ અને અંતરાલ સાથે વર્ણવેલા પરિણામમાં કૉપિ કરવામાં આવે છે અને ફ્રેમ કૅપ્શનની સાથે અવિશ્વસનીય અવલોકનો તરીકે રેન્ડર કરવામાં આવે છે. અમાન્ય, શ્રેણીની બહારનું અથવા મૂળ-સ્ત્રોત વિનાનું ટેક્સ્ટ કૅપ્શન સ્ટ્રીમમાં ભેળવવાને બદલે નકારવામાં આવે છે. બંને વિનંતી-બોડી ટ્રાન્સક્રિપ્ટ ચેનલો પૂરા પાડેલા મૂળ-સ્ત્રોતને `client` તરીકે નોર્મલાઇઝ કરે છે, જેમાં સ્વયં-દાવો કરાયેલા `embedded` અથવા `audio-bridge` લેબલ પણ સામેલ છે. માત્ર સર્વર-માલિકીનું ઍડેપ્ટર જ માત્ર-કોડ `trustedSource` આર્ગ્યુમેન્ટ મારફતે તે વિશ્વસનીય લેબલ સોંપી શકે છે; વિનંતીનું JSON ફીલ્ડ તે આર્ગ્યુમેન્ટ સુધી પહોંચી શકતું નથી. ટ્રાન્સક્રિપ્ટ ટેક્સ્ટ તેના મૂળ-સ્ત્રોતને ધ્યાનમાં લીધા વિના અવિશ્વસનીય મીડિયા-ઉદ્ભવિત સામગ્રી જ રહે છે અને તેણે ક્યારેય અધિકૃતતા નક્કી કરવી જોઈએ નહીં.

એક અદ્યતન કૉલર એ જ વિડિયો માટે `audioTranscript` ટ્રૅક આપી શકે છે;
તેને ક્લાયન્ટ દ્વારા અપાયેલ ટેક્સ્ટ તરીકે ગણવામાં આવે છે, સર્વર ટ્રાન્સક્રિપ્શનના પુરાવા તરીકે નહીં.
ફ્યુઝન સીમ એક જ સમયમર્યાદા અને રદબાતલ સિગ્નલ હેઠળ વિઝ્યુઅલ અને ઑડિયો અવલોકનો ચલાવે છે,
તેમને એક સામાન્ય સમયરેખા પર ક્રમબદ્ધ કરે છે, એકદમ સમાન નકલોને એકમાં સમાવે છે,
અને જ્યારે માત્ર એક બાજુ સફળ થાય ત્યારે આંશિક પરિણામની જાણ કરે છે.
અમાન્ય `audioTranscript` ને કારણે તે આંશિક પરિણામ સુધી મર્યાદિત થાય છે — વિઝ્યુઅલ
વર્ણન જાળવવામાં આવે છે અને ઑડિયો શાખા સ્વચ્છ કરેલો નિષ્ફળતા કોડ નોંધે છે —
સમગ્ર વિડિયોને નિષ્ફળ બનાવવાને બદલે. દરેક શાખાની ઉપલબ્ધતા, આંશિક ફ્લૅગ,
અને સ્વચ્છ કરેલા નિષ્ફળતા કોડ્સ વર્ણવેલા પરિણામમાં, ગાર્ડરેલ મેટાડેટામાં
(`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), પરિણામ-કૅશ મેટાડેટામાં અને બ્રિજ
ફ્યુઝન કાઉન્ટર્સમાં જાળવવામાં આવે છે. ડિફૉલ્ટ Video Bridge પાથ સ્પીચ-ટુ-ટેક્સ્ટનો
ઉપયોગ કરતો નથી અથવા મીડિયાની બીજી નકલ ડાઉનલોડ કરતો નથી; તે સ્પષ્ટ ટ્રૅક વિના,
તે માત્ર-વિડિયો જ રહે છે.

**કાચા વિડિયો ફીલ્ડ્સ (#12430).** જ્યારે બ્રિજ સક્ષમ હોય અને મૂળ વિડિયો સપોર્ટ અજ્ઞાત અથવા ગેરહાજર હોય, ત્યારે વ્યાખ્યાયિત `transcript`/`audioTranscript` ફીલ્ડ્સ પણ `videoBridgeObserved` સક્રિય કરે છે, વર્ણન નિષ્ફળતા અથવા `maxVideos` મર્યાદા પછી પણ. `null` અને ખાલી સ્ટ્રિંગ્સ ગણાય છે; ગેરહાજર ફીલ્ડ્સ અને બિન-વિડિયો મેટાડેટા ગણાતા નથી. જાળવેલી નકલો આ ફીલ્ડ્સને રિડેક્ટ કરે છે અથવા વિનંતી છોડી દે છે, અને કૅશ/Memoryને બાયપાસ કરવામાં આવે છે.

તે ફૉલબૅક પાથ્સ પર, માન્ય કૉલર ક્યૂઝ બિન-માનક પ્રોવાઇડર ફીલ્ડ્સને બદલે સપોર્ટેડ `text`/`input_text`

દર-ક્યૂ બજેટ બન્ને ટ્રૅક્સ પર સંયુક્ત રીતે લાગુ પડે છે;
ટાઇમસ્ટૅમ્પ્સ બ્રોકરની 600-સેકન્ડની મર્યાદા અને પૂરી પાડેલી કોઈપણ ફોકસ

કૅશ આઉટપુટને બદલતા દરેક ઇનપુટના આધારે કીબદ્ધ થાય છે — પ્રૉમ્પ્ટ, અસરકારક
મોડલ, સૅમ્પલિંગ પૉલિસી, ફ્રેમ ગણતરી, સિમેન્ટિક ઍનાલિસિસ મોડ, નૉર્મલાઇઝ કરાયેલ ફોકસ હિન્ટની SHA-256
ફિંગરપ્રિન્ટ, ફોકસ વિન્ડો, `transcript`,
`audioTranscript` અને કૉન્ટેક્ટ-શીટ ફ્લૅગ — તેથી આમાંથી કોઈ પણ
પરિમાણ બદલવાથી કૅશ મિસ થાય છે, જૂના પરિણામનો ફરી ઉપયોગ ક્યારેય થતો નથી. વિઝ્યુઅલ ડીડુપ પૉલિસી
વર્ઝન, થ્રેશોલ્ડ અને મર્યાદિત કૅન્ડિડેટ-ફ્રેમ ગણતરી પણ
રિઝલ્ટ-કૅશ કી અને મેટાડેટામાં સ્પષ્ટ છે; તેથી પૉલિસીમાં ફેરફાર જૂના
સંપૂર્ણ-વિડિયો વર્ણનનો ફરી ઉપયોગ કરી શકતો નથી. રિઝલ્ટ-કૅશ v4 મેટાડેટા મોડ અને
ફિંગરપ્રિન્ટ જાળવે છે, ક્યારેય કાચું યુઝર ટાસ્ક નહીં. ગાર્ડરેલ મેટાડેટા વિનંતી કરાયેલા અને અસરકારક—બંને
ઍનાલિસિસ મોડ રિપોર્ટ કરે છે; ઉપયોગી યુઝર ટેક્સ્ટ વિના વિનંતી કરાયેલ `focused` મોડ
અસરકારક રીતે `full` તરીકે રિપોર્ટ થાય છે.

ગાર્ડરેલ દરેક સપોર્ટેડ વિડિયો ભાગને એક્સ્ટ્રેક્ટ કરે છે, પરંતુ
`modalityBridgeVideoMaxVideos` કરતાં વધુનું વર્ણન કરતું નથી. જે ટાર્ગેટ માટે
`supportsVideo === false` હોવાનું સાબિત થયું હોય, તેમાં નિષ્ફળ અને મર્યાદા-પાર કરેલા વિડિયો સ્પષ્ટ સુરક્ષિત
ટેક્સ્ટ માર્કર બની જાય છે, જેથી કોઈ કાચો વિડિયો બાકી ન રહે. જ્યારે ક્ષમતા અજ્ઞાત હોય, ત્યારે તે ભાગો
પોતાનું વિડિયો કૅરિયર જાળવી રાખે છે; કોઈપણ ફૉલબૅક ટ્રાન્સક્રિપ્ટ ઉપરના મર્યાદિત ટેક્સ્ટ
રૂપાંતરણને અનુસરે છે. `supportsVideo === true` ધરાવતા ટાર્ગેટ બ્રિજને બાયપાસ કરે છે.
ક્લાયન્ટ રિક્વેસ્ટનું અબોર્ટ સિગ્નલ ડાઉનલોડ, બ્રોકર ક્યૂ,
સબપ્રોસેસ અને કૅપ્શન કૉલ્સ મારફતે પ્રસારિત થાય છે; અબોર્ટ વિડિયો વચ્ચે પ્રક્રિયા રોકે છે અને કાચા મીડિયાને ફેઇલ-ઓપન
થવા ક્યારેય દેતું નથી.

રનટાઇમ સેટિંગ્સ DB-બૅક્ડ અને Zod-માન્ય કરાયેલ છે:

| કી                                  | ડિફૉલ્ટ     | શ્રેણી / વર્તન                                                                                            |
| ----------------------------------- | ----------- | --------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | વૈકલ્પિક રનટાઇમ, પસંદગી દ્વારા સક્રિય                                                                     |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` સામાન્ય કૅપ્શન્સ જાળવે છે; `focused` મર્યાદિત, અવિશ્વસનીય નવીનતમ-વપરાશકર્તા સંદર્ભનો ઉપયોગ કરે છે  |
| `modalityBridgeVideoModel`          | `""`        | Vision Bridge મોડેલ વારસામાં મેળવે છે                                                                     |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                      |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware`, અથવા પ્રમાણસર `segment_aware`; ડિટેક્ટરની નિષ્ફળતા પર `uniform` પર પાછું જાય છે |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                       |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                                            |

120 સેકન્ડથી વધુની જૂની સંગ્રહિત Video સમયસમાપ્તિ કિંમતોને
બ્રોકરની સમયમર્યાદા સુધી મર્યાદિત કરવામાં આવે છે; આ મર્યાદાથી વધુની નવી સેટિંગ્સ લખવાની ક્રિયાઓ નકારવામાં આવે છે.
`GET /api/modality-bridge/video/runtime` ને પ્રમાણીકરણ અથવા રનટાઇમ તપાસ પહેલાં વિશ્વસનીય રીતે મુદ્રાંકિત લૂપબૅક
સ્થાનિકતાની જરૂર પડે છે, અને પછી મેનેજમેન્ટ
પ્રમાણીકરણની જરૂર પડે છે. તે ફક્ત `available`, શુદ્ધ કરેલા FFmpeg/ffprobe વર્ઝન્સ અને રનટાઇમ અનુપલબ્ધ હોય ત્યારે એક નિશ્ચિત
કારણ પરત કરે છે. આંતરિક એક્સ્ટ્રેક્શન એન્ડપોઇન્ટ
સાર્વજનિક અપલોડ API નથી: ક્યૂ સંતૃપ્તિ `503` સાથે `Retry-After` પરત કરે છે, કૉલરનું
ડિસ્કનેક્ટ થવું `499` પરત કરે છે, અને નિશ્ચિત બ્રોકર સમયમર્યાદા `504` પરત કરે છે. રૂપાંતરિત પ્રતિસાદો
Vision અથવા Audio સેગમેન્ટ્સ દૂર કર્યા વિના કેન્દ્રીય
`x-omniroute-modality-bridge` હેડરમાં `video->text;model=<visionModel>;parts=<videos>` ઉમેરે છે.

### PII માસ્કર (`piiMasker.ts`)

**બંને** તબક્કાઓ પર ચાલે છે.

- **`preCall`** પેલોડને ક્લોન કરે છે, `system`, `messages`, `input`, અને
  `prompt` (સાદી સ્ટ્રિંગ આઇટમ્સ સહિત)માંથી પસાર થાય છે, અને સ્ટ્રિંગ `content`/`text` ફીલ્ડ્સ પર
  `processPII()` (`@/shared/utils/inputSanitizer`માંથી) લાગુ કરે છે. જ્યારે
  `PII_REDACTION_ENABLED=true` હોય, ત્યારે શોધાયેલ PII ને આઉટબાઉન્ડ
  પેલોડમાં સંપાદિત કરવામાં આવે છે. આ `INPUT_SANITIZER_MODE`થી સ્વતંત્ર છે (જે ફક્ત
  પ્રોમ્પ્ટ-ઇન્જેક્શન નીતિને નિયંત્રિત કરે છે). જ્યારે સંપાદન બંધ હોય, ત્યારે કૉલ કન્ટેન્ટને ફરી લખ્યા વિના
  શોધની સંખ્યાઓ રેકોર્ડ કરે છે.
- **`postCall`** પ્રતિસાદને ડીપ-ક્લોન કરે છે, `sanitizePIIResponse()` ઉપરાંત
  Responses-API-આકારનું માસ્કર (`maskResponsesOutput` — જે
  `output_text` અને `output[].content[].text`ને આવરે છે) ચલાવે છે. જો કોઈ સંપાદન થાય, તો
  સંશોધિત પ્રતિસાદ મૂળ પ્રતિસાદને બદલે છે.

ગાર્ડરેલ ક્યારેય અવરોધતું નથી; તે ફક્ત એનોટેટ કરે છે (`meta.detections`,
`meta.redacted`) અથવા ફરી લખે છે.

#### પ્રકાર-દીઠ પસંદગી, કસ્ટમ પેટર્ન્સ અને શોધ કાઉન્ટર્સ

**Dashboard → Settings → Security → PII masking** _શું_ માસ્ક કરવામાં આવે છે તે પસંદ કરે છે. તે
માસ્કિંગ ચાલુ કરતું નથી: તેના માટે હજી પણ `PII_REDACTION_ENABLED` (વિનંતી) અને
`PII_RESPONSE_SANITIZATION` (પ્રતિસાદ + SSE) જવાબદાર છે, અને બંને ડિફૉલ્ટ રૂપે બંધ છે.

- **પ્રકાર-દીઠ પસંદગી** — બિલ્ટ-ઇન ids
  `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`)માં સૂચિબદ્ધ છે. સેટ ન કરેલું હોય તો તેનો અર્થ દરેક
  પ્રકાર થાય છે (આ સેટિંગ અસ્તિત્વમાં આવ્યું તે પહેલાંનું વર્તન). વિનંતી એન્જિનનું
  `ssn_us` પેટર્ન `ssn` સાથે મેપ થાય છે. ટેમ્પ્લેટ્સ (Minimal, Standard, Financial,
  Brazilian, USA, Full) ફક્ત UI માં ચેકબૉક્સ ભરે છે.
- **કસ્ટમ પેટર્ન્સ** — વધુમાં વધુ 20 regex અથવા વાઇલ્ડકાર્ડ પેટર્ન્સ (`*` = વધુમાં વધુ 64
  બિન-વ્હાઇટસ્પેસ અક્ષરો, `?` = એક). મેળ ખાતા ભાગો `[CUSTOM_REDACTED]` બને છે.
  દરેક પેટર્ન `compilePiiCustomPattern()`
  (`src/shared/utils/piiCustomPatterns.ts`)માંથી પસાર થાય છે: વધુમાં વધુ 500 અક્ષરો, ફ્લૅગ્સ
  `g i m s u` સુધી મર્યાદિત, કમ્પાઇલ થવું આવશ્યક, `safe-regex` (વિનાશક
  બૅકટ્રૅકિંગ) પાસ કરવું આવશ્યક, અને ખાલી સ્ટ્રિંગ અથવા સંપાદન પ્લેસહોલ્ડર સાથે મેળ ન ખાવો જોઈએ.
  નિષ્ફળ થતું પેટર્ન સાચવતી વખતે અને પરીક્ષણ કરતી વખતે નકારવામાં આવે છે, અને નિષ્ફળ થતી સંગ્રહિત પંક્તિને
  કમ્પાઇલ કરવાને બદલે રનટાઇમ સમયે છોડી દેવામાં આવે છે. કસ્ટમ પેટર્ન્સ ફક્ત
  માસ્કિંગ ચાલુ હોય ત્યારે ચાલે છે.
- **શોધ કાઉન્ટર્સ** — પ્રકાર-દીઠ સંખ્યાઓ (ક્યારેય મેળ ખાતી કિંમતો નહીં), મેમરીમાં
  રાખવામાં આવે છે અને રીસ્ટાર્ટ પર રીસેટ થાય છે (`src/lib/pii/piiDetectionStats.ts`). તે ફક્ત
  માસ્કિંગ ચાલુ હોય ત્યારે વધે છે.

સેટિંગ્સ `key_value` ટેબલમાં (નેમસ્પેસ `pii_settings`,
`src/lib/db/piiSettings.ts`) રહે છે અને 1 s કૅશ મારફતે વાંચવામાં આવે છે. API:

| પદ્ધતિ | પાથ                      | હેતુ                                                                     |
| ------ | ------------------------ | ------------------------------------------------------------------------ |
| `GET`  | `/api/settings/pii`      | ફ્લૅગની સ્થિતિ, `enabledTypes`, `customPatterns`, શોધ કાઉન્ટર્સ          |
| `PUT`  | `/api/settings/pii`      | `enabledTypes` (`null` = બધા) અને/અથવા `customPatterns`ને બદલો           |
| `POST` | `/api/settings/pii/test` | વધુમાં વધુ 8 KBના નમૂના સામે એક પેટર્નનો ડ્રાય-રન; કંઈ સંગ્રહિત થતું નથી |

ત્રણેયને મેનેજમેન્ટ પ્રમાણીકરણની જરૂર પડે છે અને Zod વડે બૉડીને માન્ય કરે છે
(`src/shared/validation/schemas/piiSettings.ts`).

### પ્રોમ્પ્ટ ઇન્જેક્શન (`promptInjection.ts`)

| સેટિંગ          | પર્યાવરણ ચલ                                                                                           | ડિફૉલ્ટ | અસર                                                                                                                                                                                                                         |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| સક્ષમ           | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | જ્યારે `false` હોય, ત્યારે ગાર્ડરેલ શૉર્ટ-સર્કિટ થાય છે.                                                                                                                                                                    |
| મોડ             | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`  | ઇન્જેક્શન નીતિ: `block`, `warn`, અથવા `log`. (`redact` બૅકવર્ડ સુસંગતતા માટે સ્વીકારવામાં આવે છે, પરંતુ તે ઇન્જેક્શન ટેક્સ્ટને **દૂર કરતું નથી**; વિનંતીમાં PII પુનર્લેખન `PII_REDACTION_ENABLED` દ્વારા નિયંત્રિત થાય છે.) |
| બ્લૉક થ્રેશોલ્ડ | `blockThreshold` વિકલ્પ / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ઉપનામ `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | બ્લૉક કરવા માટે જરૂરી ન્યૂનતમ ગંભીરતા. ડિફૉલ્ટરૂપે મધ્યમ ગંભીરતા માત્ર નિરીક્ષણ માટે છે.                                                                                                                                    |

**મોડની અગ્રતા** (`getMode`): કૉલર `options.mode` →
`INJECTION_GUARD_MODE` **DB ફીચર-ફ્લૅગ ઓવરરાઇડ** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`. તેથી ડૅશબોર્ડ ઓવરરાઇડને env vars કરતાં અગ્રતા મળે છે, જેથી Feature
Flags UI ચાલુ ગાર્ડને લાઇવ નિયંત્રિત કરે છે (પુનઃપ્રારંભ વિના). DB વાંચન ફેઇલ-સેફ છે:
જો તેમાં ભૂલ થાય, તો ગાર્ડ env-આધારિત વર્તન પર પાછો ફરે છે, અને જ્યારે કોઈ
ઓવરરાઇડ સેટ ન હોય ત્યારે વર્તન માત્ર env-આધારિત રિઝોલ્યુશન જેવું જ રહે છે.

શોધ સ્રોતો:

1. `@/shared/utils/inputSanitizer`માંથી `sanitizeRequest()` (પાઇપલાઇનમાં
   અન્યત્ર ઉપયોગમાં લેવાતો શેર કરેલ ડિટેક્ટર સેટ).
2. બિલ્ટ-ઇન `DEFAULT_GUARD_PATTERNS` (હાલમાં `system_override_inline` અને
   `markdown_system_block`, બંનેની ગંભીરતા `high` છે).
3. કન્સ્ટ્રક્ટર વિકલ્પો દ્વારા પાસ કરાયેલા વૈકલ્પિક `customPatterns` (સ્ટ્રિંગ્સ, regex,
   અથવા `{ name, pattern, severity }` રેકોર્ડ્સ).

જ્યારે `mode === "block"` હોય **અને** ઓછામાં ઓછી એક શોધ ગંભીરતા
થ્રેશોલ્ડને પૂર્ણ કરે, ત્યારે `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }` પરત કરે છે. `warn`/`log` મોડમાં ગાર્ડરેલ લૉગ કરે છે પરંતુ
કૉલને મંજૂરી આપે છે. રજિસ્ટ્રીમાંથી પસાર થયા વિના પ્રૉમ્પ્ટનું મૂલ્યાંકન કરવાની જરૂર હોય તેવા
કૉલર્સ માટે શેર કરેલ હેલ્પર `evaluatePromptInjection()` પણ એક્સપોર્ટ કરવામાં આવે છે.

**સ્કૅન મર્યાદા (v3.8.20):** ડિટેક્ટર જોડાયેલા પ્રૉમ્પ્ટ ટેક્સ્ટના માત્ર **પ્રથમ 16 KB**નું
નિરીક્ષણ કરે છે — `src/shared/utils/inputSanitizer.ts`માં
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 બાઇટ્સ). પેટર્ન લૂપ ચલાવતા પહેલાં
`detectInjection()` અને `evaluatePromptInjection()` બંને
`slice(0, MAX_INJECTION_SCAN_BYTES)` કરે છે. ઇન્જેક્શન નિર્દેશો ઇનપુટની શરૂઆતની નજીક હોય છે, તેથી આ
શોધને નબળી પાડ્યા વિના અનેક સો KBના પેલોડ્સ પર regex CPU/GCને મર્યાદિત કરે છે (જુઓ
#3932, #4041).

### ક્રેડેન્શિયલ માસ્કર (`credentialMasker.ts`)

ડિફૉલ્ટ ચેઇનમાં છેલ્લે (પ્રાથમિકતા `95`) **બંને** તબક્કાઓમાં ચાલે છે. આઉટબાઉન્ડ પેલોડમાંથી (સંદેશ
કન્ટેન્ટ, ટૂલ-કૉલ આર્ગ્યુમેન્ટ્સ, ટૂલ પરિણામો) **અને** પ્રદાતાના પ્રતિસાદમાંથી
જાણીતા API-key / secret-token પેટર્ન્સને રિડેક્ટ કરે છે, જેથી પ્રૉમ્પ્ટમાં પેસ્ટ કરેલું
ક્રેડેન્શિયલ (અથવા ટૂલ પરિણામ દ્વારા પાછું ઇકો થયેલું) અપસ્ટ્રીમ પ્રદાતા કે ક્લાયન્ટને
લીક ન થાય.

- **માત્ર ઑપ્ટ-ઇન**, PII રિડૅક્શન જેવી જ પદ્ધતિ (Hard Rule #20ને અડીને):
  `settings.credentialRedactionEnabled === true` **અથવા**
  `CREDENTIAL_REDACTION_ENABLED=true` ન હોય ત્યાં સુધી અક્ષમ રહે છે. તે બંધ હોય ત્યારે ગાર્ડરેલ કોઈ ક્રિયા કરતું નથી —
  તે ક્યારેય બ્લૉક કરતું નથી અને ક્યારેય પુનર્લેખન કરતું નથી.
- `redactCredentials()` સંપૂર્ણ પેલોડ/પ્રતિસાદ ટ્રીમાં ફરે છે (`walkValue()`,
  પ્રોટોટાઇપ-પોલ્યુશનથી સુરક્ષિત, `WeakSet` દ્વારા સાઇકલથી સુરક્ષિત) અને મેળ ખાતા ભાગોને
  `[REDACTED:<type>]` પ્લેસહોલ્ડરથી બદલે છે તથા માત્ર ખરેખર બદલાયેલી શાખાઓને
  ક્લોન કરે છે.
- `CREDENTIAL_PATTERNS` LLM પ્રદાતા કીઝ (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ટોકન્સ (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), પેમેન્ટ કીઝ (Stripe, Square), ક્લાઉડ
  કીઝ (AWS access key, Twilio, SendGrid, Mailgun), પ્રાઇવેટ કીઝ / JWTs,
  ક્રેડેન્શિયલ ધરાવતી કનેક્શન સ્ટ્રિંગ્સ (`mongodb://user:pass@...`, વગેરે), અને
  સામાન્ય `Authorization`/`x-api-key`/`api-key`/`apikey` હેડર-વેલ્યૂ
  પેટર્નને આવરી લે છે. હેડર-આકારની કીઝ (`authorization`, `x-api-key`, `api-key`,
  `apikey`)ને સામાન્ય ટેક્સ્ટ regex દ્વારા નહીં, પરંતુ માળખાકીય રીતે રિડેક્ટ કરવામાં આવે છે (માત્ર મૂલ્ય,
  `Bearer `/`Basic ` જેવો સ્કીમ પ્રીફિક્સ જાળવી રાખીને).
- ગાર્ડરેલ ક્યારેય બ્લૉક કરતું નથી; તે માત્ર પુનર્લેખન (`modifiedPayload` /
  `modifiedResponse`) અને ઍનોટેશન (`meta.credentialsRedacted`, `meta.count`) કરે છે.

રિગ્રેશન ગાર્ડ: `tests/unit/credential-masker-guardrail.test.ts`.

## મૂળભૂત કરાર (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ચેઇનને તરત જ અટકાવે છે
  message?: string; // અવરોધિત કરતી વખતે દર્શાવવામાં આવે છે
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // વિનંતીને ફરી લખવા માટે preCall દ્વારા પરત કરવામાં આવે છે
  modifiedResponse?: TValue; // પ્રતિસાદને ફરી લખવા માટે postCall દ્વારા પરત કરવામાં આવે છે
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ગાર્ડરેલ `void`, `{}`, અથવા `{ block: false }` પરત કરીને "કોઈ ફેરફાર નહીં"નો સંકેત આપે છે. `modifiedPayload`/`modifiedResponse` પરત કરવાથી ચેઇનમાં આગળના ગાર્ડરેલ્સ તરફ વહેતું મૂલ્ય બદલાઈ જાય છે.
`signal?: AbortSignal` કૉલરની લાઇફસાઇકલને ગાર્ડરેલ્સ સુધી લઈ જાય છે. વિનંતી રદ થવી એ ઇરાદાપૂર્વકનો fail-open અપવાદ છે: મીડિયા બ્રિજ કામ અટકાવે છે અને જે લક્ષ્ય તેને સપોર્ટ કરતું નથી તે જાણીતું હોવા છતાં તેમાં મૂળ મીડિયા પુનઃસ્થાપિત કર્યા વિના ક્લીનઅપ કરે છે.

## રજિસ્ટ્રી (`registry.ts`)

સિંગલટન `guardrailRegistry` નીચેની સુવિધાઓ પ્રદાન કરે છે:

- `register(guardrail)` — ગાર્ડરેલ ઉમેરે છે (અથવા સામાન્યકૃત નામ દ્વારા બદલે છે) અને
  ચઢતા `priority` મુજબ ફરીથી ગોઠવે છે.
- `clear()` / `list()` — વહીવટી સહાયકો.
- `runPreCallHooks(payload, context)` — સક્રિય ગાર્ડરેલ્સ પર ક્રમશઃ ફરે છે, પેલોડને
  `modifiedPayload` મારફતે આગળ ધપાવે છે અને પ્રથમ `block: true` પર અટકે છે.
- `runPostCallHooks(response, context)` — પ્રતિસાદની બાજુએ સમાન પ્રવાહ.
- `resetGuardrailsForTests({ registerDefaults })` — સ્વચ્છ ટેસ્ટ અલગીકરણ માટે સ્ટેટ સાફ કરે છે અને વૈકલ્પિક રીતે
  ડિફૉલ્ટ્સને ફરીથી રજિસ્ટર કરે છે.

બંને રનર્સ `{ blocked, payload|response, results, guardrail?, message? }`
પરત કરે છે, જ્યાં `results` એ `GuardrailExecutionResult` રેકોર્ડ્સની એરે છે, જેમાં
દરેક ગાર્ડરેલ માટેના `blocked`, `skipped`, `modified`, `error`, અને `meta` ફીલ્ડ્સ
સમાવિષ્ટ હોય છે, જે ટ્રેસિંગ માટે ઉપયોગી છે.

### દરેક વિનંતી માટે ગાર્ડરેલ્સ અક્ષમ કરવા

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` વર્તમાન
વિનંતી માટે છોડવામાં આવનાર ગાર્ડરેલ નામોની ડુપ્લિકેટ-રહિત યાદી એકત્રિત કરે છે.
સ્ત્રોતો (બધા વૈકલ્પિક, બધા મર્જ કરવામાં આવે છે):

- `apiKeyInfo.disabledGuardrails`
- વિનંતી બોડીનું `disabledGuardrails` (ટોચના સ્તરે)
- વિનંતી બોડીનું `metadata.disabledGuardrails`
- હેડર `x-omniroute-disabled-guardrails` (અથવા જૂનું
  `x-disabled-guardrails`)

મૂલ્યો સ્ટ્રિંગ્સની એરે અથવા કૉમાથી અલગ કરેલી સ્ટ્રિંગ હોઈ શકે છે; નામોને
લોઅરકેસ kebab-caseમાં સામાન્યકૃત કરવામાં આવે છે (`pii_masker` → `pii-masker`). પરિણામ
`context.disabledGuardrails` મારફતે રજિસ્ટ્રીને આપવામાં આવે છે, જે
મેળ ખાતા ગાર્ડરેલ્સને છોડી દે છે (`results`માં `skipped: true`).

## અમલીકરણ ક્રમ

`src/sse/handlers/chat.ts` અને
`open-sse/handlers/chatCore.ts`માંથી પસાર થતી દરેક વિનંતી માટે:

1. `resolveDisabledGuardrails(...)` API કી, બોડી અને હેડર્સમાંથી સ્કિપ સૂચિ બનાવે છે.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ચડતા પ્રાથમિકતા ક્રમમાં ગાર્ડરેલ્સ ચલાવે છે:
   - અક્ષમ કરેલા ગાર્ડરેલ્સ `skipped` તરીકે નોંધાય છે.
   - દરેક ગાર્ડરેલનું `preCall`, `modifiedPayload` મારફતે પેલોડને ફરી લખી શકે છે.
   - પ્રથમ `block: true` ચેઇનને શોર્ટ-સર્કિટ કરે છે અને હેન્ડલર
     ગાર્ડરેલ અસ્વીકાર પ્રતિસાદ પરત કરે છે.
3. (સંભવિત રીતે ફરી લખાયેલો) પેલોડ કોમ્બો રાઉટિંગ અને અપસ્ટ્રીમ
   ડિસ્પેચમાં જાય છે.
4. પ્રતિસાદ તૈયાર થયા પછી, `guardrailRegistry.runPostCallHooks(...)`
   પ્રતિસાદ પર એ જ ચેઇન ચલાવે છે. અહીં `block: true` અપસ્ટ્રીમ
   પ્રતિસાદને કાઢી નાખે છે.

જે ગાર્ડરેલ્સ અપવાદ ફેંકે છે તે `error: <message>` સાથે નોંધાય છે અને
`logger.warn` મારફતે લૉગ થાય છે, પરંતુ ચેઇન ચાલુ રહે છે — ડિઝાઇન મુજબ ફેઇલ-ઓપન.

## રૂપરેખાંકન

બિલ્ટ-ઇન ગાર્ડરેલ્સ દ્વારા વાંચવામાં આવતા એન્વાયર્નમેન્ટ વેરિએબલ્સ:

| વેરિએબલ                               | આના દ્વારા વપરાય છે        | અસર                                                                                                             |
| ------------------------------------- | -------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | શોધને સંપૂર્ણપણે અક્ષમ કરવા માટે `false` સેટ કરો.                                                               |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`         | ઇન્જેક્શન નીતિ: `warn`, `block`, અથવા `log`. લેગસી મૂલ્ય `redact` ઇન્જેક્શન ટેક્સ્ટને ફરીથી લખતું નથી.          |
| `INJECTION_GUARD_MODE`                | `prompt-injection`         | ઇન્જેક્શન ગાર્ડ માટેનો મોડ; આ DB ફીચર ફ્લેગ પણ છે, જે એન્વાયર્નમેન્ટ વેરિએબલ્સને **ઓવરરાઇડ** કરે છે (DB > ENV). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`         | `MODE=block` દ્વારા અસ્વીકાર થવા માટેની ન્યૂનતમ ગંભીરતા: `high` (ડિફૉલ્ટ), `medium`, અથવા `low`.                |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`         | `INPUT_SANITIZER_BLOCK_THRESHOLD` માટેનો લેગસી ઉપનામ.                                                           |
| `PII_REDACTION_ENABLED`               | `pii-masker`               | જ્યારે `true` હોય, ત્યારે વિનંતીમાં રહેલી PII રિડેક્ટ થાય છે (ઇન્જેક્શન મોડથી સ્વતંત્ર).                        |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ડાઉનસ્ટ્રીમ) | પ્રતિસાદ-બાજુના માસ્કરની વર્તણૂકને નિયંત્રિત કરે છે.                                                            |

Modality Bridge ગાર્ડરેલ્સ એન્વાયર્નમેન્ટ વેરિએબલ્સને બદલે DB-આધારિત સેટિંગ્સ
સ્ટોર (`getSettings()`)માંથી રનટાઇમ રૂપરેખાંકન વાંચે છે. Visionની પ્રાથમિક કીઓ
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, અને
`modalityBridgeCacheMaxEntries` છે. લેગસી
`visionBridge*` કીઓ ફક્ત દસ્તાવેજીકૃત એક-ચક્ર રીડ
ફૉલબૅક તરીકે સ્વીકારવામાં આવે છે; ડૅશબોર્ડ રાઇટ્સ પ્રાથમિક કીઓનો ઉપયોગ કરે છે. ડિફૉલ્ટ્સ અને ફૉલબૅક
રિઝૉલ્વર `src/shared/constants/modalityBridgeDefaults.ts`માં છે, જ્યારે લેગસી
કોન્સ્ટન્ટ્સ `src/shared/constants/visionBridgeDefaults.ts`માં જાળવી રાખવામાં આવ્યા છે.

Audio, `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout`, અને `modalityBridgeAudioMaxClips`, તેમજ શેર કરેલ
`modalityBridgeCache*` સેટિંગ્સનો ઉપયોગ કરે છે. Audio માટે કોઈ લેગસી-કી ફૉલબૅક નથી, કારણ કે આ
કીઓ Modality Bridge સ્કીમા સાથે રજૂ કરવામાં આવી હતી.

Video, `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos`, અને
`modalityBridgeVideoTimeout`, તેમજ શેર કરેલ `modalityBridgeCache*` સેટિંગ્સનો ઉપયોગ કરે છે.
તે ડિફૉલ્ટ રૂપે અક્ષમ છે કારણ કે FFmpeg/ffprobe વૈકલ્પિક ઓપરેશનલ
ડિપેન્ડન્સીઝ છે અને ફ્રેમ કૅપ્શનિંગ લેટન્સી અને મોડેલ ખર્ચ વધારે છે.

## કસ્ટમ ગાર્ડરેલ્સ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

પગલાં:

1. `BaseGuardrail`ને વિસ્તૃત કરતી `src/lib/guardrails/myGuardrail.ts` બનાવો.
2. `preCall` અને/અથવા `postCall` અમલમાં મૂકો.
3. કાં તો ઇમ્પોર્ટ સમયે નોંધણી કરો (`registerDefaultGuardrails`માંથી પુશ કરો) અથવા
   રનટાઇમ પર `guardrailRegistry.register(...)` કૉલ કરો — રજિસ્ટ્રી સમાન સામાન્યકૃત
   નામ ધરાવતા કોઈપણ અગાઉના ગાર્ડરેલને બદલી નાખે છે.
4. `tests/unit/` હેઠળ પરીક્ષણો ઉમેરો (હાલનાં ઉદાહરણો:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## પરીક્ષણ

જાણીતી સ્થિતિથી શરૂઆત કરવા માટે પરીક્ષણો વચ્ચે `resetGuardrailsForTests()`નો ઉપયોગ કરો.
ખાલી રજિસ્ટ્રીથી શરૂઆત કરવા માટે `{ registerDefaults: false }` પાસ કરો અને
માત્ર પરીક્ષણ હેઠળના ગાર્ડરેલ્સની નોંધણી કરો. Vision Bridge ડિપેન્ડન્સી
ઇન્જેક્શન (`deps.getSettings`, `deps.callVisionModel`) સ્વીકારે છે; Audio Bridge
સેટિંગ્સ, ક્ષમતાઓ, STT મોડેલ પસંદગી, ક્રેડેન્શિયલ તપાસો અને ટ્રાન્સક્રિપ્શન માટે
સમકક્ષ સીમ્સ ઉપલબ્ધ કરાવે છે. તેથી પરીક્ષણો DB અથવા નેટવર્ક ઍક્સેસ વિના બંને
પ્રવાહોને ચકાસી શકે છે.

## ઇન્જેક્શન-ગાર્ડ રૂટ કવરેજ અને રેડ-ટીમ (તબક્કો 8 · બ્લૉક D)

ઇન્જેક્શન-ગાર્ડ (`createInjectionGuard` / `withInjectionGuard`) વપરાશકર્તા પ્રોમ્પ્ટ્સ
સ્વીકારતા તમામ રૂટ્સને આવરી લે છે. તે `INJECTION_GUARD_MODE`નું પાલન કરે છે (ડિફૉલ્ટ
`warn` = ફક્ત લૉગ; `block` = HTTP 400 `SECURITY_001` પરત કરે છે).

| પ્રકાર           | રૂટ્સ                                                                                                                                                | ડિફૉલ્ટ મોડ |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| ટેક્સ્ટ (હાલનું) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn        |
| જનરેટિવ          | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn        |
| ડેટા             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn        |

ટેક્સ્ટ નિષ્કર્ષણ (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`ને આવરી લે છે.

**રેડ-ટીમ (દરરોજ રાત્રે, `nightly-llm-security.yml`):** promptfoo ચકાસે છે કે દરેક રૂટ
`INJECTION_GUARD_MODE=block`માં OWASP-LLM કોર્પસને બ્લૉક કરે છે; garak પ્રોબ્સ ચલાવે છે
(સિક્રેટ વિના સ્કિપ કરે છે). સુસંગતતા માટે `moderations`નો સમાવેશ કરવામાં આવ્યો છે —
બ્લૉક-મોડમાં ઑપરેટર્સ `resolveDisabledGuardrails` મારફતે તેને મુક્તિ આપી શકે છે.

રાત્રિકાલીન વર્કફ્લો (`.github/workflows/nightly-llm-security.yml`, cron + મેન્યુઅલ
ડિસ્પેચ)માં બે જૉબ્સ છે:

- **`promptfoo-guard` (બ્લૉકિંગ)** — `INJECTION_GUARD_MODE=block` સાથે
  `promptfoo eval -c promptfooconfig.yaml` ચલાવે છે. દરેક પ્રતિકૂળ કેસ (દા.ત. "અગાઉની
  તમામ સૂચનાઓ અવગણો…", DAN-શૈલીના જેલબ્રેક્સ) ખાતરી કરે છે કે પ્રતિસાદમાં
  `error.code === "SECURITY_001"` હોય, એટલે કે ગાર્ડે વિનંતીને ખરેખર નકારી હતી.
- **`garak` (સલાહકારી)** — સ્થાનિક OmniRoute ઇન્સ્ટન્સ
  (`http://localhost:20128/v1`) સામે garak `--probes promptinject,dan,leakreplay`
  ચલાવે છે. તે પ્રોવાઇડર સિક્રેટ (`PROMPTFOO_PROVIDER_KEY`) પર આધારિત છે; સિક્રેટ
  ન હોય તો સરળતાથી સ્કિપ કરે છે અને તેની પાછળ `|| true` જોડાયેલું છે, તેથી તે CIને
  નિષ્ફળ કર્યા વિના રિપોર્ટ કરે છે.

ગાર્ડ હેલ્પર (`createInjectionGuard` / `withInjectionGuard`)નું કવરેજ પ્રોમ્પ્ટ ધરાવતા
દરેક `/v1` રૂટ સુધી વિસ્તરે છે; પ્રોમ્પ્ટ ટેક્સ્ટને
`src/shared/utils/inputSanitizer.ts`માંના `extractMessageContents()` દ્વારા
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`માંથી
લેવામાં આવે છે.
