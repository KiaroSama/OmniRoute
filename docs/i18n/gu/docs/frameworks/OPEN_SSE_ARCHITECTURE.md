> **સારાંશમાં**: `open-sse/` એ મુખ્ય સ્ટ્રીમિંગ એન્જિન છે જે OmniRoute માંની દરેક LLM વિનંતીને સંચાલિત કરે છે. તેમાં વિનંતી પાઇપલાઇન, એક્ઝિક્યુટર્સ, સેવાઓ, MCP સર્વર અને અનુવાદ સ્તરને અમલમાં મૂકતી ~1,400 ફાઇલો છે. આ માર્ગદર્શિકા સમજાવે છે કે આ ભાગો એકસાથે કેવી રીતે કાર્ય કરે છે.

**સ્રોત:** `open-sse/` (વર્કસ્પેસ પૅકેજ, ~1,440 નોન-ટેસ્ટ `.ts` ફાઇલો)

## અલગ વર્કસ્પેસ પૅકેજ શા માટે?

`open-sse/` એ OmniRoute મોનોરેપોમાં એક **સ્વતંત્ર વર્કસ્પેસ** છે, તેના અનેક કારણો છે:

1. **પુનઃઉપયોગક્ષમતા** — `open-sse` ને npm પર `@omniroute/open-sse` તરીકે પ્રકાશિત કરવામાં આવે છે, તેથી અન્ય પ્રોજેક્ટ્સ તેનો સ્વતંત્ર રીતે ઉપયોગ કરી શકે છે
2. **સ્પષ્ટ સીમાઓ** — સ્ટ્રીમિંગ એન્જિનને OmniRoute-વિશિષ્ટ UI/DB સ્તરથી અલગ રાખવામાં આવ્યું છે
3. **પ્રદર્શન** — એન્જિનમાં કોઈ Next.js નિર્ભરતાઓ નથી, જે CLI/serverless સંદર્ભોમાં વધુ ઝડપી કોલ્ડ સ્ટાર્ટ્સ શક્ય બનાવે છે
4. **વર્ઝનિંગ** — `open-sse` પોતાની સમયસૂચિ અનુસાર રિલીઝ કરી શકે છે

```json
// package.json
"workspaces": ["open-sse"]
```

## વિનંતી પાઇપલાઇન

દરેક LLM વિનંતી **5-તબક્કાની પાઇપલાઇન**માંથી પસાર થાય છે:

```
                              ┌──────────────┐
   HTTP વિનંતી                 │  1. રાઉટ     │   કોમ્બો નિરાકરણ, મોડેલ પસંદગી
   (Next.js રૂટ)               └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  2. અનુવાદ   │   ફોર્મેટ રૂપાંતરણ (OpenAI ↔ Claude ↔ Gemini)
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  3. અમલ      │   પ્રોવાઇડર એક્ઝિક્યુટર, HTTP, પુનઃપ્રયાસ, બ્રેકર
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  4. સ્ટ્રીમ   │   SSE રૂપાંતરણ, બૅકપ્રેશર
                              └──────┬───────┘
                                     │
                                     ▼
                              ┌──────────────┐
                              │  5. રેકોર્ડ   │   વપરાશ ટ્રૅકિંગ, કૉલ લૉગ, ભૂલ વર્ગીકરણ
                              └──────┬───────┘
                                     │
                                     ▼
                              HTTP પ્રતિસાદ (SSE અથવા JSON)
```

### તબક્કો 1: રાઉટ (services/combo.ts)

**પ્રવેશ બિંદુ**: `services/combo.ts` માં `handleComboChat()`

વિનંતીને ચોક્કસ `(provider, model, account, credentials)` ટ્યુપલ સાથે મેળવે છે:

- ID દ્વારા કોમ્બો શોધો (અથવા `auto/*` મોડેલ્સ માટે વર્ચ્યુઅલ કોમ્બો બનાવો)
- રાઉટિંગ વ્યૂહરચના લાગુ કરો (પ્રાથમિકતા, વેઇટેડ, રાઉન્ડ-રોબિન, વગેરે)
- અસ્વસ્થ પ્રોવાઇડર્સને ફિલ્ટર કરીને દૂર કરો (સર્કિટ બ્રેકર)
- આગળનું વ્યવહારુ લક્ષ્ય પસંદ કરો

`auto/*` મોડેલ્સ માટે, આ તબક્કો આ પણ કરે છે:

- **16-પરિબળ સ્કોરિંગ** અલ્ગોરિધમ ચલાવે છે (`services/autoCombo/`)
- સ્વાસ્થ્ય, ખર્ચ, લેટન્સી વગેરેના આધારે `provider+model` જોડી પસંદ કરે છે

### તબક્કો 2: અનુવાદ (translator/)

જો સ્રોત ફોર્મેટ (દા.ત., OpenAI) લક્ષ્ય ફોર્મેટથી (દા.ત., Claude) અલગ હોય, તો વિનંતીનો **અનુવાદ** કરવામાં આવે છે:

- સિસ્ટમ પ્રૉમ્પ્ટ → સિસ્ટમ સંદેશ
- ટૂલ વ્યાખ્યાઓ → પ્રોવાઇડર-વિશિષ્ટ ટૂલ ફોર્મેટ
- રીઝનિંગ/થિંકિંગ પેરામીટર્સ → પ્રોવાઇડર-વિશિષ્ટ સમકક્ષો
- સંદેશ ભૂમિકાનું સામાન્યીકરણ (`developer` → નોન-OpenAI માટે `system`)

`translator/index.ts` આને ઉપલબ્ધ કરાવે છે:

```ts
translateRequest(body, sourceFormat, targetFormat): TranslatedRequest
needsTranslation(source, target): boolean
```

### તબક્કો 3: અમલ (executors/)

**પ્રવેશ બિંદુ**: `getExecutor(providerId).execute(request, options)`

બધા પ્રોવાઇડર્સ `getExecutor()` ફેક્ટરી ફૉલબૅક દ્વારા `DefaultExecutor` (`executors/default.ts`) નો ઉપયોગ કરે છે. એક્ઝિક્યુટર:

- અપસ્ટ્રીમ URL બનાવે છે (`buildUrl()`)
- પ્રોવાઇડર-વિશિષ્ટ હેડર્સ ઉમેરે છે (`buildHeaders()`)
- વિનંતી બૉડીનું રૂપાંતરણ કરે છે (`transformRequest()`)
- પુનઃપ્રયાસ + એક્સ્પોનેન્શિયલ બૅકઑફ સાથે HTTP વિનંતી મોકલે છે
- જરૂર પડે તો પ્રમાણીકરણ રિફ્રેશ સંભાળે છે (OAuth પ્રોવાઇડર્સ)

બધા એક્ઝિક્યુટર્સ `BaseExecutor` (`executors/base.ts`, 1170 LOC) ને એક્સ્ટેન્ડ કરે છે, જે આ સુવિધાઓ પ્રદાન કરે છે:

- સામાન્ય પુનઃપ્રયાસ લૉજિક
- પ્રૉક્સી ઇન્ટિગ્રેશન
- સર્કિટ બ્રેકર ઇન્ટિગ્રેશન
- વપરાશ રેકોર્ડિંગ હુક્સ

### તબક્કો 4: સ્ટ્રીમ (utils/stream.ts)

સ્ટ્રીમિંગ પ્રતિસાદો માટે, એક્ઝિક્યુટર **ReadableStream** પરત કરે છે. હેન્ડલર:

- SSE ટ્રાન્સફોર્મમાંથી પસાર કરે છે (`createSSETransformStreamWithLogger`)
- નિષ્ક્રિય કનેક્શન્સ શોધવા માટે હાર્ટબીટ પિંગ્સ લાગુ કરે છે
- ક્લાયન્ટ ડિસ્કનેક્ટને સુચારુ રીતે સંભાળે છે (`pipeWithDisconnect`)
- નોન-સ્ટ્રીમિંગ ક્લાયન્ટ્સ માટે SSE → JSON રૂપાંતરિત કરે છે

નોન-સ્ટ્રીમિંગ પ્રતિસાદો માટે, એક્ઝિક્યુટર પાર્સ કરેલો JSON ઑબ્જેક્ટ પરત કરે છે, જેને કોઈ ફેરફાર વિના આગળ મોકલવામાં આવે છે.

### તબક્કો 5: રેકોર્ડ (services/usage.ts)

### chatCore.ts (5977 લાઇનો)

**મુખ્ય વિનંતી હૅન્ડલર**. તેના મોટા કદ છતાં, તેનું માળખું સ્પષ્ટ છે:

```ts
// chatCore.ts નું છદ્મ-માળખું
export async function handleChat(request: NextRequest) {
  // 1. પ્રમાણીકરણ + CORS
  await authenticateRequest(request);
  applyCorsHeaders(response);

  // 2. બૉડીની માન્યતા ચકાસણી
  const body = await parseRequestBody(request);

  // 3. ફૉર્મેટની ઓળખ + રૂપાંતરણ
  const sourceFormat = detectFormat(request);
  const targetFormat = getTargetFormat(providerId);
  if (needsTranslation(sourceFormat, targetFormat)) {
    body = translateRequest(body, sourceFormat, targetFormat);
  }

  // 4. કૉમ્બો રાઉટિંગ
  const targets = await resolveComboTargets(comboId, body);
  for (const target of targets) {
    try {
      const result = await executeOnTarget(target, body);
      await recordUsage(result);
      return result;
    } catch (err) {
      // આગામી લક્ષ્ય પર આગળ વધો
    }
  }

  // 5. કટોકટી ફૉલબૅક
  return await emergencyFallback(body);
}
```

એક વિશાળ ફંક્શન હોવા છતાં, તે 5-તબક્કાની પાઇપલાઇન સાથે અનુરૂપ **ટિપ્પણીયુક્ત વિભાગોમાં** ગોઠવાયેલું છે.

## એક્ઝિક્યુટર્સ (150 મોડ્યુલ)

### સામાન્ય પેટર્ન્સ

પ્રદાતાઓનું રિઝોલ્યુશન `getExecutor(providerId)` દ્વારા થાય છે, જે કૉન્ફિગર કરેલું એક્ઝિક્યુટર પરત કરે છે. OpenAI/Anthropic-સુસંગત પ્રદાતાઓ `DefaultExecutor` (`executors/default.ts`) નો ઉપયોગ કરે છે. પ્રદાતા-વિશિષ્ટ વર્તણૂક (બેઝ URL, ઑથ હેડર્સ, API વર્ઝન) `open-sse/config/providers/` માં કૉન્ફિગર કરવામાં આવે છે, જ્યારે વિનંતી બૉડીના રૂપાંતરો `open-sse/translator/` માં સંભાળવામાં આવે છે.

**કસ્ટમ URL** પ્રદાતાની કૉન્ફિગરેશન મારફતે સેટ કરવામાં આવે છે:

```ts
// open-sse/config/providers/ માં પ્રદાતા કૉન્ફિગ
export default {
  id: "together",
  baseURL: "https://api.together.xyz/v1/chat/completions",
}
````

**કસ્ટમ ઑથ** પ્રદાતા રજિસ્ટ્રીની ઑથ કૉન્ફિગરેશન (API કી, OAuth, હેડર પ્રોફાઇલ્સ) દ્વારા સંભાળવામાં આવે છે.

**કસ્ટમ વિનંતી બૉડી** રૂપાંતરો (દા.ત., Anthropic દ્વારા `system` ને `messages` થી અલગ કરવું) દરેક પ્રદાતા માટે `open-sse/translator/` માં રજિસ્ટર કરવામાં આવે છે.

## અનુવાદકો

**3 ફોર્મેટ્સ** વચ્ચે અનુવાદ કરો: OpenAI, Anthropic, Gemini, તેમજ નવું Responses API.

### અનુવાદ ક્યારે થાય છે

```ts
import { needsTranslation, translateRequest } from "@omniroute/open-sse/translator";

if (needsTranslation(sourceFormat, targetFormat)) {
  body = translateRequest(body, sourceFormat, targetFormat);
}
```

સામાન્ય અનુવાદો:

- `OpenAI → Anthropic`: અલગ `system` ફીલ્ડ, `x-api-key` હેડર
- `OpenAI → Gemini`: `messages`ના બદલે `contents`, `systemInstruction`
- `OpenAI → Responses API`: `input` એરે, `previous_response_id` સ્ટેટ

### હેન્ડલ કરવામાં આવતા વિશિષ્ટ કિસ્સાઓ

- `developer` રોલ → non-OpenAI માટે `system`
- `system` રોલ → GLM/ERNIE માટે પ્રથમ વપરાશકર્તા સંદેશમાં મર્જ કરવામાં આવે છે
- `json_schema` → Geminiનું `responseMimeType` + `responseSchema`
- `tools` → પ્રદાતા-વિશિષ્ટ ટૂલ ફોર્મેટ
- થિંકિંગ પેરામીટર્સ (o1, Claude) → પ્રદાતા-વિશિષ્ટ સમકક્ષો

## MCP સર્વર

`open-sse/mcp-server/` **Model Context Protocol** સર્વર અમલમાં મૂકે છે:

- **110 ટૂલ્સ** (પ્રદાતા મેનેજમેન્ટ, કોમ્બોઝ, મેમરી, કૅશ, કમ્પ્રેશન, પ્રોક્સી, સ્કિલ્સ, ગેમિફિકેશન, પ્લગિન્સ, Notion, Obsidian, લોકલ કોર્પસ)
- **3 ટ્રાન્સપોર્ટ્સ**: stdio, SSE, Streamable HTTP
- સૂક્ષ્મ-સ્તરીય અધિકૃતતા માટે **33 સ્કોપ્સ**

### ટૂલ રજિસ્ટ્રેશન

ટૂલ્સ `open-sse/mcp-server/tools/`માં સ્વતંત્ર ફાઇલો તરીકે રજિસ્ટર કરવામાં આવે છે, જેમાંથી દરેક નામ, સ્કીમા, હેન્ડલર અને સ્કોપ એક્સપોર્ટ કરે છે:

```ts
// open-sse/mcp-server/tools/getHealth.ts
import { z } from "zod";
export default {
  name: "omniroute_get_health",
  description: "Get system health snapshot",
  scope: "read:health",
  inputSchema: z.object({}),
  handler: async (_args, ctx) => {
    return await getSystemHealth();
  },
};
```

### ટ્રાન્સપોર્ટ્સ

```ts
// stdio (CLI ઉપયોગ)
startMcpStdio(server);

// SSE (HTTP-આધારિત સ્ટ્રીમિંગ)
startMcpSse(server, port);

// Streamable HTTP (આધુનિક MCP)
startMcpStreamable(server, port);
```

### અધિકૃતતા

દરેક ટૂલ કૉલ સ્કોપ ચકાસણીઓમાંથી પસાર થાય છે (`open-sse/mcp-server/auth/`):

```ts
if (!hasScope(apiKey, "providers:read")) {
  throw new Error("Insufficient scope");
}
```

## ટ્રાન્સફોર્મર્સ

`open-sse/transformer/` **Chat Completions** અને **Responses API** ફોર્મેટ્સ વચ્ચે રૂપાંતર કરે છે.

### અલગ ટ્રાન્સફોર્મર શા માટે?

Responses API એ **સ્ટેટફુલ વાર્તાલાપો** (`previous_response_id`) સાથેનું OpenAIનું નવું ફોર્મેટ છે. જ્યારે કોઈ ક્લાયન્ટ Responses રિક્વેસ્ટ મોકલે છે, ત્યારે OmniRoute:

1. આંતરિક રીતે Responses → Chat Completionsમાં રૂપાંતર કરે છે
2. પ્રદાતાને મોકલે છે (Chat Completionsને સપોર્ટ કરતો કોઈપણ પ્રદાતા)
3. પ્રતિસાદને ફરી Responses ફોર્મેટમાં રૂપાંતર કરે છે
4. રૂપાંતરિત પ્રતિસાદને ક્લાયન્ટ સુધી સ્ટ્રીમ કરે છે

ટ્રાન્સફોર્મર (`transformer/responsesTransformer.ts`) આ પ્રદાન કરે છે:

```ts
createResponsesApiTransformStream(): TransformStream
```

આ નીચેની બાબતો હેન્ડલ કરે છે:

- `response.output_item.added` ઇવેન્ટ્સ
- `response.output_text.delta` ઇવેન્ટ્સ
- `response.completed` ઇવેન્ટ
- ટૂલ કૉલ મેપિંગ (`function_call` ↔ `tool_calls`)

## કૉન્ફિગરેશન

`open-sse/config/` કૉન્ફિગરેશન સ્તર ધરાવે છે:

| ફાઇલ                          | હેતુ                                            |
| ----------------------------- | ----------------------------------------------- |
| `providerRegistry.ts`         | 374-પ્રદાતા કૅટલૉગ પર આધારિત ચૅટ-મોડલ રજિસ્ટ્રી |
| `providerModels.ts`           | મોડલ ઉપનામો, ફૉર્મેટ મૅપિંગ                     |
| `constants.ts`                | સમયસમાપ્તિઓ, મર્યાદાઓ, સ્ટેટસ કોડ્સ             |
| `defaultThinkingSignature.ts` | ડિફૉલ્ટ Claude વિચાર સહી                        |
| `modelStrip.ts` (સર્વિસિસમાં) | દરેક પ્રદાતા મુજબ ફીલ્ડ દૂર કરવું               |

### પ્રદાતા રજિસ્ટ્રી સ્કીમા

```ts
interface ProviderConfig {
  id: string;
  name: string;
  baseUrl: string;
  authType: "bearer" | "api-key" | "oauth" | "cookie";
  executorClass: string;
  defaultModel: string;
  capabilities: ProviderCapabilities;
  models: ModelDefinition[];
}
```

મૉડ્યુલ લોડ થતી વખતે Zod માન્યતા ખાતરી કરે છે કે તમામ પ્રદાતા કૉન્ફિગ્સ માન્ય છે.

## કામગીરી સંબંધિત મર્યાદાઓ

રાઉટિંગ એન્જિન માટે કામગીરીના કડક માપદંડો છે:

| ઑપરેશન                                       | લક્ષ્ય | માપન                       |
| -------------------------------------------- | ------ | -------------------------- |
| કૉમ્બો રિઝોલ્યુશન                            | <10ms  | 50 લક્ષ્યો માટે            |
| રેટ લિમિટ તપાસ                               | <1ms   | ઇન-મેમરી ટોકન બકેટ         |
| મોડેલ ફેમિલી ફૉલબૅક                          | <5ms   | કૅશ કરેલી ફેમિલી વ્યાખ્યાઓ |
| વિનંતી રાઉટિંગ ડિસ્પૅચ                       | <2ms   | હૉટ પાથ                    |
| **રાઉટિંગ હૉટ પાથમાં કોઈ બ્લૉકિંગ I/O નહીં** | —      | બધું અસિંક્રોનસ            |

## ટાળવા જેવી પૅટર્ન્સ

❌ **`combo.ts`માં સિંક્રોનસ DB કૉલ્સ** — પૂર્વ-ગણતરી કરીને કૅશ કરો
❌ **હૅન્ડલર્સમાં રિટ્રાય લૉજિક** — રિઝિલિયન્સ સર્વિસમાંથી `retry()`નો ઉપયોગ કરો
❌ **પ્રોવાઇડર કૉન્ફિગનો સીધો ઍક્સેસ** — `providerRegistry` ગેટર્સનો ઉપયોગ કરો
❌ **હાર્ડકોડ કરેલી ફૉલબૅક ચેઇન્સ** — `modelFamilyFallback.ts`માં વ્યાખ્યાયિત કરો
❌ **સમવર્તી વિનંતીઓમાં સ્ટેટ મ્યુટેશન્સ** — ફક્ત વિનંતી-સ્કોપ્ડ કૉન્ટેક્સ્ટનો ઉપયોગ કરો

## નવો કમ્પોનન્ટ ઉમેરવો

### નવી સર્વિસ ઉમેરવી

1. કેન્દ્રિત જવાબદારી સાથે `open-sse/services/[serviceName].ts` બનાવો
2. મુખ્ય હૅન્ડલર ફંક્શન અને કોઈપણ કૉન્સ્ટન્ટ્સ એક્સપોર્ટ કરો
3. `tests/unit/services/[serviceName].test.mjs`માં યુનિટ ટેસ્ટ્સ ઉમેરો
4. `handlers/chatCore.ts`માં વિનંતી પાઇપલાઇન સાથે સંકલિત કરો (જો રાઉટિંગ-સંબંધિત હોય)
5. જો સર્વિસ લક્ષ્ય પસંદગીને અસર કરતી હોય, તો `combo.ts`માં રાઉટિંગ લૉજિક અપડેટ કરો
6. આ ફાઇલમાં દસ્તાવેજીકરણ કરો

### નવું એક્ઝિક્યુટર ઉમેરવું

1. `BaseExecutor`ને વિસ્તૃત કરતું `open-sse/executors/[provider].ts` બનાવો
2. `config/providerRegistry.ts`માં રજિસ્ટર કરો
3. `executors/index.ts` ફૅક્ટરીમાં ઉમેરો
4. એક્ઝિક્યુટર માટે યુનિટ ટેસ્ટ્સ ઉમેરો
5. `docs/architecture/ARCHITECTURE.md`માં દસ્તાવેજીકરણ કરો

### નવું MCP ટૂલ ઉમેરવું

1. `open-sse/mcp-server/tools/[category]Tools.ts` બનાવો અથવા અપડેટ કરો
2. ઇનપુટ્સ માટે Zod સ્કીમા વ્યાખ્યાયિત કરો
3. `mcp-server/index.ts`માં ટૂલ રજિસ્ટર કરો
4. `mcp-server/auth/`માં સ્કોપ મૅટ્રિક્સમાં ઉમેરો
5. યુનિટ ટેસ્ટ્સ ઉમેરો
